# 03 · 运行流程

> 本页回答一件事：**用户点一下按钮，到屏幕上出结果，中间经过了哪些环节**——
> 而且每一环都回答「**拿掉它会怎样**」。
>
> 分三半：
> - **M1（主线 1~5）**：启动 / 登录 / 连通性测试 / 元数据探查 / 前端 —— 这几条我**真的在本机跑通过**；
> - **M2（主线 A~D）**：自然语言 → 冻结版本、澄清中断与恢复、门禁与自动修复、冻结与指纹 ——
>   这几条我现在**也在本机端到端跑通了一次**（真后端 + ECS 上的真 PG/Redis/Vault/MySQL，经隧道；
>   一句需求 → 5 问 → 冻结；`workflow/` 3,538 行、`services/pipeline/` 2,992 行、`engines/` 的新六块）。
>   但只覆盖了 **happy path**（门禁 `conclusion=pass`）——`block → autofix` 那几支仍是代码级 / 单测验证。
> - **M3 前半段（主线 E）**：冻结的版本 → 准备单 → 四眼审批 → 签发单次 Capability → 提交执行 → worker 调 SeaTunnel。
>   代码是通的（`/preparations`、`/runs` 都已挂载），但**我没在浏览器里点过一遍**（没有浏览器、口令不在我手里），
>   ECS 上也没起 SeaTunnel 容器——所以那条链**跑起来会如实失败在「提交作业」这一步**。
> - **M3 后半段（主线 F）**：作业在跑 → 抄指标判阈值（越界硬中断）→ 跑完 → 出**质量报告** →
>   合格才**原子换表** → `succeeded`；失败/中断走**受管回滚**。这一条**本次刚接上**——
>   此前 be-17 与 be-18 的文档各自把「报告合格之后谁去换表」划给对方，于是那条缝没人认领
>   （详见主线 F 的「为什么需要一个收尾编排」）。**同样：真机未跑过。**
>
> 哪些是「代码里真有的」、哪些是「我没核到的」，文末单列。
>
> 每条主线结尾都有一个「**岔路口**」小节：哪里会失败、失败是重试/跳过/整个请求挂掉，
> 以及那一类最值钱的 ——「**不报错但结果不对**」。

**岔路口（登录）**：
1. **账号被禁用** → 口令对也不发令牌（[services/auth.py:118](../backend/services/auth.py#L118)）。
2. **「登出全部设备」怎么实现**：不是逐个拉黑 jti，而是给用户一个**令牌版本号**，
   登出即 `INCR`（[services/auth.py:291](../backend/services/auth.py#L291)），
   所有旧令牌的 `ver` 立刻对不上。**代价要说清**：这是「按用户」吊销，粒度粗，
   而且要保证「Redis 里的版本号」和「签进令牌里的版本号」**只有一处定义**——
   这里正是项目里少见的**漏网之鱼**：`services/auth.py:43` 定义常量，
   `api/deps_auth.py:62` 又手写了同一个字符串。改一处漏一处，症状是「登出全部设备失效，且不报错」。
   （我在 [05-开发原理](05-开发原理.md) 把它当反面例子讲。）

## 主线 3：连通性测试（**我实测跑通的那条**，异步写路径）

这是全项目**唯一一条从 HTTP 打到真数据库、再回到 HTTP 的完整链路**，所以它最适合用来讲「异步边界」。

| 谁 | 干了什么 | 在哪 | 拿掉会怎样 |
|---|---|---|---|
| 前端 | `POST /datasources/{id}/connectivity-tests` | — | — |
| api | 鉴权 + 取 `SubjectContext`（当前用户/租户/项目） | `api/datasources.py:189` | — |
| service | **先写后投**：Redis 里写 `state=pending` | [services/datasource.py:570](../backend/services/datasource.py#L570) | 先投递后写状态的话，worker 可能在状态落库前就跑完，前端永远查不到结果 |
| service | 投 Celery：`run_connectivity_test.apply_async(..., queue="etl.default")` | [services/datasource.py:583](../backend/services/datasource.py#L583) | 同步跑就是「点一下卡 30 秒直到 HTTP 超时」 |
| api | 立刻返回 `{test_id, state: "pending"}` | [services/datasource.py:589](../backend/services/datasource.py#L589) | 前端拿 `test_id` 轮询，**这是所有长任务的统一模式** |
| worker | `celeryd_init`：把 cwd 重新塞回 `sys.path`、注册执行器 | `tasks/__init__.py` | ⚠️ 见下面「坑」 |
| worker | 调 `run_probe`（注意：**worker 里跑的也是 service 函数**） | [services/datasource.py:605](../backend/services/datasource.py#L605) | — |
| service | 构造 `ToolBroker` + `ReplayGuard`，`caller="worker"` | [services/datasource.py:624](../backend/services/datasource.py#L624) | 绕开 broker = 绕开「谁批准的、有没有令牌、记没记账」 |
| **broker** | **七步执行序**：查工具 → 查前置条件 → 验令牌 → 断言上下文 → 断言指纹绑定 → **原子消费令牌** → 执行 | [harness/broker.py:155](../backend/harness/broker.py#L155) | 见 [04-代码精读](04-代码精读.md)，这是全项目最该讲的一段 |
| clients | 从 Vault 取凭据（**只在内存里物化，用完即弃**） | [clients/datasource_probe.py:277](../backend/clients/datasource_probe.py#L277) | 明文口令落到任何地方都是红线 |
| clients | `aiomysql` 连真库、执行 `SELECT 1` 之类 | [clients/datasource_probe.py:346](../backend/clients/datasource_probe.py#L346) | — |
| clients | 失败时把驱动异常译成字典 §5.7 的**三个码**之一 | [clients/datasource_probe.py:209](../backend/clients/datasource_probe.py#L209) | 见「坑 3」 |
| clients | 返回值只留**白名单字段** | [harness/broker.py:575](../backend/harness/broker.py#L575) | 漏登记一个键 = 前端看到的结论被静默改写（`state` 就踩过） |
| service | 写 `state=succeeded/failed` + 延迟毫秒 + 服务端版本 | — | — |
| service | **写证据账本** `DATASOURCE_CONNECTIVITY_TESTED` 并提交 | [services/datasource.py:650](../backend/services/datasource.py#L650) | 连过生产库却不留痕 = 审计时说不出「谁在什么时候连过」 |
| 前端 | 轮询到终态，展示结果 | — | — |

**实测结果**（经前端代理打的真请求）：`succeeded | 357ms | MySQL 8.0.27`。

**这条链上的岔路口**：

1. **Redis 不可达** → 探测**直接失败**，不退化成「只靠 PG」。
   理由：单次令牌的第二道闸就是那条条件 UPDATE，但第一道 SETNX 挂了说明基础设施有问题，
   此时**执行一个真实数据搬运**的代价远大于「让用户重试一次」。
2. **Redis 里 pending 过期了但任务已完成** → 接口必须能区分「过期」与「不存在」，
   否则前端会显示「测试不存在」，用户以为没点成功，又点一次。
3. **worker 进程被重启** → 任务还在队列里（至少一次投递），
   所以**所有任务必须幂等**（同一个任务做多少遍，结果都一样，这个词面试会问）；且 `probing/pending` 这类中间态如果 worker 在写终态前死掉，
   记录会**永远停在中间态**——⚠️ 这是项目真实存在的缺口，见本页最后一节。

## 主线 4：元数据探查 + 脱敏（同一条异步模式，但多了两道防线）

前半段与主线 3 完全一样（HTTP → pending → Celery → broker → 连库），差异在**数据回来之后**：

| 谁 | 干了什么 | 在哪 | 拿掉会怎样 |
|---|---|---|---|
| service | **提交时就落库脱敏策略**，不等执行器算完 | [services/metadata.py:103-105](../backend/services/metadata.py#L103-L105) | 探查失败时，档案里仍能看出「当时按什么规则脱的」——这是失败档案唯一的诊断价值 |
| 执行器 | 采样若干行，**逐列判敏感级别** | [engines/masking/policy.py:91](../backend/engines/masking/policy.py#L91) | — |
| 执行器 | 敏感列的每个值**就地替换成 `类型:哈希`**（加盐，盐里带租户+数据源+版本） | [engines/masking/policy.py:161](../backend/engines/masking/policy.py#L161) | 存原值 = 控制面库里出现生产数据副本，这是最典型的数据泄漏路径 |
| 执行器 | 落 `schema_snapshot` / `masked_samples` / 表数列数 / 整档哈希 | [clients/datasource_probe.py:455](../backend/clients/datasource_probe.py#L455) | — |
| 日志层 | 敏感值再脱一遍（第二道防线） | [core/logging.py:21](../backend/core/logging.py#L21) | 代码里随手 `log.info(row)` 就把原值写进日志 |
| 前端 | 展示时再兜一次（第三道防线） | `frontend/src/utils/mask.ts` | 三道防线是刻意的：**任何一道被绕过，另外两道还在** |

**实测结果**：探出 2 表 20 列 + 敏感级别；160 个样本单元格**全部是 `类型:哈希` 形状，无一等于原值**
（我直连 MySQL 取原值逐格比对过）。

**这里的坑（"不报错但结果不对" 的典型）**：
MySQL 8 的 `DictCursor` 回的是**大写键名** `TABLE_NAME`，代码若写 `row["table_name"]`
会 `KeyError`；若顺手写成 `row.get("table_name")` 则返回 `None`，
`str(None)` 变成表名 `"None"`，档案状态还是 `ready`——**错得安静**。
所以全仓取值一律走 `_pick`，**取不到就抛错**，不回 `None`（[clients/datasource_probe.py:705](../backend/clients/datasource_probe.py#L705)）。

## 主线 5：前端那条链（有一条必须先说清的真相）

🔴 **前端默认不发请求给后端。** `frontend/.env.development:7` 是 `VITE_USE_MOCK=true`，
mock 适配器会**接管全部 `/api/v1` 请求**（`frontend/src/api/mock/index.ts:1943`），
生产配置才关掉（`.env.production:5` `VITE_USE_MOCK=false`；生产构建下还会二次拒绝安装 mock，`:1938`）。

**这意味着两件事**：
1. 直接 `npm run dev` 打开页面，**每个页面看起来都能用**——数据来自 fixtures，不是后端；
2. 我在 [02-代码地图](02-代码地图.md) 给的那张「前端页面 ↔ 后端接口真实状态」表，
   是**绕过 mock 直接打后端**测出来的。
   ✅ **这张表我已经补测过了**：生成链路那两组路由现在**是 200**
   （`/pipelines`、`/pipelines/{id}`、`/pipelines/{id}/versions`、`/pipeline-versions/{id}` 及其 `/plan`、`/hocon`、`/gate`），
   经 vite 代理逐条打、全部 200；**M3 两条链也都挂上了**——`/preparations/*`、`/runs/*`、
   **`/runs/{id}/rollback`**、`/runs/{id}/publish`、`/runs/{id}/quality-report`、`/runs/{id}/error-records`、
   `/monitor/runs/{id}/errors|errors/summary|quality-report` 返回 **401**（= 存在且要鉴权，不是 404）；
   **仍然 404 的是 `/policy-rules`、`/policy-versions`、`/budget-defaults`、Benchmark 那一组**（`openapi.json` 实测 **61 条**路径）。
   （生成链路两组路由的挂载见 [router.py:33-34](../backend/api/router.py#L33-L34)。）
   💡 **顺手记一个判据**：**401 = 存在且要鉴权；404 = 真的没有**——比记路由清单可靠。

> 面试口径：这是个**诚实且专业**的点——「前端我按接口契约先做完了，并用 mock 让它能独立演示；
> 后端哪几条契约真的落地了，我是逐条打接口核过的，没落地的那几条我都标了。」

## 主线 A：自然语言 → 冻结版本（M2 主链路）

这条链的**总纲只有一句**：一次生成 = **一个 LangGraph 线程**，`thread_id` 就是 `str(pipeline_id)`；
每一轮结束（正常跑完、还是停在澄清等人回答）service 都把手上有的东西**整体落一次**制品。

⚠️ 还有一个容易被忽略的形状：**它跑在 API 进程里，同步走完**，不是 Celery 异步任务。
我 grep 过 `tasks/` 里没有任何地方调 `workflow`（`from workflow` 的命中只有
`workflow/` 自己、`services/pipeline/generation.py`、`main.py` 的 lifespan、以及测试）。

### 岔路口（主线 A）

1. **同一条 pipeline 已有生成在跑** → 取不到 Redis 锁，**立刻 409、不等待、不排队**
   （[graph.py:97](../backend/workflow/graph.py#L97)）。排队会让「用户连点两下」变成两条串行的
   LLM 生成，第二条基于旧 state 起步，产出一份谁都没看过的方案。
2. **`_persist_turn` 里少了那个早返回** → 冻结一次，版本列表里会多出一个**没有制品的候选版本**
   （不可变表插了就删不掉）。⚠️ 顺带一条「文档比代码旧」：
   [freeze.py:28](../backend/workflow/nodes/freeze.py#L28) 的 docstring 还把这个重复插入记成**未收敛的缺口**，
   而 [generation.py:391](../backend/services/pipeline/generation.py#L391) **已经实现了它建议的收敛方式**（早返回）。
   面试讲「我踩过什么坑」时这条很好用：**注释停留在修复之前**，是团队里最常见的文档腐烂。
3. **「不报错但结果不对」第一名 —— state 里未声明的键会被静默丢掉**。
   `StateGraph(EtlWorkflowState)` 只把 schema 里声明过的字段建成 channel，
   于是注入一个没声明的键时，节点读到的是缺省值、报出来的却是「需求描述不能为空」这种
   **业务语义**的错，真因（字段没声明）和症状之间隔着一整个模块
   （[state.py:32](../backend/workflow/state.py#L32)；回归用例
   `tests/test_workflow_graph.py::test_undeclared_input_keys_are_dropped_not_silently_used`）。
4. **「不报错但结果不对」第二名 —— `_status_of` 认不出状态名就地报错，而不是回退 `draft`**
   （[generation.py:466](../backend/services/pipeline/generation.py#L466)）：一个拼错的状态名会把
   「门禁没过」显示成「刚创建」，而后者看起来完全正常。
5. **`_graph()` 每次现编译**（[generation.py:203](../backend/services/pipeline/generation.py#L203)）：
   不做模块级缓存的理由写在注释里——缓存住图就等于缓存住一个**可能已经关闭的 saver**，
   症状是「重启 lifespan 之后第一个请求报连接已关闭」，看起来像连接池的问题。
   编译本身的代价只是一次字典组装，相对一次 LLM 调用可以忽略。
6. **`generate_plan` 缺注入就当场 422**（[generate_plan.py:34](../backend/workflow/nodes/generate_plan.py#L34)）：
   如果静默兜底（自己造一份预算、或跳过档案块），模型会在缺列信息时**猜列名**，
   猜出来的列名一路走到 HOCON、直到门禁才报，排查方向被带到「模型质量」上，
   而真因是**编排层漏注入了一个字段**。

### 岔路口（主线 B）

1. **`thread_id` 不存在或已被清理** → `graph._values_of` 见空 values 就抛 `NOT_FOUND`
   （[graph.py:457](../backend/workflow/graph.py#L457)）。判据是「`intent_parse` 一定会写 `intent`，
   所以空 values 不可能与『跑过但什么都没写』同时成立」。
2. **跨租户的 `thread_id`** → `_pipeline_of_thread` 仍然走一次**带 tenant 过滤**的查询
   （[generation.py:487](../backend/services/pipeline/generation.py#L487)）。直接 `int(thread_id)`
   再取，会让一个越权 id 与一个不存在的 id 得到**不同的**错误信息——那是把「有没有这条流程」泄漏给别的租户。
3. **生成锁的释放必须「比较并删除」**（Lua，[graph.py:92](../backend/workflow/graph.py#L92)）：
   不比较就 `DEL` 会遇到——A 的锁 TTL 到期被 Redis 清掉、B 拿到同名锁，此时 A 收尾时一句裸 `DEL`
   就把 B 的锁删了，B 的互斥保护凭空消失，而两个请求都返回成功、日志里什么都没有。
   另外锁的释放失败**不能盖住** body 里的异常（`finally` 里抛错会把「生成失败」变成「释放锁失败」）。
   ⚠️ **锁只写在 graph 一处**：`services/pipeline/generation.py` 的模块 docstring 明确说这里不重复加锁
   ——「两处锁的 TTL 不一致时，先失效的那把会变成假的安全感」。
4. **「不报错但结果不对」第一名 —— `interrupt()` 之前的写入会被丢掉**。
   LangGraph 恢复时把**整个节点重跑**，所以 `interrupt()` 之前写 state 的部分随那次重跑消失。
   症状是「澄清问题点进去是空的」，而原因在**另一个文件**里
   （[interrupts.py:19](../backend/workflow/interrupts.py#L19)、[clarify.py:6](../backend/workflow/nodes/clarify.py#L6)）。
   所以 `clarify` 节点「故意极薄」，问卷由前一个不中断的节点（`param_check`）产出并落检查点。
5. **问卷有两种形状，各服务一个消费者**：后端 `interrupt` 载荷是简版 `{reason, questions:[{param, prompt}]}`
   （[interrupts.py:53](../backend/workflow/interrupts.py#L53)），前端 `pending_questions` 是富版
   `{key, question, kind, options, required, hint}`（[interrupts.py:94](../backend/workflow/interrupts.py#L94)）。
   两者由同一份 `MissingParam` **单向派生**——各写一份必然会漂移成「后端说缺 A，前端问的是 B」。

   **三种停止原因是分开记的**（收敛 / 轮次耗尽 / 去抖），因为运维含义完全不同：
   收敛是成功，「模型没辙了」与「模型在原地打转」要分开看。
2. **策略阻断有两道闸**：路由层（[graph.py:187](../backend/workflow/graph.py#L187)：直接去 terminal）与回路内
   （[loop.py:148](../backend/engines/autofix/loop.py#L148)：`repair` 零调用）。autofix 节点里**故意不再排除一遍**
   （[autofix.py:197](../backend/workflow/nodes/autofix.py#L197)）——写第三份判据，改漏一份的表现就是「策略阻断悄悄进了修复」。
3. **渲染失败被接住，不是 500**（[generate_hocon.py:111](../backend/workflow/nodes/generate_hocon.py#L111)）：
   渲染器对「Plan 自洽但表达不出 HOCON」会抛 `ValueError`，抛出去 = 一次 500；
   接住它、落成 `hocon_errors`、让门禁按缺制品报 finding，用户看到的是「方案第 N 行有问题」。
   空串而不是 `None`：gate 与 freeze 都以 `isinstance(hocon, str)` 判「制品在不在」。
4. **「不报错但结果不对」第一名 —— 落库的门禁结论不能是内存里那份**。
   `_persist_repaired` 一定要拿**新制品**重新 `run_gate` 再落库
   （[artifacts.py:662](../backend/services/pipeline/artifacts.py#L662)），
   因为 `outcome.result` 是拿**旧制品**（磁盘上那份）推出来的。
   直接把内存结论落库，等于「第 1 轮门禁看到的是哪份 Plan」永远问不出来。
5. **门禁结论挂在哪**：没有独立的表，挂在 HOCON 制品的 `validation_result` 上
   （[gate.py:134](../backend/workflow/nodes/gate.py#L134) → [gating.py:87](../backend/services/pipeline/gating.py#L87)），
   `parse` 与 `gate` **分开存**——事后要能分辨「解析没过」与「解析过了但门禁没过」，两种排查方向完全不同。
6. **`evaluate_all` 刻意是另一个函数**（[gate.py:89](../backend/engines/gate/gate.py#L89)）而不是给 `evaluate`
   加个开关：否则「生产放行」与「诊断」共用一条代码路径，某天为了诊断方便把开关打开，
   生产上就会开始一次报 40 条。

### 为什么修复回路要写成生成器（[loop.py:109](../backend/engines/autofix/loop.py#L109)）

修复这一步在真实系统里要调大模型（`async`），而回路本体是同步纯逻辑。三条路：

- 把本体改成 `async def` → Celery 里那些纯同步的调用方被迫套一层事件循环；
- **两处各写一遍控制流** → 「最多 3 轮 / 去重 / 策略短路」出现**两份实现**，一份改了另一份没改，
  **而且不会有任何报错**（这是最危险的选项）；
- **写成生成器** → `yield` 的语义正好是「把请求交出去、等一个提案回来」：
  同步驱动用 `repair(req)`，异步驱动用 `await repair(req)`，**差别只有一行**
  （[loop.py:333](../backend/engines/autofix/loop.py#L333) vs [:361](../backend/engines/autofix/loop.py#L361)），
  收敛判据、去重、轮次消耗只有一份实现。

代价是签名长、三个回调（`repair` / `recheck` / `now_factory`）都要注入；收益是**回路本身能被单测逐条钉死**
——注入一个永远原地打转的 `repair` 就能确定性地验证去抖。

## 主线 D：冻结与指纹

### 五段指纹分别是什么

指纹 = `SHA256(canonical_json(信封))`，信封由**五部分**拼成
（[fingerprint/parts.py:90](../backend/engines/fingerprint/parts.py#L90)）：

| 段 | 内容 | 为什么要它 |
|---|---|---|
| `etl_plan` | `dump_plan(plan)` | 制品本体 |
| `hocon_content` | HOCON **全文、逐字节**（不 trim、不归一换行） | HOCON 的字节就是它的身份——执行的是它 |
| `quality_contract` | `rules` + `error_table_target` + `reject_rate_budget` | 决定多少脏数据被允许进生产 |
| `supervision` | 五个运行预算 + `warn_threshold_pct` | 运行期监督的判据 |
| `source_metadata_sha256` | 源档案指纹（多个源**排序后**拼一起） | 源表结构一变，指纹就该失效 |

### 岔路口（主线 D）

1. **为什么行 id / 时间戳不进指纹**（[fingerprint/parts.py:48](../backend/engines/fingerprint/parts.py#L48) 的
   `EXCLUDED_KEYS`）：行 id 是**自增的编排事实**、时间戳是**审计事实**，都与制品内容无关；
   纳入会让「同一份制品」在不同 pipeline 下、不同时刻算出不同指纹，**重算永远失败**。
   `generation_context`（模型/提示词版本）、`valid`/`validation_errors`/`parser_version`
   也排除——同一产物的复制应得到同一指纹，校验器升级不该让历史指纹失效。
2. **为什么 `data_source_id` 反而要进指纹**（[fingerprint/parts.py:17](../backend/engines/fingerprint/parts.py#L17)）：
   把源库从 A 换成 B 而指纹不变，等于放行一份「连的是 A 库」的方案带着旧指纹走完治理。
   所以「排除 id」**不是**递归地删掉所有叫 `id` 的键，而是**只在每部分的顶层**剥行级 id
   （[fingerprint/parts.py:114](../backend/engines/fingerprint/parts.py#L114) 的 `top` 参数）；
   其下的字符串节点 id（DAG 的边靠它们互相引用）**必须留**——改 id 就是改图。
3. **生成到冻结之间重新探查过源表** → 指纹对不上 → **冻结被拒**
   （[parts.py:152](../backend/services/pipeline/parts.py#L152)）。这是**要的**行为：
   档案变了就说明门禁当初看的那份结构已经不在了，该重新生成，而不是把旧的批下去。
   故障方向是「多拒一次」，不是「静默放行」。
4. **已冻结再冻一次** → 409（[artifacts.py:380](../backend/services/pipeline/artifacts.py#L380)）；
   **草案不能当版本摘要返回**（[artifacts.py:557](../backend/services/pipeline/artifacts.py#L557) 断言非空）——
   「v3」这个称呼一旦出现在版本历史里，就意味着它能被审批、被执行、被回滚，而草案三样都不是。
5. **「不报错但结果不对」第一名 —— 指纹若从 Plan 现推质量契约，落库那两行就退出了信任链**
   （[parts.py:9](../backend/services/pipeline/parts.py#L9)）：只要 Plan 一样指纹就一样，
   于是有人改了 `quality_contract.rules`（本该不可变）**不会有任何东西报错**。
6. **Diff 比的是 parts，不是数据库行**（[artifacts.py:432](../backend/services/pipeline/artifacts.py#L432)）：
   行里的 `id`/`created_at` 每版都不同，比行会让每一版都显示「全变了」。
7. **指纹比对用 `matches` 而不是 `==`**（[parts.py:162](../backend/services/pipeline/parts.py#L162)）：
   指纹会经过 jsonb、前端、审批意见的复制粘贴，`0xAB`、大写、前后空格都不该让一份好制品被判成失效。

## 主线 E：从「冻结的版本」到「作业真的在跑」（M3 前半段，be-13/14/15）

### 岔路口（主线 E）

1. 🔴 **`apply_transition` 末尾曾经有一次 `session.refresh(row)`，它会吃掉失败现场**（[run.py:392](../backend/services/run.py#L392) 的注释就是这条的墓志铭）：
   `refresh` 按主键重读整行，从而**丢弃调用方尚未 flush 的改动**（会话是 `autoflush=False`）。而 `_fail` 的形状正是
   「先把 `error_message` / `failure_snapshot` 赋在实例上，紧接着推状态」——结果运行**确实** failed，
   **失败现场却是空的**（详情页 `error_message` 为 null、`failure_snapshot` 为 `{}`），账本里那条 `run.failed` 又写着失败了。
   改法：成功路径**不 refresh 整行**，把刚写下去的字段直接赋回内存实例；抢锁失败那条只读状态列。
   ⚠️ 不能改成「加一次 `flush()`」——项目守卫 `tests/test_service_commit_boundary.py` 规定 `services/` 里公开函数要自己 `commit()`，
   而 `apply_transition` 是**故意不提交**的（事务边界归调用方）。**守卫逼出来的改法反而更对**：修掉的是「任何调用方暂存的改动都会被吃掉」这一类。
2. **重复投递同一个 run** → 幂等闸放行到 `{skipped: True}`（[execution.py:84](../backend/tasks/execution.py#L84)），**不重新签发、不重新提交**。
   顺带一提：run 不存在时**不抛异常**（[:76](../backend/tasks/execution.py#L76)）——抛出去会让 Celery 反复重投一条永远不可能成功的消息。
3. **停止一个终态的 run** → 什么都不做（[execution.py:254](../backend/tasks/execution.py#L254)）：作业已经没了还去调 `stop`，
   SeaTunnel 只会回「查无此 job」，而那句话会被记成一次失败，**把一条正常的取消写成了异常**。
4. **stop 调用失败** → **不改状态**（[execution.py:284](../backend/tasks/execution.py#L284)）：控制面已经把它标成 `cancelled`，
   而这次调用没能让作业真停下——**库里的结论与事实不一致**，这个矛盾要留给人看（告警），不是在这里悄悄改回 `running`。
5. **令牌签发时"谁点的按钮"不进绑定**（[run.py:167](../backend/services/run.py#L167)）：绑定指纹 / 环境 / 租户 / 工具。
   按钮点两次不该产生两张票（同一事实），而同一份制品在两个环境执行**必须**是两张票——环境是绑定的一部分。
6. **`_submit_args` 额外校验凭据引用的数据源还在**（[execution.py:168](../backend/tasks/execution.py#L168)）：
   引用可能指向一个已被删除的数据源，而 **Vault 路径照样能取到值**——于是作业带着一个不存在的源的凭据跑起来。这类错要在提交前拦掉。

## 主线 F：作业跑起来之后（M3 后半段：be-16/17/18 + 收尾编排，**本次刚接上**）

主线 E 的终点是「作业被提交给 SeaTunnel，库里是 `running`」。从那一刻起到「这一运行算完」，
中间有四段：**抄指标判阈值**（越界硬中断）、**跑完出质量报告**、**合格才原子换表**、
**失败/中断走受管回滚**。这四段的代码此前**只有前一段**（be-16）是接在环上的，
后三段**各自写完了但没人调用**——见下面「为什么需要一个收尾编排」。

### F-1 监督环（beat 每 30 s，be-16）

**岔路口（监督）**：① 指标读不出来 → 四维全 `unknown` → 写 `degraded` 预警，
**绝不降级成无监督**（[`_is_degraded`](../backend/services/supervision.py#L410)）；
② 两个 worker 同时对同一条越界运行动手 → 条件 UPDATE 只有一个 rowcount=1，
输家直接返回，不会签出第二张票；③ 阈值来自**冻结时那份** `runtime_supervision_contract`，
不是当前配置——否则「同一份制品在不同时间跑出不同监督强度」。

### F-2 收尾环（beat 每 40 s，本次新增）

| 谁 | 干了什么 | 在哪 | 不干这一步会怎样 |
|---|---|---|---|

| service | 报告**合格**且允许发布 → `publish_run`（be-18） | [finalize.py:186](../backend/services/finalize.py#L186) → [publish.py:315](../backend/services/publish.py#L315) | — |
| service | 报告**不合格** → 不做任何额外动作（`finalize_report` 自己已写成 `run.failed` + 现场 + 账本） | [finalize.py:159](../backend/services/finalize.py#L159) | 在收尾侧再写一遍状态 = 两份判据，迟早对不上 |
| service | 作业 `failed` → 只按 `classify_failure` 的**分类**落 `error_message`，**不搬原文** | [finalize.py:216](../backend/services/finalize.py#L216) | SeaTunnel 的失败文本里常带整段配置与连接串——落库就等于把连接串写进控制面 |
| service | 作业 `stopped` / `not_found` → **不动状态**，只告警 + `orphaned` | [finalize.py:132](../backend/services/finalize.py#L132) | 可能是人工 kill、可能 Zeta 重启丢了内存态、也可能**别人正在取消**（状态还没落库）。一律写 `failed` 会让「谁停的」**永久失去答案** |
| service | `running` 但没有 `job_id` → `orphaned` + **error 级日志** | [finalize.py:117](../backend/services/finalize.py#L117) | 这是「提交任务崩在中间」的形状：没有作业在跑，也没有任何东西会再推进它 |

**为什么需要一个收尾编排（这段话是本次最有价值的面试材料）**：
be-17 与 be-18 是两份分别写的设计，**各自都把「报告合格之后谁去换表」写给了对方**——
be-17 §5 说「投递 Swap 归发布侧」，be-18 §5 说「跑完且报告合格」归执行编排。
结果是 `finalize_report` 与 `publish_run` 两个函数的**调用方数量都是 0**：
作业跑完 → 没人出报告 → `quality_report` 永远 0 行 → 正式表永远不换。
**这不是 bug，是两个模块之间的缝没人认领**，而且**每个模块的单测都是绿的**——
因为单测直接调这两个函数。补上的是那条缝（[services/finalize.py](../backend/services/finalize.py)，354 行）。

**为什么用 beat 扫描而不是 Outbox**：扫描**每轮都会重新发现**同一个待办
（`list_pending_run_ids` 的过滤条件就是判据本身），所以丢一次投递不会永久丢失；
反过来，走 Outbox 就得让「谁发现作业跑完了」也变成一个需要持久化的状态。
收尾任务本身**幂等**——靠下游而不是自己：`uq_quality_report_run_id` 让重复出报告复用既有行，
`swap.succeeded` / `swap.failed` 事件让重复发布短路。

### F-3 发布与回滚（be-18）

| 谁 | 干了什么 | 在哪 | 不干这一步会怎样 |
|---|---|---|---|
| api | `POST /runs/{id}/rollback`（**本次新挂上**） | [api/runs.py:111](../backend/api/runs.py#L111) | 此前前端有「回滚」按钮、后端没有这条路由 |
| service | 回滚范围**四连校验**：请求体里**没有表名**，服务端从运行行读出并重算后缀 | [services/publish.py](../backend/services/publish.py) `request_rollback` | 让调用方传表名，一次误操作可能删掉别的表 |
| service | 发布前四道预检（准备单未过期 + 制品指纹一致 + 质量报告通过 + 影子表存在） | [publish.py:315](../backend/services/publish.py#L315) 起 | 任何一道不过都**不碰正式表** |
| service | Redis 独占键 + `swap.*` 事件短路 → 发布**只可能发生一次** | [publish.py:695](../backend/services/publish.py#L695) | Swap 是**对合变换**：执行两次会把数据**悄悄换回去**，而且两次都「成功」 |
| service | 判定**以执行后对账为准**（重新探查两张表的形态），不信工具自报 | [publish.py:589](../backend/services/publish.py#L589) | 工具说 published 而实际没换，是最典型的「有结论、没事实」 |
| service | 回滚清理投 Outbox → worker 经 broker 执行 `target.rollback_cleanup` | [tasks/outbox.py](../backend/tasks/outbox.py) | 此前**这个主题没有消费者**：回滚请求投出去会被判成「未知 topic」进死信 |

**岔路口（发布）**：① 工具自报成功但对账不一致 → 降级成 `unknown` 并记账，**绝不落 `published`**；
② 发布失败 → 由发布侧自己写成失败结论 + 账本（它自己 commit），收尾侧只记一条 warning、**不改它写下的结论**；
③ 中断的运行**永不发布**（两道独立判据：报告在 interrupted 时强制不合格 + 收尾侧的 `allow_publish=False`）——
硬中断意味着影子表里是**半份数据**，把它换到正式表上比不发布坏得多。
