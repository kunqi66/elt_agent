# 05 · 开发原理

> 这页讲的是「这个项目的做事规矩」，以及**面试最加分的那一栏：这条规矩有没有自动检查兜着**。
> 靠人自觉的规矩等于没有规矩——所以每条我都标了「谁在守」。
>
> 规矩的来源：仓库根的 [CLAUDE.md](../CLAUDE.md)（作者自称「唯一行为准则」，
> 与本文件冲突时以它为准）。我核过：**大部分规矩真的在代码里有对应物**。

## 1. 分层规矩：每一层被禁止做什么，以及为什么

| 规矩 | 不守会出什么事 | 谁在守 |
|---|---|---|
| `api/` 只做校验/注入/权限/转发，**禁止业务逻辑** | 业务逻辑散进几十个路由，改一条规则要翻遍全仓 | ⚠️ **人工纪律** |
| `services/` **禁止** `import fastapi` | 业务逻辑和 HTTP 框架绑死，换框架要重写业务层，且**业务无法脱离网络单测** | ⚠️ **人工纪律** |
| `engines/` 是**纯函数层**：禁止框架、DB、Redis、网络、**LLM**、时间、文件 IO | 风险评级一旦能读时间/调模型，就**不可复现**——同一个变更单两次评级结果不同，审计直接失效 | ✅ **三种自动守卫**（见下） |
| `harness/` **禁止**依赖 `services/` 与 `api/`（单向） | 内核反过来依赖业务 = 谁都能改内核，安全边界消失 | ⚠️ **人工纪律** |
| `clients/` 不许把第三方异常类型泄漏到上层 | 上层代码开始 `except aiomysql.Error`，换驱动等于重写上层 | ✅ 类型化异常有测试（`test_datasource.py`） |
| 跨层只传 Pydantic 模型，不传 ORM 实例 | ORM 实例带 session 绑定，跨层传会导致「谁负责 commit」全面失控 | ⚠️ **人工纪律** |
| 所有 SQL 查询强制带 `tenant_id` | 一次漏写 = 跨租户数据泄漏（**最难发现的越权**） | ✅ 部分（`_resolve_target` 等有专门的测试；无全局守卫） |
| `workflow/` 的节点**只能回写自己声明的 state 键** | 一个节点偷偷多写一个键 = 状态机里出现「没人声明、没人维护」的字段，改天两个节点各写一次、互相覆盖，且**不报错** | ✅ **装配期 + 运行期两道**（见 §9.1） |
| `workflow/` 的节点**只做一次状态转移**，转移合法性由一处判定 | 状态在节点之间乱跳 = 「这个管线现在到底处于哪一步」说不清，前端按钮跟着错 | ✅ `assert_transition` 单点判定 + 状态机用例 |

### `engines/policy` 那三种守卫值得单独讲（面试重点）

这是全仓**唯一**一条被自动化守死的架构约束，做法分三层
（`tests/test_policy_import_graph.py`）：

1. **AST 扫直写的 import**（[:81](../backend/tests/test_policy_import_graph.py#L81)）：
   解析源码树，断言顶层模块在白名单内，连**相对 import** 也拦。
2. **AST 扫"危险调用"**：禁 `datetime.now(` / `time.time(`（[:112](../backend/tests/test_policy_import_graph.py#L112)）、禁 `open(`（[:127](../backend/tests/test_policy_import_graph.py#L127)）。
   为什么要禁时间：**带时间的判定不可复现**。
3. **独立解释器量"增量依赖"**（[:137](../backend/tests/test_policy_import_graph.py#L137)）：
   AST 只能看见**直写**的 import，看不见「A import B、B import httpx」。
   所以它起一个 `python -I` 子进程（`-I` = 忽略环境变量与当前目录），
   先 `import models.enums` 记下基线，再 `import engines.policy.pdp`，
   断言**增量**里不出现 `httpx/sqlalchemy/openai/socket...` 任何一个。

   为什么是「增量」而不是「`sys.modules` 里没有」——注释写得很清楚：
   `engines/policy` 必然要 `import models.enums`（枚举的唯一来源），
   而 `models/__init__.py` 按设计「导入本包即导入全部 ORM」，于是 `sqlalchemy` 一定在 `sys.modules` 里。
   **但它不是 `engines/` 引入的**。用增量判断，既不误报设计上既有的那一层，
   又能抓住任何真实的间接依赖。

4. **守卫自己还有元测试**（[:104](../backend/tests/test_policy_import_graph.py#L104)
   `test_禁用依赖确实在禁用名单里`）：防止后人把 `_FORBIDDEN_TOP` 清空之后**这个文件仍然全绿**。

> 面试怎么讲这一条：**「我不相信"写在文档里的架构约束"。
> 谁都可以在 `rules.py` 里 import 一个 LLM 客户端，而且所有既有用例照样全绿。
> 所以我给这条约束写了守卫，还给守卫写了元测试。」** ——这是我能讲出的最强的工程判断。

## 2. 唯一入口：哪些东西全项目只准有一处定义

| 东西 | 为什么只能一处 | 谁在守 |
|---|---|---|
| **副作用出口**（`ToolBroker`） | 两处定义 = 有一条路径能绕开审批直接动生产 | ✅ 工具注册表 + 启动钩子注册执行器 |
| **证据账本写入**（`EvidenceLedger.append`） | 谁都能拼 `prev_hash` = 链可以伪造 | ✅ 哈希由 `append` 内部算，外部无法传入；独立验链脚本对拍 |
| **凭据明文**（只在 `clients/vault.py` 物化） | 明文多一处出现 = 多一处泄漏面 | ✅ 表结构里**没有值列**（只有 path+version+key_names）——「想存明文得先改表」 |
| **配置**（`core/config.py`） | 散落 `os.getenv` 会导致「跑的是哪份配置」说不清 | ⚠️ 部分（无 grep 守卫） |
| **风险评级规则**（`engines/policy`） | LLM 或另一处实现参与评级 = 判定不可复现 | ✅ 上面那三种守卫 |
| **令牌版本号 Redis 键模板** | 两处定义且不一致 → 「登出全部设备」**静默失效** | ❌ **无守卫，且真的被破坏了**（见下） |
| **指纹的规范化规则**（`engines/fingerprint/parts.py`） | 两处各写一份「怎么把制品拼成字节」→ 重算指纹永远对不上，**历史版本集体 verify 不过**，且查不出是谁改的 | ✅ **金值哈希钉死**（见 §9.2） |
| **档案快照 JSON 的读法**（`services/pipeline/profile_view.py`） | 门禁与提示词各解析一遍 → 探查侧改个键名，改一处漏一处，症状是「门禁说列在、模型那边列凭空消失」，于是模型猜一个列名，一路走到渲染才炸 | ⚠️ **人工纪律**（注释里写明了「本模块是唯一读法」，但没有 grep 守卫） |
| **「一个管线最多一个候选版本」** | 两个候选并存 → 冻结时不知道该冻结哪一个，且**谁的指纹被写进 current_version_id 全靠运气** | ✅ **部分唯一索引 `uq_pipeline_version_one_candidate`**（DB 层兜底） |

### 🔴 一个真实的反例（我核实过，项目里唯一的"唯一入口"破功）

`auth:token_ver:{user_id}` 这个 Redis 键模板**写了两遍**：

- [services/auth.py:43](../backend/services/auth.py#L43) 定义为常量 `_KEY_TOKEN_VERSION`；
- [api/deps_auth.py:62](../backend/api/deps_auth.py#L62) 又手写了一遍同一个字符串。

后果不是报错，而是：**有人改了其中一处，另一处会静默读到一个空键 → 读回 0 → 版本校验永远通过 →
"登出全部设备"失效，而且没有任何报错**。这正是「唯一入口」这条规矩要防的失败模式，
而它偏偏发生在**鉴权路径**上。
（这是我自己 grep 出来的，不在任何文档里。面试讲「你知道规矩会被违反吗」时可以直接用。）

## 3. 数据一致性：宁可一起失败，也不许分开成功

| 规矩 | 具体做法 | 不守会出什么事 |
|---|---|---|
| **消费标记 + 证据 + Outbox 同事务** | `ReplayGuard.consume` 与 `EvidenceLedger.append` 都**只 flush 不 commit**，事务边界留给调用方 | 令牌已消费但证据没写 → **令牌废了，还查不出为什么** |
| **业务数据与证据一起提交** | service 里 `await session.commit()` 只出现一次 | 业务成功、证据丢失 → 审计时那一次操作**不存在** |
| **Redis 判不了就拒绝执行** | [harness/replay.py:78-84](../backend/harness/replay.py#L78-L84) fail-closed | 降级成「只靠 PG」= 把两道闸变零道闸，且自己以为还很安全 |
| **账本 seq 不用自增序列** | `MAX(seq)+1` + 锁（[ledger.py:272](../backend/harness/ledger.py#L272)） | 序列回滚留空洞，审计时无法区分「有人删了一行」与「有人回滚过一次」 |
| **不改历史哈希算法** | 金值哈希钉死（`test_verify_ledger_script.py:144`） | 改算法 = **宣布此前全部证据作废**，必须显式有人为它负责 |

## 4. 命名与编号规矩

| 规矩 | 为什么 |
|---|---|
| 错误码集中在 `core/errors.py`，**不自造** | 前端要按码做分支；自造码 = 前端静默走错分支 |
| 统一响应信封（页面接口是 `{items, meta}`） | ⚠️ 与 CLAUDE.md §6 写的 `{list, total, page, page_size}` **不一致**——文档与代码漂移，以代码为准 |
| 拒绝码 → 拒绝阶段（`harness/errors.py`） | 「在哪个阶段被拒」要能进账本，否则事后无法解释 |
| 迁移 revision 本机生成、**只在容器里应用** | 本机没有 Docker/PostgreSQL，本机库和容器库不一致会导致「本机全绿、线上炸」 |
| 新增依赖用 `uv add`，**不手写版本号** | 手写版本号 = 锁文件与声明不一致，环境不可复现 |
| 注释写「为什么」，中文；标识符英文 | —— |

## 5. 一套流程：新增一个后端功能按什么顺序做

这份流程写在 `.claude/skills/dev-backend/SKILL.md` 里（本项目的 spec 驱动流程），要点：

1. **需求先落 SSOT**：`vibecoding_doc/PRD.md` 是唯一事实来源；
   接口路径与 DTO **只能**来自 PRD §8 或已有代码的 docstring，**不许自创**；
2. **先改模块设计文档，再写 spec，最后写代码**——
   发现设计文档有缺漏时**不许绕过**（否则同一个语义会出现两份实现）；
3. **同一个语义只准有一份实现**（例：`load_user_identity` 被明确归给某一份，防「登录时算的权限 ≠ 请求时算的权限」这类**最难查的越权 bug**）；
4. **新发现的缺口要两处登记**（本 spec 的待确认清单 + 数据字典的全局清单），只写一处下一个人看不到。

> 面试怎么讲：「这个项目我刻意让它**文档先行**，因为 ETL 这类系统的需求会变，
> 而变的时候最难的不是改代码，是**找出所有被影响的契约**。
> 所以接口路径、字段名、权限码、错误码我全都要有唯一来源，改之前先查它被谁引用了。」

## 6. 这个项目里反复出现的一条原理：**「有码无电」要主动标出来**

这是我读完这个仓库最想讲的一条**自己的**观察：

> **功能写完了 ≠ 功能生效了。** 一个函数实现完整、单测全绿，但它**没有任何生产调用点**，
> 在运行期就等于不存在——而所有测试都是绿的，看代码也看不出问题。

项目里我找到**四处**（全部是我核实过的；其中一条本轮刚通电，特意留着——它最能说明这类缺陷长什么样）：

| 位置 | 实现状态 | 为什么没生效 |
|---|---|---|
| 账本签名检查点 `sign_checkpoint` | [ledger.py:299](../backend/harness/ledger.py#L299) 实现完整 | 全仓每一处 `EvidenceLedger()` 都是裸构造（grep 不到任何 `signer=`），**没有一处传 signer**；且 `tasks.maintenance.checkpoint_ledger` **没登记进 beat_schedule** |
| **出质量报告 / 换表这两个终点函数**（本轮已通电） | [quality.py:387](../backend/services/quality.py#L387) 的 `finalize_report`、[publish.py:315](../backend/services/publish.py#L315) 的 `publish_run` 都实现完整、各自有单测 | 两份设计**各自把「报告合格之后谁去换表」划给了对方**，于是**两个函数的调用方数量都是 0**——作业跑完永远不会出报告、报告合格也永远不会换表。补的是 [services/finalize.py](../backend/services/finalize.py)（只做分派与顺序，不拥有算法） |
| `ProbeStatus.EXPIRED` | 枚举定义了 | **全仓无人写入**，所以「中间态」永远回收不了 |
| `evidence_ledger_block`（签名块表） | 表与 ORM 都有，`services/governance.py` 会**读**它 | **没有任何代码写过它**（与第一行是同一个缺口的两面） |

**我怎么在面试里用它**：这几条不是「找茬」，是我准备用来回答「这个项目有什么不足」的**具体弹药**，
每一条都能顺带说出「怎么改」（挂 signer + 登记 beat；补上「谁写 `quality_report`」那一步；
加一个把超时的 `probing` 回收成 `expired` 的定时任务）。
**能指出"实现了但没生效"，比说"都做完了"可信得多。**
（补一句：这一栏原本还有「四眼校验零调用点」——be-13 把准备单与审批服务接上之后**它已经通电了**。
「能通电」这件事本身也说明：这类缺口不是设计错误，是**没人认领的缝**。）

**这一条在本轮升级成了主线**：补 M3 后半段时，同一个家族一次抓到**四个**——
判据的输入**不存在或错位**，于是闸门**永远不触发**，而单测全绿：
放大比要的读字节认不出 Zeta 的计数器键名、worker 的 broker 没拿到校验公钥（**整条执行链在 worker 里一步都走不了**）、
提交执行没给操作主体、质量读取器的注册形状在物理上无法实现。
共同的问法只有两句：**「这个判据的输入从哪来，那条路径真的会填它吗？」**
**「这段代码真跑一次会怎样？」**
做成卡片见 [06-知识点精讲 ㉔](06-知识点精讲.md)，逐条证据见 [10-做到哪一步了 §2](10-做到哪一步了.md)。
**怎么防**（已写进 [CLAUDE.md §10](../CLAUDE.md) 的交付前自检）：新增的每个「终点函数」都 grep 一遍调用方；
改过启动钩子/注册点之后**真的重启一次 API 与 worker、读启动日志**。

## 7. 缺口：哪些规矩**没有**自动检查兜着（诚实清单）

| 规矩 | 现状 | 我会怎么补 |
|---|---|---|
| `services/` 不许 `import fastapi` | 人工纪律 | 把 `test_policy_import_graph.py` 那套 AST 扫描**推广到 services/harness**（几乎零成本，同一套代码） |
| `harness/` 不许依赖 `services/`/`api/` | 人工纪律 | 同上，反向白名单 |
| 跨层不传 ORM 实例 | 人工纪律 | 只能靠 review；可考虑在 `schemas/` 的类型标注上做约定 |
| 所有查询带 `tenant_id` | 部分测试覆盖，无全局守卫 | 在 repository 基类里把「必须带租户过滤」做成**签名强制**（不传 tenant_id 直接抛错），让漏写变成过不了编译期/运行期 |
| 唯一入口（配置、Redis 键模板） | **已被破坏一次**（见 §2） | 键模板统一收进 `core/keys.py` 之类的单一模块，加一条「全仓 grep 不到 `auth:token_ver:` 字面量」的用例 |
| 枚举列有 CHECK 兜底 | ❌ 迁移是裸 SQL DDL，**全库只有 1 条 CHECK**（`approval_decision` 的不可自批） | 补枚举 CHECK，至少给状态机类字段（`status`）补上 |
| `engines/` 全层纯净（无网络/无时间/无 IO） | ⚠️ **只有 `engines/policy` 有那套 AST + 独立解释器守卫**；`engines/plan`、`engines/hocon`、`engines/gate`、`engines/autofix`、`engines/fingerprint` 全靠人工纪律 | 把 `test_policy_import_graph.py` 里的白名单**参数化**（`engines/*` 各一份允许清单），同一套代码扫全层——这是投入产出比最高的一条补法 |
| 档案快照的读法唯一（见 §2） | 人工纪律 | 一条 grep 用例：全仓除 `profile_view.py` 外不许出现 `schema_snapshot["tables"]` / `.get("tables")` |

> 「枚举列有 CHECK 兜底」这条要展开说一句，因为它是**文档与实现不一致**的典型：
> `models/checks.py:1-5` 的 docstring 声称枚举列「落地为 VARCHAR + CHECK」，
> 但 `alembic/versions/0001_initial_schema.py` 里**没有枚举 CHECK**（SQLAlchemy 的 `SAEnum`
> 默认 `create_constraint=False`）。四眼这条红线的兜底，be-13 之后要拆成两条来说：
> **自批拦截**是「服务端 + DB 约束」双保险——[services/approval.py:155](../backend/services/approval.py#L155)
> 调 `is_self_approval`，`approval_decision` 上另有 `ck_approval_decision_no_self_approval`
> 的 CHECK（[0001_initial_schema.py:92](../backend/alembic/versions/0001_initial_schema.py#L92)）；
> 而「两个审批槽不得由同一人担任」仍**只有服务端一道**
> （[services/approval.py:184](../backend/services/approval.py#L184) 调 `check_dual_checker_distinct`），
> **没有 DB 兜底**——全库只有那一条 CHECK 加一条 `UNIQUE (preparation_id, slot)`，
> 都拦不住「同一个人占两个槽」。所以 CLAUDE.md §5.8「服务端 + DB 约束兜底」，
> 在自批那条上是双保险，在双槽这条上目前**只对了一半**。

## 8. 我自己踩到并修掉的一条：定时炸弹测试

**这是我在写这份文档的当天（2026-10-16）跑测试时发现的，不在任何设计文档里。**

**现象**：跑全量单测，两条用例红了——
`test_governance.py::test_按发生时间过滤` 和 `::test_导出遵守过滤条件`。
断言是「按时间窗过滤后应该只剩后面几条」，实际却多出来一条。

**定位**：多出来的那条是 **seq=1**，也就是 fixture 里 `create_project` 落的「建项目」事件。
关键差异是——**那条事件没显式给时间，走的是服务代码里的 `utcnow()`（真实当前时间）**；
而用例里被过滤的种子事件用的是**硬编码的 `_T0`**，过滤条件又只给了**下界**
（`occurred_from=_T0 + 1min`）。

**于是这个用例是否通过，取决于「跑测试时的真实钟点」**：

| 跑测试的时刻 | seq=1（真实现在）落在窗口里吗 | 结果 |
|---|---|---|
| `_T0 + 1min` 之前（即 2026-10-16 16:01 CST 之前） | 否 | ✅ 绿 |
| 那之后 | 是 | 🔴 红（**永远红下去**） |

**这不是产品缺陷**——过滤逻辑是对的，只是那条事件确实落在了时间窗内。
**是用例自己在某个时刻引爆。** 而且它还埋了第二颗：另一条用例用
`occurred_from=_T0 + 365 天`，是一年后才引爆的同类。

**修法**：把这两处（以及那颗一年后的）过滤**两端都夹住**
（`occurred_from` + `occurred_to`），那条真实时间的事件无论在哪个钟点跑都被排除。
同时把这条写进了项目的行为准则（`CLAUDE.md` §9.1），标明症状与成因。
修完复跑：**1396 passed, 3 skipped**（那是**写这段时的**全仓数；用例一直在加，报数字时一并说口径）。

**为什么这条值得在面试里讲**（它是我准备好的第二个故事）：

> 「我在交付当天跑全量测试，发现两条用例红了，而这两条**上午还是绿的**。
> 查下来发现：fixture 里有条事件走服务代码、用的是**真实当前时间**，
> 而用例拿**硬编码时刻**做下界过滤——所以**这条用例的通过与否取决于你几点跑它**，
> 它在 `16:01` 那一刻过期了。
> 我修的时候顺便查了同类写法，发现还埋着一颗『一年后引爆』的。
> 这件事让我确认一个判断：**测试里的时间必须只有一个来源**，
> 要么全用固定基准时刻，要么全用真实时钟，**混着用就会变成定时炸弹**，
> 而它的表现是『跟我改的东西完全无关的用例突然红了』，
> 最容易让人误判成自己的改动引入了 bug。」

## 9. 生成链路（M2）新增的八条规矩

这一节讲的规矩，是我在写 be-09…be-12（LangGraph 工作流 / EtlPlan 与 HOCON / 门禁 / 冻结指纹）
时立的；**§9.5 ~ §9.8 是今天端到端把它真跑通后，被真实故障逼出来补的**。
**它们的共同点：防的都是「不报错但结果不对」**——因为生成链路的每一步都能"跑通"，
跑通不等于跑对。

### 9.1 节点只能回写自己声明的键，两道守卫

`workflow/nodes/__init__.py` 里有一张 `NODE_OUTPUTS`：**每个节点允许写哪些 state 键**。
它有两道守卫：

| 守卫 | 在哪 | 抓什么 |
|---|---|---|
| **装配期** | [graph.py:200-205](../backend/workflow/graph.py#L200-L205) | `NODE_OUTPUTS` 里声明了 `EtlWorkflowState` 里不存在的键 → **启动即抛**，图根本装不起来 |
| **运行期** | [graph.py:222-226](../backend/workflow/graph.py#L222-L226) | 节点运行时回写了白名单外的键 → 抛 `ValueError` 并指名道姓说出是哪个节点、哪些键 |

**为什么非要这么麻烦**：LangGraph 的 state 是一个共享字典，节点返回什么它就合并什么。
没有守卫时，「A 节点不小心写了 `status`」的后果是**状态被覆盖、没有任何报错**，
而前端按钮是根据 `status` 灰掉的——用户看到的是「按钮该亮的时候不亮」。

**同一个坑还有另一半**（这一半更阴）：**输入侧未声明的键会被静默丢弃**。
`StateGraph(EtlWorkflowState)` 按 TypedDict 建 channel，service 层注入的
`requirement` 如果没在 schema 里声明，它就不是 channel，键**直接消失**。
症状是节点读到空串，然后报一个**业务语义的错**（「需求描述不能为空」）——
排查方向会被带到「前端没传」上去。解法是把入图注入的键也在 schema 里声明齐，
并用例盯着（`tests/test_workflow_state.py` 里有一条「state 样例必须覆盖每一个声明的键」）。

> 面试怎么讲：**「进和出各有一条静默通道：进来的键不在 schema 里会被丢掉，
> 出去的键不在白名单里会覆盖别人。两条都不报错。
> 所以我给出口加了守卫，给入口加了一条覆盖用例。」**

### 9.2 指纹的规范化规则只准有一份，用金值哈希钉死

指纹是「这份制品是不是原来那一份」的唯一判据：**冻结前重算一遍，对不上就拒绝冻结**。
于是「怎么把制品拼成字节」这件事就成了一个**契约**——规范化规则一旦漂移
（比如 JSON 序列化不小心打开了 `ensure_ascii`，或者哪天有人把键排序去掉），
后果是**历史版本全部 verify 不过**，而每一份制品看起来都完好。

做法：规则集中在 [engines/fingerprint/parts.py](../backend/engines/fingerprint/parts.py)（纯函数层），
并且钉了一个**金值哈希**——[test_fingerprint.py:30](../backend/tests/test_fingerprint.py#L30)
写死一份样例制品的 sha256，规范化规则被无意改动时**立刻红**，而不是漂到生产上才发现。

同一条规矩的另一半是**排除项也要逐项锁定**（[test_fingerprint.py:245](../backend/tests/test_fingerprint.py#L245)）：
`frozen_by` / `note` / 时间戳 / `generation_context` / 派生校验结果改了，指纹**必须不变**；
而 `inputs[0].data_source_id` 改了，指纹**必须变**。这两条方向相反的断言合起来才是完整的契约：
**排除的是数据库行 id，不是 Plan 里对数据源的引用**——把「所有 id 都排除」照字面实现的人，
会在这里翻车（而且翻车方式是「换了个数据源，指纹没变」，静默）。

### 9.3 「一个管线最多一个候选版本」交给数据库，不交给代码

「候选版本」= `pipeline_version` 里 `frozen_at IS NULL` 的那一行。生成链路会反复改写它
（重跑、自动修复、重新出方案），而**一旦冻结，这一行就不可变**。

如果靠 service 层「先查有没有候选、没有再插一条」来保证唯一性，
两个并发请求会同时查到「没有候选」然后各插一条——**冻结时冻结了哪一条全看运气**。
所以这条约束下沉到 DB：部分唯一索引
[uq_pipeline_version_one_candidate](../backend/models/pipeline.py#L165)
（只对 `frozen_at IS NULL` 的行生效，所以历史版本可以无限多）。

迁移里漏掉这个索引的后果，比漏掉普通索引重得多，所以有一条用例专门盯着
**「模型里声明的索引集合」与「迁移真正建出来的索引集合」必须一致**
（[test_migration.py:121](../backend/tests/test_migration.py#L121)）：
它既扫手写迁移里的 DDL 文本，也扫 autogenerate 出来的 `op.create_index(...)`，
再减掉 `downgrade()` 里那些「建了又删」的。

### 9.4 确定性：进指纹的东西不许带时间、随机与网络

同一条需求跑两次必须得到**逐字节相同**的制品，否则「指纹」这个概念就没有意义
（两次跑出两个指纹，谁也说不清是需求变了还是环境变了）。所以：

- 时间戳、`frozen_by`、`note` 这类「这次是谁、什么时候做的」一概**不进指纹**（§9.2）；
- 起草器（`engines/plan/draft.py`）是**纯函数**，不取时间、不用随机数；
- 离线假 Provider（`clients/llm/fake.py`）同输入必然同输出，它同时充当确定性基线：
  **同一需求两次跑的方案必须完全一致**，这条基线一旦破了，指纹与门禁就失去了可比性。

> 面试怎么讲：「ETL 这类系统的交付物是**制品**，所以『同样的输入得到同样的输出』
> 不是性能优化，是**审计前提**。我把这条落在了两处：指纹里排除掉所有‘谁在什么时候做的’，
> 以及起草器做成纯函数——所以我在没有模型 key 的机器上，也能得到一份可复现的方案，
> 它还得过一个和线上完全相同的门禁。」

### 9.5 事务边界归 service：每个写入口自己 commit

**规矩**：`services/` 是唯一决定「这一次请求算不算成功」的地方——每个写入口在返回之前
**自己 `await session.commit()`**，依赖注入层只借连接、不提交。

**不守会出什么事**（我今天真踩了）：生成链路有 5 个写入口
（发起 / 答题 / 中止 / 自动修复 / 冻结），其中一个漏了一句 `commit()`。
后果不是报错，而是**最坏的一种**：LangGraph 的图跑完了、checkpoint 也落库了
（checkpoint 是 LangGraph 框架**自己提交**的，跟我们这个 session 无关），
所以「生成会话」看起来完整；但 `pipeline` 表**一行都没有**。
用户下一次请求进来，收到的是「生成会话不存在」——
症状指向「会话」，根因却在**事务边界**上。

**有没有自动检查兜着**：它只在「真图 + 真库」的端到端路径上才现形，
单测因为每个 service 各自 `commit`、或用内存夹具，看不见，所以端到端用例是兜底的第一层
（跑真图、落真库，断言 pipeline 行与版本行都在）。
**后来补上了静态那一层**：`tests/test_service_commit_boundary.py` 用 AST 扫 `services/` 全部公开异步函数，
「会不会写」按调用链判断（写语句多半藏在 repository 里），**会写就必须自己 `commit()`**；
另有一条元用例反过来喂它一个「忘了提交」的样例，防止守卫悄悄退化成永远通过。

### 9.6 同一个语义只准有一份实现：制品元数据只在一处组装

**规矩**：`hocon_artifact.validation_result` 这种「制品元数据」**只能有一处组装**。
渲染段与门禁段各出一半，拼装由 [services/pipeline/gating.py:72](../backend/services/pipeline/gating.py#L72)
的 `render_meta` ⊕ `GateOutcome.artifact_meta()` 一处负责，持久化路径**原样透传**，不再自己拼。

**不守会出什么事**（我今天真踩了）：这个字段原先在**三个地方**各自组装
（渲染节点 / 门禁节点 / 持久化路径）。门禁节点顺手多加了一层信封
`{"gate": {...}}`，于是字段形状变成 `{gate: {evaluated_at, conclusion}}`。
读侧 `get_gate` 按 `GateResult` 解析，直接把信封当成结论对象，报
**「evaluated_at / conclusion 缺失」**——门禁明明跑了、结论也在，却表现为「没跑」。
一处多包一层、另一处按老形状读，**两边都不报错**，直到读侧解析失败。

**有没有自动检查兜着**：形状统一靠「只留一处实现」这条纪律守着；
同一族的另一件事是 **DTO/列的版本宽度**：`PARSER_VERSION`（`pyhocon+elt-render-1`，20 字符）
先后撞了三道 16 字符的墙（DB `varchar(16)` → 冻结 manifest DTO → 制品读取 DTO）。
这两条现在各有一条守卫钉着：`tests/test_version_columns_fit.py`（DB 列必须装得下常量）
和 **`tests/test_dto_version_widths.py`**（DTO 字段宽度必须与列一致）——
它们是「同一个值在多处各写一遍宽度」的直接受害者，所以用「量一遍、互相对」来守。

### 9.7 写入侧和读侧必须共用同一份契约

**规矩**：跨进程传的结构（这里是 `generation_context`）**两端都用同一个 Pydantic 模型**
（`clients/llm/base.py::GenerationContext`），不许各自手搓 dict。

**不守会出什么事**（我今天真踩了）：写入侧手搓了一个 dict，比模型**多了一个键**
`plan_issue_count`。结果读侧（答题请求体）校验时直接 422：
**「Extra inputs are not permitted」**——
写入侧多写一个键，报错却发生在**读侧**，而且报的是「多了一个输入」，
排查方向很容易被带到「前端多传了参数」上。修法是写入侧改用 `GenerationContext` 模型，
读侧 DTO 放宽成 `extra="ignore"`——**契约只认一份，多余键在入口就消化掉**。

**有没有自动检查兜着**：**没有专门守卫**。正确姿势是「不要手搓 dict，用模型」，
它靠的是「跨层只传 Pydantic 模型」这条全局纪律（CLAUDE.md §4.6）。
这也是我把它写进这一节的理由：**纪律不落地时，症状会出现在离错误最远的地方**。

### 9.8 判据要用对：同一个令牌、两道闸；默认值不能当真值

两件事共享一个教训：**用一个「看起来对」的判据，比没有判据更危险**。

- **同一个令牌、两道闸，问的不是同一个问题**。执行前问的是「口令替换干净了没有」
  （`assert_no_unresolved_tokens`：令牌必须一个不剩）；冻结时问的是
  「这些令牌到时候解得开吗」（`secret_token_problems`：字段在白名单、数据源还在且有凭据）。
  我一开始在 `freeze_version` 里**用了执行期那道闸**，后果是
  **每一份合法制品都冻不了**，报错文案还写着「仍有未替换的密钥令牌」——
  读起来像渲染器漏了替换，实际是**拿错了判据**
  （[engines/hocon/types.py:92 / :109](../backend/engines/hocon/types.py#L92)）。
- **默认值不能当真值**。门禁里若不带项目预算就直接调 `engines.policy.decide()`，
  会落到 `_ZERO_DEFAULTS`（额度全 0），于是**每一份方案都被判超预算、门禁全 block**。
  正确入口是 `services.policy.decide_for_project`——先把项目参数读进来再判。
  **「判据拿到了吗」和「判据值合理吗」是两件事**，缺一个就会得到整齐划一的错误结论。

**有没有自动检查兜着**：令牌两道闸各有各的用例（冻结与执行各一组）；
预算这条靠 `decide_for_project` 这个**唯一入口**兜着（绕过它就会踩零默认值）。
两条的共性——**判据必须是「对那个阶段有意义」的那一个**——没有通用的静态守卫，
只能靠注释里写清「为什么用这道闸、不用那道闸」。

---

> 一句话收束这一节：M2 今天端到端跑通的这一趟，暴露的**没有一个是算法错**，
> 全是**边界错**——事务边界、契约边界、判据边界。这也正好印证了 §6 那条观察：
> 功能「写完了」和「生效了」是两回事，而这两者之间隔着的，往往就是这些没人盯着就会静默走偏的边界。
