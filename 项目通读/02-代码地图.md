## 后端分层：每一层被禁止做什么

分层本身不稀奇，**稀奇的是每条「禁止」都有理由，而且大部分真的在代码里执行**：

| 层 | 目录 | 允许 | **禁止** | 谁在守 |
|---|---|---|---|---|
| HTTP | `api/` | 校验、依赖注入、权限、调 service、组装响应 | 业务逻辑、直接碰 SeaTunnel/目标库 | 人工纪律（无自动守卫） |
| 业务 | `services/` | 调 engines/clients/models/harness | `import fastapi` | 人工纪律 |
| 领域 | `engines/` | Pydantic + 标准库，**纯函数** | 框架、DB、Redis、网络、**LLM** | ✅ 有 AST import 图断言：`tests/test_policy_import_graph.py`（只覆盖 `engines/policy/`） |
| 内核 | `harness/` | 被所有层调用 | 依赖 `services/`、`api/`（单向） | 人工纪律 |
| 异步 | `tasks/` | 只编排 | 写业务逻辑 | 人工纪律 |
| 客户端 | `clients/` | 封装第三方 | 把第三方异常类型泄漏到上层 | 类型化异常（`VaultError` 等） |

⚠️ **面试要说实话的一条**：上面标「人工纪律」的那几条，**目前没有自动检查兜底**。
`engines/policy/` 有 import 图断言是因为 PDP「绝不允许 LLM/IO 参与」是红线里的红线，
而 harness/services 的同类守卫还没写。这是我在报告里明确标出来的缺口（见 [05-开发原理](05-开发原理.md) 末尾）。

> M2 补上了一类**别样**的静态断言（不是 import 图，是 AST 读源码）：`tests/test_pipeline_api.py` 里
> 用 `ast.parse` 检查「`/diff` 装饰器必须排在 `/{version_id}` 之前」「路由顺序」「schemas 里不许出现第二份门禁/Plan 定义」。
> 这类断言的动机和 import 图断言一样：**都会在测试全绿的情况下被悄悄违反**
> （路由顺序反了 → 字面量被当成 id，症状是 404 而不是报错）。但 `engines/` 那六个新目录的纯函数性**仍然只靠人工纪律**。

## M2 / M3 新增的目录块，以及「为什么这么分」

M2（自然语言 → 冻结版本）落地之后，后端多了四块目录。**分法不是随手切的**，
每一块的分界线都对应一条能被违反、且违反了不会有任何测试变红的约束：

### 1. `backend/workflow/` —— 状态机归状态机，节点归节点（16 文件 / 3,538 行）

| 文件/目录 | 它唯一负责的事 | 为什么不能并进 `graph.py` |
|---|---|---|
| `graph.py`（526 行） | 装配图 + 六个对外门面（`start`/`resume`/`snapshot`/`abort`…） | 它只做「连边」和「取锁」，**不含任何业务判断**；路由判定被提到模块级的纯函数里（`route_after_gate` 等），这样「什么情况去修复」能在没有 PG 的机器上单测 |
| `state.py`（498 行） | `EtlWorkflowState` 的**字段定义** + 快照投影 + 幂等指纹 | schema 是节点之间唯一的契约。**未声明的键会被 LangGraph 静默丢掉**——所以「哪些字段能进 state」必须有一处权威定义，而不是散在节点里 |
| `checkpointer.py`（209 行） | PG 检查点持有者（连接、`.setup()`、单例） | 检查点线程跨请求存活，必须进程级单例；而且它**刻意不回落到 `InMemorySaver`**——这条纪律需要自己的文件来写清理由 |
| `interrupts.py`（171 行） | `interrupt` 载荷与恢复输入的**形状归一** | 载荷有两种形状（后端简版 / 前端富版），各写一份必然漂移；归一收在一处 |
| `transitions.py`（184 行） | `PipelineStatus` 状态转移表 | 「哪些状态能到哪些状态」是一张**表**，不是散落的 if；非法转移要统一转 409 |
| `nodes/`（10 文件 = `__init__.py` + 9 个节点 / 1,904 行） | 九个节点，**一节点一文件** | 每个节点是一个可以单独测的纯-ish 函数（`(state, config) -> dict`）。合在一个文件里，「这个节点写了哪些 state 键」就没人说得准了——所以 `nodes/__init__.py` 里还有一张 `NODE_OUTPUTS` 白名单做出口守卫 |

### 2. `backend/engines/plan|hocon|gate|autofix|fingerprint|diff/` —— 一种算法一个目录

`engines/` 是**纯函数层**（不碰框架、不碰库、不碰网络），所以「一个目录 = 一类可独立测试的算法」：

- `plan/`（1,050 行）：`schema.py` 定 `EtlPlanModel`、`validate.py` 出结构问题清单、`draft.py` 把档案拼成提示词原料。
- `hocon/`（1,305 行）：`render.py` 渲染、`parser.py` 反解析校验、`connectors/` 按连接器类型出模板。**渲染器与解析器分家**，才能用「渲染出来的东西再解析一遍」当自检。
- `gate/`（2,086 行）：`gate.py` 是那 98 行的调度（固定顺序 + 短路），`checks/` 是五类检查各自一个文件，`types.py` 是结论/严重度/finding id 的定义。**调度与检查分开**是短路语义能被测试的前提。
- `autofix/`（580 行）：`loop.py` 是回路本体（生成器 `_drive`），`patch.py` 是补丁的施加与校验。**为什么与 `gate/` 分开**：门禁回答「合不合格」（判定），修复回答「怎么改」（行动）——把行动并进判定，判定就不再是纯函数了。
- `fingerprint/`（314 行）：`parts.py` 是**五段指纹的输入定义**，`artifact.py` 是制品形状。它被审批、令牌、执行三方共同引用**当信任根**，所以必须独立、必须有且只有一份定义。
- `diff/`（332 行）：只比 `ArtifactParts`，不比数据库行（行里的 id/时间戳每版都不同）。

### 3. `backend/services/pipeline/` —— 一个业务流程一个包，包内按「唯一实现」切（8 文件 = `__init__.py` + 下面 7 个 / 3,016 行）

这是**最容易被问「为什么拆这么碎」**的一块。分界线的判据不是「代码长短」，而是**「哪份事实只允许有一处实现」**：

| 文件 | 唯一负责的「那份事实」 | 合并的后果 |
|---|---|---|
| `generation.py`（585 行） | **驱动一轮**：建 pipeline 行、凑初始 state、调图门面、落一轮制品 | 与 `artifacts.py` 合并，就会有两处「落制品」的逻辑 |
| `artifacts.py`（768 行） | **制品与冻结**：`freeze_version` 六道闸、`diff_versions`、手动修复入口 | 冻结是「审批看到的 = 执行拿到的」的唯一保证，它值得一个能整段读完的文件 |
| `gating.py`（539 行） | **凑 `GateContext` + 跑 PDP**：读档案、读数据源、算风险 | 门禁本体是纯同步函数，PDP 要读库要 `await`——这块粘合必须有一处，且只能有一处 |
| `parts.py`（203 行） | **五段指纹怎么拼**——全项目唯一一份定义 | 生成时算一份、校验时算一份 → 指纹随机失效（同一制品有时报错有时不报） |
| `repair.py`（255 行） | **LLM 修复提案 → 受限补丁**：拼提示词、收敛成 patch、往返自检 | 补丁自检不做，症状是「修复总差一点」，会把人带去调提示词/换模型 |
| `repository.py`（543 行） | **流水线/制品/版本的落库读库**：INSERT-only、候选行、重试 | 落库散在各 service 里，就不会有人记得「制品表只许 INSERT」 |
| `profile_view.py`（105 行） | **`schema_snapshot` JSON → 中立结构**的唯一读法 | 门禁与提示词各解析一遍，探查处改个键名就会「门禁说列存在、提示词里那一列凭空消失」 |

一句话总结拆法：**`generation` 管流程、`artifacts` 管冻结、`gating` 管判定、`parts` 管指纹、`repair` 管修复、`repository` 管落库、`profile_view` 管读档案**——
每个名字对应一句能被单独审查的话。

### 4. `backend/clients/llm/` —— 把「模型是外部系统」这件事关在一个目录里（11 文件 = `__init__.py` + 6 个模块 + `prompts/` 4 个 / 2,169 行）

`base.py`（协议）→ `deepseek.py` / `fake.py`（两个实现）→ `registry.py`（按配置选一个，**缺 key 不静默降级**）→
`prompts/`（提示词与围栏标签）→ `token_budget.py`（提示词裁剪）→ `scrub.py`（出站前脱敏）。

分成这些文件的理由只有一条：**「哪一段话会被发出去」必须是可枚举、可断言的事实**。
所以提示词由 `prompts/` 集中产出（`plan_blocks` / `fit_prompt`），节点不自己拼——一旦某处自己拼一条提示词，
它就绕过了裁剪、绕过了禁投喂断言、也绕过了 `FakeProvider` 的围栏分派（无 key 环境下第一步就 500）。

### 5. M3 前半段（be-13/14/15）的落点 —— 审批面 / 执行面 / 数据面

M2 停在「冻结版本」；M3 前半段把「批准 → 真的开始搬数据」这道闸接上了。
它没有新开目录，而是三处各自独立的落点，分界线同样对应「哪份事实只允许有一处实现」：

| 落点 | 唯一负责的事 | 为什么单独放 |
|---|---|---|
| [services/preparation.py](../backend/services/preparation.py)（1,461 行）+ [services/approval.py](../backend/services/approval.py)（412 行） | **Prepare 与四眼审批**：算指纹、跑 PDP、定必需槽、把具名决定落成不可变的一行 | Prepare 是**零副作用**的（不签发 Capability、不建 run、不投 Outbox）——这是四眼能成立的前提，所以它与「真的执行」必须分家 |
| [services/run.py](../backend/services/run.py)（762 行） | **Commit**：前置校验 → 签发单次 Capability → 建 `execution_run` → Outbox 入队，**同一事务**；状态机唯一写入口 `apply_transition` | 它是「批准」与「执行」之间唯一的转换点，事务边界只能有一处 |
| [tasks/execution.py](../backend/tasks/execution.py)（324 行，`submit_run`/`stop_run`）+ [harness/outbox.py](../backend/harness/outbox.py)（183 行） | **投递与执行**：Outbox 只写库不投递；任务体验签 → 原子消费 jti → 交 `ToolBroker` | 「业务事实与待发命令同生共死」只有持事务的人能保证；投递器只搬运、不做业务判定 |

新开的两块目录都在 `clients/`：

- [clients/seatunnel/](../backend/clients/seatunnel/)（5 文件 / 1,093 行）：Zeta REST 客户端（提交/停止/状态/指标 + 三条重试纪律）与运行期配置物化（换密钥令牌、把 sink 改写成影子表、给作业起带 `run_id` 的名字）。**对外不导出执行器**——`register()` 是唯一注入入口，绕过注册表等于绕过 `ToolBroker`。
- [clients/secrets/](../backend/clients/secrets/)（3 文件 / 324 行）：`materialize.py` 是**执行期唯一把口令变成字节的地方**（目录 0700、文件 0600 + `O_EXCL`、`finally` 无条件销毁、先覆盖写零再 unlink）；`vault.py` 是 Vault 的执行侧适配器，只加执行期需要的东西，不重实现 AppRole。

还有一条**刻意的留白**：`tasks/supervision.py` 曾经是**注册了但明确返回 `not_implemented` 的真任务**（be-16 的占位）。
不注册的话，每次**正常**提交都会往死信队列留一条假警报——`submit_run` 成功后会投 `etl.run.supervise`，
未知 topic 会被投递器判 `dead`，于是死信里全是假警报，真警报就没人看了。
（**本次它已经变成了真实现**，见下一节——留下这条记录是因为它的理由对理解 Outbox 的「未知 topic 判死」很有用。）

### 6. M3 后半段（be-16/17/18 + 收尾编排）的落点 —— 监督面 / 质量面 / 目标面

这一轮**新开了三块目录**（`engines/quality`、`engines/supervision`、`clients/target`），
并且第一次出现了一个**只做编排、不拥有任何算法**的 service：

| 落点 | 唯一负责的事 | 为什么单独放 |
|---|---|---|
| [engines/quality/](../backend/engines/quality/)（7 文件 / 1,837 行） | **质量契约 → 谓词 SQL**、错误行的**受保护摘要**（哈希 + 截断）、端口定义（`ports.py` 的 `ErrorTableReader`） | 契约是**冻结时**产出的、执行时按它判——判定必须能在没有数据库的机器上单测。端口也定义在引擎侧：**消费方定义端口**，客户端去实现（依赖倒置） |
| [engines/supervision/](../backend/engines/supervision/)（4 文件 / 473 行） | **五维度阈值判定**（拒绝率 / 写字节 / 放大比 / 读行数 / 时长）+ 优先级合成 | 它是「要不要硬中断一次生产作业」的判据，和 PDP 一样属于**绝不能让 LLM 参与**的那一类 |
| [services/quality.py](../backend/services/quality.py)（896 行） | 出**不可变、一运行一份**的质量报告（`uq_quality_report_run_id`）；不合格**不抛异常**而是落结论 + 推进状态 + 记账 | 「不合格」是一个**正常的业务结论**，不是异常。抛异常会让它长得像故障，而故障路径没人会去读报告 |
| [services/publish.py](../backend/services/publish.py)（1,525 行） | **原子 Swap 与受管回滚**：四道预检、Redis 独占键、执行后对账、回滚范围四连校验 | Swap 是**对合变换**（做两次等于没做），所以「只可能发生一次」这条纪律需要一个能被整段读完的文件 |
| [services/supervision.py](../backend/services/supervision.py) + [tasks/supervision.py](../backend/tasks/supervision.py) | 抄指标 → 写时序点 → 判阈值 → 抢状态 → 签票进 Outbox | 监督**不在 worker 里直接调 SeaTunnel**（worker 的 broker 没有签发器）——停止命令必须经 Outbox 回到 worker |
| [clients/target/](../backend/clients/target/)（9 文件 / 2,276 行） | 目标端两个**写**工具的执行器（`publish_swap` / `rollback_cleanup`）+ 一个**只读**读取器（错误表计数/摘要） | 写走 `ToolBroker`、读**刻意不走**（读取无副作用，套一层 Capability 只是提高复杂度）。读取器注册的是**工厂** `(session, run) -> reader`：端口只拿到表名，而表名**定位不到主机与库** |
| [services/finalize.py](../backend/services/finalize.py)（354 行）**★ 本次新增** | **收尾编排**：读一次数据面事实，把运行推到结论 | 它是**唯一一个「不拥有任何算法」的 service**——只做分派与顺序。删掉它，be-17 与 be-18 就各自变回「写完了但没人调用」（这正是补它之前的状态） |

> 📌 有一条**反例**要主动交代：`engines/` 现在有 53 个文件、9,891 行，
> 但「engines 不许 import 框架/库/网络」这条**自动守卫只覆盖了 `engines/policy/`**
> （`tests/test_policy_import_graph.py` 用 AST 静态检查）。
> 新加的八个目录（含本次的 quality / supervision）**靠人工纪律**。为什么只给 policy 加：
> 因为「PDP 不许 LLM 参与」是红线里的红线，违反了不会有任何业务用例变红；其余几条同类守卫还没写。

另外一个实数（本次重测）：前端 `src/api/*.ts` 一共引用了 **76 条**后端路径，其中**52 条后端已注册、24 条未注册**——
未注册的 24 条分三类：① 总览工作台 `monitor/*`（7 条，M4 埋点）；② 策略管理面 `governance/policy-rules|policy-versions|budget-defaults` 与 `governance/benchmark/*`（10 条，M4）；
③ 剩下的 7 条是**本版前后端契约还没对齐的部分**——`runs/{id}` 下的 `diagnosis`/`logs`/`metrics`/`resume`（4 条，归 be-19/be-20 的根因诊断、日志与指标折线、断点续跑）与 `preparations/{id}` 下按老契约写的 `commit`/`risk-reasons`/`timeline`（3 条，后端把「提交」落在 `POST /runs`、把时间线/理由与轮询落在 `GET /preparations/{id}` 与 `GET /preparations/{id}/status`）。
**「error-records / quality-report / rollback」这三条上一版还在这个未注册清单里，本次已经变成了 401。**
这就是「前端按契约先行、后端按里程碑补」的直接证据。

**怎么理解这件事（面试要能说清）**：前端是照着 `PRD §8` 的**接口契约**先做出来的（16 个页面全是真页面，
不是占位白板）。到 M3 后半段为止，后端的现状是：
**表结构（32 张）齐、纯算法（PDP/脱敏/门禁/指纹/修复/质量契约/监督阈值）齐、M1 的完整闭环齐、
M2 的生成链路（api + service + workflow + engines）齐、
M3 两半段（Prepare/四眼审批 → Commit 单次 Capability + Outbox → 目标端备表 → Celery → SeaTunnel 提交/停止 →
监督硬中断 → 质量分流 → 原子 Swap / 受管回滚 + 收尾编排）在**控制面**上接上了，
但**分流的数据面还差最后一根线**（`render_route_selects` 零生产调用方，违规行不会被真的分出去）；
还差 M4（策略管理面、Benchmark、监控埋点与指标折线、根因诊断、备份/CI-CD）。**

所以现在能讲完整流程的**有两条半**：
①（M1）登录鉴权 → 多租户 → 数据源管理 → 连通性测试 → 元数据探查与脱敏 → 证据账本——**我真跑通过**；
②（M2）自然语言需求 → 澄清 → EtlPlan → HOCON → 门禁 → 自动修复 → 指纹 → 冻结版本——**今天也真跑通了一次**（一句需求 → 5 个澄清问题 → 冻结，重复冻结 409）；
③（M3 前半段）冻结版本 → 准备单 → 四眼审批 → Commit（单次 Capability + Outbox）→ Celery 提交 SeaTunnel——**接口与服务都在，但不是我在真机端到端验的**（哪一块还差、差在哪，见 [10-做到哪一步了](10-做到哪一步了.md)）。
再往后的「监督硬中断 → 质量分流 → Swap/回滚」：**监督与发布在控制面上都实现了**
（硬中断签票停作业、发布前四道预检、Swap 只允许发生一次），但**分流的数据面没接线**——
路由 SQL 生成器有、错误表也会建，但渲染器没有调用它们，所以现在跑起来违规行不会进错误表。
逐条现状与改法见 [10 §4.1](10-做到哪一步了.md)。

> ⚠️ 上表里 `/pipelines` / `/pipeline-versions/*` 那一行我这次**真的打过了**（真后端 + vite 代理，全 200）。
> 但页面**渲染**我还是没点过——我没有浏览器工具，手上只有「接口 200 + 能编译 + 类型过」三条间接证据。
