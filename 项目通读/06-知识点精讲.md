## ① 单次执行令牌：为什么「查了再写」不行

**一句话**：一张执行令牌只能用一次，并发下也不能用两次。

**为什么需要它**：审批通过后系统签发一张令牌，谁拿它谁就能真的动生产数据。
如果「检查用过没有」和「标记为已用」是两个动作，中间就有一条缝——
两个 worker 同时挤进去，**同一份作业被真跑两遍**。这不是报错，是**双倍的数据搬运**。

**这个项目里怎么做的**：两道闸，分工明确（[harness/replay.py:69](../backend/harness/replay.py#L69)）——
Redis `SET NX` 挡重复投递，PG 的**条件 UPDATE + 看影响行数**保证正确性。

**代码长什么样**

```python
 77  ok = await self._redis.set(key, "1", nx=True, ex=self._ttl)   # 闸一：抢锁占位
 78  except RedisError as exc:
 80      raise AppError("重放防护不可用（Redis 不可达），已拒绝执行", ...)  # fail-closed
 90  result = await session.execute(
 91      update(Capability)
 92      .where(Capability.jti == claims.jti, Capability.consumed_at.is_(None))  # 闸二
 93      .values(consumed_at=now, consumed_by_run_id=run_id))
 95  if result.rowcount == 0: return ConsumptionResult.REPLAYED       # 没抢到 = 重放
```

**为什么不那样做**
- **不用「先 SELECT 再判断再 UPDATE」**：那中间有窗口，正是这个功能要防的东西。
  正确做法是**让数据库的 WHERE 条件替我判断**——`UPDATE ... WHERE consumed_at IS NULL`
  是原子的，`rowcount` 就是判断结果。
- **不在 Redis 不可达时降级成「只靠 PG」**：看着更皮实，实际是把两道闸变成零道闸。
  **判不出「用过没有」时，唯一安全的选择是不执行。**

**踩过的坑**：Redis 键的存活时间写成 `ttl_sec + slack`（[:67](../backend/harness/replay.py#L67)），
方向**不能反**——键必须比令牌活得久。反过来的话令牌还没过期、键先没了，同一个令牌能再消费一次，而且静默。
另一个坑是 `rowcount == 0` 有三种可能（已消费/从未签发/jti 被篡改成不存在的值），
代码**故意用同一种方式处理**，并且**不回滚那个 Redis 毒键**：宁可让调用方重新签发，也不给重放留窗口。

**面试会怎么问**
1. 「你的令牌怎么保证只用一次？」
2. 「如果 Redis 挂了还执行吗？」
3. 「为什么要用 Redis，直接靠数据库不行吗？」

**你怎么答**（照着念，带数字）：
> 「分两道。第一道是 Redis 的 `SET NX`，它就是抢锁，快，主要用来挡住 Celery 的重复投递；
> 第二道是 PG 里 `UPDATE capability SET consumed_at=now WHERE jti=? AND consumed_at IS NULL`，
> 然后看 `rowcount`——并发的时候行锁会让第二个事务影响 0 行，就判成重放。
> **真正的原子性来自第二道的 WHERE 条件，不是来自 Redis**。
> Redis 连不上的时候我直接抛错拒绝执行，因为这时候我判不出这个令牌用过没有，
> 而降级成『只靠数据库』等于把两道闸变成零道闸。」

**追问会追到哪**
- **第二层**「为什么不直接用数据库的唯一约束？」→ 因为约束只能防止**插入两行**，
  而我要防的是**同一个令牌被执行两次**——那是一次 UPDATE 而不是两次 INSERT。
  真正的对应物是「条件更新 + 行数判断」，语义上是 `UPDATE` 而不是 `INSERT`。
- **第三层**「那 Redis 和 PG 不一致怎么办（Redis 说用过、PG 说没用过）？」→
  会走向不同的结果：Redis 抢输 → 直接判重放，**不会去查 PG**；
  Redis 抢赢但 PG 影响 0 行 → 也判重放，**那个毒键故意留着不删**。
  两边不一致时**一律往「拒绝」倾斜**，这就是 fail-closed 的实际含义。
- **第四层**（真的会被问）「这个函数 commit 吗？」→ **不 commit**。
  事务边界归调用方，这样「消费标记 + 证据事件 + Outbox 消息」能在同一个事务里落地；
  自己 commit 会造出「令牌已消费但证据没写」的中间态——令牌废了却查不出原因。

## ② 哈希链证据账本：改一条，全链对不上

**一句话**：每条记录都带前一条的哈希，改任何一条历史记录都会被验出来。

**为什么需要它**：审计要回答的是「这条作业是谁批的、拿什么版本跑的」。
如果记录存在数据库里就完事，那么**有库权限的人可以改完再改回来**，审计结论不可信。
做成链之后，改动会破坏所有后续哈希——**审计方不需要信任数据库管理员**。

**这个项目里怎么做的**：`prev_hash` + `event_hash` 串联，写入时自动算
（[harness/ledger.py:215](../backend/harness/ledger.py#L215)），并且有一个
**独立重写了算法的验链脚本**（`scripts/verify_ledger.py`）。真机实测 `OK checked=52`——这个数字随账本每落一条事件就涨，别把它当成固定的绝对值。

**代码长什么样**

```python
222  _assert_payload_clean(event)                     # payload 里不许夹带秘密
223  seq, prev_hash = await self._lock_tail_and_next_seq(session)   # 锁内取链尾
229  event_hash = compute_event_hash(..., prev_hash=prev_hash, occurred_at=occurred_at)
256  session.add(row); await session.flush()          # flush 不 commit，事务归调用方
259  if self._signer is not None and seq % self._checkpoint_interval == 0:
260      await self.sign_checkpoint(session, to_event_seq=seq)     # 每 N 条签一个检查点
```

并发下的关键在 [:272](../backend/harness/ledger.py#L272)：

```python
281  on_pg = session.bind is not None and session.bind.dialect.name == "postgresql"
285  await session.execute(text("SELECT pg_advisory_xact_lock(:k)"), {"k": _EMPTY_CHAIN_LOCK_KEY})
291  stmt = stmt.with_for_update()                    # 锁住链尾那一行
293  if row is None: return 1, ZERO_HASH              # 空链：seq=1，前哈希全零
295  return int(row[0]) + 1, str(row[1])
```

**为什么不那样做**
- **不用数据库自增序列做 `seq`**：序列在**回滚**时会留空洞，而验链要求 seq 连续。
  有空洞的话，「有人删了一行」和「有人回滚了一次」**无法区分**——审计工具分不清这两件事就等于白做。
- **不做批量插入优化**：批量插入会让两个并发批次交错写同一段 seq 区间，而锁只保护单条。
  注释原话是「**正确性优先于这点吞吐**」。
- **检查点不能只签链尾哈希**（[:302](../backend/harness/ledger.py#L302)）：只签最后一条等于
  中间整段被替换也能通过；所以签的是 `chain_head_hash|from|to`，区间端点一起签。

**踩过的坑**
1. **空表时的并发**：表空的时候**没有行可以锁**，两个并发写入会同时读到 `None`、同时算出 `seq=1`——
   链从第一条就分叉。所以补了一把 `pg_advisory_xact_lock`（事务级顾问锁，随 commit/rollback 自动释放）。
   这个 bug 在串行单测里**永远走不到**。
2. **时区**：`occurred_at` 必须是**带时区**的时间（[:225](../backend/harness/ledger.py#L225)）。
   裸 `datetime` 会按本地时区解释，于是**容器（UTC）和开发机（UTC+8）算出的哈希不一样**，
   看起来像账本被篡改。
3. **验链脚本读 jsonb 漏了注册解码器**：asyncpg 会把 `jsonb` 当**文本**回传，
   payload 变成带引号的字符串 → 哈希必然对不上 → 脚本一口咬定「该条被改动过」。
   实测输出是 `BROKEN checked=0 at_seq=1`，**看上去像账本被篡改，实际是读取层的缺陷**。
   现在有用例钉着（`tests/test_verify_ledger_script.py:290`）。

**面试会怎么问**
1. 「区块链那套哈希链，你这里有类似的吗？并发写入怎么办？」
2. 「审计发现账本有问题，你怎么证明不是你们自己改的？」
3. 「每 100 条签一个检查点，检查点签的是什么？」

**你怎么答**：
> 「有，但这不涉及共识，只是**防篡改留痕**。
> 每条事件带前一条的哈希，写入的时候在锁里取链尾、算 seq、插入——
> 并发靠 PG 的行锁串行化，空表那段窗口额外加了一把顾问锁，因为表空的时候没有行可以锁。
> 至于『怎么证明不是我们自己改的』：一是**算法验证脚本刻意不复用被审计的代码**，
> 它按文档重写了同一套哈希；二是每 100 条用一个**与账本签名密钥分离的 Ed25519 密钥**签一个检查点，
> 覆盖区间端点——只签链尾的话，中间整段被替换照样能通过。
> 我在 ECS 上跑过这个脚本，那天是 `OK checked=52`（这数字随事件的增加而涨）。」

**追问会追到哪**
- **第二层**「seq 为什么不用自增序列？」→ 序列回滚留空洞，验链要求连续，`MAX(seq)+1` + 锁才能保证。
- **第三层**「那把锁在测试里验证过吗？」→ **这是我要主动说的缺口**：
  单测跑在内存 SQLite 上，`FOR UPDATE` 被 SQLAlchemy 静默忽略，`on_pg` 那个分支根本不进，
  所以那 16 个用例**全是串行的**，一行并发都没碰到。
  换句话说：**这个模块最难的部分，恰好落在单测够不着的地方，而它是绿的。**
  我会补一段针对真 PG 的并发压测。
- **第四层**「如果有人改哈希算法怎么办？」→ 有一条**金值用例**（`test_verify_ledger_script.py:144`）
  把一个具体的 64 位哈希钉死，注释写着：改算法 = 宣布此前全部证据作废，
  必须有人显式改那个字面量并回答「存量账本怎么办」。

## ③ 确定性风险评级：为什么绝不让大模型参与

**一句话**：一个变更单有多危险，由纯规则算，跟模型无关，算一百次结果一样。

**为什么需要它**：如果「这个变更要不要两个人批」是模型说的，那么：
① 同一个变更单两次评级可能不同 → 审计无法解释；② 有人可以通过构造输入让模型「放水」；
③ 模型换了/升级了，历史判定无法复现。
所以**评级必须是纯函数**：输入定了，输出就定了，可以离线复算。

**这个项目里怎么做的**：`engines/policy/` 是**纯函数层**——不 import 框架、不碰数据库、
**不允许取当前时间**、连 `open()` 都不许（这三种都写了自动守卫，见卡片 ④）。
11 条内置规则命中后取**最严重**的那一档（[pdp.py:91](../backend/engines/policy/pdp.py#L91)）。

**代码长什么样**

```python
 54  if now.tzinfo is None:
 55      raise ValueError("now 必须带时区：裸 datetime 在不同时区的主机上给出不同的 evaluated_at")
 58  active_rules = tuple(rules) if rules is not None else BUILTIN_RULES
 70  for rule in active_rules:                     # 纯遍历，没有任何 IO
 84  if not hits:
 88      rule = fallback_rule(intent)              # 写入意图永不落到 P3
 91  risk_level = RiskLevel.most_severe(*(hit.level for hit in hits))
 92  blocked = risk_level.must_block              # 只有 P0 是「阻断」
 95  required_slots = ()
 96  if not blocked and risk_level.min_approval_slots == 2:
 97      required_slots = (ApprovalSlot.CHECKER_DATA, ApprovalSlot.CHECKER_SECURITY)
 99  ordered = tuple(sorted(hits, key=lambda hit: (hit.level.rank, hit.code)))   # 输出有序
```

**为什么不那样做**
- **时间不从系统取，而是当参数传进来**：`now` 是入参（[:42](../backend/engines/policy/pdp.py#L42)），
  并且**不带时区就直接报错**。这样「什么时候评的级」是**证据的一部分**，可以复现。
- **兜底不写成一条规则行，而写在代码里**（[:85-88](../backend/engines/policy/pdp.py#L85-L88)）。
  注释解释了：兜底需要「其他规则都没命中」这种**否定式聚合**，规则 DSL 里没有，也**不该有**。
- **`hits` 排序后再输出**（第 99 行）：否则命中顺序取决于字典/集合的迭代顺序，
  同一份输入会产出不同的 JSON，证据就没法逐字节比对了。

**踩过的坑**：P0 判定时**提前把审批槽位归零**（第 95 行）——P0 是要阻断的，留着槽位
会让下游纠结「到底要不要批」。**在源头把无意义的值清掉，比让下游去解释更安全。**

**面试会怎么问**
1. 「你怎么保证大模型不参与安全判定？」
2. 「同一个变更单评两次级，结果会一样吗？怎么保证？」
3. 「规则引擎跟写在代码里的 if-else 有什么区别？」

**你怎么答**：
> 「评级是纯函数：给同一个输入，结果逐字节相同。
> 具体保证有三层：**第一层**，`engines/policy` 这一层被自动守卫禁止 import 框架、
> 禁止调时间、禁止文件 IO；**第二层**，时间不从系统取，是入参，不带时区直接报错，
> 所以『评级的时刻』本身是证据的一部分；**第三层**，命中的规则按 `(严重级, 规则码)` 排序后再输出，
> 保证同一份输入的 JSON 完全一样，能逐字节比对。
> 大模型在这个项目里的位置是**起草**，它的输出要过 schema 校验和规则门禁，
> **它能提议，但它没有执行权**。」

**追问会追到哪**
- **第二层**「你的 11 条规则怎么测的？」→ `tests/test_policy_engine.py` 有 66 个用例，包含「同一输入跑 100 次结果一致」
  和 P0 的穷举，还有一条「自称只读但工具不在白名单时走兜底而不是 P3」——
  这条防的是**用自述绕过评级**。
- **第三层**「规则表存哪？改规则要发版吗？」→ 规则有两种来源：代码里的内置基线（`BUILTIN_RULES`）
  和数据库里的策略集（`policy_version > 0`）。判定结果里会带 `policy_version`，
  `0` 表示「用的是代码里的基线」——**审计能区分「按已审批的策略判定」和「按代码基线判定」**。
  这一条很重要：否则「这个判定是谁定的」说不清。
- **第四层**「策略管理界面呢？」→ **没有**。表、判定引擎、单条预演接口有，
  但策略的增删改查和版本发布界面属于 M4，还没做（我会主动交代这个边界）。

## ④ 用自动化守住架构约束：AST + 独立解释器

**一句话**：把「这层不许 import 那个」从文档里的约定，变成会让 CI 变红的用例。

**为什么需要它**：架构约束失效的方式特别隐蔽——**谁都可以在规则文件里 import 一个 LLM 客户端，
而所有既有用例照样全绿**。等发现时，判定已经不可复现了。

**这个项目里怎么做的**：三重扫描（`tests/test_policy_import_graph.py`），
外加**给守卫自己写元测试**。

**代码长什么样**

```python
 81  def test_import_白名单():                 # ① AST 扫直写的 import（含相对 import）
 85      tree = ast.parse(path.read_text(encoding="utf-8"))
112  def test_无时间依赖():                     # ② AST 扫调用名，禁 datetime.now(/time.time(
127  def test_无文件与网络IO():                 # ② 扫 open(
137  def test_纯函数层不引入自己的IO依赖():       # ③ 起 python -I 子进程量「增量」依赖
104  def test_禁用依赖确实在禁用名单里():        # ④ 守卫自己的元测试
105      for name in ("fastapi", "sqlalchemy", "httpx", "openai", "os"):
106          assert name in _FORBIDDEN_TOP
```

第 ③ 条的判据值得背下来：它先 `import models.enums` 记基线，再 `import engines.policy.pdp`，
断言**两次之间的增量**里不出现 `httpx/sqlalchemy/openai/socket` 等。
注释解释了为什么必须是「增量」：`engines/policy` 必然要 import `models.enums`（枚举的唯一来源），
而 `models/__init__.py` 按设计会连带导入全部 ORM 模型，
所以 `sqlalchemy` **一定**在 `sys.modules` 里——**但它不是这一层引入的**。

**为什么不那样做**
- **不靠 code review**：review 会漏，而且新人不知道这条约束存在。
- **不只做 AST**：AST 只能看见直写的 import，看不见「A→B→httpx」的间接依赖。
  两句注释就把这个局限说清了。
- **不用「`sys.modules` 里不许出现 sqlalchemy」这种粗暴判据**：会误报设计上既有的那一层。

**踩过的坑**：`python -I` 会**同时忽略 PYTHONPATH 和当前目录**，
所以路径必须显式 `sys.path.insert`——代码里写明了「这正是我们要的：不借助任何环境变量」。

**面试会怎么问**
1. 「架构分层你怎么保证不被后人破坏？」
2. 「你怎么保证大模型不参与核心判定？写文档管用吗？」
3. 「这个测试本身要是被人改坏了怎么办？」

**你怎么答**：
> 「我不相信写在文档里的架构约束，所以我把它做成了自动守卫。
> 三件事：AST 扫 import 白名单、AST 扫危险调用（禁 `datetime.now`、禁 `open`）、
> 再起一个 `python -I` 子进程量**增量依赖**——因为 AST 看不见间接依赖。
> 判据是相对『只 import 枚举模块』的**增量**，这样不会误报设计上本来就有的那层。
> 最后我**给守卫自己写了元测试**：断言 `fastapi/sqlalchemy/httpx/openai` 确实在禁用名单里——
> 否则有人把名单清空，这个文件会照样全绿。」

**追问会追到哪**
- **第二层**「为什么偏偏是这一层有守卫，别的层没有？」→ 因为评级的**可复现性是红线里的红线**，
  而且这条约束最容易被无意破坏（想加个『查一下配置』就 import 了 DB）。
  代价我也认：**别的层（`services/` 不许 import fastapi）目前还是人工纪律**，
  这是我在报告里标出来的缺口，补法几乎零成本——同一套扫描推广过去就行。
- **第三层**「`os` 为什么也在禁用名单里？」→ 因为 `os.environ` 是读配置的后门，
  绕过了统一的配置对象，会让「跑的是哪份配置」说不清。

## ⑤ 副作用唯一出口：所有会改变世界的动作只走一道门

**一句话**：连库、提作业、改数据，都必须挤过同一个函数，它负责「凭什么允许」。

**为什么需要它**：如果每个 service 都能自己连目标库，那么**「谁批准的、有没有令牌、记没记账」
这三件事就没有任何一处能保证**。安全系统最怕的不是漏洞多，而是**有一条路径没人看着**。

**这个项目里怎么做的**：`ToolBroker.execute` 是唯一入口，七个步骤顺序固定
（[harness/broker.py:155](../backend/harness/broker.py#L155)）。任何拒绝都走 `_reject`，
它的返回类型是 `NoReturn`——**进了这个函数就别想继续往下执行**。

**代码长什么样**

```python
167  now = (now or datetime.now(UTC)).astimezone(UTC)     # 时间只取一次，四处共用
169  spec = await self._require_tool(tool, session, ctx)   # ① 工具在注册表里吗
170  await self._check_requirements(spec, token, session, ctx)  # ② 该由哪个进程跑
174  claims = await self._verify(spec, token or "", session, ctx, now)   # ③ 验签
178  await self._assert_ctx(claims, spec, session, ctx)    # ④a 比上下文（不查库，便宜）
179  expected = await self._expected_binding(spec, claims, session, ctx)  # ④b 查期望指纹
180  await self._assert_binding(claims, expected, spec, session, ctx)     # ④b 比指纹
183  result = await self._guard.consume(...)               # ⑤ 原子消费令牌
195  await self._check_preconditions(spec, claims.preparation_id, session, ctx, now)  # ⑥
200  parsed = self._parse_args(spec, args)                 # ⑦ 参数过 schema
201  detail = await self._run_executor(spec, parsed, session, ctx)  # ⑦ 真执行
```

**为什么不那样做**
- **④a 必须在 ④b 前面**（注释在 [:175-177](../backend/harness/broker.py#L175-L177)）：
  两者都不查库时先做便宜的；否则跨租户调用会先撞上「preparation 不存在」，
  返回 `NOT_FOUND` 而不是 `TENANT_MISMATCH`——**把排查方向从"越权"带偏到"数据丢了"**。
  原则：**先做便宜且能拒绝的检查**。
- **进程检查是单向的**（[:249-259](../backend/harness/broker.py#L249-L259)）：
  `api` 进程**不许**执行 worker 工具（那是绕过审批提作业的最短路），
  但 worker 执行只读的 api 工具**故意放行**——拒掉只会逼调用方伪造 `caller`，
  **那等于让这道检查建立在谎言上，比放宽更糟**。

**踩过的坑**：返回给前端的 `detail` 走**白名单过滤**
（[broker.py:575](../backend/harness/broker.py#L575)，`_safe_detail`）。
踩的坑是：`state` 这个键忘了登记，**连通性明明成功却显示 failed**——
结论被静默改写，只有一行 warning，前端没有任何异常。现在有一条用例
**逐工具核对「契约里的结论字段」都在白名单内**（`tests/test_harness_broker.py:768`）。

**面试会怎么问**
1. 「你说副作用只有一个出口，怎么保证没人绕过去？」
2. 「为什么这两个检查要按这个顺序？」
3. 「worker 能执行 api 的工具，这不是越权吗？」

**你怎么答**：
> 「出口是一个 `ToolBroker.execute`，七个步骤顺序固定：工具在不在注册表、该由哪个进程跑、
> 验签、比上下文、比指纹绑定、**原子消费令牌**、最后才执行。
> 顺序上有两个讲究：一是**便宜且能拒绝的检查放前面**——比上下文不需要查库，就放在查期望指纹之前，
> 否则跨租户调用会返回『数据不存在』而不是『租户不匹配』，排查方向会被带偏；
> 二是**令牌消费必须在真执行之前**，消费失败就拒绝。
> 至于『怎么保证没人绕过去』：工具必须先登记进注册表，执行器只在启动钩子里注册一次，
> 而且在**两个进程的启动路径上都注册**（API 的 lifespan 和 worker 的 `celeryd_init`）——
> 漏一个的后果是运行期才抛 `UnauthorizedToolError`，单测永远发现不了。」

**追问会追到哪**
- **第二层**「worker 执行 api 工具为什么放行？」→ 见上面的「单向检查」，
  这是**权衡**：拒绝的收益是零（worker 本来就持有更强权限），
  代价是逼出伪造身份。我会主动讲这个取舍，因为它看起来像放松了安全。
- **第三层**「令牌里的指纹跟什么比？」→ 跟**当前这份制品重新算出来的指纹**比（④b），
  目的是防「审批之后有人改了制品」——令牌绑定的是**内容的指纹**，不是版本号。
  算指纹那段代码现在已经落地了（`engines/fingerprint/` 的五段拼法 + 金值哈希钉死），
  冻结时 `freeze_version` 会**从落库的制品重算一遍**再跟候选行比对（见 [01](01-这是什么.md) 的实现状态表）。
- **第四层**「拒绝也记账吗？」→ 记，`_reject` 里带 `stage`（在哪个阶段被拒），
  进账本的是拒绝码和阶段**而不是**原始参数。

## ⑥ 脱敏：为什么不用星号，而是加盐摘要

**一句话**：样本里的敏感值变成 `phone:a3f19c04b27e`——看得出是什么，看不出值，也推不出长度。

**为什么需要它**：元数据探查会把**真实样本数据**从生产库捞到控制面来展示。
如果控制面库里存了原值，那么一次库泄漏就等于生产数据泄漏。
但全打成 `******` 又会让样本失去分析价值（同一列里两个值是不是同一个？看不出）。

**这个项目里怎么做的**：按**列**加盐做 SHA256 取前 12 位
（[engines/masking/policy.py:124](../backend/engines/masking/policy.py#L124)），
盐里还带租户和数据源版本；判定结果由调用方传入，**同一张表每一行用同一套判定**。

**代码长什么样**

```python
131  payload = f"{salt}\x1f{column}\x1f{value}".encode()    # 盐 + 列名 + 值
132  return hashlib.sha256(payload).hexdigest()[:_DIGEST_LEN]   # 取前 12 位
152  if level is SensitiveLevel.PUBLIC and keep_public_plain:
156      return text                        # public 列原样保留，但由策略决定，不写死
157  prefix = kind.value if kind is not SensitiveKind.NONE else "masked"
158  return f"{prefix}:{digest(text, column=column, salt=salt)}"   # phone:a3f19c04b27e
170  """``columns`` 必须显式给出每一列的判定结果，而不是在这里现算：
171  同一张表的每一行必须用同一套判定，否则会出现「第一行的 name 脱了、第二行没脱」"""
```

**为什么不那样做**
- **不用 `138****1234` 这种掩码形态**：它保留了长度和前缀，能做关联/枚举攻击。
  模块 docstring 明确拒绝了可逆掩码——⚠️ **所以 PRD 里「掩码·哈希·截断」这个说法，
  在这个项目里实际只落地了「哈希」**，面试别把这里说成打星号。
- **不用全局盐**（第 131 行的 `column` 参与哈希）：全局盐会让「手机号列」和「备注列」里
  **同一个内容**产生**同一个摘要**，于是**跨列关联**成立（拿备注里抄的手机号去比对手机号列能对上）。
  按列加盐：保留列内可分辨性，切断跨列关联。
- **不在 `mask_rows` 里现算判定**（第 170-172 行）：那样可能出现「第一行脱了、第二行没脱」，
  **看起来像脱敏随机失效**，这种 bug 极难复现。

**踩过的坑**：`merge_policy` 里定了一条规矩——策略**只允许收紧，不允许放松**
（[policy.py:207](../backend/engines/masking/policy.py#L207)）。注释是可以直接背的：
**「一个可以被关掉的脱敏开关，迟早会因为某次排查被临时关掉，然后再也没打开。」**

**面试会怎么问**
1. 「元数据探查会不会把生产数据带出来？」
2. 「为什么要加盐？全局盐不行吗？」
3. 「脱敏能关掉吗？」

**你怎么答**：
> 「探查确实会把样本捞到控制面，所以样本是**加盐摘要**，形态是 `类型:摘要`，比如 `phone:a3f19c04b27e`。
> 盐**按列**加，而且带了租户和数据源版本——按列是因为全局盐会让不同列里的同一个值产生同一个摘要，
> 跨列关联就成立了；带租户是因为我要防『拿摘要当指纹做跨租户比对』。
> 我在 ECS 上实测过：探出 2 表 20 列，160 个样本单元格**全部是摘要形态，没有一个等于原值**，
> 我是直连 MySQL 取原值逐格比对确认的。
> 脱敏策略**只能收紧不能放松**，因为可以被关掉的开关迟早会被临时关掉然后再也没打开。」

**追问会追到哪**
- **第二层**「摘要取 12 位够吗？手机号才 11 位数字，能穷举吧？」→ **能**，
  所以真正的防线不是摘要强度，而是**控制面库里不存原值**，摘要不与原值同时存在。
  12 位是有意的取舍：要的是「不可还原 + 可比对」，不是密码学强度。
- **第三层**「日志里呢？」→ 三道防线：`core/logging.py` 的处理器对 `sk-` 开头的 key、
  `Bearer`、连接串、私钥、JWT、身份证/手机/邮箱统一脱敏；账本写入前 `_assert_payload_clean`
  拦一次；前端 `utils/mask.ts` 再兜一次。**任何一道被绕过，另外两道还在。**
- **第四层**「默认是脱还是不脱？」→ ⚠️ **默认对 `PUBLIC` 列是保留原文**（`keep_public_plain` 默认 `True`），
  安全性来自「策略表写对了」。**这是我最想改的一处**：默认值应该站在安全那一侧——
  漏配的后果应该是「样本不好看」（立刻发现），而不是「生产数据被复制到控制面库」（几个月后才发现）。

## ⑦ 无明文密钥：只存「路径 + 版本号」

**一句话**：数据库里根本没有存密钥的列，只有 Vault 里的路径和版本。

**为什么需要它**：凭据泄漏最常见的原因不是被攻破，而是**它本来就被复制到了不该在的地方**——
日志、异常栈、备份、LLM 上下文、前端接口。所以正确做法是让「存明文」在**结构上就不可能**。

**这个项目里怎么做的**：`DataSource` 表里只有 `vault_path` / `vault_version` / `key_names`，
**没有任何值列**——注释级的说法是「想存明文得先改表」。
明文只在 worker 内存里物化一次，用完即弃（[clients/datasource_probe.py:277](../backend/clients/datasource_probe.py#L277)）。

**代码长什么样**

```python
# harness/ledger.py:222
222  _assert_payload_clean(event)      # 进账本前先查 payload 有没有夹带秘密

# core/config.py:230
230  def safe_dump(...)                # 启动日志里打印配置，敏感项一律 ***configured***

# core/config.py:207
207  def _validate_by_env(...)         # 生产环境：占位密钥 / DEBUG / CORS * / 明文 Vault 地址 → 启动即失败
```

**为什么不那样做**
- **不做「加密后存数据库」**：密钥和数据同库，等于把锁和钥匙放一个抽屉。
- **生产自检不做成 warning**（[core/config.py:207](../backend/core/config.py#L207)）：
  **起不来的服务会被立刻发现，带病运行的服务会活到出事故。**
- **启动日志打印配置但脱敏**（`safe_dump`）：排查第一件事就是「跑的是哪份配置」，
  而配置里有密钥，所以打的是 `***configured***`。

**踩过的坑**：账本 payload 的清洁检查（`test_ledger.py:143` 有用例）——
账本是**长期保存、可被多方读取**的，所以「把整个 args 塞进 payload」这种图省事的写法必须被拦住。
另外 Vault 的错误也分开了：`Forbidden`（策略没配对）与 `InvalidPath`（路径写错）
**刻意不合并**——合成一个错误码会让运维去查错方向。

**面试会怎么问**
1. 「数据库口令怎么存？」
2. 「你怎么保证日志里不会打出密钥？」
3. 「Vault 挂了怎么办？」

**你怎么答**：
> 「业务库里**没有存密钥的列**，只有 Vault 路径 + 版本 + 需要的键名，
> 所以『不小心存了明文』这件事在结构上就不可能，除非有人先改表。
> 明文只在 worker 里物化一次，用完即弃。
> 日志侧是**处理器统一脱敏**，业务代码不许自己拼敏感值——
> 因为靠人自觉迟早会漏；账本进库前还有一次 payload 清洁检查。
> 生产环境还有一个启动自检：占位密钥、`DEBUG=true`、CORS 通配、Vault 走明文 HTTP，
> 命中任何一条**直接启动失败**，因为带病运行的服务会活到出事故。」

**追问会追到哪**
- **第二层**「为什么不用 KMS/环境变量？」→ 环境变量会进 `docker inspect`、进崩溃转储、
  进子进程；KMS 解决的是「密钥的密钥」，而我要的是「**可轮转 + 有版本 + 有审计**」，
  Vault 的 KV v2 天然给版本（写一次是新版本），所以轮转和回滚都不用自己实现。
- **第三层**「Vault 挂了服务还能起吗？」→ 能起，但**依赖 Vault 的操作会失败**。
  ppt 上我不会说「高可用」，我会说：**这是单点，生产上要配 HA + 缓存短 TTL 的令牌**，
  目录里有这条，但它属于 M4，还没做。

## ⑧ JWT 怎么「吊销」：版本号，以及它踩的坑

**一句话**：JWT 天生无法撤回，所以给每个用户一个版本号，登出全部设备就把版本 +1。

**为什么需要它**：access token 是无状态的，签发之后服务端**没有任何记录**——
所以你没法「让某个令牌失效」。而「改密码后踢掉所有设备」是硬需求。

**这个项目里怎么做的**：登录时把当前版本号签进令牌（`ver`），
每个请求比对 Redis 里的当前版本（[api/deps_auth.py:62](../backend/api/deps_auth.py#L62)）。
另外还有一层 jti 黑名单用于单令牌登出。

**代码长什么样**

```python
# api/deps_auth.py
 52  if await redis.exists(KEY_TOKEN_DENY.format(jti=jti)):   # 单令牌撤销（登出）
 53      raise UnauthenticatedError("令牌已撤销")
 60  # 会话版本：logout-all 与改口令都把版本 +1，于是所有在途令牌立刻失效。
 61  # 逐个拉黑 jti 做不到这一点——系统并不保存「该用户当前有哪些未过期令牌」这张表。
 62  current_version = int(await redis.get(f"auth:token_ver:{user_id}") or 0)
 63  if int(claims.get("ver", 0)) != current_version:
 64      raise UnauthenticatedError("会话已失效，请重新登录")
```

**为什么不那样做**：**不逐个拉黑 jti**——系统并不保存「该用户当前有哪些未过期令牌」这张表，
所以「全部失效」这件事**做不到**。版本号是 O(1) 的解法，代价是**粒度粗**（按用户，不按设备）。

**踩过的坑（这是我自己 grep 出来的，不在任何文档里）**：
`auth:token_ver:{user_id}` 这个键模板**写了两遍**——
[services/auth.py:43](../backend/services/auth.py#L43) 定义成常量，
[api/deps_auth.py:62](../backend/api/deps_auth.py#L62) 又手写了一遍。
**改一处漏一处，症状是「登出全部设备失效，且不报任何错」**——
另一处读到空键、返回 0、校验永远通过。这正好是「唯一入口」这条规矩要防的失败模式，
而它发生在**鉴权路径**上。

**面试会怎么问**
1. 「JWT 怎么实现登出？」
2. 「改密码后怎么让旧 token 失效？」
3. 「你这个方案有什么问题？」

**你怎么答**：
> 「分两种粒度。**单设备登出**用 jti 黑名单，把那个令牌的 jti 写进 Redis，带 TTL。
> **全部设备失效**（改密码、怀疑被盗）用**会话版本号**：登录时把当前版本签进令牌，
> 每个请求比对一次，改密码就把版本 +1，所有在途令牌立刻失效。
> 逐个拉黑做不到这件事，因为系统并不保存『这个用户现在有哪些未过期令牌』这张表。
> 代价我也清楚：**粒度是用户不是设备**，而且多了一次 Redis 读。
> 另外这里我踩过一个坑：那个 Redis 键模板在项目里**写了两遍**，一处英文常量一处手写字符串，
> 改一处漏一处的话，另一处会静默读到空值、校验永远通过——**登出全部设备失效，且不报错**。
> 这是我准备补的：键模板收敛到一处，并加一条『全仓搜不到这个字面量』的用例。」】

**追问会追到哪**
- **第二层**「Redis 里版本号丢了怎么办？」→ 读回来是 0，而令牌里签的 `ver` 通常是 0，
  于是**校验通过**——这是这个方案的失效模式（Redis 被清空 = 吊销记录丢失）。
  严格做法是把版本号也落一份在 PG 里，Redis 只当缓存。
- **第三层**「access token 有效期多久？为什么？」→ 短（分钟级），
  靠 refresh token 轮转延长；这样即使版本号机制失效，暴露窗口也有限。
- **第四层**「refresh token 怎么防重放？」→ 轮转 + 在库里有记录（每次刷新换新的，
  旧的立刻作废），所以它比 access token 更适合做「有状态」的那种。

## ⑨ 幂等：靠唯一约束，而不是「先查后写」

**一句话**：同一个请求带同一个 `Idempotency-Key` 打两遍，效果只发生一次。
（**幂等** = 同一个操作做多少遍，结果都跟做一遍一样。这个词面试一定会被问到。）

**为什么需要它**：用户点一下没反应又点一下、客户端超时重试、网关重发——
这些在真实系统里是常态。写接口不做幂等，就会出现**两份订单**。

**这个项目里怎么做的**：中间件拦所有写请求（[api/idempotency.py](../backend/api/idempotency.py)），
**靠 INSERT 撞唯一约束来判断"我是不是第一个"**，并把成功响应快照下来供重放。

**代码长什么样**

```python
143  session.add(IdempotencyKey(tenant_id=..., scope=..., key=..., request_fingerprint=fingerprint, ...))
155  await session.commit()
156  return True                       # 首次执行
157  except IntegrityError:
158      # 唯一约束挡下 → 并发或重放。靠异常而不是先查，才不会有 TOCTOU 窗口。
159      await session.rollback(); return False
...
175  if row is None:
176      # 约束冲突却没查到行：只可能是并发事务尚未提交。让客户端重试，
177      # 比替它猜一个结果安全——猜错就是一次重复执行。
180  if row.request_fingerprint != fingerprint:
181      # 同 key 不同内容：客户端复用了 key。按约定这必须拒绝，
182      # 否则第二次请求的内容会被第一次的响应悄悄吞掉。
185  if not row.completed: return _error(..., "同一请求正在处理中，请稍后重试")
188  return JSONResponse(content=row.response_snapshot)
```

**为什么不那样做**
- **不「先 SELECT 看有没有，没有就 INSERT」**：那是经典 TOCTOU
  （**检查完到写入之间**有窗口），两个并发请求会双双通过检查。
  注释写得很直接：**「靠异常而不是先查，才不会有 TOCTOU 窗口」**。
- **失败时不"记一个失败结果"**（[:112-115](../backend/api/idempotency.py#L112-L115)）：
  记失败会让客户端永远拿同一个 key 重试、却始终看到第一次的错误；
  而不释放占位更糟——那个 key 会一直被判为「处理中」，
  **等于把一次 400 升级成永久失败**。所以非 2xx 一律**释放占位**。
- **不只按 key 判重，还要比 `request_fingerprint`**（第 180 行）：
  同 key 不同内容必须拒绝，否则**第二次请求的内容会被第一次的响应悄悄吞掉**。

**踩过的坑**：第 176 行那个分支（约束冲突却查不到行 = 并发事务还没提交）——
**不猜结果**，让客户端重试。注释原话：「猜错就是一次重复执行」。

**面试会怎么问**
1. 「你这个接口重复调会怎样？」
2. 「幂等键为什么不在服务端生成？」
3. 「同一把 key 打不同内容怎么办？」

**你怎么答**：
> 「写接口都支持 `Idempotency-Key` 请求头。判断『我是不是第一个』靠的是
> **往幂等表插一行、撞唯一约束**——不是先查后写，那样中间有 TOCTOU 窗口。
> 抢到的那次正常执行，成功后把响应快照存下来，重复请求直接回放同一个响应。
> 有两个细节：**同 key 不同内容要拒绝**，否则第二次请求的内容会被第一次的响应悄悄吞掉；
> **失败请求要释放占位**，否则那个 key 会永久卡在『处理中』，等于把一次 400 升级成永久失败。
> 键的作用域带 `tenant_id`，否则跨租户可以用同一把 key 互相干扰。」

**追问会追到哪**
- **第二层**「幂等记录存哪？会不会无限增长？」→ 存 PG，带 `expires_at`（TTL 由配置给），
  需要一条清理任务——⚠️ 这条清理任务**目前没有**（`tasks/maintenance.py` 里的保留策略任务是空壳），
  所以现在幂等表会一直涨。这是我会主动交代的运维缺口。
- **第三层**「中间件做的幂等，和业务层做的幂等冲突吗？」→ 不冲突但要注意**双重生效**：
  中间件对「同一 key 的重复请求」直接回放，业务层不该再判一次；
  真实业务上的幂等（比如「同一份作业不能提交两次」）是**另一个维度**，靠数据库约束做，不靠请求头。

## ⑩ 长任务的异步模式：202 + 轮询 + 至少一次 + 任务幂等

**一句话**：重活丢给后台，请求立刻返回一个编号，前端拿编号轮询。

**为什么需要它**：连一个外部数据库探测可能几十秒。同步做，HTTP 会超时、
Nginx 会切连接、用户会以为坏了。

**这个项目里怎么做的**：**先写状态再投递**——Redis 里写 `pending`，然后投 Celery，
最后返回 `{test_id, state: "pending"}`（[services/datasource.py:570-589](../backend/services/datasource.py#L570-L589)）。

**代码长什么样**

```python
570  "state": "pending",                    # 先落一个「我能被查到」的状态
583  run_connectivity_test.apply_async(     # 再投递
584      args=[...], queue="etl.default")
589  return {"test_id": test_id, "state": "pending"}   # 立刻返回，前端拿 id 轮询
```

**为什么不那样做**
- **不先投递后写状态**：worker 可能在状态落库前就跑完了，前端永远查不到结果。
  顺序不能反。
- **不把轮询做成"等结果"接口**：那等于同步阻塞，只是把超时推给了前端。

**踩过的坑（这条链上最值钱的）**
1. **Celery 的常态重投**：投递是**至少一次**，所以**所有任务必须幂等**。
2. **中间态没有回收**：如果 worker 在写终态之前死掉（重启/被杀），
   记录会**永远停在 `pending`/`probing`**，页面一直转圈。
   ⚠️ 这个项目里 `ProbeStatus.EXPIRED` 定义了但**全仓无人写入**——缺口。
3. **状态过期 ≠ 不存在**：接口必须能区分「测试记录已过期」与「没有这个测试」，
   否则前端会显示「不存在」，用户以为没点成功又点一次。

**面试会怎么问**
1. 「为什么用异步？同步不行吗？」
2. 「任务跑了两次会怎样？」
3. 「任务卡住了怎么办？」

**你怎么答**：
> 「先写状态再投递——顺序不能反，反了的话 worker 可能在状态落库前就跑完，前端永远查不到结果。
> 接口立刻返回 202 和一个 id，前端轮询。
> 投递语义是**至少一次**，所以我要求**所有任务幂等**；Celery 重投是常态，不是异常。
> 中间态的问题我也清楚：**如果 worker 在写终态前死掉，记录会永远停在 pending**——
> 项目里定义了 `expired` 这个状态却没有任何地方写它，这是我的缺口，
> 补法是加一个定时任务把超时的中间态回收掉，并且让接口能区分『过期』和『不存在』。」

**追问会追到哪**
- **第二层**「轮询会不会把后端压垮？」→ 会，所以要限频 + 让步长（前端现在是固定间隔）；
  更好的做法是 SSE/WebSocket，但那要 Nginx 配 `proxy_buffering off`，项目里没做。
- **第三层**「任务结果存哪？丢了怎么办？」→ 状态写 Redis（有 TTL）+ 终态写 PG；
  **Redis 挂了就会丢中间态**，所以真正的结果必须以 PG 为准。
- **第四层**「任务的超时怎么定？」→ 连接超时是参数化的（按数据源配置）；
  运行期的**时长维度**由监督环判（`engines/supervision/` 的五维阈值之一），
  越界走「签票 → Outbox → worker 停作业」，**不是在 Celery 侧砍任务**
  ——因为要停的是数据面的作业，不是控制面的任务。逐条见 [10-做到哪一步了 §3](10-做到哪一步了.md)。

## ⑪ Celery 装配的三个坑（都是"单测看不见"的那种）

**一句话**：Celery 有三个坑只在真机上现形，每一个都表现为「功能静默失效」。

**为什么需要它**：这三个坑的共同点是——**单测全绿、代码看起来对、只在真跑的时候坏**，
而且坏的方式都很安静。

**这个项目里怎么做的 / 踩过的坑**

**坑 1：`@shared_task` 绑的不是你配好的那个 app。**
`@shared_task` 绑的是「当前默认 app」，如果忘了 `celery_app.set_default()`，
或者 `tasks/__init__.py` 没导入 app 模块，**API 侧投递会静默走到内置的
`amqp://localhost:5672`**。症状是「点一下按钮就 500」，报错栈在 kombu 里。
→ 现在有专门的回归用例 `tests/test_celery_app.py`。

**坑 2：worker 里 `sys.path` 会被 Celery 撤掉。**
`cwd_in_path()` 加载完 app 就把 cwd 从 `sys.path` 里 **remove**，
于是任务体里的惰性导入（`from services import ...`）报 `ModuleNotFoundError`。
**修法是无条件 remove-then-insert**——注意：用 `if not in sys.path` 保护会**失效**，
因为 Celery 插入的就是同一个字符串。另外要在 `celeryd_init` 里再补一次。

**坑 3：任务里禁止 `asyncio.run`。**
每次新建并关闭一个事件循环，而 `core.db.engine` / `core.redis` 是**模块级单例**，
第 2 个任务起必然失败：`Event loop is closed`，或者伪装成
`AttributeError: 'NoneType' object has no attribute 'send'`（**栈指向 `session.execute`**，
看起来像数据库的问题）。一律走 `tasks/async_runner.run_coro`。

**代码长什么样**（真实代码，不是伪码）

```python
# tasks/__init__.py:44 —— 为什么必须无条件删掉再压首位（注释在 35-43 行解释得很细）
while _BACKEND_ROOT in sys.path:
    sys.path.remove(_BACKEND_ROOT)          # 不能写 if not in sys.path：Celery 插的是同一个字符串
sys.path.insert(0, _BACKEND_ROOT)

# tasks/__init__.py:57
@celeryd_init.connect
def _bootstrap(**kw): ...                   # 先补 sys.path，再注册执行器 —— 顺序不能反

# tasks/celery_app.py:44
celery_app.set_default()                    # 漏了这句，@shared_task 就会绑到内置的 amqp://localhost
```

**面试会怎么问**
1. 「Celery 你踩过什么坑？」
2. 「任务里为什么不能 `asyncio.run`？」
3. 「你怎么保证这些坑不会回归？」

**你怎么答**（挑一个讲成故事）：
> 「最坑的一个是 `@shared_task` 绑的 app 不对。这个装饰器绑的是**当前默认 app**，
> 不是我配好 broker 的那个实例。忘了 `set_default()`，API 侧投递就会静默走到
> 内置的 `amqp://localhost:5672`——症状是『点一下按钮就 500』，
> 而报错栈在 kombu 里，跟我的代码没关系。
> worker 侧永远看不出问题，因为 `-A` 启动时已经把当前 app 设对了。
> 我最后写了一个回归用例把 app 的绑定关系钉住。
> 还有一个是任务里不能用 `asyncio.run`：它每次新建并关闭事件循环，
> 而数据库引擎和 Redis 客户端是模块级单例，第二个任务起必然报
> `Event loop is closed`——更恶心的是它有时会伪装成
> `AttributeError: 'NoneType' object has no attribute 'send'`，栈指向 `session.execute`，
> 看起来像数据库的锅。」

**追问会追到哪**
- **第二层**「为什么单测发现不了？」→ 因为单测直接 import 模块、不走 Celery 的加载器，
  `sys.path` 不会被撤、默认 app 也不参与投递。**这类坑只能靠"在真 worker 上跑一次"发现，
  所以我把它写进了项目的行为准则里，并配了回归用例。**
- **第三层**「你还遇到过别的'单测看不见'的坑吗？」→ 有，可以接着讲：
  `ToolBroker` 的 detail 白名单静默丢键、`aiomysql` 的 `DictCursor` 键名大小写、
  归因把 `KeyError` 错算成「连接失败」。**这些都是"不报错但结果不对"那一类。**

## ⑫ 连接池健康检查：隧道断一次，worker 就永久卡死

**一句话**：连接是单例、进程常驻，所以一条死连接永远不会被换掉——除非你显式开健康检查。

**为什么需要它**：这个坑的形态是「**服务还活着，但再也不干活了**」。
日志里只有一句 `Error 22 while writing to socket`，看不出跟连接池有关。

**这个项目里怎么做的**：Redis 客户端显式开健康检查 + 重试
（[core/redis.py](../backend/core/redis.py)），并**断言配置本身**的回归用例
（`tests/test_core_clients.py`）。

**代码长什么样**

```python
# core/redis.py
client: Redis = Redis.from_url(
    settings.redis_url(settings.REDIS_DB_CACHE),
    decode_responses=True,
    health_check_interval=30,                                   # 定期探活，换掉死连接
    retry=Retry(ExponentialWithJitterBackoff(base=0.05, cap=1.0), retries=3),
    retry_on_error=[RedisConnectionError, RedisTimeoutError],   # 不覆盖连接错误等于没重试
)

# tests/test_core_clients.py:22 —— 断言的是「配置」，不是「能不能连上」
kwargs = client.connection_pool.connection_kwargs
assert kwargs.get("health_check_interval"), "没开健康检查：隧道抖动一次，worker 就永久卡死"
```

**为什么不那样做**
- **不靠「重启一下就好了」**：这是把运维当作修复手段，故障会以「偶发」的形式长期存在。
- **不靠 `pool_pre_ping` 一把梭**：DB 侧确实靠它自愈（`test_core_clients.py:43` 断言了它开着），
  **但 Redis 客户端默认没有对应机制**，两边不是一回事——这正是坑的成因。

**踩过的坑（这个我亲手修了，过程完整）**
现象：连通性测试卡在 `pending`。排查：worker 日志里
`redis.exceptions.ConnectionError: Error 22 while writing to socket. 指定的网络名不再可用。`
根因：**隧道重启过**，而 redis 客户端是 `lru_cache` 单例、跑在**进程级复用**的事件循环里，
且**默认不做连接健康检查**——那条死连接永远不会被替换。
修法：开健康检查 + 重试 + 明确 `retry_on_error`；
配一条**断言配置**的回归用例（因为这类参数删掉不会报错、本地也复现不出来，
**只在连接被中间设备掐断时现形**）；同步更新行为准则和模块设计文档的变更记录。
验证：重启 worker 和 API，重跑 → `succeeded | 357ms | MySQL 8.0.27`。

**面试会怎么问**
1. 「长跑的服务连不上数据库了，服务却没挂，你怎么查？」
2. 「为什么要给连接池配健康检查？」
3. 「这个测试为什么断言配置而不是断言能连上？」

**你怎么答**（这是最好的故事，讲完整）：
> 「我遇到过一个『服务活着但再也不干活』的故障：连通性测试一直卡在 pending。
> 排查发现 worker 日志里有一句 `Error 22 while writing to socket`。
> 根因是**隧道重启过**，而 Redis 客户端是单例、跑在进程级复用的事件循环里，
> 而且**默认不做连接健康检查**——那条死连接永远不会被换掉，后续所有请求都死在它上面。
> 修法是显式开健康检查 + 重试，并且**明确列出重试覆盖哪些异常**
> （不覆盖连接错误等于配了个空重试）。
> 我还加了一条**断言配置本身**的用例——因为这类参数删掉不会报任何错、本地也复现不出来，
> 只有在连接被中间设备掐断时才现形。我在注释里写清了这段经过，
> 免得后人当成『多余的一行配置』删掉。」

**追问会追到哪**
- **第二层**「为什么 SQLAlchemy 那边没事？」→ 因为 DB 侧开了 `pool_pre_ping`，
  取连接前会探一下；**Redis 客户端默认没有等价机制**，所以要手动配。
  两边是同一个坑的两个面，这也是我为什么把两条断言写在同一个测试文件里。
- **第三层**「还有哪些配置属于'删了不报错'这一类？」→ 重试次数、超时、
  幂等键 TTL、健康检查间隔——**这类"沉默配置"必须有断言**，
  否则它会以「偶发故障」的形式一直存在到上线。
- **第四层**「你怎么知道修好了，而不是碰巧？」→ 重启 worker 前它稳定复现
  （连续几次都是 pending），改完重启后连跑成功、耗时 357ms、服务端版本正常返回。
  **我没有做「改完看着好像好了」这种判断**。

## ⑬ 多租户隔离：为什么返回「不存在」而不是「无权访问」

**一句话**：所有查询都带租户过滤；跨租户访问看起来像「这东西不存在」。

**为什么需要它**：多租户系统最严重的 bug 就是**跨租户读到别人的数据**。
而它的成因往往只是一行漏写的 `WHERE tenant_id = ?`。

**这个项目里怎么做的**：查询一律带 `tenant_id` 过滤；
跨租户时**不返回 403，而是返回 NOT_FOUND / 未认证**。

**代码长什么样**

```python
# clients/datasource_probe.py:248 —— 注释写着「本模块最容易写漏的一行」
.where(DataSource.tenant_id == ctx.tenant_id, DataSource.project_id == ctx.project_id)

# api/deps_auth.py:71 —— 令牌里的租户与库中不一致：用户被迁移过
71   if int(claims.get("tenant_id", 0)) != user.tenant_id:
72       logger.warning("tenant_mismatch_denied", ...)      # 留痕，但对外只说「不符」
73       raise UnauthenticatedError("令牌与账号所属租户不符")
```

**为什么不那样做**：**不返回 403「你无权访问该项目」**——那等于确认「这个 ID 真实存在」，
攻击者可以靠枚举 ID 探测出别的租户有哪些资源（**存在性泄漏**）。
返回 404 则信息量为零。
⚠️ 但要说实话：`TENANT_MISMATCH` 这个码在**数据面**其实不用，
只在令牌校验和 broker 里用——文档把这条写成了通用契约，**与实现不完全一致**（文档漂移）。

**踩过的坑**：租户过滤是**人工纪律**，没有全局守卫。项目里给最危险的一处
（按 ID 取数据源）写了专门的注释和测试，但**没法保证所有人都不漏**。
这是我列的缺口之一，补法是在 repository 基类里把 `tenant_id` 做成**签名强制**。

**面试会怎么问**
1. 「多租户怎么隔离的？」
2. 「跨租户访问你返回什么？」
3. 「怎么保证每个人都没漏写租户过滤？」

**你怎么答**：
> 「查询全部带 `tenant_id`，包括 Redis 的键也要带租户维度——
> 比如登录失败计数的键是 `租户码:用户名`，**不带的后果是一个租户的攻击者能锁死另一个租户的同名账号**。
> 跨租户访问我**返回"不存在"而不是"无权访问"**，
> 因为 403 等于确认『这个 ID 真的存在』，可以被用来枚举探测。
> 至于『怎么保证不漏』——**诚实说：现在靠人工纪律 + 对最危险那几处的专门测试，
> 没有全局守卫**。要彻底解决，应该把租户过滤做成 repository 层的签名强制，
> 不传 `tenant_id` 直接报错，让漏写变成过不去的一步。」

**追问会追到哪**
- **第二层**「Redis 键的租户维度呢？」→ 都带（登录失败计数、令牌版本号按 user_id 天然唯一）。
  不带租户的键是跨租户干扰的入口。
- **第三层**「有没有超级管理员能跨租户？」→ 有意做了「按角色」而不是「按人」：
  看账本要 `auditor` 角色，**我实测过 maker 角色访问账本返回 403，这是设计不是 bug**。
  跨租户的运营视角目前**没做**。

## ⑭ 不可变制品：只准 INSERT

**一句话**：审批单、版本、令牌、账本这些一旦写下就不能改，改只能产生新版本。

**为什么需要它**：如果审批记录能被 UPDATE，那「谁批的」就永远说不清——
出事之后改一下就行。所以**不可变不是洁癖，是审计的前提**。

**这个项目里怎么做的**：ORM 层一个 `before_flush` 钩子，
拦截不可变实体的**修改与删除**（[models/base.py:75](../backend/models/base.py#L75)）。

**代码长什么样**

```python
75  @event.listens_for(Session, "before_flush")
76  def _guard_immutable(session, _flush_context, _instances) -> None:
82      for obj in session.deleted:
84          if getattr(cls, "__immutable__", False):
85              raise ImmutableViolationError(f"{cls.__name__} 是不可变制品，禁止删除…")
89      for obj in session.dirty:
93          allowed: frozenset[str] = getattr(cls, "__mutable_columns__", frozenset())
95          changed = {attr.key for attr in state.attrs if attr.history.has_changes()}
96          illegal = changed - set(allowed) - {"updated_at"}
97          if illegal:
98              raise ImmutableViolationError(f"…禁止修改列 {sorted(illegal)}（只允许改 {sorted(allowed)}）")
```

**为什么不那样做**
- **不只在数据库上做（撤 UPDATE 权限/触发器）**：那样报错信息只会说「权限不足」，
  **不知道是哪个字段**。逐列判断是为了**排障时能直接看到被改的是哪个字段**。
- **不做成"整表禁改"**：状态机需要推进（`preparation.status` 要变），
  所以设计成 `__mutable_columns__` 白名单，其余全禁。
- **钩子挂在 `before_flush` 而不是 `before_update`**：这样**连 DELETE 一起拦**
  （比文档里写的更严）。

**踩过的坑**：拦截必须**落库之后**再验证——只有 persistent 对象才进 `session.dirty`，
刚 `add()` 还没 flush 的对象不在里面（测试文件的注释里专门写了这个前提，
否则测试会得出「拦截没生效」的错误结论）。

**面试会怎么问**
1. 「审计要求记录不可篡改，你怎么做？」
2. 「那状态怎么改？」
3. 「为什么不在数据库层做？」

**你怎么答**：
> 「`pipeline_version`、`preparation`、`approval_decision`、`capability`、`evidence_event`
> 这几张表在 ORM 层被标成不可变，一个 `before_flush` 钩子拦住对它们的**修改和删除**，
> 报错信息会直接指出**是哪个字段**被非法改。
> 状态推进不是例外——它走 `__mutable_columns__` 白名单，比如 `preparation` 只允许改 `status`。
> 挂在 `before_flush` 而不是 `before_update`，是为了**连删除一起拦**。
> 为什么不在数据库层用触发器做：也能做，但报错只会说『权限不足』，
> 排障时要人肉对比，而**这类错误的排查成本主要在"是哪个字段"上**。」

**追问会追到哪**
- **第二层**「ORM 钩子能绕过吗？」→ 能：**裸 SQL（`text()`）绕不过钩子**，
  但用 `session.execute(update(...))` 这种 Core 语句**会绕过**。
  所以这是「防手滑」而不是「防恶意」，防恶意要靠数据库权限。
  **我会主动说清这个边界**，不假装它是万能的。
- **第三层**「那你怎么防恶意的？」→ 账本那条链才是防恶意的：改了会被验链发现。
  两者是**互补**的——不可变管「日常不写错」，哈希链管「事后能证明有没有被改」。
- **第四层**「检查一下你的迁移，真的落了吗？」→ ⚠️ 这里有个真问题：
  `models/checks.py` 的注释说枚举列落地为「VARCHAR + CHECK」，
  但迁移是裸 SQL DDL 写的，**全库只有一条 CHECK**（审批不可自批那条），
  枚举列**没有 CHECK 兜底**。**这是我核实过的文档与实现不一致**，我会主动交代。

## ⑮ 独立验链：为什么验证脚本要重写一遍算法

**一句话**：验证账本的脚本**刻意不复用**账本的代码——用被审计的代码验证被审计的对象，等于自证清白。

**为什么需要它**：如果我写一个「验链函数」放在被审计的模块里，那么只要有人改了算法，
**写入和验证会一起改，两边永远一致**，验证就等于没做。

**这个项目里怎么做的**：`scripts/verify_ledger.py` 按设计文档**重写了同一套哈希**，
并且有用例把两份实现**对拍**（`tests/test_verify_ledger_script.py`）。

**代码长什么样**

```python
# tests/test_verify_ledger_script.py
 32  _SPEC = importlib.util.spec_from_file_location(   # 按路径加载，不作为包安装
 33      "verify_ledger_script", .../ "scripts/verify_ledger.py")
104  def test_脚本与账本算出的哈希一致(...):           # 同批输入喂两边，逐字节对拍
109  assert script._FIELD_ORDER == (...)                # 字段顺序本身就是契约
144  _GOLDEN = "d782b745ed94067d77c7f6ed0abce062d0c19039a63dee15212a38151cc8a8b9"
135  assert actual == _GOLDEN, ("账本哈希算法与本文件记录的不符。若这是有意的算法变更，"
136                             "必须同时给出存量账本的迁移方案，而不是改掉这个字面量。")
212  rows[1]["payload"] = {"i": 1, "name": "被改过的项目名"}   # 反例：篡改必须被检出
```

**为什么不那样做**
- **不 `import harness.ledger` 复用算法**：那就是自证清白。
- **不「验链脚本只跑正例」**：注释写得很狠——**「一个永远返回 ok 的验链器在所有正例上都绿灯，
  而它毫无价值。」** 所以它有篡改、断链、删中间行三类反例。
- **不改那个金值哈希**：金值是**人写下来的**，改它必须有人显式动手，
  并在评审里回答「**历史账本怎么办**」——因为哈希链只能追加，
  算法一改，此前所有 `event_hash` 都验不过，那不是修 bug，那是宣布全部历史证据作废。

**踩过的坑**
1. **两份实现一起改错仍会通过**：所以除了对拍，还钉了一个**金值**。
   对拍防「单边改动」，金值防「双边一起改」。
2. **从中间起验的语义**（`--from-seq`）：从中间开始验时链条本就缺了头，
   拿第一行的 `prev_hash` 去对零哈希必然失败。所以只报「这一段自洽」，
   并在输出里带上 `from_seq`——否则运维会以为「全绿 = 整条链没问题」，
   而**前面可能被删了一截**。
3. **退出码而不是看输出**：CI 和验收按**退出码**判定。
   理由很实在——**Windows 控制台是 GBK，中文输出会乱码**，肉眼读输出不可靠。

**面试会怎么问**
1. 「审计系统怎么让第三方独立验证？」
2. 「你的验证脚本跟生成代码是同一份吗？」
3. 「这个脚本的测试为什么这么绕？」

**你怎么答**：
> 「验证脚本**刻意不复用**账本的实现——按设计文档重写了同一套哈希。
> 因为用被审计的代码验证被审计的对象等于自证清白：
> 只要有人改了算法，写入和验证会一起改，两边永远一致，验证就没意义了。
> 为了防两份实现漂移，我用同批输入**对拍**，还额外钉了一个**金值哈希**——
> 对拍防『单边改动』，金值防『两边一起改错』。
> 反例也有：篡改 payload、删中间一行、断开链，都必须被检出。
> 验收按**退出码**判定，不看输出——因为 Windows 控制台是 GBK，中文会乱码，
> 肉眼读输出不可靠。」
> （真机实测结果：`OK checked=52`，数字随事件增长。）

**追问会追到哪**
- **第二层**「验链能发现哪些篡改？」→ payload 改动、租户/项目归属改动、删除中间事件、
  断链、seq 不连续。**不能发现**：整条链被一次性重算（所以要靠签名检查点和外部留存）。
- **第三层**「签名检查点谁在签？」→ ⚠️ **这是我要主动交代的缺口**：
  实现齐了，但全仓每一处 `EvidenceLedger()` 都是裸构造（grep 不到任何 `signer=`）、**没有一处传 signer**，
  而且 `tasks.maintenance.checkpoint_ledger` **没登记进 beat**——
  所以运行期**永不产生检查点**。这是我说的「**有码无电**」的第一个例子。
- **第四层**「怎么证明账本没被整段重写？」→ 单靠链做不到，要靠
  **定期把链尾哈希签到外部**（比如发布到只写的另一个存储），
  这样重写整条链就会与外部记录不一致。**这是我知道但项目还没做的部分。**

## ⑯ LangGraph 的检查点与「中断 → 恢复」：为什么它必须真的落 PG

**一句话**：澄清问题问出去之后，用户可能半小时后才答——这半小时里 API 可能重启过、
请求可能被另一个进程接管。所以「问到哪了、答过什么」必须存在数据库里，
而不是进程的内存里。

**为什么需要它**：LangGraph 的 `interrupt()`（在节点中间停下来、把控制权交回调用方）
和 `Command(resume=...)`（把答案送回去、从断点继续）这套机制，**它的持久化语义
就建立在「检查点（checkpoint）」上**：所谓恢复，就是把 state 从检查点里读回来、
从断掉的那个节点重新跑。没有检查点，`interrupt()` 根本没有落脚点。
而这个项目里「一次生成」是跨进程的：发起请求的是 API，跑图的是 worker，
所以检查点只能落在**两边都能连上的 PG**。

**这个项目里怎么做的**
- 图在装配时就**必须**拿到检查点存器，没有默认值（[workflow/graph.py:264](../backend/workflow/graph.py#L264)）。
- 生产用 `AsyncPostgresSaver`（`langgraph-checkpoint-postgres`），由
  [workflow/checkpointer.py:115](../backend/workflow/checkpointer.py#L115) 的 `CheckpointerHolder` 管开与关。
- **线程号就是 pipeline id**，写成一个函数而不是各处 `str(...)`
  （[workflow/state.py:422](../backend/workflow/state.py#L422)）。
- 中断发生在澄清节点：缺参数时 `clarify` 调 `interrupt()`，载荷形状见
  [workflow/interrupts.py:54](../backend/workflow/interrupts.py#L54)。

**代码长什么样**

```python
# workflow/state.py
422  def thread_id_for(pipeline_id: int) -> str:
427      """... api 与 worker、今天的调用与明天的调用，只要 pipeline_id 相同
428      就必须落到同一条检查点线程。任何一处写成 f"pipeline-{id}" 都会让恢复静默失败。"""
429      return str(int(pipeline_id))
```

```python
# workflow/graph.py
402      async with generation_lock(redis, pipeline_id):         # 同一 pipeline 的生成串行化
403          result = await graph.ainvoke(payload, config=config)  # config 里带着 thread_id
```

**为什么不那样做**
- **不用随机 uuid 当 thread_id**（[state.py:424-428](../backend/workflow/state.py#L424)）：
  恢复是「再发一次同样的请求、用同一个 thread_id 找回检查点」。随机 uuid 一旦没被客户端
  完整带回（比如用户刷新了页面），那次澄清就永远接不上了，用户只能从头再来一遍。
  `pipeline_id` 是**天然存在、天然可复现**的钥匙。
- **不用进程内字典假装持久化**：CLAUDE.md §9 明令禁止。它的失败模式是
  「本机单进程开发时一切正常，上线换个 worker 就全丢」。
- **`build_graph` 不给 `checkpointer` 默认值**（[graph.py:267-271](../backend/workflow/graph.py#L267)）：
  默认 `None` 会让 `interrupt()` 在**运行期**报「没有 checkpointer」，
  而那时图已经跑了一半。装配期拿到它，等于把「忘了配检查点」变成启动失败。
- **`CheckpointerNotReadyError` 不回落内存存器**（[checkpointer.py:57-63](../backend/workflow/checkpointer.py#L57)）：
  回落会让「容器重启后恢复失败」变成「图从头再跑一遍」——用户看到的是澄清问题重问，
  而运维看到的一切正常。**这正是「错得安静」的典型。**

**踩过的坑**
1. **`interrupt()` 之前的写入不会被持久化**（[state.py:267](../backend/workflow/state.py#L267)、
   [interrupts.py:19-20](../backend/workflow/interrupts.py#L19)）。原因是恢复时**整个节点会重跑**，
   那次重跑把 `interrupt()` 之前写的 state 全冲掉。所以澄清问卷**不能**由 `clarify` 产出，
   必须由一个**不中断**的节点写进检查点（[param_check.py:201](../backend/workflow/nodes/param_check.py#L201)），
   `clarify` 只负责中断与合并答案。**这条顺序是整个澄清往返能工作的前提**，
   而它不看注释是看不出来的。
2. **DSN 要归一**：`settings.postgres_dsn` 是 `postgresql+asyncpg://...`，
   而 psycopg 不认 `+asyncpg` 这个驱动前缀（[checkpointer.py:66](../backend/workflow/checkpointer.py#L66) 的 `to_psycopg_dsn`）。
   把它做成纯函数的好处是**没有 PG 的机器也能单测**。
3. **恢复 = 节点重跑，所以每个节点都必须幂等**。靠的是
   `already_done`（[state.py:400](../backend/workflow/state.py#L400)）+ 输入指纹
   （[state.py:391](../backend/workflow/state.py#L391)）：节点开头先算「喂给我的东西变了没」，
   没变就 no-op 返回 `{}`。有的用例专门守这条——
   `tests/test_workflow_graph.py:438` 断言「恢复时元数据绑定不会**重新探查**源库」。

**面试会怎么问**：「LangGraph 的中断恢复，为什么不能放内存里？」「thread_id 用什么？为什么？」

**你怎么答**：带数字——`thread_id = str(pipeline_id)`（一个函数，全项目一处）；
检查点落 PG（`langgraph-checkpoint-postgres`，`setup()` 自建表）；
生成锁 TTL 600 秒（[graph.py:88](../backend/workflow/graph.py#L88)）；
`tests/test_workflow_graph.py` 里 57 条用例，其中
`test_interrupt_resume_roundtrip_through_param_check_and_clarify`（[:351](../backend/tests/test_workflow_graph.py#L351)）
是端到端的中断-恢复往返。然后主动讲「`interrupt()` 之前的写入不落盘」这条，
因为**它是最容易写错、且错了之后单测还能全绿的一条**。

**追问会追到哪**
- **第一层**「恢复的时候节点会不会重新执行副作用？」→ 会重跑，所以每个节点靠
  `already_done` + 输入指纹做幂等；有副作用的那几个（元数据探查、写证据事件）都有用例守着。
- **第二层**「`already_done` 判什么？」→ 判「该节点写过的指纹 + 必需字段都在」。
  指纹取的是**实际进提示词的内容**（校验后的模型 dump），不是 `profile_sha256` 这种间接指代——
  因为用户答题期间源表可能被重新探查过，那时档案哈希没变、画像却变了
  （[backend/workflow/nodes/generate_plan.py:228-236](../backend/workflow/nodes/generate_plan.py#L228)）。
- **第三层**「检查点表会无限膨胀吧？」→ 会。`langgraph-checkpoint-postgres` 写的是
  线程级的完整快照，一个 pipeline 反复澄清会积累多份。项目现在**没有**清理策略——
  这是我准备交代的缺口（要么按保留数裁剪，要么在 pipeline 终结时清线程）。

## ⑰ 候选行：草案就是那一行 `frozen_at` 为空的版本

**一句话**：生成出来的方案要有个 id 让前端去拉，但它还没冻结、还不该是不可变的——
于是「草案」不是另一张表，而是 `pipeline_version` 里 `frozen_at IS NULL` 的那一行。

**为什么需要它**：前端「一句话生成」之后要立刻按 id 拉 Plan / HOCON / 门禁结论
（Studio 的中部面板渲染的就是草稿），那个 id 在冻结之前就得存在。
但 `pipeline_version` 是**不可变制品表**（见卡片 ⑭）——草案要能被替换、被改，
两边的需求是冲突的。这个项目的解法是把「可变」限定在**一行**上。

**这个项目里怎么做的**
- 候选 = `frozen_at IS NULL` 的行，用一条**部分唯一索引**保证一个 pipeline 最多一行
  （[models/pipeline.py:165](../backend/models/pipeline.py#L165)，建在 `pipeline_id` 上，
  `WHERE frozen_at IS NULL`）。
- 不可变的判断依据是**库里已存的值**，不是「本次改动有没有带 freeze 列」
  （[models/base.py:118](../backend/models/base.py#L118) 的 `_is_frozen`）——
  否则「同一事务里先写 `frozen_at`、再改别的列」就绕过了守卫。
- 可改的列有一份显式白名单 `__mutable_columns__`（[models/pipeline.py:177](../backend/models/pipeline.py#L177)），
  冻结列单列（[models/pipeline.py:191](../backend/models/pipeline.py#L191)）。
- 取/建候选在 [services/pipeline/repository.py:362](../backend/services/pipeline/repository.py#L362) 的
  `get_or_create_candidate`，写入走 `savepoint` + 重试（`_VERSION_RETRY = 3`，[:58](../backend/services/pipeline/repository.py#L58)）。

**代码长什么样**

```python
# models/pipeline.py

168          postgresql_where=text("frozen_at IS NULL"),   # 一个 pipeline 最多一行候选
```

**为什么不那样做**
- **不建一张独立的 candidate 表**（迁移文件
  [backend/alembic/versions/20261016_1918_813dec0bb4bb_pipeline_version_candidate_row_nullable_.py:11-12](../backend/alembic/versions/20261016_1918_813dec0bb4bb_pipeline_version_candidate_row_nullable_.py#L11)）：
  草案与正式版本除了「冻没冻」之外，字段完全一样。分成两张表意味着
  「冻结」变成一次**跨表搬数据**，而搬的过程中任何一步出问题，都会留下一份
  「冻结了但制品还挂在旧表上」的版本。
- **不用哨兵值**（比如 `frozen_at = 1970-01-01`）：`NULL` 的语义由 DB 的三值逻辑保证，
  哨兵值要靠所有人记得这个约定，忘一处就漏一个。
- **不靠代码「先查有没有候选、没有就建」**：两个请求同时进来，都查到「没有」，
  都去建——**DB 那条部分唯一索引是这里唯一的兜底**。代码侧的重试只是让冲突变成
  一次无害的重试，而不是让冲突「不出现」。
- **删掉了 sha256 的全局唯一约束**（[models/pipeline.py:153-159](../backend/models/pipeline.py#L153)）：
  同一份制品被两个 pipeline 引用是合法的（复制一个方案到另一个 pipeline），
  全局唯一会禁掉它。

**踩过的坑**
1. **并发建候选会撞唯一索引**，处理方式是 `IntegrityError` 在 `savepoint` 里接住后重试，
   而不是回滚整个事务（[repository.py:379](../backend/services/pipeline/repository.py#L379) 起）。
   ⚠️ **但单测跑在 SQLite 上，而 SQLite 会忽略 `with_for_update()`**——
   所以「并发下只建一行候选」这条**没有被真跑过的用例证明**，只有开发机全量过的直觉。
   这是我准备主动交代的测试缺口（见 04 文档里同一处提醒）。
2. **候选不出现在版本列表里**（[repository.py:119-120](../backend/services/pipeline/repository.py#L119)）：
   `list_versions` 过滤掉 `frozen_at IS NULL` 的行。不这么做的话，用户点一次生成就多一条
   「版本」，而它随时可能被下一次生成覆盖掉——列表里会出现一个**会变的版本号**。
3. **草案可以改内容，但不能改身份**：`pipeline_id` / `version_no` 不在白名单里。
   允许改 `pipeline_id` 等于允许把一份草案挪到别的 pipeline 底下，而候选唯一索引的语义
   就建立在「一行候选属于一个 pipeline」上。

**面试会怎么问**：「草案没冻结，那它凭什么能被改？」「你怎么保证一条 pipeline 只有一个草案？」

**你怎么答**：带数字——一个 pipeline 最多 **1** 行候选（部分唯一索引 `WHERE frozen_at IS NULL`）；
可改列一份白名单，冻结列 `frozen_at`；`sqlite` 与 `postgresql` 两侧都写了谓词
（否则单测与生产行为不一致）。**并且主动说**：这条并发保证目前只有索引、没有并发用例，
因为测试库是 SQLite、`with_for_update()` 在那里是空操作。

**追问会追到哪**
- **第一层**「部分唯一索引与普通唯一约束有什么区别？」→ 普通唯一约束是「整列唯一」，
  部分唯一索引是「只对满足谓词的行唯一」。这里需要的是后者：
  一个 pipeline 可以有**很多个已冻结版本**，但只能有**一个未冻结草案**。
- **第二层**「草案被覆盖时旧的内容去哪了？」→ 直接改（[repository.py:431](../backend/services/pipeline/repository.py#L431) 的
  `replace_candidate_artifacts`）。草案不是版本历史的一部分，**故意不留痕**——
  留痕的代价是每次重生成都多一份永不使用的不可变行。
- **第三层**「那用户不小心覆盖了想保留的草案怎么办？」→ 项目**没有**「把草案存为版本」的入口。
  正确做法是让他**冻结**（冻结后就是不可变版本）。这是个真实的可用性缺口：
  没有「冻结成版本但暂不发布」之外的中间态——不过在当前模型里，
  「冻结」本身就是那个中间态（发布是 be-18，代码已落地但**在真 Doris 上一次都没换过表**——
  见 [10-做到哪一步了](10-做到哪一步了.md)）。

## ⑱ 五段指纹：为什么行 id 不进指纹、为什么冻结前要重算一遍

**一句话**：把「这份制品长什么样」压成一个 SHA256。难的不是算哈希，
而是**决定哪五样东西进哈希、每样里哪几个键要剥掉**——因为它一旦有两处定义，
症状是**随机的**：同一份制品，有时报「指纹失效」，有时正常。

**为什么需要它**：审批看的 A 与执行拿到的 B 必须是同一份。审批之后制品可能被改
（哪怕是「重新探查了一次源表」这种无辜的改动），指纹就是那道「还是同一份吗」的判据。

**这个项目里怎么做的**
- 五部分：`etl_plan` + `hocon_content` + `quality_contract` + `supervision` + `source_metadata_sha256`
  （[engines/fingerprint/parts.py:103-111](../backend/engines/fingerprint/parts.py#L103)，
  整个 `ArtifactParts` 是 `frozen=True` 的，[:100](../backend/engines/fingerprint/parts.py#L100)）。
- 拼法**只有一处**（[services/pipeline/parts.py:134](../backend/services/pipeline/parts.py#L134) 的 `fingerprint`），
  生成期与校验期各有一个构造入口，但都调同一个 `build_parts`。
- **冻结之前从落库的行重算一遍**，对不上就拒绝冻结
  （[artifacts.py:382-392](../backend/services/pipeline/artifacts.py#L382)）。

**代码长什么样**

```python
# engines/fingerprint/parts.py —— 排除规则里最值钱的一行
114  def _is_excluded(key: str, *, top: bool) -> bool:
116      if key.endswith(EXCLUDED_KEY_SUFFIXES):   # *_by（操作者）
117          return True
119      if key == "id":
120          return top                             # 只在**每部分顶层**剥行级 id
121      return key in EXCLUDED_KEYS                # 26 个键的字面量清单
```

```python
# services/pipeline/parts.py —— 校验期：从**落库的行**重算，不是从内存对象
126      plan_row.plan,                            # 库里的 jsonb
127      hocon_row.content,                        # HOCON 全文，逐字节
128      quality_body_from_row(quality_row),
129      supervision_body_from_row(supervision_row),
130      source_metadata_sha256,
```

```python
# services/pipeline/parts.py —— 第五部分怎么由多个源算出来
159  return "|".join(sorted(digest for digest in digests if digest))
```

**为什么不那样做**
- **行 id 与时间戳不进指纹**（[EXCLUDED_KEYS](../backend/engines/fingerprint/parts.py#L48)，26 项）：
  自增 id、`created_at`、`frozen_at` 是**编排事实**，与「制品是什么」无关。
  把它们算进去，同一份制品在不同 pipeline 下会算出不同指纹，于是「复制一个方案」
  这个合法操作永远无法通过校验。
- **但 Plan 内部的 `data_source_id` 必须保留**（[parts.py:15-19](../backend/engines/fingerprint/parts.py#L15)）：
  反过来才是对的——把源库从 A 换成 B 而指纹不变，等于放行一份「连的是 A 库」的方案走完治理。
  排除清单剥的是 `tenant_id`/`project_id`/`pipeline_id` 这类编排事实，**不是内容里的语义引用**。
- **不递归地删掉所有叫 `id` 的键**，只剥每部分**顶层**那个（[parts.py:119-120](../backend/engines/fingerprint/parts.py#L119)）：
  `dag.edges[0].id`、`inputs[0].id` 是**语义引用**，删了等于丢掉图的形状。
  这条有专门的用例：`tests/test_fingerprint.py:266`（顶层行级 id 排除但 Plan 内语义 id 保留）。
- **第五部分只放 sha256，不放档案快照全文**（[parts.py:110-111](../backend/engines/fingerprint/parts.py#L110)）：
  全文会让指纹随采样波动——同一张表两次探查拿到的样本可能不一样。
- **比对不用 `==`**：指纹会经过 jsonb、前端、审批意见的复制粘贴，`0xAB`/大写/空格
  不该让一份好制品被判失效（[parts.py:162](../backend/services/pipeline/parts.py#L162) 的 `fingerprint_matches`）。
- **不做「先冻结、发现不对再解冻」**：冻结是单向的（卡片 ⑭），
  所以「要不要拒」这个判断必须在 `flush` 之前做完。

**踩过的坑**
1. **一次「重新探查源表」会让冻结被拒**：候选行里的第五部分还是生成那一刻的，
   而现在重算出来的是新的，两者不等 → `ConflictError`
   （[artifacts.py:391](../backend/services/pipeline/artifacts.py#L391)）。
   **这是要的行为**（档案变了就说明门禁当初核的那份结构已经不在了，该重新生成），
   故障方向是「多拒一次」而不是「静默放行」。**但报错文案没有提示这一点**——
   用户会以为自己的制品坏了。这是我准备讲的取舍，也是我要改的一处文案。
2. **多源摘要必须排序后拼**（[parts.py:159](../backend/services/pipeline/parts.py#L159)）：
   `inputs` 换个书写顺序还是同一个方案，指纹不该因此变。
   「取不到档案的源**跳过**而不是塞空串」——塞空串会让「没探查过」与
   「探查过、摘要恰好是空」两种状态产生同一个指纹。
3. **金标准指纹**：`tests/test_fingerprint.py:35` 有一个写死的 `_GOLDEN_SHA256`，
   用例 `test_固定样例命中金标准指纹`（[:147](../backend/tests/test_fingerprint.py#L147)）断言它。
   任何对「规范化规则」的改动都会让它变红——**这是故意的**：
   改规范化就等于改历史指纹的算法，必须是显式决定，不能顺手改。

**面试会怎么问**：「指纹里为什么不能有 id 和时间戳？」「冻结前为什么还要重算一遍？」

**你怎么答**：带数字——**5** 部分；排除清单 **26** 个键 + 一条 `_by` 后缀规则；
第五部分是**排序后拼**的多源摘要；`tests/test_fingerprint.py` **51** 条用例里有一条是写死的金标准。
然后主动讲第 1 条坑：**一次重新探查会让冻结被拒**，并说「我认为这是保守失败、
方向是对的，但报错要能告诉用户去重新生成，而不是让他以为制品坏了」。

**追问会追到哪**
- **第一层**「指纹相等就等于制品相等吗？」→ 在 SHA256 的意义上是；
  但这依赖「同一份事实只有一处解释」（见卡片 ㉓）。项目里把这处解释放在
  `services/pipeline/parts.py`，并有用例断言键集合完整
  （`tests/test_fingerprint.py:335` 的 `test_artifact_envelope_键集合完整`）。
- **第二层**「一次重新探查就让冻结被拒，是不是太脆了？」→ 是脆，但比「悄悄放行一份
  与门禁结论不符的制品」好得多。真正的修法是让门禁结论本身带指纹：冻结时先核
  「门禁是拿哪份档案判的」，对不上就**明确要求重新生成**。项目现在只做到「拒」。
- **第三层**「那历史版本的指纹怎么保证一直能重算？」→ 靠 `FINGERPRINT_FORMAT_VERSION`
  与「派生校验结果键被剥掉」（`tests/test_fingerprint.py:249`）：
  校验器/解析器升级不该让历史指纹失效。但**如果规范化规则本身要改**，
  旧指纹就真的重算不出来了——那时只能靠版本号分流，而项目还没有第二版规则。

## ⑲ 确定性门禁 vs 结构校验：谁查自己、谁查档案、谁短路

**一句话**：`validate_plan` 只看 Plan **自己**有没有矛盾（不需要任何外部信息），
门禁才对着**元数据档案**核列、对着策略表评级；而且门禁一遇到 `block` 就停。

**为什么需要它**：这是两件不同的事。「你自己说的话自相矛盾吗」——生成后立刻能跑
（第一道闸）；「这份方案能不能上生产」——要档案、要策略、要 HOCON 解析结果。
把它们混在一个函数里，就会出现「结构问题也要等查完库才报」这种慢且难归因的行为。

**这个项目里怎么做的**
- 分工写在 [engines/plan/validate.py:1-18](../backend/engines/plan/validate.py#L1) 的 docstring 里
  （一张表），`validate_plan` 在 [:30](../backend/engines/plan/validate.py#L30)。
- 门禁的检查顺序写在常量里：[engines/gate/types.py:32](../backend/engines/gate/types.py#L32) 的
  `CHECK_ORDER = ("policy", "syntax", "schema", "mapping", "resource")`（**5** 项）。
- 短路在 [engines/gate/gate.py:72-77](../backend/engines/gate/gate.py#L72)。
- 门禁结论挂在 HOCON 制品上（**没有独立的表**），`parse` 与 `gate` 分开存
  （[services/pipeline/gating.py:87](../backend/services/pipeline/gating.py#L87) 的 `artifact_meta`）。

**代码长什么样**

```python
# engines/gate/gate.py
72  for check_id in CHECK_ORDER:              # policy → syntax → schema → mapping → resource
73      produced = _CHECKS[check_id](ctx)
74      findings.extend(produced)
75      if any(f.severity == "block" for f in produced):
77          break                              # 前提已被推翻，继续跑只会产出噪声
```

```python
# engines/plan/validate.py
30  def validate_plan(plan: EtlPlanModel) -> list[PlanIssue]:
31      """返回**全部**问题（不短路）。... 一次列全能让重生成提示词带上完整反馈；
34      而门禁那边短路是因为它的检查**互相依赖**，这里没有依赖关系，短路只是白丢信息。"""
```

**为什么不那样做**
- **`validate_plan` 不短路**（[validate.py:31-35](../backend/engines/plan/validate.py#L31)）：
  它的问题互相独立，一次列全能让**重生成提示词带上完整反馈**。它还有个用处：
  `generate_plan` 把它的输出落进 `plan_errors`，而**非空的问题清单不抛异常**——
  它是自动修复的输入，抛错等于把「可修」变成「终局」
  （[workflow/nodes/generate_plan.py:270-272](../backend/workflow/nodes/generate_plan.py#L270)）。
- **门禁短路**：HOCON 解析失败之后再去核「源字段存不存在」是没意义的，
  只会对着空配置报几十条连带错误，把真正的第一条埋掉。
- **不给生产路径一个「诊断开关」**：另一个入口 `evaluate_all`
  （[gate.py:88](../backend/engines/gate/gate.py#L88)）跑全量。
  把它做成 `evaluate(diagnose=True)` 的风险是**某天为了诊断打开开关，生产就一次报 40 条**。
  分成两个函数，生产路径上只存在短路那一条。
- **`info` 不短路**（[gate.py:22](../backend/engines/gate/gate.py#L22) 附近）：
  它不构成「前提被推翻」。等级只有 `block` 才停。
- **门禁结论落库后不重跑**（[artifacts.py:203](../backend/services/pipeline/artifacts.py#L203) 的 `get_gate`）：
  重跑会得到一个「现在」的结论，而策略表改过之后两者会不一样——
  用户要的是「当时被判成了什么」。

**踩过的坑**
1. **"门禁没通过"与"配置没解析出来"必须能分开**：所以 `artifact_meta` 把 `parse` 与 `gate`
   分两个键存（[gating.py:87-105](../backend/services/pipeline/gating.py#L87)）。
   合成一个 `ok: false` 之后，用户看到「门禁失败」去改字段映射，而真因是 HOCON 里少了一个引号。
2. ⚠️ **我读出来的一个真实缺口**：`tests/test_gate_checks.py` 有 **35** 条用例，
   但它们全部直接 import `engines.gate.checks` 与 `engines.gate.types`，
   **没有一条调用 `engines.gate.gate.evaluate`**。也就是说
   **`CHECK_ORDER` 的顺序、短路行为、`evaluate_all` 的存在，都没有测试覆盖**。
   改错顺序或去掉 `break` 都不会让任何用例变红。这是我准备主动交代的缺口。
3. ✅ **一个「文档化时核出来、后来已修」的真实缺陷**：`api/pipeline_versions.py` 的 diff 端点
   一度用 `from_version_id=` / `to_version_id=` 去调 `artifacts.diff_versions`，
   而该函数的参数名是 `base_version_id` / `target_version_id`
   （[services/pipeline/artifacts.py:436-437](../backend/services/pipeline/artifacts.py#L436)）——
   运行期会抛 `TypeError`。而 `tests/test_pipeline_api.py` 只做**源码级**断言
   （断言路由的装饰器顺序与 DTO 形状），**没有真的调这个端点**，所以当时没被发现。
   **现在端点已改成传 `base_version_id=`，两者对上了**（[api/pipeline_versions.py:52](../backend/api/pipeline_versions.py#L52)）。
   它仍是「测试全绿但功能不生效」的好例子——**讲它时我讲的是「这类 bug 怎么被漏掉的」，不是「它现在还在」**。

**面试会怎么问**：「门禁为什么短路而结构校验不短路？」「门禁结论为什么不重算？」

**你怎么答**：带数字——门禁 **5** 类检查，顺序 `policy → syntax → schema → mapping → resource`；
`block` 才短路，`warn`/`info` 不短路；结构校验**返回全部**问题、**不抛异常**（它是修复的输入）。
然后主动说上面第 2、3 条：**门禁主函数没有用例覆盖**，以及 **`diff` 端点的参数名一度对不上（现已修）**。
能自己说出「我文档化的时候发现我的 35 条门禁用例没测到短路」，比说「门禁写得很完善」强得多。

**追问会追到哪**
- **第一层**「短路会不会漏报？用户只看到第一条怎么修？」→ 会漏报，这是取舍。
  修完第一条再跑一次就会看到第二条。`warn` 不短路保证了「非阻塞问题」一次看全。
- **第二层**「那为什么不做成一次报全、前端按类折叠？」→ 可以，但代价是
  「HOCON 解析失败之后再报 30 条 schema 错」这种**噪声淹没真因**。
  真想看全量，走 `evaluate_all`（诊断路径），生产路径保持短路。
- **第三层**「`policy` 为什么排第一？」→ 因为它是**唯一一个即使配置全是语法错也成立的结论**：
  「你越界了」与「你的 HOCON 写错了」是两回事，而前者是治理判定（P0/P1），
  必须先出、且**不能被修复回路碰**（卡片 ⑳）。排序在这里是语义，不是性能。

## ⑳ 生成器驱动的有限自动修复：一份控制流，同步与异步两个驱动

**一句话**：门禁报错后，让模型最多改 **3** 轮、每轮重判；把「轮次 / 去抖 / 策略短路」
这套控制流写成**一个生成器**，于是同步的 worker 和异步的 API 共用同一份逻辑。

**为什么需要它**：修复这一步要**调大模型（async）**，而回路本体是**同步纯逻辑**。
两处各写一遍的话，「最多 3 轮 / 去重 / 策略短路」会有两份实现——
一份改了另一份没改，**而且不会有任何报错**。

**这个项目里怎么做的**
- 回路本体是 [engines/autofix/loop.py:109](../backend/engines/autofix/loop.py#L109) 的 `_drive`，一个生成器。
- 同步驱动 `run_autofix_loop`（[:316](../backend/engines/autofix/loop.py#L316)）与
  异步驱动 `arun_autofix_loop`（[:339](../backend/engines/autofix/loop.py#L339)），service 侧走异步那条。
- 轮次上限来自配置（`settings.LLM_AUTOFIX_MAX_ROUNDS`，默认 **3**，见
  [graph.py:143-151](../backend/workflow/graph.py#L143)）；
  [artifacts.py:78](../backend/services/pipeline/artifacts.py#L78) 也有一份常量 `_AUTOFIX_MAX_ROUNDS = 3`。

**代码长什么样**

```python
169      proposal = yield AutofixRequest(          # ← 把「该修什么」交出去，等一个提案回来
```

**为什么不那样做**
- **不写成 `async def`**：Celery 任务里是同步调用，纯同步的调用方会被迫套一层事件循环。
  生成器让「谁提供修复提案」成为注入项，而不是让控制流跟着 IO 模型走。
- **不两处各写一遍控制流**：见上面「为什么需要它」。这是整张卡片的核心。
- **不在回路里做超时/重试**：那属于「怎么调模型」的策略，归 `clients/llm`。
  回路只管**轮次**。两种「次数」混在一起之后，「为什么停了」就无法归因。
- **上限不硬编码**：从 `settings` 惰性读（[graph.py:143-151](../backend/workflow/graph.py#L143)），
  而且**惰性**是故意的——模块级读配置会让 `import workflow.graph` 触发 `.env` 读取与生产自检，
  把纯函数单测变成一次配置校验。

**踩过的坑**
1. **策略阻断绝不进修复**（[loop.py:147-160](../backend/engines/autofix/loop.py#L147)）：
   只要 findings 里有一条 `category == "policy"` 且 `severity == "block"`，
   就地停手、`repair` **一次都不调**。让模型去「修掉」策略阻断等于把 P0/P1 判定交给 LLM
   （PRD §1.4 禁止），还白烧三轮钱。用例：
   `tests/test_autofix.py:114` 的 `test_policy_阻塞时一轮都不跑`。
   图路由层还有第二道（[graph.py:187-191](../backend/workflow/graph.py#L187)），
   放在**路由**是为了让「它压根没进修复」在图结构上可见。
2. **去抖签名必须稳定**（[loop.py:233-240](../backend/engines/autofix/loop.py#L233)）：
   只取 `block` 项、只由 `(category, code, locator_key)` 组成。
   `id` 里一旦混进随机数/时间戳，「同一问题」就会被判成新问题 → 无限重试。
   用例：`test_发现项在循环里绕回来也会被去抖拦住`（[:180](../backend/tests/test_autofix.py#L180)）。
3. **模型返回整份 Plan，而回路只收「补丁」**。中间那层「差成补丁」在 service 侧
   （[repair.py:138-158](../backend/services/pipeline/repair.py#L138)），
   且**当场做一次往返自检**（`apply_plan_patch(old, patch) == new`）。
   不做这一步的症状是「修复总是差一点、模型看起来不太行」——
   一个会让人去调提示词、永远查不到根因的故障。
4. **模型这轮吐不出可解析的 Plan → 记一轮空补丁**（[repair.py:93-105](../backend/services/pipeline/repair.py#L93)），
   但**模型不可用（`LLMUnavailableError`）如实抛出**（[:106-109](../backend/services/pipeline/repair.py#L106)）：
   环境问题不能伪装成「修不动」，否则用户看到「已尝试 3 轮仍未通过」，而真因是 key 过期。

**面试会怎么问**：「为什么用生成器？」「修复最多几轮？到顶了怎么办？模型乱改怎么办？」

**你怎么答**：带数字——最多 **3** 轮（`LLM_AUTOFIX_MAX_ROUNDS`，可配）；
`tests/test_autofix.py` **27** 条用例，其中同步/异步两条驱动各有收敛、去抖、策略短路三组；
策略阻断时 `repair` 调用次数是 **0**。然后主动讲第 3 条（整份 Plan → 补丁的往返自检），
因为它是「模型看起来不太行」这类糊状故障的根因所在。

**追问会追到哪**
- **第一层**「3 轮的上限怎么定的？」→ 经验值 + 成本：每轮一次完整 Plan 的生成费用。
  它在 `settings` 里可配，因为「上限该是几」取决于模型与预算，不该写死在代码里。
- **第二层**「跑满 3 轮还没好怎么办？」→ 路由去 `terminal` 节点，把候选停在
  `gate_failed`，并写 `terminal_error`（`AUTOFIX_EXHAUSTED`）
  （[graph.py:171-173](../backend/workflow/graph.py#L171)、[graph.py:237-242](../backend/workflow/graph.py#L237)）。
  用户看到的是「已尝试 N 轮仍未通过」，而不是一个假的「成功」。
- **第三层**「去抖判据够吗？」→ **不够**。现在的判据是「下一轮要修的签名集合此前出现过」，
  它能挡住「一模一样地打转」，但挡不住「修好 A 弄坏 B、修好 B 又弄坏 A」这种**交替循环**——
  那种情况每次签名都不同，回路会傻跑满 3 轮。改成「本轮阻塞项数量没有变小、
  且没消掉任何一个上一轮的 finding」才停，能覆盖交替循环。
  **这是我知道但项目还没做的一处。**

## ㉑ 确定性假 Provider：没有 API key 也要能跑通整条生成链

**一句话**：`LLM_PROVIDER=fake` 是一条**正式通路**，不联网、不取时间、不用随机数——
同输入必然逐字节同输出。它不是 mock，是「没有凭据时」的正确路径。

**为什么需要它**：本机（Windows 开发机）与 CI 都没有模型 key。
如果生成链第一步就断在「没有凭据」，那整条链路（提示词 → 起草 → 结构校验 → 门禁 → 修复）
在开发机上就**一次都没跑过**，而它恰恰是提示词拼装错误最先暴露的地方。
另外，「同一需求两次跑出完全一样的方案」也是**指纹与门禁可比性**的前提，
所以它同时充当 Benchmark L0 的确定性基线。

**这个项目里怎么做的**
- provider 名字只有两个（[clients/llm/registry.py:38](../backend/clients/llm/registry.py#L38) 的
  `SUPPORTED_PROVIDERS = ("deepseek", "fake")`），在 [:41](../backend/clients/llm/registry.py#L41) 的
  `build_provider` 里选。
- 假 Provider 的做事方式只有一件：把提示词里 `<<…>>` 围栏中的档案读出来，
  交给纯函数 `draft_plan` 起草，再把结果序列化成 JSON
  （[clients/llm/fake.py:1-11](../backend/clients/llm/fake.py#L1)）。
- 它**按围栏内容分派**，不按 `prompt_version` 或 `task`（[fake.py:326-336](../backend/clients/llm/fake.py#L326)）。

**代码长什么样**

```python
333      if extract_or_none(text, TAG_SOURCE_PROFILE) is not None:  # 有 <<SOURCE_PROFILE>> → 起草
334          return self._render_draft(text)
335      if extract_or_none(text, TAG_REQUIREMENT) is not None:     # 有 <<REQUIREMENT>> → 意图解析
336          return self._render_intent(text)
```


**为什么不那样做**
- **没有 key 时静默降级成 fake**：这是最诱人也最坏的选项。它会让「线上配错了 key」
  表现为「方案质量突然变差」，审计里一点痕迹都没有。**宁可报错**。
- **按 `prompt_version` 或 `task` 分派**（[fake.py:328-330](../backend/clients/llm/fake.py#L328)）：
  版本号是给人看的**审计字段**，让它承担控制流，会让「升个版本号」变成一次行为变更。
  判据只用「提示词里有没有那种围栏」——**提示词自己声明它要什么**。
- **意图解析时用规则猜参数**（[fake.py:346-357](../backend/clients/llm/fake.py#L346)）：
  猜错了**没人拦**——模型猜的参数会被 `find_missing_params` 当成已有值，

  结果就是五个必填参数**全部**进澄清问卷

- **明确列出「不修」的码**（[fake.py:63-66](../backend/clients/llm/fake.py#L63) 的 `UNFIXABLE_CODES`）：
  `budget_nonpositive` 属策略、`mapping_unmapped_target` 需要目标表结构。
  写出来，免得下一个人以为是漏了。

**踩过的坑**
1. **假 Provider 也走 `assert_outbound_safe`**（[fake.py:283](../backend/clients/llm/fake.py#L283)）：
   「不出网」不代表「不用过闸」。绕过的后果是**本地演示用不到它**，
   而本地演示恰恰是提示词拼装错误最先暴露的地方。这是「契约属于接口、不属于实现」。
2. **`generate_plan` 曾经自己拼 `CompletionRequest`**，四个后果写在

**面试会怎么问**：「没有模型凭据的时候你的系统怎么跑？」「你怎么保证假 Provider 不漂移？」

并且说清它的定位：**不是测试替身，是「无凭据环境」的正式通路**，
所以它也必须过 `assert_outbound_safe`、也必须有 `model_version`。
漂移的保护是「单测断言的是真实提示词 → 真实起草 → 真实校验这条链」——
`prompts/plan.py` 的围栏约定一改，测试立刻红。

**追问会追到哪**
- **第一层**「假 Provider 生成的方案也能过门禁吗？」→ 能，而且这是它有价值的原因：
  它走的是**同一条** `validate_plan` + 门禁。门禁能否通过取决于
  「档案 + 预算 + 起草规则」，与模型是不是真的无关。
- **第二层**「那演示时怎么区分『演示』与『真模型』？」→ 看 `generation_context.model_name`：
  假 Provider 固定写 `"fake-deterministic"`
  （[fake.py:46](../backend/clients/llm/fake.py#L46)），一眼可辨；它也会进证据事件的 payload。
- **第三层**「它凭什么算 Benchmark L0 基线？」→ 因为「不联网、不取时间、不用随机数」
  保证了**可复现**：同一需求两次跑的方案逐字节相同，性能与门禁结论才有可比性。
  真模型做不到这一点（同 prompt 也可能不同输出），所以基线必须由它来提供。
  **它的确定性是硬要求，不是巧合。**

## ㉒ Windows 上 psycopg 异步与 ProactorEventLoop：为什么要有 `core/eventloop.py`

**一句话**：psycopg 的异步模式**拒绝**在 Windows 默认的 `ProactorEventLoop` 上跑，
而 LangGraph 的 PG 检查点用的就是 psycopg 异步——
所以「在本机 Windows 起 API」会在启动那一步直接退出。项目把「该建哪种循环」
收敛进 **一处**。

**为什么需要它**：这不是可选优化，是「本机跑不起来」的硬拦路。
在 Windows 上，Python 默认的事件循环自 3.8 起是 `ProactorEventLoop`；
而 `asyncpg` 仍走 `psycopg` 之外的路径（能跑），`psycopg` 的异步模式则明确不兼容 Proactor。
项目用的是 `AsyncPostgresSaver`（psycopg 系），于是撞上。

**这个项目里怎么做的**
- 判断只有一处：[core/eventloop.py:47](../backend/core/eventloop.py#L47) 的 `loop_factory()`。
- API 侧用它建循环（[dev_api.py:68](../backend/dev_api.py#L68)）；
  worker 侧复用同一个判断（[tasks/async_runner.py:52-60](../backend/tasks/async_runner.py#L52)）。

**代码长什么样**

```python
# core/eventloop.py
47  def loop_factory() -> LoopFactory:
53      if sys.platform == "win32":
54          return asyncio.SelectorEventLoop    # psycopg 异步的硬要求
55      return asyncio.new_event_loop           # 其它平台保持默认，不改生产行为
```

```python
# dev_api.py
68      asyncio.run(server.serve(), loop_factory=loop_factory())
```

**为什么不那样做**
- **不在被 import 的模块里 `asyncio.set_event_loop_policy`**
  （[eventloop.py:16-19](../backend/core/eventloop.py#L16) 的说明）：
  uvicorn 的 `Server.run()` 会**先建循环、后 import `main:app`**——
  等 `main.py` 执行时循环已经建好了，设 policy 是**无效的**（它只影响之后建的循环）。
  **这是本卡最值钱的一行**：一个看起来完全合理的写法，实际静默无效。
- **不指望 uvicorn 的开关**：uvicorn 0.54 起用 **loop factory** 而不是 policy
  （[eventloop.py:14-16](../backend/core/eventloop.py#L14)），
  在 win32 且非 subprocess 时它自己返回 Proactor，没有 CLI 开关绕开。
- **不换同步检查点**：那等于在异步图里塞回同步 IO + 线程池，
  用「多一个线程池」换掉「一处平台判断」，不划算。
- **不做「跨平台抽象层」**（[eventloop.py:26-29](../backend/core/eventloop.py#L26)）：
  非 Windows 一律返回默认行为。多一层抽象只会让「Linux 上跑的和本地不一样」更难查。

**踩过的坑**
1. **`--reload` 在 Windows 上会退回 Proactor**：所以 `dev_api.py`
   对它的处理是**打一行提示并返回退出码 2**
   （[dev_api.py:61-64](../backend/dev_api.py#L61)），而不是静默跑一个「启动即崩」的配置。
   把一个平台坑做成了**显式失败 + 可操作的提示**。
2. **worker 侧循环建好就不再关闭**（[async_runner.py:52-60](../backend/tasks/async_runner.py#L52)）：
   因为 `core.db.engine` 是**模块级单例**，每个任务都 `asyncio.run`（新建并关闭循环）
   会让第 2 个任务起失败（`Event loop is closed`，或伪装成
   `AttributeError: 'NoneType' object has no attribute 'send'`，栈指向 `session.execute`）。
   所以任务里**禁止 `asyncio.run`**，一律走 `run_coro`（CLAUDE.md §9.1 有专门一条）。
3. **同一个坑的两个面**：`core/redis.py` 那边的表现是「隧道抖动一次后
   worker 从此不干活，重启才好」（客户端是 `lru_cache` 单例、要显式开健康检查与重试，
   见卡片 ⑫）。事件循环与连接池是同一个「进程级单例 + 跨轮次复用」问题的两面。

**面试会怎么问**：「Windows 上跑 FastAPI 有什么坑？」「你为什么要自己建事件循环？」

**你怎么答**：带数字/版本——判断只有 **1** 处（`core/eventloop.py`）；
uvicorn **0.54** 起用 loop factory；Python **3.12** 起 `asyncio.run` 支持 `loop_factory` 参数。
关键的那句是：**「在 `main.py` 里设 event loop policy 是无效的，因为 uvicorn 先建循环、
后 import 应用；要用 loop factory。」** 这句话区分了「背过这个坑」和「真踩过这个坑」。

**追问会追到哪**
- **第一层**「为什么不在 Linux 上也统一用 Selector？」→ 不必要地改变生产行为。
  Linux 上默认的循环工作正常，改动只会让「本地与线上差异」多一项。
- **第二层**「`loop_factory` 和 `set_event_loop_policy` 到底差在哪？」→
  policy 是「**以后新建**循环时用哪个类」，factory 是「**你这一次**要建哪个」。
  uvicorn 自己调 `asyncio.run(...)` 时决定，所以必须在**它的入口**把工厂传进去。
- **第三层**「还有哪些库在 Windows 上有这种问题？」→ 任何「自带事件循环管理」的框架
  （uvicorn / hypercorn / Celery 的异步扩展）都会遇到，且它们各自的注入点不同
  （CLI 开关 / 参数 / 环境变量）。**所以正确做法是把判断收敛成一处函数，
  然后每个入口都用它——而不是在每个入口各写一遍 `if win32`。**

## ㉓ 「唯一实现」原则：同一份事实只许有一处解释

**一句话**：指纹的拼法、档案快照的 JSON 解析、Redis 键模板——
凡是「同一份事实被多处使用」的地方，解释只留一处，其它地方都调它。

**为什么需要它**：两处各写一份的失败模式是**最难查的那一类**——
不报错、结果只是「有时不对」。指纹分叉的症状是「偶尔报指纹失效」；
档案解析分叉的症状是「门禁说那列存在、提示词里那列凭空消失」，
模型于是猜一个列名，一路走到渲染才炸。

**这个项目里怎么做的**
- 五段指纹的拼法只在 [services/pipeline/parts.py](../backend/services/pipeline/parts.py) 一处
  （模块 docstring 第 1-23 行明说「全项目唯一的一份定义」），
  生成期 `parts_from_plan`（[:95](../backend/services/pipeline/parts.py#L95)）与
  校验期 `parts_from_rows`（[:112](../backend/services/pipeline/parts.py#L112)）共用 `build_parts`。
- 档案快照的读法只在 [services/pipeline/profile_view.py](../backend/services/pipeline/profile_view.py) 一处，
  它把 JSON 读成中立结构，**投影（打平 / 分组）由各自消费者做**
  （[profile_view.py:1-19](../backend/services/pipeline/profile_view.py#L1) 的 docstring 把这件事说得很直白）。
- Redis 键模板也只有一处：`gen_lock_key`（[workflow/graph.py:110](../backend/workflow/graph.py#L110)）
  是 `core.redis.KEY_GEN_LOCK` 的**唯一填充点**。

**代码长什么样**

```python
# services/pipeline/gating.py
141  # 拼法**只在 parts.py 里有一份**：门禁这里算的、生成时进指纹的、冻结时重算的
142  # 必须是同一个值。三处各写一次 "|".join(sorted(...)) 就是指纹系统的第一次分叉
144  source_metadata_sha256 = parts.source_metadata_sha256(profiles_sha)
```

```python
# services/pipeline/profile_view.py 的 docstring（摘要）
门禁（gating._snapshot_tables）要按 (data_source_id, schema, table) **打平**的列表
提示词（engines.plan.draft 的 DraftSourceTable）要**按表分组**的列
两边各写一份 profile.schema_snapshot["tables"] 的解析 = 同一份事实的两次解释
```

**为什么不那样做**
- **不各写各的**：见上面两条「为什么需要它」。
- **不让 `engines` 自己去查库再解析**：engines 是纯函数层，
  快照必须由 service 读出来后**作为参数传进去**（[profile_view.py:71](../backend/services/pipeline/profile_view.py#L71) 的 `tables_of` 收的是 ORM 行，
  但产出的是中立 Pydantic 模型）。这条同时守住了分层铁律。
- **`tables_of` 对 `None` 回空元组而不是 `None`**（[profile_view.py:72-76](../backend/services/pipeline/profile_view.py#L72)）：
  「没有档案」与「档案里没有表」对调用方的处置是一样的，
  而**多一种返回形状就多一个忘判的分支**。
- **认不出的敏感分级一律按 `INTERNAL`**（[profile_view.py:59-68](../backend/services/pipeline/profile_view.py#L59)）：
  不能退回 `PUBLIC`——`PUBLIC` 等于「随便出域」，而认不出来说明「档案里的值我们不认识」。
  **失败方向站在保守那一侧**。

**踩过的坑**
1. **「调用点可以多，实现只有一处」**：service 侧的 `_source_metadata_sha256`
   在 [artifacts.py:523](../backend/services/pipeline/artifacts.py#L523)、
   [generation.py:467](../backend/services/pipeline/generation.py#L467) 各有一份定义，
   但它们内部的收尾一律是 `parts.source_metadata_sha256(...)`。
   所以「唯一实现」不等于「唯一调用点」——前者是要守的，后者允许。
2. **`_snapshot_tables` 忘了把档案 id 拼进摘要**（[gating.py:141-144](../backend/services/pipeline/gating.py#L141) 的注释）：
   拼进去会导致「换一个内容相同的档案」也算变化，从而频繁拒冻。注释写在那儿，
   是为了让下一个改这段代码的人先想清楚。
3. **仓库里有 AST 用例守架构约束**（`tests/test_policy_import_graph.py`，**6** 条用例）：
   这是「唯一实现」思路的**可自动验证版本**——不让 `engines` import `fastapi`、
   不让 `harness` 依赖 `services` 这类铁律，靠人记会漏，靠 AST 遍历不会。

**面试会怎么问**：「你说『同一份事实一处解释』，具体到代码是什么样？」

**你怎么答**：带数字——`services/pipeline/parts.py` 是五段指纹拼法的**唯一**实现
（生成、门禁、冻结、验链四个调用点都调它）；
`profile_view.tables_of` 是快照 JSON 的**唯一**读法（一份解析、两种投影）；
`KEY_GEN_LOCK` 只有一个填充点。然后说**反例**：
`api/pipeline_versions.py` 的 diff 端点曾经把「artifact 服务的签名」在 API 层**又抄了一份**、
而且抄错了（`from_version_id` vs `base_version_id`）——**现已修**，
但形态上正好违反这条原则。**能举出自己项目里的反例，比只讲原则可信。**

**追问会追到哪**
- **第一层**「怎么防止下一个人再抄一份？」→ 三条：注释里写明「这里只有一份」并解释代价；
  用例断言结构（键集合完整、AST 约束）；把「重复实现」写进审查清单。
  项目做了前两条。
- **第二层**「有没有该有、但还没收敛的？」→ 有。
  `_AUTOFIX_MAX_ROUNDS` 同时出现在 [artifacts.py:78](../backend/services/pipeline/artifacts.py#L78)（常量）
  与 `settings.LLM_AUTOFIX_MAX_ROUNDS`（配置，[graph.py:143-151](../backend/workflow/graph.py#L143)）——
  两个来源。这是同一个「轮次上限」的两处解释，值一样纯属幸运。
- **第三层**「为什么这一条比其它规范更值钱？」→ 因为它的违反**不报错**。
  分层铁律违反了会 import 失败，类型错了会 mypy 报错，
  而「同一份事实两处解释」只有在**事实恰好不一致的那一刻**才炸——
  那一刻通常在生产，且现场信息最少。**这才是要花力气防的。**

## ㉔ 「哑闸门」：判据的输入从哪来、那条路径真的会填它吗

**一句话**：一道判据（阈值、校验、前置条件）写对了没用——**要问它的输入在运行期到底是谁填的**，
没人填的判据从来不生效，而且**不报错**。

**为什么需要它**：这一轮补 M3 后半段时，**同一个形状的缺陷一次抓到四个**，
每一个都躲过了当时全绿的 1370 条单测。共同点不是「代码写错了」，
而是**判据的输入不存在或错位**：判据本身逻辑正确、单测覆盖良好，
可运行期那条输入永远是空的，于是这道闸门**永远不触发**——
它看起来像一道防线，实际是一条注释。

| # | 闸门 | 输入为什么到不了 | 症状 |
|---|---|---|---|
| ① | 监督的**放大比**阈值 | 它要 `read_bytes` 做分母，而 SeaTunnel/Zeta 报的计数器**键名没有标准**：客户端依次试 `readBytes` / `readBytesTotal` / `sourceReceivedBytes` / 键名里含 `readbytes`（[client.py:203](../backend/clients/seatunnel/client.py#L203)），**一个都不中就落 0，再翻成 `None`** | 放大比这一维**长期 `unknown`（永不越界）**——而「读 1 万行写出 1 亿行」正是最该拦的失控形态。唯一的线索是那行 `seatunnel_read_bytes_unmapped` **debug 日志（只记键名、不记值）** |
| ② | broker 第 ③ 步**验签** | worker 侧构造 `ToolBroker` 时**没传 `verifier`**（[broker.py:294](../backend/harness/broker.py#L294) 的 `if self._verifier is None: raise`） | 报错文案是「**本进程未配置 Capability 校验公钥**」——读起来像部署漏配，实际是**这个进程永远执行不了任何带令牌的工具**，也就是整条执行链一步都走不了 |
| ③ | broker 第 ④b 步**绑定比对** | `_submit` 把 `actor_id=None` 交给执行上下文（第 ④b 步要求「ctx 里的主体 == 令牌里签的主体」，拒空） | `UnauthorizedToolError: Capability 执行缺少操作主体` → 提交永远失败；**`_stop` 早就修过同一个错**，`_submit` 漏了 |
| ④ | 质量报告的**读取器** | 注册接口的形状错了：端口方法全是「表名进、计数出」（[ports.py:60](../backend/engines/quality/ports.py#L60)），而**影子表名会跨运行复用、光有表名定位不到主机与库** | 这个注册在**物理上无法实现**——写成进程级单例就必然拿不到连接；它是被 review 出来的，不是跑出来的 |

> ①这一格值得单独说一句：它**不是「代码写错了」，而是「输入可能永远到不了」**。
> 处置方式也一样是设计的一部分——不猜、不报 0，判 `unknown`
> （[supervision.py:200-210](../backend/services/supervision.py#L200) 把 DTO 的 `0` 翻成 `None`，
> 因为 0 做分母会算出**无穷大**，把一次正常的运行误报成失控），
> 并**留下唯一能校准它的线索**：引擎实际报了哪些计数器键名。
> 这条线索只进 debug 日志，因为值里可能有配置片段。

**这个项目里怎么做的**——四条修法各自示范了一种「把输入接上」的手法：

- **① 缺值不许顶替**：监督侧读到缺失一律 `unknown`，**绝不用 0 顶替**。
  0 会让「没测到」看起来像「测到了、很正常」；`unknown` 会出现在结论里，
  逼着人去看「为什么这一维没数据」。
- **② 唯一推导点**：公钥路径 = 私钥路径换个后缀，这条推导只留一处
  ——[capability.py:303](../backend/harness/capability.py#L303) 的 `verifier_from_settings()`，
  所有进程都调它。守它的用例**不只断言属性非 `None`**，而是
  **拿同一把密钥签一张令牌、验签必须过得去**（断言「配上了」不等于断言「能用」）。
- **③ 主体从哪来，是三种不同的答案**——这是本轮最值钱的一处认知：

  | 工具 | 主体来源 | 为什么 |
  |---|---|---|
  | `seatunnel.submit` | 运行行的 `triggered_by`（[execution.py:132](../backend/tasks/execution.py#L132)） | 令牌本来就签给发起人，运行行上记的是同一个人；读行**不是「信任自己」**，broker 之后照样比对 |
  | `seatunnel.stop` | Outbox 载荷里的 `subject_id`（[execution.py:302](../backend/tasks/execution.py#L302)） | **取消人 ≠ 发起人**，在这里读 `triggered_by` 会把归因永久记错 |
  | `target.rollback_cleanup` | 账本里 `rollback.started` 的载荷、兜底 `triggered_by`（[publish.py:1298](../backend/services/publish.py#L1298) 的 `_rollback_actor`） | 令牌签给的是**发起回滚的人**，只有那次动作自己写下的账本记得住 |

  不变的那条判据始终是：**`ctx.actor_id` == 令牌里签的 `subject_id`**。
  「主体来源」是业务事实，「比对」是安全机制，**两者不能混**。
- **④ 注册什么，由端口的物理约束决定**：`ErrorTableReader` 必须是**工厂**
  （`(session, run) -> reader`，[errors_table.py:359](../backend/clients/target/errors_table.py#L359)），
  不能是进程级单例——因为「定位到哪张表、哪个库」这件事**只有拿到这一行 run 才知道**。

**代码长什么样**

```python
# services/quality.py:490 —— 闸门不是「写没写」，而是「触发它的那一刻输入在不在」
488  # 结论这一项**不能**叫 ``passed``：``harness.ledger`` 的入账前置校验
489  # 与日志处理器共用一份键名正则，里面有 ``pass(word|wd)?``，
490  # ``passed`` 整体命中，于是**每一份**报告都会被拒（SensitivePayloadError）
```

```python
# harness/capability.py:303 —— 公钥路径的推导只留一处，谁要构造 broker 都调它
303  def verifier_from_settings() -> CapabilityVerifier:
```

**为什么不那样做**
- **不把缺失值当 0**：见 ①。**降级成 0 是最危险的「静默错误」形态**——
  它把「不知道」伪装成「正常」。同一个道理在质量侧也出现过一次：
  目标端连不上时**抛错**而不是回一份「全 0 的报告」，因为 0 是合法的报告值，
  一份「看着干净」的报告会被下游拿去换表。
- **不让监督自己去停作业**：`services/supervision.py` 越界后只**签一张 `seatunnel.stop` 的票丢进 Outbox**，
  由 worker 侧执行。因为 worker 的 broker 只有验签器、没有签发器
  ——一个能自签令牌的进程等于「被攻陷就能随便执行」。
  代价是库里的 `interrupted` **先于**作业真的停下，这个中间态由
  `failure_snapshot.needs_manual_stop` 显式暴露，而不是假装不存在。
- **不把「函数被人调用」当成「功能生效」**：本轮补的那条缝就是这么来的——
  be-17 的 §5 与 be-18 的 §5 各自把「报告合格之后谁去换表」划给了对方，
  于是 `finalize_report` 与 `publish_run` **两个函数的调用方数量都是 0**，
  作业跑完永远不会出报告、报告合格也永远不会换表，而**两边的单测都是绿的**。
  补上的是 [services/finalize.py](../backend/services/finalize.py)：它**不拥有任何算法**，
  只做分派与顺序（只有它知道「质量合格之后才轮到发布」这个先后关系）。
- **同一个形状还有一处没修完，而且我没把它说成已实现**：分流的控制面
  （`render_tagged_select` / `render_route_selects` / 错误表 DDL / 质量报告）全在、都有用例，
  但 `render_route_selects` **零生产调用方**——渲染器仍是单源单 sink，
  违规行不会被真的分出去，报告会读到 0 条、显示「很干净」。
  它怎么改（运行期令牌 `{{runtime:run_id}}` + tagged/valid/rejected + 双 sink + 放行错误表）
  写在 [10 §4.1](10-做到哪一步了.md)；面试口述稿在 [07 必答 6](07-面试题库.md)。
  **判断标准是同一句：不是「函数写完了」，而是「有没有人调它、真跑一次会怎样」。**

**踩过的坑**
1. **`_stop` 修好了、`_submit` 没修**：同一个「主体为空」的坑，两处入口，
   修一处留一处。教训是**修这类缺陷时要横向扫同形状的调用点**，别只修报错那一处。
2. **脱敏按键名匹配，会误伤非敏感字段**：账本载荷里一个叫 `passed` 的键，
   撞上 [logging.py:21](../backend/core/logging.py#L21) 的 `_SENSITIVE_KEY_RE`（含 `pass(word|wd)?`），
   于是**不是被脱敏成 `***`，而是整条账本写入被拒**——每一份质量报告都写不出账本。
   修法是**只改账本里的键名**（`conclusion`），DTO 的对外字段 `passed` 不动。
3. **（测试侧）一个夹具里的跨文件全局状态**：`tests/test_harness_broker.py` 的假执行器夹具写着
   `if registered_executors(): return`（「别人注册过就整体跳过」），
   新写的 `test_finalize.py` 先注册了**真**执行器 → 本模块的 `seatunnel.submit`
   变成「未注册」，四条用例红，**单跑绿、同跑红**，报错还指向本模块毫不相干的地方。
   修法：夹具把注册表换成本模块私有的空表、跑完还原。**共享全局状态的夹具必须自己隔离，
   不能指望「别人没动过它」。**

**面试会怎么问**：「你怎么保证你写的校验真的在跑？」

**你怎么答**：不背「我写了测试」——讲这一轮的四个同类缺陷和它们的**统一形状**：
判据的输入不存在或错位。然后给两条**可操作的问法**：
**「这个判据的输入从哪来，那条路径真的会填它吗？」**
**「这段代码真跑一次会怎样？」**（第一个问题抓出 ①②④，第二个抓出 ②③）。
最后给**证据等级**的分法：单测绿只是最低一级；
本轮真正把 ② 从「看起来对」变成「确实能用」的，是
**重启一次 API 与 worker、在启动日志里看到那行 `quality_error_table_reader_registered`**
（漏挂钩子的症状是**运行时才 500**，跑一次才看得见）。

**追问会追到哪**
- **第一层**「为什么不写个用例覆盖？」→ 因为**用例很容易绕开真路径**：
  worker 的 broker 缺陷之所以全绿，是因为单测用的是**绕过七步序的假 broker**。
  所以补的不只是用例，还有**启动钩子**（API 的 lifespan + worker 的 `celeryd_init` 各注册一次）
  与**「拿真密钥签一张票验一遍」**这种端到端的小用例。
- **第二层**「那怎么防止下一次？」→ 把问法固化成审查清单里的两句（见上），
  并承认这条**没法靠自动化完全守住**：AST 能守「不许 import fastapi」，
  守不了「这个键在运行期有没有人填」。**能说清哪条靠机器、哪条只能靠人，比说「我们都有规范」可信。**
- **第三层**「这四个缺陷里，哪一个最像生产事故？」→ ② 最像：
  它的**报错指向错误的方向**（说「没配公钥」，实际是「这条路永远走不通」），
  而且单测永远绿。这类「错误信息把人带偏」的缺陷，
  排查成本比缺陷本身高一个数量级——**归因不要冤枉无关的组件**（同一个道理也出现在
  `clients/datasource_probe.py::_classify` 只把驱动异常译成连接失败码，
  `KeyError` 一律归 `INTERNAL_ERROR` 并留栈）。

## 附：三个「一句话」总结（面试收尾用）

1. **安全的核心不是"加了多少校验"，而是"有没有一条路径没人看着"**——
   所以这个项目把所有副作用收进一个出口，把令牌消费做成原子的，把账本做成链。
2. **"不报错但结果不对"比"崩溃"危险得多**——
   `detail` 白名单静默丢键、`DictCursor` 键名大小写、归因把代码缺陷算成连接失败，
   这三类坑我都写了注释和用例，它们的共同点是**测试全绿**。
3. **功能写完 ≠ 功能生效**——实现完整但零调用点（签名检查点、过期状态回收）
   在运行期等于不存在，而看代码看不出来。这条在最近一轮**一次抓到四个**
   （见卡片 ㉔：判据的输入不存在或错位 → 闸门永远不触发，且**单测全绿**），
   同族的还有一处最典型的：be-17 与 be-18 **各自把「报告合格之后谁去换表」划给了对方**，
   于是 `finalize_report` 与 `publish_run` 谁都没有调用方——
   已由 [services/finalize.py](../backend/services/finalize.py) 补上。
   **能主动指出这几处，比说"都做完了"可信得多。**
