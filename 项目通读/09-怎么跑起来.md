## 1. 拓扑：谁在本机、谁在云上

```
┌──────────────────── 你的 Windows 本机（没有 Docker / 没有 WSL / 没有 Java）────────────────────┐
│                                                                                              │
│   uvicorn          127.0.0.1:8000   ← 控制面 API（本机进程）                                  │
│   celery worker    队列 etl.default,etl.execute ← 异步任务（本机进程，-P solo）               │
│   vite :5175       真后端模式       ← 同一份代码，请求真的打到 8000                            │
│   vite :5173       mock 模式（按需）← 页面全都能看，但数据是前端假数据（右下角有角标）          │
│                                                                                              │
└───────────────────────────────┬──────────────────────────────────────────────────────────────┘
                                │  SSH 隧道（deploy/tunnel.py）
                                │  本机 5432 → ECS 5432   PostgreSQL 16（控制面库）
                                │  本机 6380 → ECS 6380   Redis 7
                                │  本机 8200 → ECS 8200   Vault（口令存这里）
                                │  本机 3307 → ECS 3307   MySQL 8（演示源库）
┌───────────────────────────────▼──────────────────────────────────────────────────────────────┐
│  阿里云 ECS 60.205.138.167（Docker Compose 全在这里，安全组只放行 22/8000/19530）             │
│  postgres / redis / vault / mysql 全在（均 healthy）——**没起**的是 demo profile 的 Doris 与   │
│  SeaTunnel（Doris 吃 8G+ 内存）。执行器与收尾编排都已落地（含 target.swap / rollback_cleanup），│
│  但整条链（监督 / 质量分流 / 发布回滚 / 收尾）在真库上一次都没跑过                            │
└──────────────────────────────────────────────────────────────────────────────┘
```

**为什么是这个形状**：本机没有 Docker，而数据库不该为了开发暴露到公网（改安全组等于把 PG 开到公网）。
所以选了 SSH 隧道——**这条路本身就是一个面试素材**，见 [01-这是什么 §6 ③](01-这是什么.md)。

⚠️ **一个必须知道的坑**：`localhost` 与 `127.0.0.1` 在这里**不等价**。
Vite 只监听 IPv6 的 localhost，所以浏览器**必须**用 `http://localhost:5175`，
写成 `127.0.0.1:5175` 会连不上。

## 2. 启动（四条命令，按顺序）

> 下面命令里的 `<ECS 口令>` 从环境变量进，**不写进任何文件**（`CLAUDE.md` §5.2）。

### ① 先起隧道（最容易被忘，且断了以后症状很奇怪）

```bash
cd d:/myself_complete_code/agent/elt_agent
ELT_ECS_PASSWORD='<ECS 口令>' PYTHONIOENCODING=utf-8 uv run --with paramiko python deploy/tunnel.py 5432 6380 8200 3307
```

**怎么知道起来了**：日志出现转发成功的行，且下面四个端口都通：

```bash
for p in 5432 6380 8200 3307; do (echo > /dev/tcp/127.0.0.1/$p) >/dev/null 2>&1 && echo "$p 通" || echo "$p 不通"; done
```

**我这次实测**：四个全通。

> 🔴 **但这个检查会骗你一次，我当场被它骗过**（值得当成面试素材讲）：
> 我**先**跑了一次隧道，把它留在后台去忙别的；回来发现它其实已经被收掉了，
> 而端口检查**照样显示「四个全通」**——因为端口转发是**一条条独立的 TCP 连接**，
> 「TCP 能握上手」只说明有东西在听，不代表转发链路还活着。
> 真正的症状出现在**下一步**：API 连 PG 时报
> `psycopg.OperationalError: connection failed: ... Software caused connection abort (0x00002745/10053)`，
> 也就是**握完手、读到一半被掐断**。
> **规矩：启动隧道前先确认没有残留的隧道进程**（本会话里我先 `TaskStop` 停掉旧的那条再起新的），
> 别用「端口通」当作唯一判据——`/readyz` 里 `{"postgres":"ok","redis":"ok"}` 才是真的判据。

### ② 起 API

```bash
cd d:/myself_complete_code/agent/elt_agent/backend
LLM_PROVIDER=fake PYTHONIOENCODING=utf-8 uv run python dev_api.py
```

> ⚠️ **不要用 `uv run uvicorn main:app`**：psycopg 异步拒绝 Windows 的 `ProactorEventLoop`，
> 而 uvicorn 是**先建循环、后 import app**，在 app 里设 policy 太晚——症状是**应用启动即退出**
> （很容易误判成「PG 连不上」）。`dev_api.py` 用 `loop_factory` 先把循环类型建对再起服务
> （见 `CLAUDE.md` §9.1）。也别加 `--reload`（会退回 Proactor）。
>
> `LLM_PROVIDER=fake` **不是测试开关，是正式通路**：没有模型 key 时它给出一份**确定性**的起草结果
> （同一需求两次跑，方案逐字节相同），用来演示生成链路的编排与门禁；反过来，写了 `deepseek` 却没配 key 会 503。

**怎么知道起来了**（两条都要，含义不同）：

```bash
curl -s http://127.0.0.1:8000/healthz     # 存活：只证明进程活着，返回 {"status":"ok","app":...,"env":...}
curl -s http://127.0.0.1:8000/readyz      # 就绪：真的去查 PG 与 Redis
```

**我这次实测**：`readyz` → `{"status":"ok","checks":{"redis":"ok","postgres":"ok"}}`。

> 💡 **面试可以主动讲这里的设计**（[health.py:1-5](../backend/api/health.py#L1-L5)）：
> `/healthz` **刻意不查任何依赖**——依赖挂了不该让容器被反复重启，因为**重启解决不了 PG 掉线**；
> `/readyz` 才查依赖，任一不可用返回 503，供网关摘流量。
> 而且每一项有 **3 秒上限**（[:30](../backend/api/health.py#L30)）：不设上限时 asyncpg 会一直等到自己的 60 秒超时，
> 于是 `curl -m 8` 拿到的是**超时而不是 503**——网关既摘不掉流量、也拿不到「未就绪」这个结论，
> **一次依赖故障会被放大成一次全站超时**。
>
> ⚠️ 注意 `readyz` **只查 PG 与 Redis 两项**，Vault 不在探针里（[:68](../backend/api/health.py#L68)）。
> Vault 是另一条路径验证的：建数据源时写入 → 连通性测试时读回 → 真的连上了库。

### ③ 起 worker

```bash
cd d:/myself_complete_code/agent/elt_agent/backend
PYTHONIOENCODING=utf-8 uv run celery -A tasks.celery_app worker -P solo -l info -Q etl.default,etl.execute
```

**怎么知道起来了**（别只看日志说 ready，要问它一句）：

```bash
cd d:/myself_complete_code/agent/elt_agent/backend
PYTHONIOENCODING=utf-8 uv run celery -A tasks.celery_app inspect ping
```

**我这次实测**：`pong` + `1 node online.`

> `-P solo` 不是可选项：Windows 上默认的 prefork 池不可用（`CLAUDE.md` §7）。

> 🔴 **`-Q` 要写两个队列：`etl.default,etl.execute`，少一个都不行**（`docker-compose.yml:220` 里 worker 用的就是这两个）。
> `tasks.execution.*`（提交 / 停止 / 收尾）**全部路由到 `etl.execute`**（[celery_app.py:65-70](../backend/tasks/celery_app.py#L65-L70)），
> 所以只订阅 `etl.default` 的 worker **永远不消费这几条消息，而且日志里一行都不打**——
> 它不是报错，是沉默，最容易被误判成「任务投出去了、就是没跑」。
> （`CLAUDE.md` §7 里那条本地命令**本次已同步改成两个队列**，两处一致。）

### ④ 起前端（**两个实例，用途不同**）

```bash
cd d:/myself_complete_code/agent/elt_agent/frontend && npm run dev

# 另一个终端：真后端模式（页面相同，但数据来自后端）
cd d:/myself_complete_code/agent/elt_agent/frontend && VITE_USE_MOCK=false npm run dev -- --port 5175 --strictPort
```

**打开哪个**：

| 地址 | 数据来自 | 用来干什么 |
|---|---|---|
| `http://localhost:5173`（裸 `npm run dev`） | **前端假数据（mock）** | 想展示「16 个页面长什么样」时用，后端在不在线都行。**右下角有 `DEV MOCK` 角标**，看见它就说明屏幕上的数不是后端的 |
| `http://localhost:5175` | **真后端**（经 vite 代理打到 8000） | 想证明「前后端真连上了」时用 |

**我这次实测的坑**：`vite.config.ts` 的 `server.port` 写的是 **5173**，我加的 `--port 5175 --strictPort` 那次也**没能落在 5175**——
机器上别的项目占着这两个口，vite 一路往上找，最后真后端实例起在 **5176**（启动日志里 `Local: http://localhost:5176/`）。
**所以别背端口，看启动日志里那句 `Local:`**；`--strictPort` 只保证「不悄悄换口」，不保证「你要的那个口是空的」。

> ✅ **顺手做一次「代理真的打到后端」的验证**（这一步能戳穿 mock 那一层）：
> 拿一个**注定失败**的请求打 dev server，看回来的是**谁的** 401：
> ```bash
> curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:5176/api/v1/auth/login \
>   -H 'Content-Type: application/json' -d '{"username":"x","password":"y"}'
> ```
> 拿到 **401 + 后端的错误信封** = 请求真的经代理到了 8000（mock 是浏览器端的 axios 适配器，**服务端看不到**，
> 所以 mock 模式下 curl 拿到的也是这个 401——**「curl 通」不能证明页面连的是后端**，只能证明代理没坏）。

> 这一轮结束时我只留着 **5175（真后端）**：同时跑两个 vite 会吃掉几个 G 的提交内存，`npm run build` 会直接 `memory allocation of N bytes failed` 中断（见 `CLAUDE.md` §9）。要用 mock 模式再按需起一个就行。

> 💡 **一个值得讲的细节**：`VITE_USE_MOCK` 影响的是**浏览器里**的行为——
> mock 是一段挂在 axios 上的适配器（`http.defaults.adapter = mockAdapter`，
> [mock/index.ts:1941](../frontend/src/api/mock/index.ts#L1941)），**不是服务端中间件**。
> 所以：
> - 用 `curl` 打 mock 那个实例（如 `localhost:5173/api/v1/datasources`）拿到的是**后端的 401**，不是假数据——
>   **命令行验证不到 mock 这一层**；
> - 那个适配器在**生产构建下直接拒绝安装**（[:1937](../frontend/src/api/mock/index.ts#L1937)），
>   注释写明理由：**mock 数据不得混进审计视图**。

**再加三条「外围依赖是不是真活着」的现场核对**（这三条是我今天补做的，比 `/readyz` 更深一层——
`/readyz` 只证明 TCP 与 `PING` 通，不证明**我们的用法**对）：

```bash
cd d:/myself_complete_code/agent/elt_agent/backend
# Vault 真登录 + 读路径（真 AppRole，不是看端口）
uv run python -c "import asyncio;from clients.vault import get_vault;print(asyncio.run(get_vault().health()))"
# Redis 原子占位：同一键第一次 True、第二次 None —— 这就是「一次性令牌」的底座
uv run python -c "import asyncio;from core.redis import get_redis;\
async def m():\n r=get_redis();print(await r.set('probe:x',1,nx=True,ex=30), await r.set('probe:x',1,nx=True,ex=30))\nasyncio.run(m())"
```

| 核对项 | 实测结果 | 它在证明什么 |
|---|---|---|
| Vault | `health() → True` | 口令库能真读（不只是端口通） |
| Redis 原子占位 | `True` 然后 `None` | `SETNX` 语义可用 = 「单次消费」的底座在 |
| ReplayGuard | 拿**从未签发过的** jti 去 `consume` → **被拒**（`REPLAYED`） | 双保险的**两半都在工作**：Redis 占位成功、而 PG 的条件 UPDATE 命中 0 行 |
| 证据账本 | 真 PG 里写入一行（`seq=51`、`prev_hash=1a87b41a7c…`），再独立验链 `OK checked=52` | 账本是**真库真写**，不是内存里演一遍 |

> 🔴 **这一条尤其值得在面试里讲**：ReplayGuard 的「拒绝」在单测里可以用内存 Redis 假装，
> 但**PG 那一半条件 UPDATE 只有在真库上才成立**。我拿一个「从没签发过的 jti」去打，
> 它被拒的理由**恰好是**「Redis 占位成功 + PG 更新 0 行」——说明两半都没偷懒。

## 4. 演示脚本（按顺序做，8 分钟）

**用 `http://localhost:5175`（真后端模式）。** 顺序是按「数据依赖」排的——后一步依赖前一步的产物。

### 4.0 一键把整条链跑一遍：`backend/scripts/demo_run.py`（本轮新增）

如果不想手点，这个脚本按同一顺序打真 HTTP：登录 5 个角色 → 建/复用数据源 → 连通性测试 →
元数据探查 → 发起生成并**自动回答澄清问题** → 冻结 → 准备单 → 两个不同的人审批 →
提交执行 → 轮询运行到终态 → 拉质量报告与账本。

```bash
cd backend
ELT_DEMO_PASSWORD='<demo2 租户开张时定的口令>' PYTHONIOENCODING=utf-8 \
  timeout 600 uv run python scripts/demo_run.py --scenario 1 --target mysql
```

- 它**不是测试**：真 HTTP、真 worker、真 SeaTunnel（如果起了），产物全部留在库里。
- 口令**只从环境变量进**，脚本里没有默认值——「无明文 Secret」这条对脚本同样成立。
- `--target mysql` 是**退路**：PRD 的默认目标是 Doris，但 ECS 内存/磁盘起不来 Doris 时，
  用 [deploy/mysql/init/02-target-schema.sql](../deploy/mysql/init/02-target-schema.sql)
  建了同名的 `dw_demo.orders_wide`，脚本会把数据源类型换成 `mysql`。
  两种目标端**表名与列形状完全一致**，所以需求文本不用改。
- `LLM_PROVIDER=fake` 时走的是**确定性兜底起草器**，不是测试桩；它只产出
  `not_null` 与敏感列 `regex` 两类规则，所以场景二需要的「金额 > 0 / 状态枚举」规则
  它**不会生成**——这是脚本当前到不了硬中断的原因，不是链路缺陷。

⚠️ **本轮第一次真跑时，本机进程在脚本启动瞬间被系统杀掉（exit 107），没有输出**；
随后 API / worker / 隧道一起退出。所以这个脚本**只经过语法与单测层面的检查，
没有一条真实的端到端结果**。你要用之前，先把它当成「待验证的驱动」而不是「已验证的工具」。

| 7 | 提交答案 | **同一个请求里**依次走过：元数据绑定 → EtlPlan（**10 条字段映射、1 条质量规则、0 结构问题**）→ HOCON（**885 字符 / 42 行**）→ 门禁（`conclusion=pass`，0 block、1 info）→ **冻结**（`version_no=1`、`sha256=f3ea7843…`、`frozen_by=需求提出人`） | 整条生成链一次走完；**放行结论是纯函数门禁给的**（`required_approval_slots=checker_data, checker_security`） |

| 9 | 再点一次冻结 | **409**：「该版本已经冻结过了；冻结是不可逆的」 | **不可变**是设计，不是 bug——重复冻结就该被拒 |
| 10 | 在终端跑 `verify_ledger.py` | `OK checked=52 from_seq=1`（数字随事件增长） | 🔴 **收尾王牌**：独立脚本从零复核整条链，不依赖任何应用代码 |

### 第三段（M3 **两半**都落地了，**但整条链在真库上一次都没跑过**）：准备单 → 四眼审批 → 提交执行

M3 的**两半**现在都在代码里：前半是准备单 / 四眼审批 / 提交执行（be-13/14/15），
后半是监督 / 质量分流 / 原子发布与回滚 / 收尾编排（be-16/17/18 + [finalize.py](../backend/services/finalize.py)），
`/preparations`、`/runs`、`/runs/{id}/rollback`、`/runs/{id}/publish` 都挂在 API 上。
但**我没有浏览器、也不知道登录口令**，所以下面这份流程是**照代码与路由清单写的，不是亲眼点过的**。
硬证据：真库里 `preparation` **0 行**、`execution_run` **0 行**、`quality_report` **0 行**
（`capability` / `outbox_message` / `error_record` / `execution_metric` 也都是 0 行）
——**整条链从来没有在真环境里被执行过，它只有单测覆盖**。

⚠️ **演示前你自己按这个顺序点一遍，把每一步的真实样子记下来**。第一遍点的时候大概率会碰到

「这段我是照契约推的，第一次真点才发现 X」比背一段没跑过的流程可信得多。
（这段是加分项：它证明你懂「为什么必须先有准备单」。）

| 步 | 你做什么 | 该出现什么 | 这一步在证明什么 |
|---|---|---|---|
| 11 | 用**刚冻结的那个版本**发起准备单 | 准备单里冻结了一批**输入指纹**（表结构哈希 / 凭据版本 / 清洗规则 / 预算） | 「审批的对象」是一份**可复现的输入快照**，不是一个编号 |
| 12 | 用**同一个人**去批两个槽 | **被拒** | **四眼**是真的。⚠️ 说清精度：**「发起人不能自己批」有两道**（`services/approval.py:155` 的服务端校验 + 迁移 0001:92 的 CHECK 约束 `ck_approval_decision_no_self_approval`）；**「两个槽必须不同人」只有服务端一道**（`approval.py:184`），`UNIQUE(preparation_id, slot)` 管的是「同一槽别批两次」，不管「两槽是不是同一个人」——**这里数据库没有兜底**，被追问要主动承认 |

**提交时多了一步（本轮新增，面试可以讲）**：`POST /runs` 在签发单次 Capability 之后、
把消息投进 Outbox **之前**，会**同请求、同事务**地执行一次 `target.ensure_tables` ——
在目标库建**影子表**（`CREATE TABLE ... LIKE 正式表`）与**错误表**
（[clients/target/executor.py:129](../backend/clients/target/executor.py#L129)、[services/run.py:340](../backend/services/run.py#L340)）。
它同样走 `ToolBroker` 七步、要验签，因为建表是**写外部系统**。
为什么要放在提交时而不是执行时：**建表失败要当场可见**——进了队列才发现目标库没权限，
用户看到的是一条「作业失败」，而归因会指向 SeaTunnel。

**这一段现在会停在哪儿（要主动说，别等翻车）**：
提交走到 `target.ensure_tables` 时就会失败（目标端连不上或没有 DDL 权限），
或者（如果目标端是 MySQL）继续走到「提交 SeaTunnel」，而 **ECS 上没起 SeaTunnel**——
所以你会看到运行**如实**变 `failed`，`error_message` 是连接类错误，账本里有一条 `run.failed`。
**这不是 bug，是「如实失败」**，正好用来讲 `_fail` 的三件事（状态 + 消息 + 账本，一处都不能少）：
> 「它没有假装成功，也没有把失败写成一个漂亮的空——我在修另一个缺陷时发现过**失败现场被吃掉**的情况
> （`refresh` 把还没 flush 的 `error_message` 冲掉了），现在有专门的用例守着『有结论就必须有原因』。」

**如果你不想在现场面对这个失败**：跳过第 14 步之后的所有步骤，把 M3 讲成
「路由与契约都在、执行器已注册，但数据面没起，所以我讲到『票是怎么来的』为止」。**诚实的边界比尴尬卡住强。**

**演示时说这几句话**（把「能跑」升级成「懂设计」）：

1. 「这个页面的口令**不在数据库里**——库里只有 Vault 的路径和版本号。这样库被拖走也拿不到口令。」
2. 「元数据样本的每个格都是 `类型:哈希`，**不是用星号盖掉**——星号盖掉的样本没有任何分析价值，而哈希保留了『这一列的格式是什么样』。」
3. 「生成这一段，模型只产出一份被 Pydantic 约束的 `EtlPlan`；**能不能放行由纯规则门禁判**（这里是 `pass`），模型碰不到。制品里也**没有明文口令**，只有 `{{secret:1:...}}` 令牌。」
4. 「最后一步 `verify_ledger.py` 是**独立脚本**——它只读数据库、自己重算哈希链，所以它能证明『没人改过历史』，而不是『我相信应用说的』。」
5. 「重复冻结返回 409，这是**故意的**：冻结是一个不可逆的事实，重来就得重新生成一份草案。」

## 5. 出故障怎么办（症状 → 先看什么 → 怎么办）

这张表是我和 `CLAUDE.md` §9.1 里那些坑的**对照表**：左边是你会看到的症状，右边是根因。

| 症状 | 先看什么 | 怎么办 |
|---|---|---|
| 登录**超时**（不是立刻失败） | **隧道进程**。隧道断了 ≠ 端口关着，表现是「能连上但不通」 | 重启隧道（第 2 节 ①） |
| **端口检查说「四个全通」，但 API 连 PG 报 `Software caused connection abort (0x10053)`** | **残留的旧隧道进程**（我实测踩过：端口在听，转发链已死） | 先停掉旧隧道再起新的，**别用「端口通」当唯一判据**——看 `/readyz`（第 2 节 ① 的告警） |
| `/readyz` 里 `postgres` 变 `error`，`/healthz` 还 `ok` | 这正是两个探针**刻意分开**的地方 | 依赖挂了不该让容器被反复重启（重启解决不了 PG 掉线）。查隧道、查 ECS 上 `elt-postgres` 是否 healthy |
| 重启隧道后**第一个请求 503** | 这是**自愈**不是故障 | **重试一次**。连接池里握着指向旧隧道的死连接，`pool_pre_ping` 会逐个淘汰——**别去改 `pool_recycle`** |
| **worker 从此不干活**，日志只有 `Error 22 while writing to socket` | 这是**连接池死连接**，不是网络问题 | 已在 `core/redis.py` 修掉（健康检查 + 重试）。若又出现，看健康检查配置是否被删——有回归用例守着（[test_core_clients.py:22](../backend/tests/test_core_clients.py#L22)） |
| **点一下按钮就 500**，栈全在 `kombu` 里 | Celery 的**默认应用**是不是我们配的那个 | `tasks/celery_app.py` 的 `set_default()` 与 `tasks/__init__.py` 的导入链（用例 [test_celery_app.py:28](../backend/tests/test_celery_app.py#L28) 守着） |
| 连通性测试显示 **failed**，但日志里明明成功 | `ToolBroker` 的 detail 白名单是不是少登记了键 | 看有没有 `tool_detail_keys_dropped` 警告（见 [08-面试故事](08-面试故事.md) 故事 6） |
| 前端页面**打开就报错**、接口全 401 | 你是不是开在了 **5175**（真后端模式）而**没登录** | 这是正常的：真后端模式需要先登录。想看「页面长什么样」用 mock 模式那个实例（默认 5173） |
| 前端**连不上**（浏览器报无法访问） | `localhost` vs `127.0.0.1` | 必须用 `http://localhost:5175`（Vite 只听 IPv6） |
| 后端起来就崩、报配置缺失 | 环境变量 | 生产配置自检**会让缺失密钥的应用启动即失败**——这是刻意设计，不要改成 warning |
| 中文输出乱码 | Windows 控制台是 GBK | 命令前加 `PYTHONIOENCODING=utf-8` |

## 7. 一句话总结这一节

> **跑起来的难点不在代码，在环境**：本机没有 Docker、数据库在云上、中间隔一条会断的隧道。
> 所以真正的判据不是「进程在不在」，而是**「依赖真的通不通」**——
> 这也是为什么 `/healthz`（不查依赖）和 `/readyz`（查依赖）要分成两个接口：
> **进程活着和系统可用是两件事。**
