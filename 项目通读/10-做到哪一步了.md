## 2. 本次（2026-10-16 → 10-17）修掉的真缺陷 —— 面试里最值钱的一段

> 一共 **六个**真缺陷，全都是「不报错、不失败、**功能等于不存在**」那一类，
> **全都躲过了当时全绿的 1370 条单测**。前两个在执行链上（§2.1），
> 中间两个在监督链上（§3.1），最后两个是本次新写的那半条链上的（§2.2）。

### 2.1 执行链上的两个

be-14 的测试文件写完时留下了两个 `xfail`，我先当成「测试写法问题」，
**实测之后确认两个都是真缺陷**，都修在**坑源**而不是调用点：

**缺陷①　`get_run` 把 `seatunnel_job_id` 传了两次 → 四条主路径全 500**

```python
return RunDetail(
    **summary.model_dump(),      # ← 这里面**已经**有 seatunnel_job_id
    capability_id=row.capability_id,
    seatunnel_job_id=row.seatunnel_job_id,   # ← 再传一次 = TypeError
```

`RunSummary` 与 `RunDetail` 共有那几个字段，`model_dump()` 展开后重复传参 → `TypeError`。
**炸的不是边缘路径**：`commit`（提交执行）、运行详情、`pause`、`cancel` **全部 500**。
更糟的是**副作用已经落库**（运行记录、账本、Outbox、Capability 都写完了），
用户看到「操作失败」、库里躺着一次真实运行——**报错的方向和事实相反**。

**缺陷②　`apply_transition` 末尾的 `session.refresh(row)` 会吃掉失败现场**

`tasks/execution._fail` 的形状是「先把 `error_message` / `failure_snapshot` 赋在 ORM 实例上，
紧接着调 `apply_transition` 把状态推成 failed」。而 `apply_transition` 末尾有一次
`session.refresh(row)`（按主键重读整行），**它会丢弃尚未 flush 的属性改动**
（实测：`row.error_message = "x"` 之后 `refresh` → 变回库里的旧值；会话是 `autoflush=False`）。

结果：运行**确实**变成 failed，**失败现场却是空的**——详情页 `error_message` 为 null、
`failure_snapshot` 为 `{}`，而账本里那条 `run.failed` 又写着「失败了」。
**「有结论、没原因」的失败**是排查时最容易被带偏的一类。

**改法**（[services/run.py:334](../backend/services/run.py#L334) 起）：
成功路径不再 `refresh` 整行，而是把**刚写下去的那几个字段**赋回内存实例
（值就是我们自己写进去的，准确且省一次回读）；抢锁失败那条路径**只读状态列**，
不碰整行。我一开始的改法是「动状态前先 `flush()`」，但被项目自己的守卫拦下了——
`tests/test_service_commit_boundary.py` 规定「`services/` 里**公开**函数只要会写就必须自己 `commit()`」，
而 `apply_transition` 是**故意不提交**的（事务边界归调用方：worker 的 `session_scope`、
API 侧 `pause`/`cancel` 各自提交）。**守卫逼着我去掉 `refresh` 而不是加一次 flush**，
而结果更好：修掉的是「任何调用方暂存的改动都会被吃掉」这一类，而不是 `_fail` 这一处。

> 附带收获：`session.flush([row])` 在 SQLAlchemy 2.x 里已弃用（`SADeprecationWarning`），
> 我是在把 `-W error::DeprecationWarning` 打开跑全量时发现的。

### 2.2 本次新写那半条链上的两个（**最新，也最典型**）

be-17（质量分流）与 be-18（原子发布）是同一批落地的，写完之后单个模块各自全绿，
但**两个模块都没能真的跑起来**。两个缺陷长得很像，都是「**具名参数少传一个**」：

**缺陷③　worker 侧的 `ToolBroker` 没有校验公钥 → 四个工具在 worker 里一步都过不去**

```python
# backend/tasks/execution.py（修之前）
return ToolBroker(guard=_build_guard(), ledger=_ledger)     # ← 少了 verifier
```

[harness/broker.py:294](../backend/harness/broker.py#L294) 的第 ③ 步是「验签」，
它在 `self._verifier is None` 时**直接拒绝**，而拒绝文案是
**「本进程未配置 Capability 校验公钥」（`INTERNAL_ERROR`）**——读起来像一次部署配置问题，
实际是「这个进程永远不可能执行任何带 Capability 的工具」。
worker 里要通过 broker 执行的是 **`seatunnel.submit` / `seatunnel.stop` /
`target.publish_swap` / `target.rollback_cleanup` 四个**，也就是说
**整条执行链一步都走不了**，而单测全绿：单测用的是**绕过七步序**的假 broker。

修法：把「公钥路径 = 私钥路径换个后缀」这条推导**只留一份**
（[harness/capability.py:321](../backend/harness/capability.py#L321) 的 `verifier_from_settings()`），
`services/publish.py` 与 `tasks/execution.py` 都调它。守它的用例是
`tests/test_finalize.py::test_worker侧的broker带得上Capability校验公钥`——
它不只断言「属性不是 None」，而是**拿同一把密钥签一张令牌，验签必须过得去**。

**缺陷④　`_submit` 把 `actor_id=None` 传给执行上下文 → 第 ④b 步拒空主体**

第 ④b 步（绑定比对）要求 `ctx.actor_id` 非空，否则
`UnauthorizedToolError: Capability 执行缺少操作主体`。`_stop` 早就修过同一个错
（主体的来源是 Outbox 载荷里的 `subject_id`——**取消作业的人 ≠ 发起作业的人**），
但 `_submit` 漏了。**同一个坑的两种正确解**是这次最值得讲的一点：

| 工具 | 主体从哪来 | 为什么 |
|---|---|---|
| `seatunnel.submit` | `run.triggered_by` | 提交令牌签给的就是这个人，运行行上记着同一个值 |
| `seatunnel.stop` | Outbox 载荷的 `subject_id` | 操作员取消时，回落到 `triggered_by` 会把账记成「发起人要停」 |
| `target.publish_swap` | 调用方（`ctx`） | 发布由发布服务签发并立即使用，主体就是发起发布的那个人 |
| `target.rollback_cleanup` | 账本里 `rollback.started` 的载荷，回落到 `run.triggered_by` | 回滚可能由定时对账触发，那时没有「当前用户」 |

三个来源**都是对的**，因为 broker 的判据始终是**「ctx 里的主体 == 令牌里签的主体」**——
令牌是谁签的，主体就得是谁。这条我写进了 [tasks/execution.py](../backend/tasks/execution.py) 的注释里。

**缺陷⑤（同一个模块，另一个形状）　质量报告的读取器注册成了进程级单例，而端口只拿到表名**

be-17 定义的端口 `ErrorTableReader` 全是「表名进、计数出」的方法
（[engines/quality/ports.py](../backend/engines/quality/ports.py)），
而**光有表名定位不到主机与库**（影子表名还会跨运行复用）。
所以注册的不能是一个进程级单例，必须是一个**工厂** `(session, run) -> reader`：
运行行才带着目标数据源的引用。这是我 review 时发现「这个注册接口在物理上无法实现」而改的，
改完顺手把那条「未注册就拒绝、绝不降级成全 0」的纪律也守住了——
**0 是一个完全合法的报告值**，降级成 0 会让一次连不上的运行产出一份「干净」的报告，
然后被拿去换表（[services/quality.py](../backend/services/quality.py)）。

**缺陷⑥（测试侧）　执行器注册表是跨文件的隐式状态，让「文件执行顺序」决定红绿**

`tests/test_harness_broker.py` 的假执行器夹具里有一句
`if registered_executors(): return`（「别人注册过就整体跳过」）。
新写的 `tests/test_finalize.py` 要走**真的** `target.publish.swap`，于是它先注册了真执行器，
那句守卫就因为**在别的文件里**注册过而跳过——本模块的 `seatunnel.submit` / `metadata.probe`
变成「未注册」，四条用例红。**单跑绿、同跑红**，而且报错信息指向与本模块毫不相干的东西。
修法是让那个夹具把注册表**换成本模块私有的空表、跑完还原**（`monkeypatch.setattr(harness.tools, "_EXECUTORS", {})`），
把跨文件的隐式事实变成局部状态。

**这段的统一讲法**：六个缺陷里有四个是**「闸门的判据缺失/错位」**——
阈值维度的来源字段不存在（放大比）、要验签的进程没拿到公钥、
要绑定主体的调用没给主体、要定位目标库的端口只拿到表名。
它们**都不会抛异常、不会让测试变红**，只会让某个功能**悄悄地永不生效**。
所以我现在对这类代码的问法固定是两句：
**「这个判据的输入从哪来，那条路径真的会填它吗？」** 和 **「这段代码真跑一次会怎样？」**

## 3. 🟢 代码与单测齐（真库未跑过）· be-16 运行监督与硬中断

**要做什么**（设计意图）：作业跑起来之后，按周期抄 SeaTunnel 的指标（读/写行数、字节数、
拒绝行数、时长）→ 对照**冻结时那份** `runtime_supervision_contract` 的阈值 → 越界就**硬中断**
（签发一张只能用一次的 Capability 去停作业、把运行置 `interrupted`、写账本、出告警）。
PRD 里「脏数据超限硬中断 + 受管回滚」那个演示场景靠它。

**证据等级**：代码 + 单测齐（`tests/test_supervision.py` **71 条**、`tests/test_seatunnel_metrics.py` 8 条），
接口与任务都挂好了（beat 每 30 s、Outbox topic `etl.run.supervise`），
但 **`execution_metric` / `outbox_message` 都是 0 行**——这条环在真机上一次都没跑过。

### 3.1 这一块里我修掉了两个**「配着、绿着、永不生效」的哑闸门**

两个都不报错、都有用例、单测全绿，**功能等于不存在**：

1. **放大比维度永远开不了火**。[clients/seatunnel/models.py](../backend/clients/seatunnel/models.py) 的

   而 [services/supervision.py:209](../backend/services/supervision.py#L209) 干脆硬写 `read_bytes=None`
   → 放大比恒判 `unknown`。它唯一拦得住的是**笛卡尔积式的 join 写错**：不涨行数、不涨拒绝率，
   只涨写出去的字节量。修法：DTO 加 `read_bytes`、客户端解析并按候选键名容错、

   在 BINDING 阶段就拒空 actor → **人工取消与监督硬中断两条 `seatunnel.stop` 路径同时是死的**。
   单测看不出来：假 broker 不走那七步。修法是让主体**随 Outbox 载荷**走到 Worker
   （`subject_id`，与令牌里签的同值），而不是在 Worker 侧回落到 `run.triggered_by`——
   操作员取消时那会把账记成「发起人要停」。

### 3.2 与设计文档的四处偏差（追问「为什么和文档不一样」时答这个）

1. **停止动作不由监督模块直接执行**，而是签 Capability 随 Outbox 投给 Worker。因为监督跑在 Worker 里，
   而 Worker 的 broker **刻意不带签发器**——自建一个带签发器的 broker 等于给「被攻陷的 Worker」发签名能力。
   代价：库里的 `interrupted` 先于作业真的停下，中间态用 `failure_snapshot.needs_manual_stop` 显式暴露。
2. 事件的 `subject_type` 用 `"run"` 而不是设计写的 `"execution_run"`：`services/governance.py`
   把 `execution_run_id` 过滤映射成 `subject_type="run"`，用设计值则这些事件在运行时间线里**一条都看不到**。
3. `interrupt_run` 收 `DimensionVerdict` 而不是 `Dimension`：失败现场要记 `observed`/`limit`/`ratio_pct`，
   只传维度名会逼出第二处重算。
4. `stop_ok` 的语义收窄为「命令已进 Outbox」，**不表示作业已停**——真的停下由
   `capability.consumed` / `run.stopped` 两条证据证明。

**还没做的**：指标的**时序折线**没有 HTTP 出口（只在前端拿到的
`RunDetail.metrics` 汇总 + 失败快照里的最后 20 个点里），设计上归 be-21；
`execution_metric` 缺 `(run_id, ts)` 唯一约束；SeaTunnel 指标端点与键名都未经真机验证——
**若 Zeta 不提供 `job-metrics`，读行数/写字节/放大比三维将长期 `unknown`**。

`render_route_selects` 产出的两条 SELECT（有效行进影子表、违规行进错误表）

所以真跑起来时，违规行会跟着有效行一起进影子表；质量报告读错误表会读到 0 行，
**报告看起来「非常干净」**——这是这个项目里最危险的一类错：不报错、结果不对。

### 4.1 🔴 硬伤 A：分流没有接线（现状 / 为什么 / 怎么改 / 怎么验）

**① 现状（可核查，不是猜）**

**为什么单测没抓住**：所有用例都是**直接调** `render_route_selects(...)` 断言 SQL 文本，

两个模块各自全绿，中间那条线不存在；测试天然只测「我这个函数对不对」。

**② 为什么不能「在渲染时就把 run_id 写进去」**

制品是**冻结时**渲染的、不可变的；`run_id` 是**提交时**才产生的。若把 run id 写进 HOCON：
- 同一份版本每次运行都得重新渲染 → 制品哈希每次不同 → 「审批过的就是执行的」这条链断掉；
- 若反过来用固定值，两次运行的错误行会混在一起，质量报告按 `run_id` 计数就对不上。

所以正确的形状是：**制品里留一个「运行期令牌」字面量，执行时由 Worker 替换**——
和 `{{secret:1:password}}` 同一套思路，只是来源不同（密钥来自 Vault，运行期事实来自
`execution_run` 那一行）。

**③ 怎么改（六步，按顺序做）**

| 步 | 改哪 | 做什么 | 为什么必须是这一步 |

**④ 一个必须先验证的外部事实（决定第 4 步的形状）**

SeaTunnel 2.3.9 的 `Sql` 插件**是否支持一个 transform 产出多张结果表、多个 sink 按
`source_table_name` 分流**，我没有真机验证。两种写法选一种，**先验证再写死**：

验证成本很低：起 Zeta，把两条 SQL 各提交一次看状态机。**在这一步验证之前，不要在文档里
写「分流已实现」**——这正是本页维持 🟢 的原因。

### 4.2 🔴 硬伤 B：脱敏断言的正则和数据面掩码「不是同一个形状」

**现状**（两处定义，各自都对，合起来必错）：

- 兜底起草器给敏感列加的规则是
  `^[a-z_]+:[0-9a-f]{12}$`（[engines/plan/draft.py:172](../backend/engines/plan/draft.py#L172)），
  注释说这是「engines/masking 的脱敏口径」——那是**探查期 Python 掩码**的产物，
  形如 `phone:3f2a1b4c9d0e`；
- 而数据面渲染出的掩码是
  `CONCAT(LEFT(x, 2), '****', RIGHT(x, 2))`（[engines/hocon/render.py:120](../backend/engines/hocon/render.py#L120)），
  形如 `13****01`。

**后果**：一旦某条流水线含敏感列，分流接线之后**每一行**都会命中
`E_SENSITIVE_PLAINTEXT`——而按 be-17 的 `hard_block_codes` 定义（设计文档第 257 行）这个错误码是**零容忍**的，于是
「数据其实已脱敏」被当成「明文泄漏」，运行直接硬中断。现在没炸，只是因为分流没接线
（硬伤 A）——**两个缺陷刚好互相掩盖**，这是最典型的「都在绿着，凑一起才错」。

**怎么改（推荐做法，不是唯一）**：

1. **让形状只有一份定义**。在 `engines/masking` 里加 `mask_sql_pattern(method)`，
   `render._masking_expr` 与起草器的规则**都从它取**；`mask_middle` 对应的正则就是
   `^..\*{4}..$`（先按长度参数算，`hash`/`truncate` 各自一条）。这和
   `error_table_name`（[services/pipeline/parts.py:40](../backend/services/pipeline/parts.py#L40)）
   遵循的是同一条规矩：**同一个语义只准有一份实现**。
2. **更根本地问一句「这条规则该不该存在」**：be-17 第 331 行写的是
   `E_SENSITIVE_PLAINTEXT` 由 **P0 门禁**产出，不是字段规则。字段规则拦的是「行级数据违反契约」，
   而「明文有没有出域」是**制品与映射的属性**，在门禁阶段就能判定。若采纳这条，
   起草器**不该生成**这条 regex 规则，改由门禁在冻结前检查「敏感列是否带 mask 变换」。
   **我的取舍**：保留字段规则（防运行时漏配），但正则必须由渲染器同一份定义推导；
   同时在门禁侧补一条静态检查。两条闸判两件事，和 `assert_no_unresolved_tokens` /
   `secret_token_problems` 的关系一模一样。

**怎么验**：构造一条含 `phone` 列的同步，跑一次分流，断言错误表 0 行；
再用一条「故意去掉 mask」的计划，断言错误表 100% 行——一正一反才算验过。

### 4.3 🟡 硬伤 C：两处渲染器缺陷（本轮已改，但没在真 SeaTunnel 上验证）

| 缺陷 | 改法 | 证据 |
|---|---|---|

一个报表不存在），所以面试时值得单独讲：**单测断言的是「渲染出了什么字符串」，
不是「SeaTunnel 认不认这个字符串」**。

### 4.4 🟡 硬伤 D：Doris 侧两个没核过的假设

| 假设 | 风险 | 核法 |
|---|---|---|
| `CREATE TABLE shadow LIKE formal` 在 Doris 上可用 | Doris 的 `LIKE` 语法与 MySQL 不完全一致，且主键模型可能不复制 | 起 Doris 后执行一次 `SHOW CREATE TABLE` 对比 |
| `wire._PK_SQL` 通过 `constraint_name = 'PRIMARY'` 取主键 | Doris 的 information_schema 里主键约束名可能为空 → 指纹退化成空主键 → 发布前对账「看着一样」 | 在 Doris 上查 `information_schema.table_constraints`；取不到时必须**判 unknown 并拒绝发布**，不能 default 成空 |

这两条不改代码也讲得清：**目标端的「我不知道」必须映射成「拒绝」，不能映射成「没问题」**——
和 §3 里 `read_bytes` 拿不到就判 `unknown` 是同一条判据。

### 5.1 本次新增：`services/finalize.py`（把这条链的两端接上）

**为什么需要它**：be-17 §5 把「报告合格之后投递 Swap」划给发布侧，
be-18 §5 把「跑完且报告合格」划给执行编排——**两份设计各自指向对方**，
于是 `finalize_report` 与 `publish_run` **两个函数的调用方数量都是 0**。
症状是：作业跑完 → 没有人出质量报告 → `quality_report` 永远 0 行 → 正式表永远不换。
这不是 bug，是**两个模块之间的缝没人认领**。

收尾编排（[services/finalize.py](../backend/services/finalize.py)）读**一次**数据面状态，
按事实把运行推到结论：

```
beat 每 40 s → tasks.execution.scan_finished_runs → list_pending_run_ids()
                                      ↓ 逐个
                     sync_run_outcome(run_id)
   ┌──────────────────────┬───────────────────────┬──────────────────────┐
   │ 作业 finished        │ 作业 failed           │ stopped / not_found  │
   │ ↓ 出质量报告         │ ↓ 判 failed + 现场 +  │ ↓ **不动状态**（orphaned）│
   │ 合格 → 原子 Swap →   │   账本（只记分类，     │   只告警 + 留痕      │
   │        run=succeeded │   不记原文）          │                      │
   │ 不合格 → run=failed  │                       │                      │
   └──────────────────────┴───────────────────────┴──────────────────────┘
```

四条纪律（都在模块 docstring 里）：

1. **只在 `running` / `interrupted` 上推进**（`queued` 作业还没起来、`paused` 正在写影子表、
   `rolling_back` 世界正在被改写——这时算出来的结论都不算数）；
2. **中断的运行永不发布**（两道判据：be-17 的报告在 interrupted 时强制不合格 +
   收尾侧的 `allow_publish=False`。硬中断意味着影子表里是**半份数据**，
   把它换到正式表上比不发布坏得多）；
3. **查不到作业不改控制面状态**（`orphaned`）：可能是人工 kill、可能 SeaTunnel 重启丢内存态、
   也可能别人正在取消（状态还没落库）。一律写 `failed` 会让「谁停的」**永久失去答案**；
4. **失败不搬原文**：SeaTunnel 的失败文本常带整段配置与连接串，只留 `classify_failure` 的分类。

**为什么用 beat 扫描而不是 Outbox**：扫描**每轮都会重新发现**同一个待办
（`list_pending_run_ids` 的过滤条件就是判据本身），所以丢一次投递不会永久丢失；
反过来，走 Outbox 就得让「谁发现作业跑完了」也变成一个需要持久化的状态。
收尾任务本身也**幂等**（下游 `uq_quality_report_run_id` 与 `swap.*` 事件短路保证）。

**证据等级**：`tests/test_finalize.py` **25 条**，其中一条是**真的走发布**
（内存假发布器 + 真执行器 + 真状态机）：跑完 → 报告合格 → 指纹互换 → `succeeded`，
并且断言**副作用只发生一次**（重复扫到第二次是空操作）。但——
**同样没在真 Doris 上跑过**（本机没有 Doris，ECS 上没起 `demo` profile）。

## 9. 面试里怎么用这一页（三道必答题的现成答案）

**「这个项目做完了吗？」**

> 没做完，而且我能一句话说清做到哪：**「一句话需求 → 生成 → 审批 → 执行 → 监督 → 分流 → 发布」
> 这条链的代码第一次全部接上了，但它在真基础设施上一次都没跑过**——
> `preparation` / `execution_run` / `quality_report` 这些表到现在都是 0 行。
> 说细一点分三段：① **生成段**（需求 → 澄清问答 → EtlPlan/HOCON → 确定性门禁 → 不可变版本冻结）
> 我**端到端真跑过**，就在真 PG 上，库里 5 个冻结版本、5 份制品就是证据。
> ② **审批与执行段**（准备单 → 两个不同的人审批 → 签发一张只能用一次的 Capability → 进执行队列）
> 代码与单测都在、接口也挂上了（`/preparations`、`/runs`、`/runs/{id}/rollback` 都在 openapi 里），
> 但我没有浏览器、也没有当初那个登录口令，所以**真库上一次都没执行过**，这是物证。
> ③ **监督 / 分流 / 发布段**是我这次补完的：指标抄取与硬中断、错误行只存摘要的质量分流、
> 原子 Swap 与受管回滚，加上一个把两边接起来的收尾编排。
> 这一段的特别之处是：**两个模块各自写完、各自全绿，但谁都没有调用方**——
> 两份设计各指向对方，缝里没人，所以作业跑完永远不会出质量报告、报告合格也永远不会换表。
> 我补的不是功能，是**那条缝**。补完我验到的是「单测 1407 条全绿 + 一条真的走发布的集成用例」，
> 但**没验到**「真 Doris 上换表成功」——那需要起数据面，我没起。
> ④ 而且**同一条缝还剩最后一根线没接**：分流的控制面（路由 SQL、错误表、质量报告）都写完了，
> 但渲染器还是单源单 sink，`render_route_selects` **没有一个生产调用方**。
> 也就是说现在跑起来，违规行不会被真的分出去，报告会显示「0 条错误」——**看起来干净，其实没分流**。
> 改法我已经固定下来了（§4.1）：加一类运行期令牌 `{{runtime:run_id}}`、渲染成
> `tagged → valid/rejected → 双 sink`、执行器替换令牌并放行错误表。
> 我没现在写，是因为它影响**所有**流水线，而 SeaTunnel 多结果表的写法没真机验证——
> 在这种环境里凭想象写渲染逻辑，正是这个项目已经踩过四次的那类坑。

**「那你凭什么说这条链是通的？」**（追问，一定要准备好）

> 三层证据，一层比一层弱，我会把弱的那层自己说出来：
> ① **单测层**：整条链的状态分支都有一条用例，其中发布那一段用的是**内存假发布器 + 真执行器 + 真状态机**，
> 断言的是**目标端的物理形态**（两张表的指纹互换）而不是服务自报的字段——
> 因为「我发布了」这句话能骗过断言，骗不过指纹。
> ② **接线层**：应用真的起来了——API 和 worker 的启动日志里各有一行
> `quality_error_table_reader_registered`，`/readyz` 的 redis 与 postgres 都是 ok，
> worker 的已注册任务里有三个新的收尾任务。接线的错法是「运行时才 500」，
> 所以这一层必须真的启动一次才算验过。
> ③ **没验的那层**：真 Doris 上的 `REPLACE WITH TABLE` 到底通不通、SeaTunnel 的指标端点
> 到底叫不叫 `job-metrics`、错误表的真实列名——这三件我**都不知道**，因为本机没有数据面。
> 面试官如果继续问「那你怎么办」，我的答法是：把「不确定性」收敛到**可替换的一层**——
> 目标端所有动作都走 `ToolBroker` 里注册的执行器，数据面所有读取都走一个专门的端口/函数
> （`_status_reader` / `ErrorTableReader` / `build_publisher`），所以换成真引擎时**只动那一层**。

**「你觉得哪里做得不好？」**（诚实 + 有反思，比吹「都做完了」可信）

> 四处。① **六个缺陷里有四个是同一类**（§2）：判据的输入不存在或错位，
> 于是某个功能**悄悄地永不生效**——放大比没有来源字段、worker 的 broker 没有公钥、
> 提交没给主体、质量读取器的注册形状在物理上无法实现。
> 它们全都躲过了当时全绿的 1370 条单测，因为**假替换品比真实现宽松**：
> 假 broker 不走七步序、假读取器不需要定位主机。我现在的做法是**每修一个就在真路径上加一条断言**
> （比如「worker 的 broker 要能验签」这条，是从真实现出发验的，不是从假件出发）。
> ② 遗留 4 张**零引用**的表（benchmark 三张 + `login_attempt`），外加 `evidence_ledger_block`
