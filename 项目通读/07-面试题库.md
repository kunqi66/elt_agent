## 必答 1 · 一句话说清这个项目是干什么的

**口述稿（约 3 分钟，照着念）**

> 「它是一个**数据同步作业的治理与执行平台**。解决的场景是：
> 业务方要用一句人话把 MySQL 里的两张表合成宽表同步到 Doris，
> 传统做法是人手写配置文件再让人去执行——
> **谁改的、谁批的、凭什么让它动生产数据，全靠人的自觉。**
>
> 我的做法是把『**不可信的部分**』和『**不可商量的部分**』用一道确定性的墙隔开：
> 大模型只负责**起草**作业计划，而『这个变更有多危险、要不要两个人批、能不能执行』
> 全部由**纯规则的代码**判定，每一步都留**哈希链证据**。
>
> 整条链是：自然语言 → 结构化作业计划（EtlPlan）→ 渲染成 SeaTunnel 的 HOCON 配置
> → 确定性门禁 → 冻结成不可变版本 → 双人审批 → 签一张**一次性执行令牌** → 执行到影子表
> → 质量校验 → 原子切换 → 全过程写账本。
>
> **整条链在代码上现在第一次全部接上了。** 生成链路是一个 10 节点、15 条边的状态机：
> 意图解析 → 参数检查 →（缺参数就）交互式澄清 → 元数据绑定 → 生成方案 → 渲染 HOCON
> → 门禁 → 最多 3 轮自动修复 → 冻结版本 → 终局。
> `backend/workflow/` 3,538 行、`backend/services/pipeline/` 3,016 行；
> 门禁是 5 类检查按固定顺序短路；制品指纹由 5 个部件拼出来，有一个**金值哈希**钉在用例里。
> 全仓 **1073 个测试函数 / 1410 collected**（`uv run pytest` 实跑 **1407 passed, 3 skipped**、**0 xfail**）——
> 说明一下：**这几个数字是我写这份文档那天的快照**，还在并行加用例，它会继续涨。
> 而且不是「只收集没跑」——**生成这条链我今天在本机端到端跑通了**（真后端 + ECS 上的真库，一句需求 → 5 问 → 冻结）。
>
> **M3 的两半（审批与执行、监督与发布）也都落地了**：`POST /api/v1/runs`（= Commit）会把一张**审批通过**的准备单变成一条排队中的运行——
> 先签发一张**只能用一次**的 Capability、同事务写 Outbox；worker 取消息、验签、用 Redis `SETNX` + 数据库条件 UPDATE **原子消费**这张票，
> 再经 `ToolBroker` 调 SeaTunnel 提交作业；`/preparations`、`/runs` 这些端点都真的挂出来了（未登录是 401，不是 404）。
> 执行之后的那半段也齐了：运行监督与硬中断（`engines/supervision/` 473 行 + `services/supervision.py`）、
> 质量契约与数据分流（`engines/quality/` 1,837 行 + `services/quality.py` + `clients/target/errors_table.py`）、
> 影子表原子发布与受管回滚（`services/publish.py` 1,525 行 + `clients/target/executor.py`）都从「未实现」变成了「代码 + 单测齐」，
> `/runs/{id}/publish`、`/runs/{id}/rollback`、`/runs/{id}/quality-report` 也挂出来了（未登录 401，不是 404）。
> 把这两半缝起来的是一份**收尾编排** [backend/services/finalize.py](../backend/services/finalize.py)（354 行）：
> 此前 be-17 和 be-18 两份设计**各自把「报告合格之后谁去换表」划给了对方**，于是 `finalize_report` 与 `publish_run`
> **两个函数的调用方都是 0**——作业跑完永远不会出质量报告，报告合格也永远不会换表，**而两边的单测都是绿的**；补上的就是那条缝。
> 所以「一句话生成一条作业、两个人批了、签票提交、跑起来被监督、脏数据分流、原子切换」这条链，**代码上是通的**。
> **但它在真基础设施上一次都没跑过**：真 PG 里 `preparation` / `execution_run` / `quality_report` **全是 0 行**，
> 它的证据等级是「单测 1407 条全绿 + ruff 全绿 + 端点 401」，**不是「跑通了」**。
>
> 演示口径上我要如实交代三条边界，因为**这三条我自己心里很清楚**：
> 一是我在本机跑的是**确定性假 Provider**（`LLM_PROVIDER=fake`）——真 DeepSeek 那条**没跑过**，
> 本机没有 key。而且我们是**刻意不做静默降级**的：配了 deepseek 却没 key 会显式报 `LLM_UNAVAILABLE`（503），
> 绝不会偷偷换成假模型。因为静默降级会让『线上 key 配错了』表现成『方案质量突然变差』，
> 而前端和审计里一点痕迹都没有——那是这个项目最想防的一种错。
> 二是 **M2 的 Checkpoint 是真落 PostgreSQL 的**，而且**我今天在本机端到端跑通过一次**
> （真后端 + ECS 上的真 PG/Redis/Vault/MySQL，经隧道）：一句需求 → 5 个澄清问题 → 冻结，
> 重复冻结 409。不过要说清级别：**只覆盖了 happy path（门禁 `conclusion=pass`）**，
> `block → autofix` 那几支仍是单测 / 代码级验证。
> 三是**目标端的 Doris 在我的本机演示环境里没有起**（compose 里 mysql / doris / seatunnel 都在 `demo` profile 下），
> 所以**我只连过源端 MySQL，目标端连通性从未验证过**。
>
> 这个顺序是我故意的：**先把不可商量的部分做扎实**——安全内核（密钥、账本、原子消费）
> 和生成链路（声明式制品 + 确定性门禁），**再往上接审批、执行、监督与发布**。
> 理由是两个验收标准不一样：**生成链路会随需求反复变，判定与留痕不会**；
> 而契约又先冻结了（32 张表、前端 16 个页面都是照它建的），所以接后面几段时不用返工。
> 代价我也认——**演示链路代码上已经能跑到『提交执行 → 监督 → 分流 → 原子切换』，
> 但数据面没起（ECS 上没开 `demo` profile）、整条执行链在真库上 `preparation` / `execution_run` / `quality_report` 全 0 行、
> 我还没有浏览器一次都没在页面上点过**。」

## 必答 2 · 你负责哪部分、最难的地方是什么

**口述稿（主体约 3 分钟；后面几个加粗小标题都是「被追问时再展开」的延伸，不要一口气全念完）**

> 「我负责的是**后端全部**：M1 那条业务闭环（登录、多租户、数据源、元数据探查与脱敏、证据账本），
> 加上 **M2 的生成链路**（LangGraph 状态机、EtlPlan 与 HOCON、确定性门禁、有限自动修复、版本冻结与 Diff），
> 再加上 **M3 的治理链路**（准备单与四眼审批、执行编排与单次令牌、运行监督与硬中断、质量分流、影子表原子发布与受管回滚）。
> 前端是另一位同事在做，安全内核是我做的。
>
> 最难的地方我想讲两层：**一层是设计上的难，一层是只有真机才暴露的坑。**
>
> **设计上最难的不是『怎么调模型』，是『怎么不让模型乱来』。**
> 第一，我不允许模型输出自由文本：它必须吐一份被 Pydantic 约束住的 `EtlPlan`；
> 第二，拿到 Plan 之后跑一遍纯函数结构校验，它**返回问题清单而不是抛异常**——
> 抛异常等于把『可修』直接判成『死』，而清单正好是下一轮修复的输入；
> 第三，真正的兜底不在模型那一侧，在它下游那道**确定性门禁**：5 类检查按固定顺序短路，
> 拿的是档案里的**真实列**去比 Plan 的引用。门禁是纯函数，模型、时间、随机数都进不去——
> **风险评级绝对不让大模型参与**，这是我在这个项目里最坚持的一条线。
>
> **真机才暴露的坑里，最省事也最贵的一个是『应用一启动就退出』。**
> 现象是：我把控制面在本机起起来，**进程直接就没了**，连『监听 8000』那行日志都没有。
> 我的第一反应是『PostgreSQL 连不上』——因为 PG 在阿里云 ECS 上，中间是一条 SSH 隧道。
> 我查了隧道、查了容器、查了口令，全是对的。
> 真因其实就写在报错里：`Psycopg cannot use the 'ProactorEventLoop' to run in async mode`。
> Windows 上 `asyncio` 默认给的是 `ProactorEventLoop`，而 psycopg 的异步模式不接受它。
> 更绕的是**修法的位置**：在被 import 的模块里设事件循环策略是**无效**的——
> uvicorn 的 `Server.run()` 会**先把循环建好**，之后才去 import `main:app`，
> 所以你写在 `main.py` 顶层的那一句根本来不及执行。
> 最后的做法是给出一个 `loop_factory`，在**建循环那一刻**就决定用哪个（Windows 用 `SelectorEventLoop`）：
> 本机的启动脚本走它，容器里继续用 `uvicorn main:app`；
> 顺带在 Windows 上**显式拒绝 `--reload`**——reload 的父进程不经过我的工厂，会以同样的方式静默退出。
>
> 这件事让我总结出一条：**『某个模块没被加载』和『循环类型不对』这两种错，症状几乎一模一样——
> 应用启动即退出、栈里没有一行业务代码。** 所以我在注释里把这两件事写在一起，免得下一个人再去查半小时网络。
>
> **还有一个更安静的坑，属于『报的错指向别处』那一类**：
> 往 State 里注入一个 schema 没声明的键，报出来的错会是业务语义的
> 『**需求描述不能为空，无法生成方案**』——而用户明明填了需求。
> 真因是 **LangGraph 只为 schema 里声明过的字段建通道，没声明的键被静默丢掉**，
> 节点读到的就是缺省值。**真因和症状之间隔了一整个模块。**
> 这个坑我核过**两个方向都上了守卫**：一条用例走真图证明「未声明的键确实会被丢掉」，
> 另一条用 AST 读编排层的源码，断言「它注入的键全都声明过」。
> 而第二条守卫的由来是一处真实的键名漂移——编排层注入 `user_id`，State 上却写着 `subject_id`，
> 名字不一致时键就被丢掉，账本里的操作者会恒为默认值、**而且不报错**（细节见 [08 故事 8](08-面试故事.md)）。
>
> 现在讲那个跨了三层的故障——
>
> **现象**：我做了个连通性测试的接口，前端点一下、轮询结果。
> 开发时是好的，后来有一次测试**永远停在 pending**，前端一直转圈。
>
> **定位**：接口和 worker 都没报错、进程都在、日志里业务信息一切正常。
> 最后在 worker 日志最下面翻到一句
> `Error 22 while writing to socket`——**Redis 连不上了**。
>
> **为什么它不恢复**：我们的 Redis 客户端是**单例**，跑在 worker 那个**进程级复用的事件循环**里，
> 而且客户端**默认不做连接健康检查**。
> 中间那条连接是在我**重启 SSH 隧道**的时候断的，
> 之后每一次请求都复用那条死连接——**永远不会被换掉**。
> 数据库那边反而没事，因为 SQLAlchemy 我们开了 `pool_pre_ping`，
> 每次取连接会先探一下；**而 Redis 客户端默认没有等价机制**，这是同一个坑的两个面。
>
> **试过什么不行**：第一反应是『重启一下服务就好了』——
> 那是把运维当修复手段，故障会以『偶发』的形式长期存在，所以我没停在这里。
> 也想过加大 `pool_recycle`、调超时，那些都是治症状。
>
> **最后怎么解决**：显式给 Redis 客户端开
> `health_check_interval=30`＋重试，并且**明确列出重试覆盖哪些异常**——
> 不覆盖连接错误等于配了个空重试。
> 然后我加了一条**断言配置本身**的回归用例，
> 因为这类参数**删掉不会报任何错、本地也复现不出来**，只有在连接被中间设备掐断时才现形；
> 我还在注释里把这段经过写清楚了，免得后人当成『多余的一行配置』删掉。
> 同时在项目的行为准则里加了一条，标明症状是『服务活着但再也不干活』。
>
> **验证**：改之前它稳定复现（连续几次都卡 pending），
> 改完重启 worker 后连跑成功，`succeeded | 357ms`，服务端版本 `8.0.27`。
>
> 这件事让我总结出一条：**这一类系统的难点，往往不在算法，而在
> 『不报错但结果不对』——服务活着、日志正常、测试全绿，但功能已经死了。**
> 所以我在这个项目里专门留意这一类坑，比如返回给前端的结论字段有个白名单，
> 少登记一个键，连通性明明成功却会显示 failed，**只有一行 warning**。」

**如果面试官想听「测试/质量」方向的难点**（第二好用的故事，同样真实）：

> 「交付当天我跑全量测试，发现**两条用例红了，而上午它们还是绿的**，
> 而且我改的东西跟它们完全无关。
> 查下来是这样的：fixture 里有一条事件是走服务代码落的，用的是**真实当前时间**；
> 而用例里被过滤的事件用的是**硬编码的时刻**，过滤条件只给了**下界**。
> 于是这条用例是否通过，取决于**跑测试时候的真实钟点**——
> 真实时钟一旦越过那个硬编码时刻加 1 分钟，那条事件就混进结果，
> 用例永久变红。**它在 16:01 那一刻过期了。**
> 修法是两端都夹住，让真实时间的那条事件无论在哪个钟点跑都被排除；
> 我还顺手查了同类写法，发现另一条用『基准时间 + 365 天』做下界，
> 是**一年后才会引爆**的同一颗雷，一起堵了。
> 修完复跑全绿；我把这条成因写进了项目的行为准则，
> 因为**它的表现是「跟你改的东西无关的用例突然红了」，最容易让人误判成自己引入了 bug**。」

**如果面试官想听「为什么单测全绿、产品却是错的」**（这是我在这个项目里最想讲的一类判断力）：

> 「补 M3 后半段的时候，我一口气修掉了**四个同类的真缺陷**，它们**全躲过了当时全绿的 1,370 条单测**。
> 之所以是我自己找出来的，是因为我逼自己问了一个问题：**『这个判据的输入从哪来，那条路径真的会填它吗？』**
>
> **遇到什么**：我先把运行监督、质量分流、原子发布三块从设计落成代码，再补一份收尾编排
> [backend/services/finalize.py](../backend/services/finalize.py) 把「跑完了 → 出报告 → 合格就换表」这条缝缝上；
> 单测全绿，看上去是通的。
>
> **怎么定位**：我没有停在『绿了就是对了』，而是顺着四个具体点回推它的输入。
> 第一个：执行链上 worker 侧的 `ToolBroker` **构造时没传校验公钥**，而验签那一步在没公钥时**直接拒绝**——
> 报出来是『本进程未配置 Capability 校验公钥』，读起来像部署配置问题，实际是**这个进程永远执行不了任何一个带 Capability 的工具**，
> 也就是整条执行链一步都走不了。单测没抓到，是因为单测用的是**绕过七步序的假 broker**。
> 第二个：`seatunnel.submit` 的执行上下文**没给操作主体**，第 ④b 步的绑定比对拒空主体；同一个错 `stop` 早修过、`submit` 漏了。
> 第三个：质量报告的读取器被注册成**进程级单例**，可它的接口是「表名进、计数出」——**光有表名定位不到主机与库**，
> 这个注册形状**在物理上就实现不了**，必须换成工厂 `(session, run) -> reader`。
> 第四个是测试侧的：一条新用例先注册了**真**执行器，让另一个测试文件的**假**执行器夹具整体跳过，
> 于是那个文件四条用例红、**单跑绿、同跑红**，报错还指向毫不相干的地方。
>
> **试过什么不行**：一开始我以为是输入数据不够——把假对象喂得更全、把桩搭得更像，那几个点照样『通过』。
> 因为**故障根本不在数据，在『这段代码真跑一次会怎样』**——桩越像，越把真路径藏起来。
>
> **最后怎么解决**：每个都换成**真的跑一次**。
> 公钥推导**只留一份**（`harness/capability.py` 的 `verifier_from_settings()`），守它的用例**不再只断言属性非 None，而是拿同一把密钥签一张令牌、验签必须过得去**；
> 执行主体按『ctx 里的主体 == 令牌里签的主体』逐条对齐（`submit` 用发起人、`stop` 用 Outbox 载荷里的人、swap/rollback 用调用方或账本载荷）；
> 读取器改成工厂；测试夹具改成把注册表**换成本文件私有的空表、跑完还原**。
> 还有一个小而好笑的：账本载荷里一个叫 **`passed`** 的键，会被脱敏正则按**键名**判成敏感字段——
> 不是改成 `***`，是 `SensitivePayloadError` **直接拒绝写账本**，于是每一份质量报告都写不进账本；把键名改成 `conclusion` 就好。
>
> **这四个的统一讲法**：**判据的输入不存在或错位**，于是某个功能**悄悄地永不生效**——
> 放大比的阈值**没有来源字段**、worker 的 broker **没拿到公钥**、提交**没给主体**、读取器的注册形状**物理上无法实现**。
> 它们不会被任何一条『我 mock 过了』的用例抓住，只有真跑一次才现形。
> 所以我现在验证可疑点用的是『跑一次再说』，不是读代码相信它。」
>
> 「还有一条缝是我在这次才看清的：**两个模块各自绿灯、中间那条缝谁都没有认领。**
> be-17 和 be-18 的两份设计，**各自把『报告合格之后谁去换表』划给了对方**，
> 于是 `finalize_report` 和 `publish_run` **两个函数的调用方都是 0**：
> 作业跑完永远不会出质量报告，报告合格也永远不会换表——**而两边的单测都是绿的**。
> 这不是某一行写错了，是**责任在两张设计图之间掉地上了**。
> 教训是：光看每个模块自己的用例绿，证明不了链路通；得有人去数**这条链上的每个函数，到底有没有人调它**。」

**如果面试官想听「设计上的难」**，接着讲（**三选一；第一条「令牌消费」现在是一条真的在跑的路径——生产调用点在 worker 的执行链路里，不再是「有码无电」**）：

> 「第一个是**一次性令牌的原子消费**——这块实现和单测在 `harness/replay.py`，
> 生产调用点在 worker 的执行链路（`tasks/execution.py`：验签后原子消费 jti），**它现在是一条真的在跑的路径**。
> 设计上的难点是并行：审批过了发一张令牌，它**只能用一次**——
> 用两次的后果不是报错，是**同一份作业被真跑两遍**，真花钱真改数据。
> 检查『用过没有』和『标记已用』如果是两个动作，中间就有 TOCTOU 窗口。
> 我的做法是**让数据库的 WHERE 条件替我判断**：
> `UPDATE capability SET consumed_at=now WHERE jti=? AND consumed_at IS NULL`，
> 然后看影响行数——并发时行锁会让第二个事务影响 0 行，就判成重放。
> **原子性来自这个条件，不是来自 Redis**；Redis 的 `SET NX` 只是挡重复投递的第一道闸。
> 还有一条边界我特意定了：**Redis 连不上时直接拒绝执行**，
> 因为这时候我判不出令牌用过没有——降级成『只靠数据库』等于把两道闸变成零道闸。」
>
> 「第二个是**门禁为什么必须短路**。5 类检查的顺序是固定的：
> 策略 → 语法 → schema → 映射 → 资源，**遇到第一个 block 就停**。
> 顺序不是随便排的：策略排第一，是因为它答的是『这份制品**配不配**继续被评估』——
> 比如明文口令出域、或者敏感列写去外网，这种问题讨论『列名拼错了没有』毫无意义；
> 而且**策略类阻塞绝不进自动修复回路**。后面四类之间也有依赖：语法还没过，
> 就不该拿一份根本解析不动的配置去比列。**短路省的不只是时间，是不让下游在错误的前提上给出结论。**」
>
> 「第三个是**指纹为什么是整条链的信任根**。
> 制品指纹由 5 个部件拼出来（Plan、HOCON、质量契约、监督契约、源端档案快照哈希），
> 用规范化 JSON 算（键排序、小数统一量化到 4 位），并且**排除掉时间戳、请求 id 这类不可复现的字段**。
> 因为审批绑的是指纹、令牌签的是指纹、执行前还要再核一次指纹——
> **它是三方共同引用的一份事实**，所以它必须可复现：同一份制品，无论谁在什么时候算，都必须逐字节一致。
> 我给它钉了一个**金值哈希**在用例里，任何一处拼装改动都会让用例红。」

## 必答 4 · 你怎么保证大模型不瞎编？（M2 · 完整口述稿）

**口述稿（约 3 分钟）**

> 「我分四层回答，从最弱的一层到最强的一层——因为**只靠提示词约束模型是不够的**。
>
> **第一层，结构约束。** 我不让模型输出自由文本：它必须吐一份被 Pydantic 约束住的 `EtlPlan`——
> 字段映射、主键、去重口径、质量规则、运行预算，全在 schema 里。
> 模型给不出结构，我们就拿不到 `EtlPlan` 这个对象，后面每一步都跑不下去。
> 而且渲染配置那一步**只接受结构化的 Plan**，不做『从一段文字里提取意图』这种事。
>
> **第二层，把结构问题变成『可修复的输入』，而不是终局。**
> 拿到 Plan 之后我先跑一遍纯函数结构校验，它返回一份**问题清单，不抛异常**。
> 这一点是刻意的：抛异常等于把『可修』直接判成『死』；而清单正好是下一轮修复的输入。
> 修复回路最多 3 轮（`LLM_AUTOFIX_MAX_ROUNDS`，默认 3），每轮只允许按清单做**定向补丁**，
> 而且每轮都**重新跑一遍完整的门禁**——不是只跑补过的那一条，全部重跑。
> 如果一轮下来要修的问题跟前面某一轮**完全一样**，说明在原地打转，立刻停下（去抖），不烧 token。
>
> **第三层，真正的兜底是门禁，不是模型。**
> 渲染出 HOCON 之后过一道**确定性门禁**，5 类检查按固定顺序短路：
> 策略 → 语法 → schema → 映射 → 资源。
> 具体到『模型会不会编一个不存在的列』：schema 这一类检查拿的是**元数据档案里的真实列**去比 Plan 里的引用，
> 编出来的列名在这一步就被拦下；而且过期档案**不算有档案**——过期的列清单可能已经不是事实了。
> 这类检查是**纯函数**，只吃 Plan、HOCON 和档案，不吃模型、不吃时钟。
> 这就是我最坚持的那条线：**风险评级与放行判定绝对不让大模型参与**。
>
> **第四层，也是我最想强调的一层：不能修的，根本不许进修复回路。**
> 策略类阻塞——P0/P1，比如明文口令出域、或者敏感列写去外网——**不进自动修复**，直接进终局。
> 因为『让模型自己把安全违规改一改』正是最不该做的事：**那是一个判定，不是一道题。**
>
> 最后一条工程保障：**每次生成都留痕。**
> 生成成功会写一条 `PIPELINE_GENERATED` 事件进哈希链账本，带上模型名、模型版本、提示词模板版本、
> 修复轮次、档案 id——但**不放需求原文、不放任何样本**（账本永久保留，密级不一样）。
> 而且**账本写失败会让这次生成失败**：生成可以重来，漏掉的那条事件永远补不回来。
>
> 我得说清这套东西的边界：**它防的是『模型编错』，防不了『模型没编错、但方案本身就烂』。**
> 方案好不好最终还得看门禁的规则表和人的审批——所以 M3 的审批不是形式主义，它是这道墙的第二段。」

## 必答 5 · 冻结之后还能改吗？（M2 · 完整口述稿）

**口述稿（约 2 分半）**

> 「**不能。而且这不是靠自觉，是靠两道机制。**
>
> **第一道在 ORM 层。** `pipeline_version`、`etl_plan`、`preparation`、`approval_decision`、
> `capability`、`evidence_event` 这些表我在模型上标了不可变，并挂了一个 `before_flush` 钩子**逐列判断**——
> `update` 被拦，**`delete` 也一起拦**。
> 它的边界我也说清楚：它只拦 ORM 路径，绕过 ORM 直接发 Core 语句或 SQL 是拦不住的
> （这是防手滑，不防恶意）；而且不可变**连白名单列都不开口子**，唯一允许的例外是
> `frozen_at` 由空置成值的**那一次**转移，用例里专门钉着『冻结之后再改白名单列也要报错』。
>
> **第二道在业务语义上。** 冻结这一步有四件事，顺序固定：
> 先**重算一次制品指纹**（不是拿内存里那份），再写版本行、写制品行、写账本事件，
> 最后把状态推到 `version_frozen`。
> 重算是关键：它必须和生成时算的那份**逐字节相等**，否则这次冻结直接失败。
> 因为指纹是**审批、令牌、执行三方共同引用的信任根**——审批绑的是指纹、令牌签的是指纹、
> 执行前还要再核一次指纹；只要有一份制品被动过，指纹就对不上，链就断在那里。
>
> 指纹本身由 5 个部件拼出来：EtlPlan、HOCON、质量契约、监督契约，以及源端档案的快照哈希。
> 拼装用**规范化 JSON**——键排序、小数统一量化到 4 位；并且**排除掉时间戳、请求 id 这类不可复现的字段**。
> 为什么这么较真：它必须可复现，同一份制品无论谁在什么时候算都得逐字节一致。
> 这个算出来有一个**金值哈希**钉在用例里，任何一处拼装改动都会让用例红。
>
> 所以『想改』只有一条路：**产生一个新版本**——用旧版本做 Diff 说清改了什么，重新走一遍门禁和审批。
> 审计上看到的是『谁在第几个版本上改了什么』，而不是『那条记录被人更新过』。
>
> 我得主动补一句不足：**『指纹只能有一份定义』这件事目前是注释约束，没有自动守卫。**
> 我核过拼装函数在非测试代码里只有一个调用点，但**没有任何用例能阻止别人再写第二份**——
> 而这正是我下一步要补的那类检查。」

## 必答 6 · 「分流到底跑没跑？」——主动交代一处硬伤（完整口述稿）

> **为什么单独写这一题**：这一处如果你不说，面试官只要问一句
> 「那违规行是怎么进错误表的？」就会当场露。**自己先说、说清改法**，它是加分项；
> 被问出来才是减分项。完整现状与逐行证据见 [10 §4.1–4.4](10-做到哪一步了.md)（硬伤 A 在 §4.1）。

**如果面试官问「质量分流是怎么实现的？」**

> 「分两截说，因为**一截通了、一截没通**，我不想混着讲。
>
> **通的那截在控制面**：质量契约编译成谓词 SQL（`render_predicate`，每条都带
> `IS NOT NULL` 守卫，因为 SQL 三值逻辑里 `NULL NOT REGEXP 'x'` 是 NULL 不是真，
> 不守卫的话『没取到值』会被静默判成合规）；然后 `render_tagged_select` 给源查询
> 外套一层 `CASE WHEN`，产出带路由列 `_quality_route` 的中间结果；
> `render_route_selects` 再切成两条 SELECT——有效行显式列列进影子表，违规行只带
> `run_id / rule_id / field_name / error_code / payload_digest / reason / occurred_at`
> 进错误表，**原文不落库**，摘要用 MD5 加截断。错误表的建表语句在
> `clients/target/engine.py` 里，MySQL 和 Doris 各一份，列清单和违规行 SELECT 同源。
> 这一截有单测，`tests/test_quality_engines.py` 逐条断言 SQL 文本。
>
> **没通的那截在数据面**：渲染器还是『一个源 → 一条 SELECT → 一个 sink』，
> `render_route_selects` **没有一个生产调用方**——全仓库 grep 只有导出和测试。
> 所以真跑起来，违规行会跟有效行一起进影子表；质量报告去错误表数，数到 0，
> 报告显示『非常干净』。**这是我最怕的那类错：不报错、结果不对。**
> 我没有把它说成『已实现』，页面上这整段标的是 🟢。」

**如果面试官追问「那你打算怎么改？」**

> 「难点不在 SQL，在**时间顺序**：制品是冻结时渲染的，`run_id` 是提交时才有的。
> 把 run id 写进制品，同一份版本每次运行哈希都不一样，审批过的和执行的就不是同一份了。
> 所以正确做法是加一类**运行期令牌** `{{runtime:run_id}}`，和密钥令牌同一套思路：
> 制品里留字面量，Worker 执行时替换。落地六步——
>
> ① 类型层加 `runtime_token` 与 `find_runtime_tokens`，**但不能扩 `TOKEN_RE`**，
> 因为 `parse_tokens` 的结果是『去 Vault 取密钥』的清单，混进去会去查一个不存在的数据源；
> ② 两道闸分开：`secret_token_problems` 只管密钥（冻结前），
> `assert_no_unresolved_tokens` 两类令牌都要清零（执行前）——
> 拿执行前的闸去卡冻结，会把每一份合法制品都拦下，这个误用我已经踩过一次；
> ③ 渲染器多接两个入参：编译后的契约和错误表名（它们都是版本的一部分，由 service 传）；
> ④ 渲成 `tagged → valid/rejected → 双 sink`，错误表的列序必须和
> `render_route_selects` 的输出列序一致，错了不报错、只会整列错位；
> ⑤ 执行器先换密钥、再换 run id，最后统一断言无残留；
> 还要扩 `_assert_writes_covered`——它现在要求『制品里每个 sink 表都得有影子表』，
> 错误表天然没有影子表，必须**只放行这一个名字**；
> ⑥ 四条单测：有两个 sink、run id 变化制品哈希不变、替换后无残留、错误表被放行而漏影子表仍被拒。」

**如果面试官追问「SeaTunnel 支持一个源分两个 sink 吗？」（这题要诚实）**

> 「**没在真机上验证过**，所以我有两种写法备着：
> 甲是一个 `tagged` 结果表 → 两条路由 SELECT 各产一张结果表 → 两个 sink 用
> `source_table_name` 各取一张；乙是退路，两个 source 各带 `WHERE` 条件、各走各的 sink，
> 读两遍但只依赖最基础的 source + sink 能力。
> 我选甲，但**验证成本很低**：起 Zeta 提交一次看状态机就知道。
> 在这一步验证之前我不会写『分流已实现』——这就是为什么整段还挂着 🟢。」

**如果面试官追问「还有没有类似没接线的？」（主动加分）**

> 「有，而且我已经修过一处同类的：`finalize_report` 和 `publish_run` 都写完了、
> 用例全绿，但两份设计各自把收尾划给对方，于是**两个函数的调用方数量都是 0**——
> 作业跑完永远不出报告、报告合格永远不换表。我补的是 `services/finalize.py`，
> 一个不拥有任何算法的分派器。所以我现在交付前会做一件事：
> **每个新写的『终点函数』都 grep 一遍调用方**，因为单测永远不会告诉你『没人调我』。」

**如果面试官追问「那脱敏那条规则呢？会不会也炸？」**

> 「会，而且是同一个坑的另一面。起草器给敏感列加的断言是
> `^[a-z_]+:[0-9a-f]{12}$`，那是**探查期 Python 掩码**的形状（`phone:3f2a1b4c9d0e`）；
> 而数据面 SQL 掩码是 `CONCAT(LEFT(x,2),'****',RIGHT(x,2))`，形状是 `13****01`。
> 两处各自都对，凑一起就 100% 误杀——只是现在分流没接线，所以还没炸。
> 改法是把掩码形状收成**一份定义**，渲染器和规则都从它取；
> 更好的做法是回到设计原文：`E_SENSITIVE_PLAINTEXT` 本来就该由 P0 门禁产出，
> 而不是字段规则——『敏感列有没有带 mask』是制品属性，在冻结前就能判。
> 我倾向两条闸都留，和『冻结前解不解得开 / 执行前替没替换』是同一个模式。」
