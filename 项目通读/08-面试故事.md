# 08 · 面试故事

> 面试官记住的从来不是结论，是故事。
> 「我做了重放防护」是结论，听完就忘；「我发现 worker 会永久卡死，重启才好，查了三层才找到是连接池」是故事，他会记住。
>
> 这份文档里每个故事都是**这个项目里真实发生过的**，证据是代码注释、回归用例和 `CLAUDE.md` §9.1。
> （M2 的三个故事另外多了一层证据：**我在写这份文档时逐个对着代码核过**——
> 哪条断言真的在、哪个键真的没被声明、哪条注释引用的用例其实不存在。核实结果都写在故事里。）
> 每条都按同一个骨架写：**现象 → 怎么定位 → 为什么它不自己恢复 → 走过什么弯路 → 怎么修 → 怎么证明修好了 → 会被追问什么**。
> 中间那两步（**为什么不自己恢复**、**走过什么弯路**）是分水岭——只讲「我怎么修的」的人到处都是，
> 能讲清「为什么它会持续坏」的人才是懂这个系统的。

## 0. 怎么用这份文档

**先挑故事，不要全背。** 按你被问到的方向选：

| 面试官问的方向 | 讲哪个 | 为什么 |
|---|---|---|
| 「你遇到过最难的 bug」 | **故事 1（Redis 死连接）** | 跨了网络、连接池、进程生命周期三层，故事最完整 |
| 「你怎么保证代码质量」 | **故事 2（定时炸弹测试）** | 它证明你会怀疑「跟我无关的红」，而不是乱改 |
| 「你踩过什么坑」 | 故事 3、4（Celery 两个） | 都是「启动一切正常、一干活就炸」的隐式环境问题 |
| 「你怎么处理错误」 | 故事 5（安静失败 / 归因） | 展示的是**判断力**：哪种失败更危险 |
| 「你的设计里最巧妙的地方」 | 故事 6（detail 白名单） | 一个「少写一个词」如何静默改写结论 |
| 「你在本地开发踩过什么坑」/「你怎么处理平台差异」 | **故事 7（Windows 事件循环）** | 装配期就死、容器里永远复现不出来——**平台专属**的那种坑 |
| 「你怎么设计状态/数据契约」/「大模型的输出你怎么管」 | **故事 8（State 的键被静默丢掉）** | 真因与症状隔了一整个模块：报的错指向用户输入 |
| 「你的设计里有没有『只靠注释守住』的规矩」 | **故事 9（指纹只能有一份定义）** | 它讲的是**注释约束的边界**：能解释「为什么」，不能阻止「怎么做错」 |
| 「你怎么验证代码真的是对的」/「测试全绿就信吗」 | **故事 10（测试是绿的，产品却是错的）** | 它讲的是**怀疑的姿势**：两个 `xfail` 一跑全是真缺陷，属于「测试写对了、产品是错的」 |

**讲故事的通用骨架**（每个故事都照这个顺序，别倒着讲）：

1. **一句话说结论**（「worker 会永久卡死，重启才好」）——先给钩子，别铺垫；
2. **现象**：具体到「日志里只有这一句」「症状是点一下按钮就 500」；
3. **定位**：我按什么顺序排除了什么（**这一步要讲得细，因为它证明你会查问题**）；
4. **为什么它不自己恢复**（🔴 最加分的一步，详见下面每个故事）；
5. **怎么修**（一句人话 + 一行代码）；
6. **怎么证明修好了**（有回归用例就说用例，有实测数字就说数字）。

**每条故事后面的「追问链」**：面试是三层起步的。第一层答完，他会顺着问第二层，
第二层答得漂亮，才有第三层。**每层怎么写，我都给了**。

> ⚠️ **诚实前提**：这些坑真实存在于这个仓库（有注释和用例为证），但**不都是我今天现场踩的**——
> 每个故事标了来源：「本会话实测」= 我做这份文档时亲手跑出来并修掉的；
> 「建造期记录」= 当时写代码时踩到、修完把经过留在了注释和 `CLAUDE.md` 里。
> **面试时你可以讲全部**：只要你能讲清根因、能指着代码说清每一处在防什么，它就是你的。

## 故事 1 · worker 会永久卡死，重启才好

> **来源：本会话实测**（修 `core/redis.py` 时踩到，完整经过写在 [redis.py:52-72](../backend/core/redis.py#L52-L72) 的 docstring 里）

### 一句话结论

> **「隧道断过一次之后，worker 就再也不干活了，重启才好。根因不是网络，是连接池里那条死连接永远换不掉。」**

### 现象

本机跑控制面（API / worker），基础设施在阿里云 ECS 上，中间是一条 SSH 隧道
（[deploy/tunnel.py](../deploy/tunnel.py)，把 ECS 的 127.0.0.1 端口映射到本机同号端口）。

现象是**不对称的**，这也是最误导人的地方：

- **API 一切正常**，页面能打开、能登录、能查数据；
- **worker 彻底不干活**：投递过去的任务永远停在 PENDING，前端轮询一辈子；
- 日志里**只有一句**：`ConnectionError: Error 22 while writing to socket`。

重启 worker 立刻恢复，一切正常——**直到下一次隧道抖动**。

### 怎么定位的（按排除顺序讲，这步要细）

1. **先怀疑隧道**——`curl` 打 ECS 的端口：通的。所以不是「端口关了」，
   而是「连得上、但不通」（这个区别坑了我一次，见 [CLAUDE.md](../CLAUDE.md) §9.1）。
2. **再怀疑 Redis 本身**——`redis-cli ping` 直接打隧道：**PONG**。
   所以 Redis 活着、隧道活着，**是 worker 进程内部握着的东西坏了**。
3. **看错误类型**：`Error 22 while writing to socket` 是 **写**的时候炸的，不是连的时候炸的。
   这说明连接**建立过**，是**后来失效**的对端 socket——也就是「死连接」。
4. **看唯一性**：为什么 API 不会这样？因为 **API 每个请求都可能新建/复用连接且流量不断**，
   而 worker 空闲期长、进程活得更久、且 `core.redis.get_redis()` 是 **`lru_cache` 单例**
   （[redis.py:48](../backend/core/redis.py#L48)）。
5. 结论：**死连接被缓存在单例里，而 redis-py 默认不会在用它之前检查它。**

### 🔴 为什么它不自己恢复（这是这个故事的灵魂）

一般的连接问题会自愈，这一个不会，有三个原因叠在一起：

| 条件 | 单独看都合理 | 合起来就是「永久卡死」 |
|---|---|---|
| 客户端是 `lru_cache` 单例 | 省连接、省配置 | 死连接**没有第二处**可以替换它 |
| worker 进程复用一个事件循环 | 符合 `CLAUDE.md` 的要求（任务里禁止 `asyncio.run`） | 循环不重建，**池子也不重建** |
| redis-py 默认不做 pre-ping | 减少一次来回、更快 | **下一次调用直接撞上死连接** |

类比 SQLAlchemy 那边：SQLAlchemy 有 `pool_pre_ping`，所以 **PG 侧会自愈**
（[core/db.py](../backend/core/db.py) 开了它，CLAUDE.md §9.1 里也记着「重启隧道后第一个请求可能 503，但那是自愈」）。
**Redis 侧没有对应物**——两者是同一个坑的两个面，而我只给一面上了保险。
这也是最初没意识到的原因：PG 会自愈，就以为 Redis 也会。

### 走过什么弯路

- 第一反应是**加长超时**——没用，因为问题不是慢，是连接**已经死了**，等多久都等不到；
- 试过**改 `pool_recycle`**（PG 侧的对应参数）——Redis 客户端压根没这个语义，白改；
- 试过**在任务里 catch 住重连**——能救这一次，但下一次调用还是从同一个单例拿到同一条死连接，
  **治的是症**；而且每个任务都要写一遍。
- 正确的方向是把修复下沉到**客户端构造**这一处，让所有调用方受益。

### 怎么修的

两层，缺一不可（[redis.py:75-81](../backend/core/redis.py#L75-L81)）：

```python
client: Redis = Redis.from_url(
    settings.redis_url(settings.REDIS_DB_CACHE),
    decode_responses=True,
    health_check_interval=30,          # 闲置超 30 秒的连接，用之前先 PING，失败即丢弃重建
    retry=Retry(ExponentialWithJitterBackoff(base=0.05, cap=1.0), retries=3),
    retry_on_error=[RedisConnectionError, RedisTimeoutError],  # 隧道刚断就到的请求，这一次自己换连接完成
)
```

**为什么要第二层重试**：`health_check_interval` 只能兜「闲置超过 30 秒」的连接；
而**隧道刚断就到达的请求**，它那条连接可能只闲置了几秒——照样撞上死连接。
（这句推理写在注释 [redis.py:62-64](../backend/core/redis.py#L62-L64) 里，面试可以直接引用。）

**还有一个反直觉的判断**（这句最能体现想清楚了）：

> 重试对 `SETNX`（Capability 令牌消费）是**失败即安全**的：
> 万一第一次其实已经生效、只是响应丢了，重试会拿到「已被消费」——也就是**误拒一次合法消费**，
> 属于可用性损失；而反过来（把消费过的当成没消费）在重试语义下**不可能发生**。
> 所以这里可以放心加重试，**因为错误的方向是安全的那个方向**。

### 怎么证明修好了

写了一条**断言配置本身**的回归用例（[test_core_clients.py:22-34](../backend/tests/test_core_clients.py#L22-L34)）：

```python
assert kwargs.get("health_check_interval"), "没开健康检查：隧道抖动一次，worker 就永久卡死"
assert kwargs["health_check_interval"] <= 60, "间隔太长等于没开"
assert {"ConnectionError", "TimeoutError"} <= names, f"重试没覆盖连接错误：{names}"
```

**为什么断言的不是行为而是配置**：因为没有真 Redis 也要能守住这条——
这类参数被删掉**不会报错**，只在断连那天现形。断言配置是唯一能在单测里挡住它的办法。
另外顺带把 PG 侧也钉住了：`assert engine.pool._pre_ping is True`（[:43-47](../backend/tests/test_core_clients.py#L43-L47)）。

### 追问链

| 层 | 他会问 | 你怎么答 |
|---|---|---|
| 1 | 「加个 `health_check_interval` 不就完了？」 | 「不够。它只兜闲置超 30 秒的连接，而隧道刚断就到的请求那条连接只闲置了几秒，照样撞死连接，所以还要一层重试让这次调用自己换连接完成。」 |
| 2 | 「重试不会让令牌被消费两次吗？」 | 「方向恰好相反。重试最坏是**误判成已消费**→拒掉一次合法执行（可用性损失）；而『把消费过的当成没消费』在重试语义下不可能发生。**错误的方向是安全的那个**，所以能加重试。」 |
| 3 | 「那正确做法是不是每次都新建连接？」 | 「那就把连接池的意义丢了：每次握手、TLS、认证的成本全回来，高频接口直接被打穿。**连接复用要保留，代价是必须做健康检查**——这才是这个坑真正的教训。」 |
| 4 | 「你怎么知道 API 侧不会也这样？」 | 「API 侧同一个单例、同样会持有死连接，只是请求密集、连接被反复使用和淘汰，暴露窗口小得多。而且我 PG/Redis 两处都配了保险（`pool_pre_ping` + `health_check_interval`），**没有只修我看到症状的那一侧**。」 |

> 💡 **这个故事为什么值钱**：它同时展示了三件事——会看错误类型（写失败 ≠ 连失败）、
> 会找「为什么只在这里坏」（进程生命周期 + 单例）、**会修一类而不是一个**（把 PG 那一面也检查了）。
> 而且它的第 3 层追问（「怎么知道别的进程没有同样问题」）是**主动把范围扩大**，不是被动挨打。

## 故事 2 · 两条用例在某个钟点准时过期

> **来源：本会话实测**（2026-10-16 我做最终验证时跑出来并修掉的，完整经过见 [05-开发原理 §8](05-开发原理.md)）

### 一句话结论

> **「交付当天跑全量测试，两条用例红了，而它们上午还是绿的——因为这两条用例的通过与否取决于你几点跑它，它们在 16:01 过期了。」**

### 现象

跑 `pytest -q`，两条用例失败，都在 `test_governance.py`：

```
FAILED tests/test_governance.py::test_按发生时间过滤      assert [1, 3, 4] == [3, 4]
FAILED tests/test_governance.py::test_导出遵守过滤条件     assert [1, 4] == [4]
```

**而且这两条跟我这次改的东西毫无关系**——我这次只动了文档和一个 Redis 客户端配置。

### 怎么定位的

1. **先确认自己没改坏**：`git` 对比 + 回头看改动范围 → 确实没碰 `test_governance.py`、也没碰 `governance.py`。
   **这一步很重要**：大多数人在这一步就慌了，开始乱改代码。
2. **看多出来的是谁**：实际结果 `[1, 3, 4]` 比期望的 `[3, 4]` **多了一个 `seq=1`**。差值只有一条 → 不是全表错，是**多算了一条**。
3. **`seq=1` 是谁**：顺着 fixture 往上找，`seq=1` 是 `_bootstrap` 里 `create_project` 落的「建项目」账本事件
   （[test_governance.py:155](../backend/tests/test_governance.py#L155)）。
4. **它和别的种子有什么不同**：别的种子事件都显式给了时间 `occurred_at=_T0 + timedelta(minutes=idx)`
   （[:122](../backend/tests/test_governance.py#L122)），**只有它没给**——没给就由服务代码填 `utcnow()`，即**真实当前时间**。
5. **过滤条件给了两端吗**：只给了下界 `occurred_from=_T0 + timedelta(minutes=1)`。
6. 🔴 **于是「它算不算命中」取决于真实时钟有没有越过 `_T0 + 1min`。**

而 `_T0 = datetime(2026, 10, 16, 8, 0, 0, tzinfo=UTC)`（[:45](../backend/tests/test_governance.py#L45)）
**就是今天**。北京时间 16:01 = UTC 08:01 —— 我在 16:0x 跑的这次，正好越过了那条线。

### 🔴 为什么它不自己恢复

**因为它不是产品缺陷，是用例自己埋的定时炸弹。** 清楚了这一点，后面才不会乱改：

| 跑测试的时刻 | `seq=1`（真实现在）落在窗口里吗 | 结果 |
|---|---|---|
| 越过 `_T0 + 1min` 之前 | 否 | ✅ 绿 |
| 越过之后 | 是 | 🔴 红，**而且永远红下去** |

过滤逻辑本身**完全正确**——那条事件确实落在了时间窗内。
错的是**断言把「真实现在」和「硬编码过去」混在了一个窗口里**。

而且我还顺手查了同类写法，发现**还埋着第二颗**：另一条用例用 `occurred_from=_T0 + 365 天`
（[:381](../backend/tests/test_governance.py#L381)）——那是**一年后才引爆**的同一颗雷。

### 走过什么弯路（以及差点走上的弯路）

- 差点**直接改产品代码**：多算了一条，第一反应是「过滤条件写漏了」——
  但过滤是对的，改它才是真引入 bug。
- 一度想把 `_T0` 换成 `utcnow()` 让时间「跟得上现在」——**这会让问题更糟**：
  两个时间都变成真实时钟，断言就依赖两次 `utcnow()` 之间有没有跨分钟边界，变成**随机 flake**。
- 也想过把 `_T0` 挪到更远的过去——**同样更糟**：那真实时间的事件就永远在窗口里，永远红。

### 怎么修的

**让过滤窗口两端都夹住**（下界排除最早那条种子，上界排除真实时间那条），三处都改了：

```python
EvidenceFilter(
    project_id=seed.project_id,
    occurred_from=_T0 + timedelta(minutes=1),
    occurred_to=_T0 + timedelta(minutes=3),     # ← 上界：与跑测试的钟点彻底无关
)
```

改完把成因写进了 [CLAUDE.md](../CLAUDE.md) §9.1（项目的已知坑清单），
并把这次的完整经过留在 [05-开发原理 §8](05-开发原理.md)。

### 怎么证明修好了

复跑全量：**1396 passed, 3 skipped**（这是**写这份文档时**的全仓数——修这个缺陷那天的数字是 1041；
用例一直在加，报数字时一并说口径），
`ruff` 也是干净的。
而且这次修的是「**无论哪个钟点跑都成立**」，不是「这次跑绿了」。

### 追问链

| 层 | 他会问 | 你怎么答 |
|---|---|---|
| 1 | 「这不就是把测试改绿了吗？会不会掩盖了真 bug？」 | 「我先把产品代码排除了：多出来的是一条**真实时间**的事件，它确实落在时间窗内，过滤逻辑没错。**改断言不是为了让测试变绿，是因为断言的前提写错了**——它假设『真实现在永远早于硬编码的 `_T0`』，这个假设会过期。」 |
| 2 | 「那怎么保证以后不再出现同类问题？」 | 「我把判据写成了规矩：**测试里的时间必须只有一个来源**，要么全用固定基准时刻、要么全用真实时钟，别混。并且我顺手扫了同类写法，把另一颗『基准时间 + 365 天』的雷一起堵了。」 |
| 3 | 「为什么这种 bug 平时发现不了？」 | 「因为它的表现是『**跟你改的东西完全无关的用例突然红了**』——最容易被误判成自己引入了回归，然后开始乱改。这也是我把它写进 `CLAUDE.md` 的原因：下次别人看到，能直接对上号。」 |

> 💡 **这个故事为什么值钱**：它讲的不是技术，是**工程判断**——
> 红的测试要先分清「产品错」还是「断言错」，以及**别为了让测试变绿而改产品代码**。
> 而且它是**当天发生的**，讲起来有时间、有数字、有对照（上午绿、16:01 红），真实感最强。

## 故事 3 · 点一下按钮就 500，报错栈却在一堆看不懂的地方

> **来源：建造期记录**（写在 [CLAUDE.md](../CLAUDE.md) §9.1 与 [tasks/__init__.py](../backend/tasks/__init__.py) 注释里，回归用例 `tests/test_celery_app.py:28`）

### 一句话结论

> **「接口返回 500，报错栈全是框架内部代码。根因是 Celery 的任务装饰器绑到了『默认应用』，而默认应用连的是 `amqp://localhost:5672`——一个根本不存在的 RabbitMQ。」**

### 现象

- 前端点某个按钮（触发异步任务）→ **500**；
- 栈里**没有一行我自己的代码**，全在 `kombu`（Celery 的消息层）里面；
- 单测**全绿**——因为单测直接调任务函数，根本不经过 broker。

### 怎么定位的

1. **先怀疑业务代码**：报错栈里没有业务的帧 → 说明**还没走到业务逻辑就炸了**。
2. **看栈的顶层在干什么**：kombu 在**建连接**。于是问题变成「它想连哪」。
3. **打印实际使用的 broker**：`celery_app.conf.broker_url` 是对的（Redis），
   但**投递时用的不是这个 app** —— 装饰器 `@shared_task` 绑定的是 Celery 的**默认应用**。
4. **确认默认应用是谁**：没人设过 → 它是内置的、默认 `amqp://localhost:5672`。

### 🔴 为什么它不自己恢复，而且**在 worker 侧永远看不出来**

这是这个故事最关键的一层：

- **修复只有一句**：`celery_app.set_default()`（[celery_app.py:44](../backend/tasks/celery_app.py#L44)）；
- **但它必须被执行到**——`tasks/__init__.py` 要导入 app 模块，否则这句永远不跑；
- 🔴 **worker 侧看不出问题**：worker 是用 `celery -A tasks.celery_app worker` 启动的，
  `-A` 已经把 current_app 设对了，所以 **worker 端一切正常**；
  坏的只有 **API 侧投递**这一半——而 API 侧的错，只有真的从 API 投一次任务才会露出来。
  **单测不投递，所以单测永远绿。**

三个条件叠起来就是「静默」：配置对、worker 对、单测绿，**只有真点一次按钮才知道坏了**。

### 走过的弯路

「配置看起来是对的」这一段会耗掉最多时间——因为 `celery_app.conf.broker_url`
打印出来就是 Redis，**你会反复怀疑 Redis 而不是怀疑「用的不是这个 app」**。
转折点是意识到：**Celery 的 app 不只有一个，而装饰器绑的那个可能不是你配置的那个。**

### 怎么修的

`tasks/celery_app.py` 里显式 `celery_app.set_default()`，并保证
`tasks/__init__.py` 一定会导入 `celery_app`（[tasks/__init__.py:54](../backend/tasks/__init__.py#L54)）。

### 怎么证明修好了

回归用例 **`test_默认应用就是配置好的那个`**（[test_celery_app.py:28](../backend/tests/test_celery_app.py#L28)）——
断言的是「默认应用 == 我们配置的那个」，**在没有真 broker 的环境里也能守住**这条。

### 追问链

| 层 | 他会问 | 你怎么答 |
|---|---|---|
| 1 | 「为什么不干脆不用 `@shared_task`，直接 `@celery_app.task`？」 | 「那确实能绕开这一坑，但会失去『任务可在别的 app 上复用』的能力，而且项目里已经用 `shared_task`，改装饰器是**大面积改动**；正确做法是**把默认应用设对**这一处，而不是让每个任务各自防御。」 |

## 故事 4 · 启动一切正常，一干活就 `ModuleNotFoundError`

> **来源：建造期记录**（根因分析完整写在 [tasks/__init__.py:22-46](../backend/tasks/__init__.py#L22-L46) 的 docstring）

### 一句话结论

> **「Celery 加载完 app 之后，会把当前目录从 `sys.path` 里删掉。于是 worker 启动完全正常，可任务第一次惰性导入业务模块时就报 `No module named 'services'`。」**

### 现象

- `celery -A tasks.celery_app worker` **启动日志一切正常**，`ready`；
- 任务一执行就 `ModuleNotFoundError: No module named 'services'`（[tasks/datasource.py](../backend/tasks/datasource.py) 里的 `from services import datasource`）；
- 更迷惑的是：**有些模块导入得到，有些不行**。

### 怎么定位的（这段推理最值得讲）

1. **为什么「有些行、有些不行」** → 说明不是路径全错，而是**时机问题**：
   顶层就导入过的模块早就进了 `sys.modules`，之后怎么都不会再报错；
   **只有「任务运行期才第一次导入」的模块会炸**。这一条直接把方向从「路径配错」扭到「**导入时机**」。
2. **谁动了 `sys.path`**：Celery 用 `celery/utils/imports.py::import_from_cwd`，
   里面是 `cwd_in_path()` 这个**上下文管理器**——**进入时把 cwd 插到首位，退出时再删掉**。
3. 于是：worker 起来那一刻 cwd 还在（app 与它牵连的 `core`/`models` 都进了 `sys.modules`），
   **真正开始干活时 cwd 已被撤走**，`sys.path[0]` 实为 `.venv/Scripts/celery.exe`。
4. **为什么 API 侧没事**：uvicorn 会把 `''`（即 cwd）放进 `sys.path`，它不走 Celery 那套。

### 🔴 为什么「加个守卫」修不好它（这个细节最值钱）

第一版修复写的是这类「防御性」写法：

```python
if _BACKEND_ROOT not in sys.path:      # ← 看起来更安全，实际让修复静默失效
    sys.path.insert(0, _BACKEND_ROOT)
```

**它不生效**：因为 Celery 插进来的 cwd 和 `_BACKEND_ROOT` **是同一个字符串**
（worker 的 cwd 就是后端根目录），守卫认为「已经在里面了」，于是跳过——
紧接着 Celery 就把那个路径撤走了。实测打印出来 `present_before=True`。

**正确的写法是「无条件删掉再压首位」**（[tasks/__init__.py:44-46](../backend/tasks/__init__.py#L44-L46)）：

```python
while _BACKEND_ROOT in sys.path:
    sys.path.remove(_BACKEND_ROOT)
sys.path.insert(0, _BACKEND_ROOT)
```

还要在 `celeryd_init` 信号里**再补一次**（[:57-74](../backend/tasks/__init__.py#L57-L74)）——
因为第一次插入发生在 Celery 的 `cwd_in_path()` **之内**，退出时会被它一并清掉。

> 这段可以直接当金句：**「白名单式的『已经在里面了』守卫，在一个会主动删路径的框架里是个陷阱——
> 你以为的安全检查，正好让修复静默失效。」**

### 走过的弯路

- 试过 `PYTHONPATH` 环境变量：**能修，但不能只靠它**——它依赖「怎么启动」，
  而同一份代码有多个入口（脚本 / 单测 / uvicorn / worker），**依赖外部环境的修复会在某个入口漏掉**；
- 试过在任务函数里逐个 `sys.path.append`：能救，但每加一个任务模块就要记得加一次，
  属于**让人记住的规矩**（而 `CLAUDE.md` §5 的原则是「靠人自觉的规矩等于没有规矩」）。

### 怎么证明修好了

`ensure_backend_root_importable()` 被放在 `tasks/__init__.py`——**任何 `tasks.*` 的导入都必然先执行它**，
所以「谁在跑」不再影响导入结果。并且 worker 启动钩子里再补一次，双保险。

### 追问链

| 层 | 他会问 | 你项目里的接法 |
|---|---|---|
| 1 | 「改 `PYTHONPATH` 不就行了？」 | 「能修但不能只靠它：它把正确性放在**启动方式**上，而这个仓库有四个入口。我要求『谁在跑都不影响导入』。」 |
| 2 | 「为什么放在 `tasks/__init__.py` 而不是 `celery_app.py`？」 | 「`celery_app.py` 自己就要 `from core.config import settings`，**它本身就依赖路径已经对了**。必须先补路径再谈导入，所以只能放在更早被执行的 `tasks/__init__.py`。」 |
| 3 | 「`sys.path` 这种全局可变状态拿来改，不怕副作用吗？」 | 「怕，所以这个副作用是**刻意的且只做一次**：它幂等（先删再插，重复执行结果相同）、位置明确（包级初始化）、且注释里写清了为什么不能加守卫。这是我能接受的副作用，因为另一条路是让每个任务模块各自处理导入失败。」 |

## 故事 5 · 取不到值的时候，是回 `None` 还是抛错？

> **来源：建造期记录**（判断依据写在 [datasource_probe.py:706-713](../backend/clients/datasource_probe.py#L706-L713) 的 docstring）

### 一句话结论

> **「元数据探查里，从结果集取值取不到时我选择抛错而不是回 `None`——因为回 `None` 会被 `str()` 变成表名 `"None"`，档案状态还是 `ready`，错得安安静静。」**

### 现象（这个 bug 的形态本身就是故事）

真实成因很小：**MySQL 8 在部分配置下返回的列名是大写的**，
而 `aiomysql` 的 `DictCursor` **键名大小写敏感**——写 `row["table_name"]` 在演示库上直接 `KeyError`。

但如果这里用「防御性」写法 `row.get("table_name")`，后果是：

| 写法 | 出错时的表现 | 会被发现吗 |
|---|---|---|
| 回 `None` | `str(None)` → 表名变成 **`"None"`**，列名也变成 `"None"`，**档案状态仍是 `ready`** | ❌ 前端看到一张叫 `None` 的表，可能几个月没人细看 |
| **抛错** | `_classify` 归到 `INTERNAL_ERROR` 并留栈 | ✅ 立刻暴露 |

### 怎么修的（[datasource_probe.py:705-719](../backend/clients/datasource_probe.py#L705-L719)）

```python
def _pick(row: Any, key: str) -> Any:
    """两种都取不到时**抛错**而不是返回 None：返回 None 会被 str() 变成表名 "None"、
    列名 "None"，档案看起来是「成功」的，只是内容悄悄错了。
    抛错则会被 _classify 归到 INTERNAL_ERROR 并留下栈——错得响亮好过错得安静。"""
```

先试原样、再试大写；**两种都取不到就抛**。并且全仓约定：**凡从结果集取值一律走 `_pick`**。

### 🔴 为什么这条值得单独讲

因为它是一条**可以推广的判断**，不是一个补丁：

> **「错误处理的选择标准不是『哪种更不容易崩』，而是『哪种失败更容易被发现』。
> 一个安静的错值，比一次响亮的异常危险得多。」**

配套的兄弟判断还有一条——**归因不要冤枉别人**（[datasource_probe.py:209](../backend/clients/datasource_probe.py#L209) 的 `_classify`）：
只把**驱动异常**翻译成字典 §5.7 的连接类错误码；
`KeyError` / `TypeError` / `AttributeError` / `IndexError` 是**我们自己的代码缺陷**，
一律归 `INTERNAL_ERROR` 并留栈——否则**真因在解析代码里，排查方向却被「连接失败」带去查网络和凭据**。

### 追问链

| 层 | 他会问 | 你怎么答 |
|---|---|---|
| 1 | 「直接 `row[key]` 不就完了，为什么要兼容大小写？」 | 「因为演示源库正是 MySQL 8，实测回的是大写列名。这不是防御性编程，是**针对已知目标环境的适配**，注释里写了具体成因（`lower_case_table_names`）。」 |
| 2 | 「抛异常会不会让用户看到一个 500？」 | 「会，但**这是我要的**：这个错误不可能靠重试变好，它需要人去看栈。接口层把它转成统一错误码，同时留栈——**用户可以只看到『服务内部错误』，但我和日志必须看到真因**。」 |
| 3 | 「你怎么保证以后别人不又写回 `row.get(...)`？」 | 「约定写进 `CLAUDE.md` §9.1（凡取值一律走 `_pick`），而且有测试覆盖探查的解析路径。**但我承认这条没有自动守卫**——真要彻底防，得让解析层的返回类型不接受 `None`，那是我下一步会做的。」 |

## 故事 6 · 少写一个词，MySQL 明明连上了却显示「失败」

> **来源：建造期记录**（这段推理就写在 [broker.py:83-91](../backend/harness/broker.py#L83-L91) 的白名单定义旁）

### 一句话结论

> **「安全内核会丢弃执行器返回的 detail 里没登记的键——只留一行 warning。少登记一个 `state`，连通性测试明明成功，前端却永远显示 failed。」**

### 现象

连通性测试的实际结果是：`succeeded`、`latency_ms=357`、`server_version=8.0.27` 都拿到了，
**但前端显示失败**。

### 为什么会这样（设计意图其实是好的）

`ToolBroker` 会把执行器返回的 `detail` 过一遍白名单（[`_safe_detail`](../backend/harness/broker.py#L575)），
因为：

- `detail` 会**进账本，而账本不可变、不可删**——一次泄漏就是**永久泄漏**；
- 所以策略是**白名单而非黑名单**：未知键直接丢弃并告警，**不是「看起来不敏感就放过」**；
- **嵌套结构也丢弃**——那是「不小心把整行数据带出来」的典型形态。

设计没问题。问题是**代价**：

```python
if key not in _ALLOWED_DETAIL_KEYS or isinstance(value, (Mapping, list, tuple, set)):
    dropped.append(key)
    continue
...
if dropped:
    log.warning("tool_detail_keys_dropped", dropped_keys=sorted(dropped))
```

**丢弃是静默的**（只有一行 warning），于是下游
`detail.get("state", "failed")` 回落到默认值 `"failed"` —— **结论被白名单改写了，而不是报错。**

### 🔴 为什么它是最危险的一类 bug

三个特征叠在一起：

1. **不报错**：接口 200、账本正常、`latency_ms` 也在；
2. **方向是「更保守」**：显示 failed 而不是 succeeded ——**看起来像是系统在谨慎工作**，没人会怀疑；
3. **单测永远发现不了**：单测**直接调执行器**，不经过 broker 的白名单（这句话就写在 [broker.py:88-89](../backend/harness/broker.py#L88-L89)）。

### 怎么修的

除了把 `state` 登记进白名单，更重要的是**加了一条会自己发现这类缺失的用例**：

**`test_工具结论字段都在_detail_白名单内`**（[test_harness_broker.py:768](../backend/tests/test_harness_broker.py#L768)）——
**逐个工具**核对「执行器输出的键」是否都在白名单内。这样**新增一个工具或改一个输出键时，
用例会立刻红**，而不是等前端显示错了才有人发现。

### 追问链

| 层 | 他会问 | 你怎么答 |
|---|---|---|
| 1 | 「白名单丢键只留 warning，为什么不直接抛错？」 | 「抛错会让**执行器的一个多余键**把一次已经成功的执行变成失败——那是我更不想要的。**但丢弃必须可发现**，所以配了逐个工具核对白名单的用例，把『沉默』变成『测试期就红』。」 |
| 2 | 「那为什么不干脆允许所有键，靠日志脱敏兜底？」 | 「因为这个值会**进账本**。日志脱敏是运行期的、可回滚的；账本一旦写入不可改、不可删，**泄漏就是永久的**。所以我在最接近写入的那一处就做白名单，不把安全寄托在下游处理器上。」 |
| 3 | 「嵌套结构为什么也丢？」 | 「因为『不小心带出整行数据』最常见的形态就是一个 dict 或 list——执行器作者未必有意，但 `rows: [...]` 这种键名太自然了。宁可丢，也不能赌。**要带结构化数据，就该定义明确的键并逐个登记。**」 |

## 故事 7 · 应用一启动就退出，我却先怀疑了半小时数据库

> **来源：建造期记录 + 本会话核实**
> （根因与修法写在 [eventloop.py:1-21](../backend/core/eventloop.py#L1-L21) 与 [dev_api.py](../backend/dev_api.py) 的 docstring 里；
> 我另核了两件事：本机 psycopg 3.3.6 自带 libpq、`AsyncPostgresSaver` 可 import；
> 以及**全仓用例里没有任何一条碰过 `loop_factory`**。）

### 一句话结论

> **「控制面在本机一启动就退出，连『监听 8000』那行日志都没有。根因不是数据库连不上，是 Windows 给的事件循环类型 psycopg 不接受——而且修这一条的地方不在 `main.py`，在『谁负责把循环建出来』。」**

### 现象

- 在本机起控制面（基础设施在 ECS，中间一条 SSH 隧道）：**进程直接就没了**，
  退出码非 0，`Uvicorn running on http://...` 那行从来没打出来过；
- 报错栈最底下是：`psycopg.InterfaceError: Psycopg cannot use the 'ProactorEventLoop' to run in async mode`；
- **症状的误导性极强**：它看起来就是「数据库连不上」。而我刚把隧道重连过，
  心里已经有一个现成的嫌疑人了。

### 怎么定位的（这步最有讲头）

1. **先按嫌疑最大的查**：隧道通不通、容器在不在、口令对不对——全都正常。
   到这一步如果我停手，就会去改 PG 的连接串，那是完全错的方向。
2. **转折点是「读错误的类名，而不是读错误的消息」**：
   这是 `InterfaceError`，不是 `OperationalError`。前者来自 psycopg 的**接口层**——
   「你用它用错了」，与网络、口令、库版本都无关。
   **这一条把方向从『环境』扭到『用法』。**
3. **为什么只有本机坏**：容器里跑的是 Linux，默认循环是 epoll 那一套；
   Windows 从 Python 3.8 起默认给的是 `ProactorEventLoop`（为了 IOCP）。
   同一份代码在容器里**永远没有症状**——所以这是**本地开发环境专属**的坑。
4. **为什么修起来这么绕**：uvicorn 的 `Server.run()` 是**先把循环建好**，
   之后才去 `import main:app`。所以你在 `main.py` 顶层写一句
   `asyncio.set_event_loop_policy(...)` **根本来不及执行**——
   **在被 import 的模块里设策略是无效的**，这是最容易白忙半小时的地方。

### 🔴 为什么它不自己恢复

因为它不是运行期故障，是**装配期故障**：没有降级、没有重试、没有告警，进程直接死。
而且它**只在 win32 上存在**——CI 在容器里跑、同事在 Mac 上跑，都不会复现，
所以「别人跑得好好的」这件事本身就是它最好的伪装。

| 条件 | 单独看都合理 | 合起来就是「本机起不来、别处都对」 |
|---|---|---|
| Windows 默认给 Proactor 循环 | Python 的默认行为，理由充分（IOCP） | psycopg 的异步模式**不接受**它 |
| uvicorn 先建循环再 import app | 与 app 的初始化解耦，是正常设计 | 顶层设策略的那一句**永远来不及跑** |
| 容器里是 Linux | 部署目标就该是 Linux | 于是它**只**在开发机上炸 |

### 走过什么弯路

- **改连接串 / 换驱动**：方向全错——错误类名已经说了这不是连接问题；
- **在 `main.py` 顶层设 policy**：无效，原因见上（这是这个坑真正的门槛）；
- **找 uvicorn 的 CLI 开关**：`core/eventloop.py` 的注释里记着「uvicorn 0.54 起走的是 loop factory、没有那个开关」。
  这一条是**注释里的记录**，我没有在容器里逐版本验证过 uvicorn 的 CLI，
  面试时我会把它说成「按注释里的记录」，不当成我实测的结论。

### 怎么修的

**把「用哪个循环」变成一处显式决定**（[eventloop.py:47-55](../backend/core/eventloop.py#L47-L55)）：

```python
def loop_factory() -> LoopFactory:
    if sys.platform == "win32":
        return asyncio.SelectorEventLoop
    return asyncio.new_event_loop
```

- 本机的启动脚本 [dev_api.py](../backend/dev_api.py) 走它：
  win32 用 `asyncio.run(server.serve(), loop_factory=loop_factory())`，其它平台继续 `server.run()`；
- 容器 / ECS **不变**：还是 `uvicorn main:app`；
- 而且在 Windows 上**显式拒绝 `--reload`**——reload 的父进程不经过这个工厂，会以同样的方式静默退出；
  宁可报一句清楚的错，也不要再让人猜一次；
- 值得单独说的是：**它是共享的**。worker 侧 [tasks/async_runner.py](../backend/tasks/async_runner.py)
  也走同一处决策（`core.eventloop.new_loop()`），因为「任务里禁 `asyncio.run`、所有任务复用一个进程级循环」
  这条要求在两处都得成立——**决策点只能有一处，否则会出现『API 能跑、worker 不能』这种只在一半路径上现形的故障**。

### 怎么证明修好了

- **当时**的验证方式很朴素：改完能起来了、能连上 ECS 上的 PG，症状消失；
- 我这次做文档时**只核了代码和依赖本身**：本机 psycopg 3.3.6、libpq 在、`AsyncPostgresSaver` 能 import，
  而 `loop_factory()` 的判定就摆在 `core/eventloop.py` 里——**没有重跑一遍启动**（那要 PG、Redis 都在）；
- **要如实说的一条缺口：没有回归用例守它。** 我 grep 过全仓，**没有任何用例提到
  `loop_factory` / `ProactorEventLoop`**——这类「只在某个操作系统上存在的装配问题」，
  单测里天然守不住。我现在有的只是**注释 + 一个可执行的启动脚本**。

### 追问链

| 层 | 他会问 | 你怎么答 |

| 1 | 「为什么不干脆在 Windows 上别用 psycopg 的异步模式？」 | 「那要为开发机维护第二条代码路径：同步连接桥进异步服务，等于让开发环境的执行模型和线上不一样。**开发机应该尽量贴近部署形态**，所以我在『谁建循环』这一处做最小改动，业务代码一行都不动。」 |

## 故事 8 · 「需求描述不能为空」——可用户明明填了

> **来源：建造期记录 + 本会话核实**
> （坑本身记在 [state.py](../backend/workflow/state.py) 模块 docstring 的第 3 条，
> 与 [intent_parse.py:58](../backend/workflow/nodes/intent_parse.py#L58) 的 `requirement_of` 注释里。
> 我核了三件事：注释引用的那条回归用例**确实在**（走真图的那条，`test_workflow_graph.py`）；
> 「编排层注入的键必须都声明过」这条也**已经上了 AST 守卫**；
> 而 `subject_id` → `user_id` 那次键名漂移，被写进了守卫自己的 docstring 里当反面例子。
> ⚠️ `backend/workflow/` 正在被并行改动，这段核到的状态是**我写这份文档那天**的。）

### 一句话结论

> **「一个字段被静默丢掉，报出来的却是业务语义的错。根因是 LangGraph 只为 schema 里声明过的键建通道——而我注入的那个键没声明。真因与症状之间隔了一整个模块。」**

### 现象

- 报错是一句业务语义的话：**「需求描述不能为空，无法生成方案」**，
  `details` 里还带着 `{"field": "requirement"}`（[generate_plan.py:220-226](../backend/workflow/nodes/generate_plan.py#L220-L226)）；
- 但用户**确实填了**需求，对话记录里也有；
- 更迷惑的是它**不是稳定复现**：同一份节点代码，换个调用方式就报「需求为空」。

### 怎么定位的

1. **先读报错的节点**：它读 `state.get("requirement")`；
   而且作者已经预料到单来源不可靠——[intent_parse.py:58](../backend/workflow/nodes/intent_parse.py#L58)
   的 `requirement_of` 刻意做了双来源（先读 `requirement`，再回落到 `messages` 最后一条），
   注释里写着：只看一处「就会在某次调用方式变化时表现成『需求描述不能为空』，而用户明明填了」。
2. **再往上找注入方**：需求来自编排层的 `_initial_state`（一个普通 dict）。
3. **关键一步：把「注入的键」和「声明的键」对一遍。**
   State 的类型是 `TypedDict`，而 `StateGraph` **只为 schema 里声明过的字段建通道**——
   没声明的键**不会报错**，它只是**不会成为通道**，于是节点读到缺省值。
   **真因（字段没声明）与症状（需求为空）之间，隔着「图怎么建通道」这个模块。**
4. 我是在 [state.py](../backend/workflow/state.py) 的模块 docstring 里读到这个坑的，
   而且注释里**引用了那条回归用例的名字**。我去核：**它确实在**——
   一条**走真图**的用例（`build_graph` + `InMemorySaver`），证明「未声明的输入键会被整键丢掉」。
   注释没有说谎。
5. **但注释说的还不够。** 那条用例守的是**框架行为**（「没声明的键会被丢」），
   它不守**「编排层到底注入了哪些键」**——而后者才是真的会有人写错的地方。
   我核到 `_initial_state` 注入的是 `"user_id": ctx.user_id`，
   而当时 State 上声明的字段叫 `subject_id`。
   **名字不一致 → 键被丢掉 → 读它的地方看到「没有操作者」，而且不报错**：
   账本里记的操作者会恒为默认值，症状是审计时才发现「这条事件不知道是谁触发的」。
   这个漂移现在是**历史**（字段名已经统一成 `user_id`），
   但它的痕迹留在了守卫自己的 docstring 里：**「`subject_id` 曾经就是这么一个漂掉的键名」**。

### 🔴 为什么它不自己恢复、也难被发现

| 条件 | 单独看都合理 | 合起来就是「报错指向用户输入」 |
|---|---|---|
| `TypedDict(total=False)`：字段可选 | 图节点逐步填字段，缺值是常态 | 缺了**不会报错** |
| 图只为声明的键建通道 | 这是 LangGraph 的设计 | 没声明的键**静默消失** |
| 节点对缺值有业务兜底（回落到 `messages`） | 增强健壮性 | **有时救得回来、有时救不回来**——于是表现成「偶发」 |
| 上报的错是业务语义 | 对用户友好 | 排查方向被带到「前端为什么没传需求」 |

结果：**没人会去怀疑一行字典字面量。**

### 走过什么弯路

- 第一反应是去查前端有没有把 `requirement` 传上来——**方向完全错**；
- 也想过给 `state.get("requirement")` 加个 `or ""`——那是治症状：
  错误会从「需求为空」变成「方案莫名其妙」，**更安静、更难查**；
- 正确的方向是**让丢键这件事变响**：把「注入的键」也拿 schema 校一遍。

### 怎么修的 / 现在真实的防线（这里必须说实话）

这个方向现在有**三条**守卫，我逐个核过：

1. **框架行为**：一条走真图的用例，证明「未声明的输入键确实不会成为 channel、会被整键丢掉」
   （[test_workflow_graph.py](../backend/tests/test_workflow_graph.py)）。
   它用**回显桩**顶掉 LLM，所以「节点确实读到了注入进来的需求」是被证明的，不是被假定的。
2. **注入方向**：一条 **AST 守卫**——读 `_initial_state` 的**源码**、取出它 `return` 的那个字面量 dict 的键，
   断言这些键**全都**在 `STATE_KEYS` 里；并且**显式断言** `user_id` 既在注入侧、也在声明侧
   （注释里点了名：`user_id` / `subject_id` / `actor_id` 是「最容易两侧各写一个名字」的地方）。
   为什么不写死清单而读源码：**这样 service 那边加了新注入键，用例立刻红**，而不是等某天某条链路拿不到值。
3. **身份同值**：一条守卫断言 `NodeRuntime` 的身份字段与 state 的同名键**同值**，
   守的是「重命名只改了一边」——节点里读 `runtime.user_id`，而账本里写 `state["user_id"]`，
   只要有一边漂了，轻则 `AttributeError`、重则**写进账本的 actor 变成默认值**。

**我还会主动说的两条边界**：

- 这三条守的是**键名**，守不了「**键声明了，但没人填**」。声明只是建了通道，
  填值是各节点的责任——要守这一层，得按状态转移表断言「到了某个阶段，某几个键必须非空」，
  **这一步还没做**；
- 状态契约的用例靠的是一份**手写的完整样本**（它断言「样本的键集合 == 声明的键集合」，
  [test_workflow_state.py:168](../backend/tests/test_workflow_state.py#L168)）。
  那只证明「**schema 与样例一致**」——**样例里当然每个键都有值**，
  所以它证明不了「真实链路里每个键都会有值」。

### 追问链

| 层 | 他会问 | 你怎么答 |
|---|---|---|
| 1 | 「既然节点已经抛了 422，为什么不算修好了？」 | 「节点抛的是**症状的错**——它说的是『需求为空』，而真因是键没进得来。抛错不能替代『让键进得来』：同一个错误还会以别的字段、别的位置再出现一次。」 |
| 2 | 「把 `TypedDict` 改成 `total=True` 不就行了？」 | 「那只会让**类型检查器**更严格；运行期建通道的依据仍是 schema 的键集合，缺的键还是缺的。**这个坑的本质是『通道集合由 schema 决定』，不是类型注解的松紧。**」 |
| 3 | 「怎么保证以后不再犯？」 | 「注入方向已经上了 **AST 守卫**：它读的是产出方的**源码**，所以 service 那边加了新注入键会立刻红，而不是等人肉回忆。**还差的一层是『声明了但没人填』**——那要按状态转移表断言每个阶段哪些键必须非空，这一步我还没做。」 |

> 💡 **这个故事为什么值钱**：它是「**报的错指向别处**」这一类里最纯粹的一个——
> 报错说用户没填，其实是框架把字段吃了。
> 而它更值钱的地方在**修法**：守卫不去比对「我以为的键名」，
> 而是**读产出方的源码**——所以「service 加了新注入键」这件事会在用例上立刻暴露，
> 不需要任何人记得回来改测试。
> 反过来，这也说明一件我常提醒自己的事：
> **「键名漂了」这种错，只有让两侧互相校验才守得住——靠人记两个名字，等于没有规矩。**

## 故事 9 · 一条只写在注释里的规矩

> **来源：建造期记录 + 本会话核实**
> （规矩写在 [parts.py](../backend/services/pipeline/parts.py) 的 docstring 与
> [gating.py:141-144](../backend/services/pipeline/gating.py#L141-L144) 的注释里；
> 我核了三个事实：生产代码里那处拼装**只有一份**、两个方向**共享同一对构造器**、
> 以及**没有任何用例在守「只允许有一处实现」这条规矩**——值层面的性质有用例，规矩本身没有。）

### 一句话结论

> **「制品指纹的拼装必须只有一份实现——而这条规矩只写在注释里。真分叉的症状不是报错，是『偶尔报指纹失效』：最难查的那一类。」**

### 现象（这是「设计的症状」，不是事故）

指纹是**审批、令牌、执行三方共同引用的信任根**。
[gating.py:141-144](../backend/services/pipeline/gating.py#L141-L144) 的注释把后果写得很清楚：

> 「拼法**只在 `parts.py` 里有一份**：门禁这里算的、生成时进指纹的、冻结时重算的必须是同一个值。
> 三处各写一次 `"|".join(sorted(...))` 就是指纹系统的第一次分叉——
> 而且分叉的症状是『偶尔报指纹失效』，最难查的那一类。」

也就是说：**一旦有两处定义，症状不是稳定失败**——
同一份制品，有时报「指纹失效」、有时正常，取决于哪条路径先算、以及数据里有没有「空 digest」这类被不同写法处理得不一样的边界。

### 这条规矩现在靠什么站着

我核了三件事：

1. **生产代码里那份拼装只有一处**：`"|".join(sorted(digest for digest in digests if digest))`
   在非测试代码里只出现在 [parts.py:159](../backend/services/pipeline/parts.py#L159)；
2. **两个方向共享同一对构造器**（`quality_contract_body` / `quality_body_from_row`），
   也就是「落库」和「读回来」不是两套拼法；
3. **算指纹的地方都走 `parts`**：生成编排与冻结节点都调它。

但——**这三条都是「我 grep 出来的现状」，不是「用例保证的性质」**。
**没有任何用例能阻止别人明天照着门禁那段注释再写一遍。**
这正是这个故事的靶心：**规矩被写下来了、也被遵守了，但它靠的是人和注释，不是机器。**

要说得更准一点，**守住了的和没守住的各是一半**：

| 性质 | 守住了吗 | 靠什么 |
|---|---|---|
| 指纹的**信封键集合** | ✅ 守住 | 用例里断言键集合 + 一个**金值哈希**（任何一处拼装改动都会让它红） |
| 每类字段变化**都会改变指纹** | ✅ 守住 | 一组逐个字段的「改一个、指纹必须变」的矩阵用例 |
| **拼装只允许有一处实现** | ❌ **没守** | 只有注释。用例自己也需要用一份构造样本（它写在测试里），但那只证明「键名对得上」，证明不了「生产代码里没写第二遍」 |

### 唯一的一对例外，而且它是故意的

「同一个值有两处实现」的地方，我按拼接模式 grep 全仓，核到的只有这一对：
[harness/ledger.py:143](../backend/harness/ledger.py#L143)（生产）与
[scripts/verify_ledger.py:95](../scripts/verify_ledger.py#L95)（独立验链脚本）。

它们拼的不是排序后的 digest，而是一列**固定字段序**的 parts；
而**验链脚本还额外断言「字段数没变」**——它自己定义了一份字段序清单，
对不上就直接报错「拼接契约已改动」。

**这一对是刻意不复用产品代码的**：验链脚本的价值恰恰在于**能对拍**——
如果它复用了产品代码，两边一起改就会一起错，对拍就没有意义。
所以「只此一份」这条规矩有一个**明确的、写在代码里的例外**：
一个是信任根（必须唯一），一个是自证清白（必须独立）。

### 走过什么弯路 / 我会怎么补

- 想过用 **AST 扫描**断言「非测试代码里只有一处这种拼接」——太脆弱：写法一变（换成 `join` 的别名、
  换成分步拼）断言就失效，**守的是一个字符串而不是一个性质**。
- 更稳的是**性质测试**：拿一份固定制品，从**三个入口**（生成时 / 门禁时 / 冻结时）分别算指纹，
  断言三者相等。这才是「三处必须同一个值」的直接表达。
- **这一条我还没写**——属于「我知道该怎么补、但还没补」的那一类，面试时我会照实说。

### 同一件事的另一面：注释也可能比代码旧

我在做这份文档时逐个核代码，还核到两处**注释与代码漂移**：

1. `workflow/nodes/freeze.py` 的注释写着某个重复「已记入交付说明」、并把收敛方案描述成**待做**的事，
   而 `services/pipeline/generation.py` 里**其实已经按那个方案收敛了**（冻结过的那一轮直接早退）；
2. 更典型的是**键名漂移**：State 上的字段一度叫 `subject_id`、而编排层注入的是 `user_id`——
   名字不一致，键就被丢掉，**而且不报错**。这个漂移现在被 AST 守卫拦住了（见 [故事 8](#故事-8--需求描述不能为空可用户明明填了)），
   但它的痕迹只能从守卫自己的 docstring 里读出来。

**注释的保鲜期和代码不一样**：代码改了会红，注释改了不会。
所以它是最容易积累误导的地方——**让人按一个已经不成立（或从未存在）的保证去做判断。**

### 追问链

| 层 | 他会问 | 你怎么答 |
|---|---|---|
| 1 | 「那你怎么保证以后不会分叉？」 | 「两件事：把拼接收口成**唯一的构造器**（让想分叉的人无从下手），再加一条**性质测试**——从三个入口算同一个值并断言相等。**后者比前者重要**，因为构造器可以被绕过，而性质测试绕不过。」 |
| 2 | 「验链脚本为什么可以重复实现一遍？」 | 「因为它**必须**独立。验链的意义就是用自己的实现对拍产品代码；复用产品代码等于让两边一起改、一起错。**所以『只此一份』这条规矩有例外，而这个例外是有理由的、写在注释里的。**」 |
| 3 | 「为什么这种 bug 比崩溃更危险？」 | 「崩溃有栈、有因果链；指纹分叉没有栈——它只有『偶尔失败一次』，而人的第一反应是怀疑网络和并发。**一个偶发的失败，比一个必然的失败更难定位。**」 |

> 💡 **这个故事为什么值钱**：它讲的是**约束的等级**——
> 「注释写的规矩」「构造器收口」「用例守住的断言」是三档不同的保证，
> 而大多数项目停在第一档却以为自己有第三档。
> 而且这个故事**没有事故、全是核实**：我说得出这条规矩现在靠什么站着、以及它什么时候会倒。

## 故事 10 · 测试是绿的，产品却是错的

> **来源：本会话实测**（2026-10-16 我给 be-14 补回归用例时跑出来并修掉的，两个缺陷都修在
> [services/run.py](../backend/services/run.py)；完整经过见 [10-做到哪一步了 §2](10-做到哪一步了.md)）

### 一句话结论

> **「这两个缺陷我原先在测试里标成了 `xfail`，以为是测试写法问题；跑了一次才发现两个都是真缺陷——而且都属于『测试写对了、产品是错的』。我现在的规矩是：可疑点先跑一次，再决定信不信代码。」**

### 现象

两个缺陷，症状完全不同，但都出在同一个新模块 `services/run.py`（执行编排）。

**缺陷①：提交执行四条主路径全 500。**

- `get_run` 组装 `RunDetail` 时先 `**summary.model_dump()` 展开——里面**已经**有 `seatunnel_job_id`
  （`RunSummary` 与 `RunDetail` 共有那几个字段），末尾又显式传了一次 `seatunnel_job_id=row.seatunnel_job_id`
  → **`TypeError`**（同一关键字参数传了两遍）；
- 炸的不是边缘路径：`commit`（提交执行）、运行详情、`pause`、`cancel` **四条主路径全部 500**；
- 更糟的是**副作用已经落库**——运行记录、账本事件、Outbox、Capability 在 `get_run` 之前就写完了，
  所以用户看到「操作失败」，**库里却躺着一次真实运行**。**报错的方向和事实正好相反**。

**缺陷②：运行确实失败了，失败现场却是空的。**

- `tasks/execution._fail` 的形状是「先把 `error_message` / `failure_snapshot` 赋在 ORM 实例上，
  紧接着调 `apply_transition` 把状态推成 failed」；
- 而 `apply_transition` 末尾有一次 `session.refresh(row)`（按主键重读整行）——它会**丢弃尚未 flush 的属性改动**
  （会话是 `autoflush=False`；我实测：`row.error_message = "x"` 之后 `refresh` → 变回库里的旧值）；
- 结果：运行**确实**变成 failed，详情页 `error_message` 是 null、`failure_snapshot` 是 `{}`，
  而账本里那条 `run.failed` 又写着「失败了」。**「有结论、没原因」的失败**，是排查时最容易被带偏的那一类。

### 怎么定位的

1. 这两个 bug 在 be-14 的用例里表现为两条 `xfail`——**我第一反应是「测试写法问题」**，
   因为「新写的模块 + 红的用例」最容易归因成断言写错。
2. 决定**跑一次真的看看**。实跑之后发现：不是断言错，是产品代码里**两条必然触发的路径**。
3. 缺陷①靠读栈定位：`TypeError` 直接指向 `RunDetail(...)`，重复传参一眼可见——
   根因是**同一份语义组装了两次**（`RunSummary.model_dump()` 与显式参数）。
4. 缺陷②靠**做一次最小实验**：把 `row.error_message = "x"` 之后 `refresh`，看值有没有被吃回去——
   **变回旧值**，于是「末尾那次 `refresh`」成了嫌疑人；再顺着调用方 `_fail` 的形状一对，坐实。

### 🔴 为什么它们不自己恢复

| 缺陷 | 为什么测不出来 / 不报错 |
|---|---|
| ① 重复传参 | **只有走到 `get_run` 才炸**。单测若只覆盖 `commit` 之前的步骤、或把 `get_run` mock 掉，永远碰不到 |
| ② `refresh` 吃改动 | **它根本不抛错**：状态确实变了（failed），只有「原因」被吃掉——而账本那条 `run.failed` 又会替你确认「确实失败了」，**两个来源一对照，你会以为是前端没显示** |

两个的共同点：**它们都不在「会抛异常」的那条线上**——① 只在主路径触发，② 压根不抛。
而 **`xfail` 标记的作用恰好是把「红」变成「预期内」——等于把警报关掉**：
如果不去跑一次，这两条 `xfail` 会一直躺在用例里，**假装我知道自己在标什么**。

### 走过什么弯路

- 差点停在「这是测试写法问题」——**新模块 + 红的用例，最容易误判成断言错**，而这两个都不是；
- 缺陷②我一开始的改法是「动状态前先 `flush()`」，**被项目自己的守卫拦下**：
  `tests/test_service_commit_boundary.py` 规定 `services/` 里**公开**函数只要会写就必须自己 `commit()`，
  而 `apply_transition` 是**故意不提交**的（事务边界归调用方：worker 的 `session_scope`、
  API 侧 `pause` / `cancel` 各自提交），所以不能简单地加一次 flush；
- 顺带踩到一个坑：`session.flush([row])`（只 flush 一行）在 SQLAlchemy 2.x 里**已弃用**（`SADeprecationWarning`）——
  是在把 `-W error::DeprecationWarning` 打开跑全量时发现的。

### 怎么修的

两处都修在**坑源**，不是调用点：

- 缺陷①：`get_run` 里**去掉那次重复传参**——`**summary.model_dump()` 之后只补详情独有的字段
  （[run.py:646](../backend/services/run.py#L646)）；
- 缺陷②：`apply_transition` 的**成功路径不再 `refresh` 整行**，而是把**刚写下去的那几个字段**赋回内存实例
  （值就是我们自己写的，准确、还省一次整行回读）；**抢锁失败**那条路径**只读状态列**
  （`status` / `started_at` / `finished_at`），不碰整行（[run.py:392](../backend/services/run.py#L392) 起）。
  这样修掉的是「**任何调用方暂存的改动都会被吃掉**」这一类，而不是 `_fail` 这一处——
  **守卫逼着我去掉 `refresh`，结果比加一次 `flush` 更好。**

### 怎么证明修好了

- 两个缺陷原先在测试里挂着 `xfail`，修完**摘掉标记**，那批用例成了它们的**回归守卫**；
  所以全仓现在 **0 xfail**（`uv run pytest` → **1396 passed, 3 skipped**，写这份文档时的数）；
- 缺陷①的直接证据：四条主路径（`commit` / 详情 / `pause` / `cancel`）都返回 `RunDetail`，不再 `TypeError`；
- 缺陷②的直接证据：`_fail` 之后详情里的 `error_message` / `failure_snapshot` **不再为空**——失败现场留下来了。

### 追问链

| 层 | 他会问 | 你怎么答 |
|---|---|---|
| 1 | 「这两个缺陷难吗？」 | 「一点都不难——**是我不该用 `xfail` 把警报关掉**。难的不是修，是**知道该去跑一次**：新模块 + 红的用例，最容易归因成断言写错，而这两个都不是。」 |
| 2 | 「为什么 `refresh` 会吃掉改动？」 | 「会话是 `autoflush=False`，`refresh` 按主键重读整行、覆盖掉内存里尚未 flush 的赋值。我做了个最小实验验证：赋值后 `refresh`，值变回旧值。**这类 ORM 隐式行为单看代码看不出来，跑一次就现形。**」 |
| 3 | 「为什么不干脆加一次 `flush()`？」 | 「因为 `apply_transition` 是**故意不提交**的——事务边界归调用方，而项目有条守卫规定 `services/` 公开函数会写就必须自己 `commit()`。加一次 `flush` 只救 `_fail` 这一处；**去掉 `refresh` 救的是一整类**：任何调用方暂存的改动都不会再被吃掉。」 |
| 4 | 「0 xfail 能证明什么？」 | 「证明**没有躺在用例里假装『已知的失败』**。`xfail` 本身不是坏东西，但**如果你说不出它为什么失败，它就是给警报静音的开关**——这次两个我都说不出，所以它们从一开始就不该是 `xfail`。」 |

> 💡 **这个故事为什么值钱**：它讲的是**怀疑的姿势**——测试全绿（甚至「已知红」）都不代表产品是对的。
> 而它的两个缺陷恰好是两类经典陷阱的实例：**同一份语义组装两遍**（`RunSummary` 与 `RunDetail` 共有字段）、
> **ORM 的隐式行为**（`refresh` 吃掉未 flush 的改动）。金句就一句：
> **「测试写得对，不代表产品是对的；我是靠『跑一次再说』，而不是靠读代码相信它。」**

## 故事 11 · 两个函数都没有调用方，而全仓用例全绿

> **来源：本会话实测**（2026-10-17 补 be-17/18 的收尾编排时核出来的，
> 根因写在 [finalize.py:3-14](../backend/services/finalize.py#L3-L14) 的模块 docstring 里）

### 一句话结论

> **「be-17 与 be-18 是分别写的两份设计，各自都把『报告合格之后谁去换表』划给了对方——于是 `finalize_report` 与 `publish_run` 两个函数的调用方数量都是 0：作业跑完永远不会出质量报告、报告合格也永远不会换表，而两边的单测都是绿的。」**

### 现象

把 be-16 / be-17 / be-18 三块的代码与用例都写完、`uv run pytest` 全绿（**1396 passed, 3 skipped**）、
`ruff check .` 全绿之后，我按「**这条链能不能从头走到尾**」去核**调用关系**，发现：

- `services/quality.py` 的 `finalize_report`（[quality.py:387](../backend/services/quality.py#L387)）在整个仓库里**没有调用点**；
- `services/publish.py` 的 `publish_run`（[publish.py:315](../backend/services/publish.py#L315)）同样**没有调用点**；
- 换句话说，grep 这两个名字，出来的**只有定义和用例**。

表结构齐了、执行器注册了、用例也齐了——**但没有任何进程会在运行期走到它们**。
后果一句话：**作业跑完永远不会出质量报告，报告合格也永远不会换表。**

### 怎么定位的

1. **不是看模块清单**——按模块清单核，每一块都是绿的。要按**链路的每一跳**问「谁调用它」。
2. 从「作业跑完」这一跳往两头追：数据面 FINISHED 之后，**谁**会去出报告？→ 找 `finalize_report` 的调用方 → **0**。
3. 报告合格之后，**谁**会去换表？→ 找 `publish_run` 的调用方 → **0**。
4. 读两份设计的交界处（这句被写进了 [finalize.py:6-8](../backend/services/finalize.py#L6-L8)）：
   **be-17 §5 把「报告合格之后投递 Swap」划给发布侧，be-18 §5 把「跑完且报告合格」划给执行编排**——两边各自指向对方。
5. 🔴 结论：不是某一行写错了，是**没有人负责把两段接起来**。每一份设计都是自洽的，合起来是断的。

### 走过什么弯路（三条都是「先怀疑别处」）

- **先怀疑「执行器没注册」**：因为 be-18 的工具里有两个是新加的（`target.publish_swap` /
  `target.rollback_cleanup`），第一反应是「它们是不是只有参数模型」。核完发现
  **七个工具的执行器全都注册了**（这是另一件必须核的事，但它不是这条链断掉的原因）。
- **再怀疑「是不是监督那条环的桩」**：`tasks/supervision.py` 一度是个**注册了却直接返回
  `not_implemented`** 的真任务（be-16 的占位），所以「跑完没人管」很像它的症状。
  核过之后发现那是**另一条环**（过程指标的阈值判定），与「跑完之后的收尾」不是一回事。
- **想过「新加一个 Outbox 主题」**：让「作业跑完了」也变成一条持久化消息，看起来很对称。
  否掉的理由在下面「怎么修的」里——**扫描每轮都会重新发现自己的触发器，不需要额外的持久化状态**；
  而且走 Outbox 就要回答「谁发现作业跑完了」，那正是我们要避免的那个问题本身。

### 🔴 为什么它不自己恢复（这一节回答的是「为什么单测永远发现不了它」）

因为它**根本不是运行期的错**，是**设计边界上的一个空洞**，而单测的视野恰好绕开了它：

| 条件 | 单独看都合理 | 合起来就是「没人调它」 |
|---|---|---|
| 单测只测「我这个函数对不对」 | 这是单测的本分 | **它不测「有没有人调它」** |
| `finalize_report` 的用例**直接调它** | 覆盖了函数全部分支 | 调用关系不在断言范围里 |
| `publish_run` 的用例**直接调它** | 同上 | 同上 |
| 两份设计各自自洽 | 每份读起来都完整 | **交界处谁写谁漏**，而这份「漏」不属于任何一方 |

**「模块内正确」与「链路正确」是两件事**：每个模块自洽、每条用例绿，连起来却可能是断的。
而且它有一个特别容易被放过去的伪装——**表结构齐、执行器齐、用例齐**，
这三样凑在一起会让「这条链是通的」看起来**证据充分**，其实它**从未被验证过**。

### 怎么修的

新写 [services/finalize.py](../backend/services/finalize.py)（**354 行**）作为**收尾编排的唯一所有者**。
它**不拥有任何算法**——这正是它唯一的存在理由，也是它可以这么薄的原因：它只做两件事——**分派**与**顺序**：

```
作业跑完 → 出质量报告 → 合格才换表 → succeeded
                       → 不合格     → failed
```

- 入口是 `sync_run_outcome`（[finalize.py:93](../backend/services/finalize.py#L93)），
  取一批待收尾运行的是 `list_pending_run_ids`（[finalize.py:311](../backend/services/finalize.py#L311)）。
- **触发方式**：beat 每 **40 秒**跑 `tasks.execution.scan_finished_runs`
  （[execution.py:466](../backend/tasks/execution.py#L466)；[celery_app.py:92](../backend/tasks/celery_app.py#L92)
  的 `beat_schedule` 里叫 `finalize-finished-runs`，带 `expires: 35`）。
- **为什么不走 Outbox**：扫描**每一轮都会重新发现同一个待办**（它的过滤条件本身就是判据），
  丢一次投递不会永久丢失；走 Outbox 就得把「谁发现作业跑完了」也变成需要持久化的状态。
  幂等靠下游保证：`uq_quality_report_run_id`（一个运行一份报告）+ `swap.succeeded` / `swap.failed` 事件短路
  （[finalize.py:96-99](../backend/services/finalize.py#L96-L99)）。
- **为什么不共用 30 秒那条环**：两条环的周期都是浮点、相位跟着 beat 启动时刻走，
  **同周期又同时起跑就是永久锁步**（同一秒里对每条活跃运行各发一次数据面请求）；
  Celery 的 `crontab` 只到分钟、**没有秒字段**，所以错开只能靠**不同周期**
  （40 与 30 的最小公倍数是 120 秒；理由写在 [celery_app.py:83-91](../backend/tasks/celery_app.py#L83-L91)）。

**它在实现里显式处理的四种状态**（每条都要讲「为什么」，这是加分点）：

1. **只在 `running` / `interrupted` 上推进**（[finalize.py:58-60](../backend/services/finalize.py#L58-L60)）：
   `queued` 还没起来、`paused` 正在写影子表、`rolling_back` 世界正在被另一次操作改写——这几种状态下算出来的结论都不算数。
2. **中断的运行永不发布**（[finalize.py:107-110](../backend/services/finalize.py#L107-L110)）：两道**独立**判据——
   报告在 `interrupted` 时强制不合格 + 收尾侧的 `allow_publish=False`。
   硬中断意味着影子表里是**半份数据**，换上去比不换更糟，所以拦两道也不嫌多。
3. **查不到作业（`stopped` / `not_found`）不动控制面状态**，只告警记 `orphaned`（[finalize.py:132-144](../backend/services/finalize.py#L132-L144)）：
   可能是人工 kill、可能是 Zeta 重启丢了内存态、也可能别人正在取消——**一律写 `failed` 会让「谁停的」永久失去答案**。
4. **失败只留 `classify_failure` 的分类，不搬原文**（[finalize.py:216-224](../backend/services/finalize.py#L216-L224)）：
   SeaTunnel 的失败文本常带整段配置与连接串，属于「无明文凭据」红线。

### 怎么证明修好了

- 守住它的用例是 [test_finalize.py](../backend/tests/test_finalize.py) 的 **25 例**，
  其中一条**真的走发布**（[test_finalize.py:150](../backend/tests/test_finalize.py#L150)）——
  **内存假发布器 + 真执行器 + 真状态机**，断言两张表的指纹互换、且**副作用只发生一次**。
- 本机全套单测 **1396 passed, 3 skipped**、`ruff` 全绿。
- **但要说清证据等级**：这条链**在真基础设施上一次都没跑过**——真 PG 里
  `preparation` / `execution_run` / `capability` / `outbox_message` / `quality_report` / `error_record` / `execution_metric`
  **全是 0 行**（当场数的）。所以我有的是**单测与调用关系**，没有真环境端到端。

### 追问链

| 层 | 他会问 | 你怎么答 |
|---|---|---|
| 1 | 「单测全绿怎么会漏掉这个？」 | 「用例天然只测『我这个函数对不对』，**不测『有没有人调它』**。`finalize_report` 的用例直接调它、`publish_run` 的用例直接调它，调用关系从来不在任何断言的范围里——这是『模块内正确』与『链路正确』的差别。」 |
| 2 | 「那以后怎么防？」 | 「交付前多核一遍**链路**，而不是模块清单：凡新增一个『终点函数』，就 grep 它的调用方，为 0 就是缺陷。本项目已经有一个反面清单可以照着核——就是这两个函数。」 |
| 3 | 「为什么不用 Outbox 而用 beat 扫描？」 | 「扫描**每一轮都会重新发现自己的触发器**（判据就是它的过滤条件），丢一次投递不会永久丢失，所以不需要额外的持久化状态；走 Outbox 反而要把『谁发现作业跑完了』也变成需要落库的状态。幂等由下游兜住（一份报告 + `swap.*` 事件短路）。」 |
| 4 | 「40 秒和 30 秒为什么要错开？」 | 「两条环周期都是浮点、相位跟着 beat 启动时刻走，**同周期 + 同时启动就是永久锁步**，会在同一秒里对每条活跃运行各发一次数据面请求；而 Celery 的 `crontab` 只到分钟、**没有秒字段**，错开只能靠不同周期——40 与 30 的最小公倍数是 120 秒。」 |

> 💡 **这个故事为什么值钱**：它抓的是「**测试全绿**」最容易骗人的那一面——
> 单测证明的是「每个函数对」，证明不了「链路通」。
> 而且它比崩溃更难发现：**表齐、执行器齐、用例齐**，一切都像是证据，
> 唯独没有一条证据是「有人真的从这头走到了那头」。
> 金句一句话：**「模块内正确不等于链路正确——两个函数都没人调，1370 条用例也会全绿。」**

## 7. 一页速查：每条故事的一句话 + 追问落点

| # | 故事 | 一句话 | 最容易被追到的那层 |
|---|---|---|---|
| 1 | Redis 死连接 | 隧道断一次，worker 永久卡死，重启才好 | 重试会不会让令牌被消费两次（答：错误方向是安全的） |

> 「这些坑的共同点是——**它们都不报错，或者报的错指向别处**。
> 所以我现在对这个项目的判断不是『功能做完了没有』，
> 而是『**它在什么情况下会静默地做错事**』。」
