## 精读 1：`ToolBroker.execute` —— 七步执行序（[harness/broker.py:155](../backend/harness/broker.py#L155)）

**它要解决什么**

系统里**所有会改变外部世界的动作**（连库、提交作业、改数据）都必须挤过这一个函数。
它的职责不是「执行」，而是**在执行之前把「凭什么允许你执行」这件事查清并留痕**。
一句话：**它是一道闸门，不是一个工具包。**

**逻辑怎么走的**

```python
167  now = (now or datetime.now(UTC)).astimezone(UTC)     # 时间只取一次
169  spec = await self._require_tool(tool, session, ctx)   # ① 这工具存在吗
170  await self._check_requirements(spec, token, session, ctx)  # ② 该由哪个进程跑
172  claims: CapabilityClaims | None = None
173  if spec.requires_capability:
174      claims = await self._verify(spec, token or "", session, ctx, now)  # ③ 验签
178      await self._assert_ctx(claims, spec, session, ctx)              # ④a 比上下文
179      expected = await self._expected_binding(spec, claims, session, ctx)  # ④b 查库取期望值
180      await self._assert_binding(claims, expected, spec, session, ctx)     # ④b 比指纹
183      result = await self._guard.consume(claims, session, run_id=ctx.run_id)  # ⑤ 原子消费
195      await self._check_preconditions(spec, claims.preparation_id, session, ctx, now)  # ⑥
200  parsed = self._parse_args(spec, args)                 # ⑦ 参数过 schema
201  detail = await self._run_executor(spec, parsed, session, ctx)  # ⑦ 真执行
```

逐行说「在防什么」：

- **第 167 行**：`now` 只算一次，后面验签、过期判定、账本时间戳**共用**它。
  注释写得很直白——否则跨秒执行时会出现「验签说过期了、账本说还没过期」的**自相矛盾证据**。
  证据链一旦自相矛盾，就等于没有证据。
- **第 169 行 ①**：工具**必须先在注册表里**。注册表就是「副作用清单」——
  没登记的工具根本走不到执行器。这是「副作用唯一出口」的第一道落实。
- **第 170 行 ②**：检查「声明由哪个进程执行」。
  这一条**只堵一个方向**：**api 进程不许执行 worker 工具**（那是绕过审批直接提作业的最短路）。
  反方向**故意放行**（[broker.py:249-259](../backend/harness/broker.py#L249-L259) 的注释）：
  worker 多跑一次只读探测不增加攻击面，**拒掉反而会逼调用方伪造身份**——
  那等于让这道检查建立在谎言上，比放宽更糟。
- **第 173 行**：`requires_capability` 为假的工具（P3 只读探测）走另一条分支，
  **不需要令牌**，但仍要走 ⑥ 的质量契约检查（第 197 行）。
  「只读」不等于「不用守规矩」。
- **第 178 行 ④a 必须在第 179 行 ④b 之前**（注释就在 175-177 行）：
  两者都在手上、**不用查库**，所以先做；
  顺序反了的话，跨租户调用会先撞上「preparation 不存在」，返回 `NOT_FOUND` 而不是 `TENANT_MISMATCH`——
  **归因被带偏**，排查方向从「越权」变成「数据丢了」。原则是：**先做便宜且能拒绝的检查**。
- **第 183 行 ⑤**：原子消费令牌，且**在真正执行之前**（第 201 行）。
  失败就 `_reject(..., stage=RejectStage.REPLAY)`——拒绝也要留痕。
- **第 195 行 ⑥**：检查 preparation 的**状态和有效期**（审批通过了但已经过期，不能执行）。
  令牌只证明「批准过」，不证明「现在还允许」。
- **第 205-224 行**：执行成功后写 `CAPABILITY_CONSUMED` 账本事件。
  注意 payload 里放的是 **`detail_keys`（键名）而不是 `detail`（值）**——
  账本是长期保存、可被多方读取的，**值里可能带业务数据**。

**最容易看漏的地方**

1. **④a 在 ④b 前面**这件事，从代码上看两行相邻、谁先谁后都「能跑」。
   它防的是**错误码的可解释性**，不是功能。这类顺序约束最容易在重构时被顺手调换。
2. **第 260-262 行的单向检查**：注释比代码长得多，而且**代码允许的方向和直觉相反**。
   如果不读注释，很容易「顺手修一下」把 worker→api 也堵上，结果逼出伪造身份。
3. **异常路径全部走 `_reject`**，它的返回类型是 `NoReturn`（[broker.py:506](../backend/harness/broker.py#L506)）——
   意思是「进了这个函数就别想继续往下执行」。这保证**没有任何一条失败路径能漏过留痕**。
4. **`detail` 白名单**（[broker.py:575](../backend/harness/broker.py#L575)）：只留登记过的键，
   且**丢弃嵌套结构**。这里踩过坑：`state` 没登记，连通性明明成功却显示 failed——
   **结论被静默改写**，而且只在真机上看得出来。
5. **第 ③ 步（第 174 行）在 worker 侧曾经「永远拒绝」**——
   这是「七步序」最值得讲的一处实战：
   `ToolBroker` 的构造参数 `verifier` 在 worker 里**没传**，于是第 294 行
   （[broker.py:294](../backend/harness/broker.py#L294)）直接抛「**本进程未配置 Capability 校验公钥**」——
   **文案像部署漏配，真因是这个进程永远执行不了任何带令牌的工具**
   （worker 要执行的正是提交 / 停止 / 发布 / 回滚四个）。
   而单测全绿，因为单测用的是**绕过七步序的假 broker**。
   修法是把「公钥路径 = 私钥路径换后缀」这条推导**只留一处**
   （[capability.py:303](../backend/harness/capability.py#L303) 的 `verifier_from_settings()`，所有进程都调它），
   并让守它的用例**拿同一把密钥签一张令牌、验签必须过得去**——
   **断言「配上了」不等于断言「能用」**。这一条与上面第 4 条（白名单）是同一个家族的：
   **判据的输入没接上**，于是闸门悄悄失效。同族的另外两个见
   [06-知识点精讲 ㉔](06-知识点精讲.md)——这一家族的共同卖点不是代码多聪明，
   而是**它错得很安静**，只有在真路径上跑一次才看得见。

**如果让我重写**

我会把 ①②③④⑤⑥⑦ 抽成一个**显式的步骤列表**（`list[Step]`）顺序执行，
而不是平铺在一个函数里。理由：顺序本身就是契约（④a 先于 ④b、⑤ 先于 ⑦），
平铺写法下「顺序」只存在于代码的行序里，**重构时不可见**；
抽成列表后顺序变成数据，还能顺手给每一步生成「拒绝阶段 → 错误码」的映射表。
代价是多一层间接，且热路径上多几次迭代——对这个调用频率（每次作业级）完全不值一提。

## 精读 2：`ReplayGuard.consume` —— 一次性令牌的原子消费（[harness/replay.py:69](../backend/harness/replay.py#L69)）

**它要解决什么**

审批通过后签发一张令牌（Capability），**这张令牌只能被执行一次**。
做砸的后果不是报错，而是**同一份作业被真跑两遍**——真花钱、真改数据。
Celery 的常态重投、worker 的并发、用户的重复点击都会撞上这件事。

**逻辑怎么走的**

```python
 67  self._ttl = ttl_sec + _TTL_SLACK_SEC          # 键比令牌活得久一点
 74  key = consumed_key(claims.jti)                # 键 = cap:consumed:{jti}
 77  ok = await self._redis.set(key, "1", nx=True, ex=self._ttl)   # 闸一：SETNX
 78  except RedisError as exc:
 80      raise AppError("重放防护不可用（Redis 不可达），已拒绝执行", ...)  # fail-closed
 86  if not ok: return ConsumptionResult.REPLAYED   # 抢输了
 90  result = await session.execute(
 91      update(Capability)
 92      .where(Capability.jti == claims.jti, Capability.consumed_at.is_(None))  # 闸二：条件写
 93      .values(consumed_at=now, consumed_by_run_id=run_id))
 95  if result.rowcount == 0: return ConsumptionResult.REPLAYED
101  return ConsumptionResult.CONSUMED
```

- **第 67 行**：Redis 键的存活时间 = 令牌 TTL **+ 一点余量**。
  方向不能反：键必须**比令牌活得久**。反过来的话，令牌还没过期、键先没了，
  **同一个令牌就能再消费一次**——而且是静默的。
- **第 77 行**：第一道闸用 Redis 的 `SET NX`（**只有键不存在时才写入**，即抢锁）。
  它快、能挡住 Celery 的常态重投，但它**不是**正确性保证——Redis 可能被清、可能主从切换。
- **第 78-84 行**：Redis 不可达时**直接拒绝执行**，而不是「跳过这道闸，只靠数据库」。
  理由要背下来：**判不出「用过没有」时，唯一安全的选择是不执行**。
  降级成「只靠 PG」看着更皮实，实际是把一道闸变成零道闸——
  因为 `UPDATE ... WHERE consumed_at IS NULL` 只有在**先经过 SETNX 的串行化**时才够用（见下）。
- **第 90-95 行**：第二道闸是**条件 UPDATE + 看影响行数**。
  并发时 PG 的行锁让第二个事务影响 0 行 → 判为重放。
  这是**唯一真正的原子性来源**：`UPDATE ... WHERE` 是原子的，
  而 `SELECT` 再 `UPDATE`（先查后写）中间有窗口。
- **第 96-99 行**：`rowcount == 0` 的三种可能（已消费 / 从未签发 / jti 被篡改成不存在的值）
  **用同一种方式处理**——都当重放拒绝。**并且 Redis 键故意不回滚**：
  留一个短时的「毒键」，代价是调用方要重新签发令牌，收益是不给任何重放留窗口。

**最容易看漏的地方**

1. **第 72-73 行的注释**：本函数**不 commit**。事务边界归调用方，
   这样「消费标记 + 证据事件 + Outbox 消息」能在**同一个事务**里落地。
   如果这里自己 commit，就会出现「令牌已消费但证据没写」的中间态——**令牌废了，却查不出为什么**。
2. **两道闸不是冗余，是分工**：SETNX 负责「挡住重复投递」，
   条件 UPDATE 负责「正确性」。反过来理解（以为 SETNX 是安全保证）会得出
   「Redis 挂了可以降级」的错误结论。
3. **`rowcount` 上的 `type: ignore`**：SQLAlchemy 的 `Result.rowcount` 在类型标注里不是所有 Result 都有。
   这行 ignore 是可以接受的——但要知道它 ignore 的是什么，别当成万能膏药。

**如果让我重写**

我会**把两处 `REPLAYED` 的产生点分开命名**（比如 `REPLAYED_INFLIGHT` / `REPLAYED_ALREADY_USED`），
只在对外错误码上合并。理由：现在两种完全不同的情况（正在被别人执行 vs 已经执行完）
在日志里长得一模一样，排查「用户说没反应」时会白走弯路。
不改的理由也成立（对外不该泄漏执行细节），所以这是我准备在面试里讲的**取舍**，不是缺陷。

## 精读 3：`EvidenceLedger.append` —— 并发下不断链（[harness/ledger.py:215](../backend/harness/ledger.py#L215)）

**它要解决什么**

每条证据事件都带 `prev_hash`（前一条的哈希）和 `event_hash`（自己算出来的哈希），
连成一条链；**改了任何一条历史事件，它之后的所有哈希都对不上**。
难点不在算哈希，而在**多个 worker 同时写**时不能出现两条事件指向同一个 `prev_hash`（分叉），
也不能出现 `seq` 空洞（验链要求连续）。

**逻辑怎么走的**

```python
222  _assert_payload_clean(event)                        # payload 里不许有秘密
223  seq, prev_hash = await self._lock_tail_and_next_seq(session)   # 锁内取链尾
225  if occurred_at.tzinfo is None or ...: raise LedgerError(...)   # 必须带时区
229  event_hash = compute_event_hash(..., prev_hash=prev_hash, occurred_at=occurred_at)
256  session.add(row); await session.flush()             # flush 不 commit
259  if self._signer is not None and seq % self._checkpoint_interval == 0:
260      await self.sign_checkpoint(session, to_event_seq=seq)      # 每 N 条签一个检查点
```

`_lock_tail_and_next_seq`（[:272](../backend/harness/ledger.py#L272)）里才是关键：

```python
281  on_pg = session.bind is not None and session.bind.dialect.name == "postgresql"
282  if on_pg:
285      await session.execute(text("SELECT pg_advisory_xact_lock(:k)"), {"k": _EMPTY_CHAIN_LOCK_KEY})
291  stmt = stmt.with_for_update()                       # 行锁锁住链尾
292  row = (await session.execute(stmt.order_by(EvidenceEvent.seq.desc()).limit(1))).first()
293  if row is None: return 1, ZERO_HASH                 # 空链：seq=1，prev 全零
295  return int(row[0]) + 1, str(row[1])
```

- **第 282-285 行**：**表空的时候无行可锁**，两个并发写入会同时读到 `None`、
  于是同时算出 `seq=1`——链从第一条就分叉。
  顾问锁（`pg_advisory_xact_lock`，一个「事务级的全局锁」，随 commit/rollback 自动释放）
  就是来补这段窗口的。
- **第 291 行**：非空时锁**链尾那一行**（`SELECT ... FOR UPDATE`）。
  两个并发 append 争同一把锁 → 「读链尾 → 算 seq → 插入」这段被串行化。
  注释明确写了：**这才是链正确性的主要保证，READ COMMITTED 下就成立**；
  文档要求的 SERIALIZABLE 是**额外**的纵深防御，不是唯一依赖。
  （这句话很重要：它说明作者知道「隔离级别」和「锁」各自负责什么，没有把正确性寄托在配置上。）
- **第 293-295 行**：`seq` 用 **`MAX(seq)+1`** 而**不是**数据库自增序列。
  理由写在 docstring 里：序列在**回滚**时会留空洞，而验链要求 seq 连续——
  有空洞的话，「有人删了一行」和「有人回滚了一次」**无法区分**。
  审计工具分不清这两件事，等于白做。
- **第 225-227 行**：**必须是带时区的时间**。
  注释给了真实场景：**容器里是 UTC、开发机是 UTC+8**，裸 `datetime` 会按本地时区解释，
  于是同一件事在两个环境算出的哈希**不一样**——链看起来被篡改了。
- **第 266-268 行**（`append_many`）：**不做批量插入优化**。
  批量插入会让两个并发批次交错写同一段 seq 区间，而锁只保护单条。**正确性优先于这点吞吐。**
- **第 259 行**：每 `checkpoint_interval` 条签一个 Ed25519 检查点，
  签的是 `chain_head_hash|from|to`（[:302-303](../backend/harness/ledger.py#L302-L303)）——
  **只签链尾等于只签了「最后一条」**，中间被整段替换仍能通过；带上区间端点才堵得住。

**最容易看漏的地方**

1. **空链那条分支**（第 293 行）是最容易被忽略的并发 bug：
   单测里串行写永远走不到，只有并发 + 全新表才触发。
2. **`flush` 而不是 `commit`**（第 257 行）：和 ReplayGuard 一样，
   事务边界留给调用方——这样「业务数据 + 证据」要么一起成功，要么一起失败。
3. **payload 清洁检查**（第 222 行）：账本是长期保存、可被多方读取的，
   所以进账本之前先查 payload 里有没有夹带秘密。
4. **哈希算法的字段顺序是契约**：`tests/test_verify_ledger_script.py:109` 断言 `_FIELD_ORDER` 这个元组，
   还有一条**金值哈希**（`_GOLDEN`，:144）钉死一个具体值。
   意图写在注释里：**改算法 = 宣布历史证据全部作废**，所以必须有人显式改那个字面量并回答「存量账本怎么办」。

**如果让我重写**

我**不会**改这里的实现，但会补一样东西：**一段针对真 PG 的并发写用例**（N 个协程同时 append，
断言链无分叉、seq 连续）。理由是这一段有个更硬的问题：

🔴 **账本的并发正确性在当前测试环境里根本验证不了。** 单测跑在**内存 SQLite** 上
（`tests/conftest.py:60` `sqlite+aiosqlite://`），而：
- `with_for_update()` 在 SQLite 上被 SQLAlchemy **静默忽略**（SQLite 没有行级锁）；
- `on_pg` 那个分支（第 281 行）在 SQLite 下**直接跳过**，顾问锁一次都不会执行。

也就是说：`test_ledger.py` 里那 16 个用例**全部是串行的**，验的是哈希算法与链式结构，
**一行并发都没碰到**；而那把锁的正确性只在我对真 ECS 上的 PG 跑时才真正生效过。
这不是「没写测试」这么简单——是**这个模块最难的那部分，恰好落在单测够不着的地方**，
而它看起来是绿的。我会把这条当成「测试策略的缺口」在面试里讲。

另外会把 `_EMPTY_CHAIN_LOCK_KEY` 这个魔法常量的**选取理由**写进注释（为什么是这个值、冲突了会怎样）。

## 精读 4：`digest` / `mask_value` / `mask_rows` —— 脱敏为什么不用星号（[engines/masking/policy.py:124](../backend/engines/masking/policy.py#L124)）

**它要解决什么**

元数据探查会把**真实的样本数据**从生产库捞到控制面来展示。
所以「捞什么、怎么存、存成什么样」都必须先定死。
难点是既要**不可还原**，又要**还能用**（同一列的两个相同值要看出相同，否则样本失去分析价值）。

**逻辑怎么走的**

```python
131  payload = f"{salt}\x1f{column}\x1f{value}".encode()   # 盐 + 列名 + 值
132  return hashlib.sha256(payload).hexdigest()[:_DIGEST_LEN]   # 取前 12 位
...
152  if level is SensitiveLevel.PUBLIC and keep_public_plain:
156      return text                        # public 列原样保留（但由策略决定，不写死）
157  prefix = kind.value if kind is not SensitiveKind.NONE else "masked"
158  return f"{prefix}:{digest(text, column=column, salt=salt)}"   # phone:a3f19c04b27e
```

- **第 131 行的盐按「列」固定**（`column` 参与哈希），注释解释了为什么不是全局盐：
  全局盐会让「手机号列」和「备注列」里**同一个内容**产生**同一个摘要**，
  于是**跨列关联**就成立了（拿备注里抄的手机号去比对手机号列，能对上）。
  按列加盐保留**列内**可分辨性，切断**跨列**关联。
- **第 132 行**：只取 12 位十六进制（48 bit）。
  这是**有意的可碰撞**：它要的是「不可还原 + 能比对」，不是密码学强度——
  真要防穷举，手机号只有 11 位数字，任何定长摘要都能被穷举，所以真正的防线是
  **不许把原值和摘要放在一起**（控制面库里不存原值）。
- **第 152-156 行**：`PUBLIC` 列原样保留，理由是「脱敏不是全部打码，那会让样本失去演示价值」；
  但**保留与否读参数**，因为策略层允许把它收紧成 `false`——
  注释里那句「写死会让策略里那句 `keep_public_plain=false` 变成谎话」是本文件最值钱的一句注释。
- **第 157-158 行**：形态统一成 `类别:摘要`。
  好处：看的人一眼知道这列是什么类型，但**看不到值，也推不出长度**。
- **`mask_rows` 第 170-172 行**：每列的判定结果**由调用方传入**，不在函数里现算。
  理由：同一张表每一行必须用**同一套**判定，否则会出现「第一行的 name 脱了、第二行没脱」——
  **看起来像脱敏随机失效**（这种 bug 极难复现）。
- **`merge_policy`**（[:207](../backend/engines/masking/policy.py#L207)）：策略**只允许收紧，不允许放松**。
  注释的理由是可以直接背的：**一个可以被关掉的脱敏开关，迟早会因为某次排查被临时关掉，然后再也没打开。**

**最容易看漏的地方**

1. **「掩码」这个词在这个项目里不成立**。
   PRD 写的是「掩码·哈希·截断」，实现是**加盐摘要**，模块 docstring 明确拒绝了
   `138****1234` 这种**可逆**形态——因为它保留了长度和前缀，能做字典攻击式的关联。
   面试时若把这里说成「打星号」，一追问就露。
2. **false 的默认方向**：`keep_public_plain` 默认 `True`（保留），
   所以「默认安全」在这里**不成立**，靠的是策略表里对敏感列的显式收紧。
   这是这块我最想改的地方（见下）。
3. **盐里带了租户和数据源版本**（调用侧：`f"{tenant_id}:{data_source_id}:{profile.version}"`），
   所以跨租户拿同一份数据算出的是**不同**摘要——**摘要不能跨租户比对**，
   这是防「用摘要当指纹做跨租户数据比对」的刻意设计。

**如果让我重写**

把 `keep_public_plain` 的默认值改成 `False`，即**默认全脱，只有策略显式声明 public 的列才原文保留**。
现在的默认是「保留」，安全性来自「策略表写对了」——
而脱敏这种功能的失败模式恰恰是**没人发现策略没写对**。
改成默认脱之后，漏配的后果是「样本不好看」（立刻会被发现），
而不是「生产数据被复制到控制面库」（几个月后才发现）。
这属于我在面试里会主动讲的「**默认值应该站在安全那一侧**」。

## 精读 5：`freeze_version` —— 冻结前的六道闸（[services/pipeline/artifacts.py:350](../backend/services/pipeline/artifacts.py#L350)）

> 这是 M2 生成链路的终点：把「候选行」变成**不可变版本**。读懂这一段，
> 就理解了「审批看到的」与「执行拿到的」为什么必然是同一份东西。

**它要解决什么**

生成链一路跑下来，库里已经有了一份 Plan / HOCON / 质量契约 / 督导契约，和一行
`frozen_at IS NULL` 的候选 `pipeline_version`。冻结就是**盖棺定论**：落下 `frozen_at`，
这一行连同它指向的四份制品从此一条 UPDATE 都不许发
（[models/base.py:118](../backend/models/base.py#L118) 的 `_is_frozen` 会让整行连白名单都失效）。
盖棺之前必须查完六件事，**顺序不能换**——因为每一件事都建立在前一件成立的基础上。

**逻辑怎么走的**

```python
379  if version.frozen_at is not None:                      # 闸 1：只许冻草案
380      raise ConflictError("该版本已经冻结过了；冻结是不可逆的，要改请重新生成一份草案。")
382  stored_parts = parts.parts_from_rows(...)              # 闸 2：从**落库的制品**重算
391  if not parts.fingerprint_matches(stored=version.sha256, parts=stored_parts):
392      raise ConflictError("制品指纹与候选版本记录的不一致：制品在生成之后被改动过。拒绝冻结…")
394  await _assert_tokens_resolvable(session=..., ctx=..., content=hocon_row.content, version_id=...)  # 闸 3
398  gate = await get_gate(...)                             # 闸 4：读**落库的**门禁结论
399  if any(f.severity == "block" for f in gate.findings):
401      raise ValidationError(f"门禁未通过（{len(gate.blocking)} 项阻塞），不能冻结…")
404  version.frozen_at = now                                # 闸 5/6：落冻结人 + 推进状态
405  version.frozen_by = ctx.user_id
407  await session.flush()
408  await repository.set_current_version(..., status=PipelineStatus.VERSION_FROZEN)
```

逐行说「在防什么」：

- **第 379 行（闸 1）**：`frozen_at` 非空就拒。冻结是单向的，`frozen_at IS NULL`
  既是「这是草案」的标记、也是那条**部分唯一索引**的谓词（见 06 卡片 ⑰）。
- **第 382-390 行（闸 2）**：**从落库的四行制品重算指纹**，不是拿内存里那份。
  为什么这么较真：生成期的指纹是「内存里的 Plan + 刚渲染的 HOCON」算的，
  而审批、Capability、执行三方引用的都是库里的那份。只有当「库里的制品重算出来」
  等于「候选行上记着的 sha256」时，「审批看到的」才等于「执行拿到的」。
- **第 391-392 行**：对不上就 `ConflictError`，**不是**「以库为准悄悄改成库的指纹」。
  后者会把「制品在生成之后被动过」这件事抹掉——而它正是这里要抓的东西。
- **第 394 行（闸 3）**：**判据不是「执行期那道闸」**。冻结时问的是「令牌**到时候解得开**吗」——
  `_assert_tokens_resolvable` 判两件事：① 令牌字段名在渲染器的白名单里；
  ② 令牌指向的数据源在本租户里**存在、未停用、且配了密钥引用**（三者缺一条，审批通过也跑不起来）。
  这和执行期的 `assert_no_unresolved_tokens` 问的**不是同一个问题**（那道闸问「口令替换干净了没有」，
  令牌必须一个不剩）。**两道闸混用是我真踩过的坑**：一开始拿执行期那道闸来冻结，
  后果是**每一份合法制品都冻不了**，报错还写着「仍有未替换的密钥令牌」——
  读起来像渲染器漏了替换，实际是**拿错了判据**（详见 [05-开发原理 §9](05-开发原理.md)）。
- **第 398 行（闸 4）**：门禁结论走 `get_gate` **读落库的**，不重跑。重跑会得到一个
  「现在」的结论，而策略表改过之后两者会不一样——那等于让用户看到一份与他审批时不同的结论。
- **第 399-403 行**：只要有一条 `block` 就拒。**且报错里带上阻塞条数**——
  用户下一步该去「修复」还是「改需求」，看的就是这个数字。
- **第 404-413 行（闸 5/6）**：`frozen_by` 落当前用户（四眼判定的后置条件靠它）；
  冻完把 `pipeline.current_version_id` 指过来、状态转 `version_frozen`。
  注意第 407 行是 **`flush()` 不是 `commit()`**：事务边界归调用方，
  这样「冻结 + 证据事件」能一起成功或一起失败。

**最容易看漏的地方**

1. **闸 2 的输入是「落库行」而不是「状态里的对象」**。看代码时两行相邻、都「能跑」，
   但把 `parts_from_rows` 换成 `parts_from_plan(plan=内存对象)` 之后，
   「有人 UPDATE 了 `etl_plan.plan` 但没改候选行的 sha256」就再也检不出来了——
   **而这类改动恰好是不可变表本该禁止、却可能通过裸 SQL 发生的**。
2. **闸 3 用的是 `_assert_tokens_resolvable`（冻结语义），不是 `assert_no_unresolved_tokens`（执行语义）**。
   两道闸**各自有定义、各管一段**（都在 [engines/hocon/types.py:92](../backend/engines/hocon/types.py#L92) 与
   [:109](../backend/engines/hocon/types.py#L109)）：一个问「替换干净没有」，一个问「解得开吗」。
   看代码时千万别把两者当成同一件事——**用错的那次后果是「所有合法制品都冻不了」**，
   而且报错文案会把你带偏。
3. **闸的顺序**：前三道都**不查门禁表**（本地数据就够），第四道才查库。
   和 `ToolBroker` 那条「先做便宜且能拒绝的检查」是同一个原则——
   先拒绝的检查应该最便宜，且它的错误码要指向真正的原因。

**如果让我重写**

我会把六道闸抽成一个**显式的检查列表**（`list[FreezeCheck]`），每项带
「名字 / 只读 or 查库 / 拒绝时抛什么错误码」，然后顺序执行。理由和精读 1 完全一样：
现在的「顺序」只存在于行序里，重构时不可见；而这里还多一层——**六道闸里有三道是纯本地的、
一道要查库**，抽成列表后能顺手断言「查库的检查一定排在本地检查之后」。
代价是多一层间接，收益是这段最容易在重构中被调换顺序的代码变成**数据**。

## 精读 6：五段指纹的拼法（[services/pipeline/parts.py:95](../backend/services/pipeline/parts.py#L95)）

**它要解决什么**

指纹是审批、Capability、执行三方共同引用的**信任根**：它把「这份制品长什么样」
压成一个 64 位十六进制串。难点不在算哈希，而在**决定哪五样东西进哈希、每样里哪几个键要剥掉**——
因为它一旦有两处定义，症状是**随机的**：同一份制品，有时报「指纹失效」，有时正常。

**逻辑怎么走的**

```python
# services/pipeline/parts.py —— 生成期
103  return build_parts(
104      plan,                                     # 内存里的 EtlPlanModel
105      hocon_content,
106      quality_contract_body(plan, pipeline_id=pipeline_id),
107      supervision_body(plan),
108      source_metadata_sha256,
109  )
# services/pipeline/parts.py —— 校验期（freeze / 验链脚本走这条）
125  return build_parts(
126      plan_row.plan,                            # **落库的 jsonb**，不是内存对象
127      hocon_row.content,
128      quality_body_from_row(quality_row),
129      supervision_body_from_row(supervision_row),
130      source_metadata_sha256,
131  )
# services/pipeline/parts.py —— 第五部分「源档案指纹」怎么由多个源算出来
159  return "|".join(sorted(digest for digest in digests if digest))
```

真正决定「什么进指纹」的在 [engines/fingerprint/parts.py:114](../backend/engines/fingerprint/parts.py#L114)：

```python
114  def _is_excluded(key: str, *, top: bool) -> bool:
116      if key.endswith(EXCLUDED_KEY_SUFFIXES):   # *_by（操作者）
117          return True
119      if key == "id":
120          return top                             # **只在每部分顶层**剥行级 id
121      return key in EXCLUDED_KEYS                # created_at / status / sha256 …
```

- **第 119-120 行**是这一段最值钱的一行：排除**不是**「递归地删掉所有叫 `id` 的键」。
  只有在**某一部分的顶层**（也就是数据库行的列位置）那个 `id` 才是「自增的行 id」；
  Plan 内部的 `inputs[0].id` / `dag.edges[0].id` 是**语义引用**，删了就等于丢了图的形状。
- **`data_source_id` 故意保留**（[engines/fingerprint/parts.py:15-19](../backend/engines/fingerprint/parts.py#L15)）：
  把源库从 A 换成 B 而指纹不变，等于放行一份「连的是 A 库」的方案带着旧指纹走完治理。
  排除清单里剥的是 `tenant_id` / `project_id` / `pipeline_id` 这类**编排事实**，
  不是 Plan 内容里的语义引用。
- **第 159 行**：多个源端的档案摘要**排序后拼**。排序是必需的——
  同一个方案把 `inputs` 换个书写顺序还是同一个方案，指纹不该因此变。
  「取不到档案的源**跳过**而不是塞空串」，理由写在 docstring 里：
  塞空串会让「没探查过」和「探查过、sha 恰好是空」两种状态产生同一个指纹。
- **第 103-109 行 与 125-131 行必须共用同一对构造器**：
  `quality_contract_body(plan, ...)` 既用来**建库里的行**、又用来算指纹；
  校验期则用 `quality_body_from_row(row)` 从行里读出同一个 dict。
  两边的键名与值来自同一个 dict，**在结构上就不可能漂移**。这是模块 docstring 第 8-22 行
  那句「指纹只能由落库的制品重算」的落点。

**最容易看漏的地方**

1. **一次「重新探查源表」会让冻结被拒**（[parts.py:150-154](../backend/services/pipeline/parts.py#L150)）。
   场景：用户从生成到点冻结之间去刷新了一次元数据档案。此时重算的第五部分变了，
   `freeze_version` 的第 391 行判「指纹不一致」→ 拒冻，报「制品在生成之后被改动过」。
   **这是要的行为**：档案变了就说明门禁当初核的那份结构已经不在了，该重新生成。
   故障方向是「多拒一次」，不是「静默放行」——但报错文案没提「档案可能变过」，
   用户会以为是自己的制品坏了。**这是我准备在面试里讲的取舍，也是我要改的一处文案。**
2. **`fingerprint_matches` 不用 `==`**（[parts.py:162-168](../backend/services/pipeline/parts.py#L162)）：
   指纹会经过 jsonb、前端、审批意见的复制粘贴，`0xAB`、大写、前后空格都不该让一份好制品被判失效。
   归一逻辑在 `engines.fingerprint.matches` 里，`parts.py` 不再写第二份。
3. **契约体与 Plan 里的规则不允许裁剪**（[parts.py:55-69](../backend/services/pipeline/parts.py#L55)）：
   每条 rule 用 `by_alias=True` 原样序列化。裁掉 `enabled` 之类的字段看着省空间，
   实际是让「契约体」与「Plan 里的规则」成为两个概念，于是**指纹算的是一份、执行用的是另一份**。

**如果让我重写**

我会给 `source_metadata_sha256` 的**拒绝路径**补一句可操作的建议：现在报错只说
「制品在生成之后被改动过」，而真实原因有三种（制品真被改 / 源表被重新探查过 / 档案过期被换掉）。
我会让 `_source_metadata_sha256` 在算的时候顺手记下「本次用到的每个源的 `profile.version`」，
拒冻时把它和候选行 `generation_context` 里的档案版本比一比，**在错误信息里分出是哪一种**。
代价是多读一个字段，收益是把「保守失败」从「用户以为制品坏了」救回到
「用户知道该重新生成」。这也是我面试里会主动讲的：**保守失败也要能被解释**。

## 精读 7：生成器驱动的有限自动修复回路（[engines/autofix/loop.py:109](../backend/engines/autofix/loop.py#L109)）

**它要解决什么**

门禁报出一批阻塞问题后，要**有限地**让模型改一轮、再判一轮，最多 3 轮
（[artifacts.py:78](../backend/services/pipeline/artifacts.py#L78) 的 `_AUTOFIX_MAX_ROUNDS = 3`）。
难点是：修复这一步在真实系统里要**调大模型（async）**，而回路本体（轮次、去抖、策略短路）
是**同步纯逻辑**。这个项目不想把控制流写两遍。

**逻辑怎么走的**

```python
# engines/autofix/loop.py
168  for round_no in range(1, max_rounds + 1):
169      proposal = yield AutofixRequest(        # ← 把「该修什么」交出去，等一个提案回来
170          round_no=round_no, plan=plan, hocon_content=hocon, findings=list(findings)
171      )
173      try: patched = apply_plan_patch(plan, proposal.patch)
175      except PatchError: patched = plan       # 补丁非法 → 本轮 Plan 原地不动，但轮次照消耗
179      last_result = recheck(patched, next_hocon)   # 复检：纯函数，不碰库
196      if not _has_block(findings): converged = True; break
201      if signature in seen:                   # 本轮要修的和此前某轮完全相同 → 原地打转
203          debounce = True; break
```

两个驱动器共用上面这一个生成器，差别只有一行：

```python
# engines/autofix/loop.py
333  outgoing = driver.send(repair(outgoing))            # 同步（run_autofix_loop，:316）
361  outgoing = driver.send(await repair(outgoing))      # 异步（arun_autofix_loop，:339，service 走这条）
```

- **第 169 行的 `yield`** 就是「把请求交出去、等一个提案回来」这个语义。
  同步驱动用 `repair(req)`、异步驱动用 `await repair(req)`；收敛判据、去重、
  轮次消耗**全部只有这一份**。这是「为什么用生成器」的全部理由：
  两处各写一遍的话，「最多 3 轮 / 去重 / 策略短路」会有两份实现——
  一份改了另一份没改，**而且不会有任何报错**。
- **第 133-145 行**：没有阻塞项就直接收敛（不调 repair、也别谎报 exhausted）。
  注释写得很直白——「没有可修的东西不是失败」。
- **第 147-160 行**：只要 findings 里有一条 `policy` 阻塞，**就地停手、`repair` 一次都不调**。
  让模型去「修掉」策略阻断等于把 P0/P1 判定交给 LLM（PRD §1.4 明令禁止），
  还白烧三轮钱。这条约束在路由层还有一道（[workflow/graph.py:176](../backend/workflow/graph.py#L176)），
  放在路由是为了让「它压根没进修复」在图结构上可见。
- **第 175 行**：`PatchError` 时 Plan 不推进，但**轮次照常 +1**。这是「补丁是唯一变更形态」
  的落实——补丁指不到的路径就是一次失败的轮次，而不是一次静默改动。
- **第 199-204 行（去抖）**：下一轮要修的阻塞项若**此前出现过**，说明修复在原地打转，
  立刻停。签名只由 `(category, code, locator_key)` 组成（[:233-240](../backend/engines/autofix/loop.py#L233)）——
  只取 `block` 项，且 `id` 里一旦混进随机数/时间戳，「同一问题」就会被当成新问题，于是无限重试。

**最容易看漏的地方**

1. **回路不知道「模型返回的是整份 Plan」**。模型按提示词输出**完整的** EtlPlan，
   而回路只认 `PlanPatch`。中间那层「差成补丁」在 service 侧
   （[repair.py:138-158](../backend/services/pipeline/repair.py#L138)），
   而且**当场做一次往返自检**（`apply_plan_patch(old, patch) == new`）。
   不做这一步，「差得漏了一条」的症状是「修复总是差一点、模型看起来不太行」——
   一个会让人去调提示词、调温度，却永远查不到根因的故障。
2. **`hocon_content=None` 的语义是「HOCON 不变」**，但 service 侧只要 Plan 变了就一定重渲染
   （[repair.py:20-24](../backend/services/pipeline/repair.py#L20)）。因为门禁是拿 Plan 核对 HOCON 的，
   两半制品来自不同时刻 = 「问题已修」与「门禁仍报错」同时出现。
3. **模型这一轮吐不出可解析的 Plan 时，service 记一轮空补丁而不是抛 500**
   （[repair.py:93-105](../backend/services/pipeline/repair.py#L93)）——把「模型没答好」
   降级成一个「没进展的轮次」，让去抖规则把它停下；但**模型不可用（`LLMUnavailableError`）
   如实抛出**（[:106-109](../backend/services/pipeline/repair.py#L106)）：
   环境问题不能伪装成「修不动」，否则用户看到的是「已尝试 3 轮仍未通过」。

**如果让我重写**

我会让**去抖的判据从「集合相同」升级成「集合没有变小」**。现在的判据是
「下一轮要修的阻塞项集合此前出现过」（`signature in seen`），它能挡住「一模一样地打转」，
但挡不住「修好 A 又弄坏 B、下一轮修好 B 又弄坏 A」这种**两者交替**的循环——
那种情况每次签名都不一样，回路会傻跑满 3 轮烧 token。改成
「本轮阻塞项数量 >= 上一轮数量，且本轮没有消掉任何一个上一轮的 finding」才停，
能覆盖交替循环，代价是要在 `_drive` 里多带一个「上轮 finding id 集合」。
这属于我面试里会讲的「去抖的强度」问题，不是现成的缺陷。

## 精读 8：`_guarded_node` 与生成锁（[workflow/graph.py:200](../backend/workflow/graph.py#L200) / [:116](../backend/workflow/graph.py#L116)）

**它要解决什么**

图装配期有两类**「不报错但结果不对」**：一是节点偷偷回写了一个未被声明的 state 键
（LangGraph 对未知键是宽容的，于是执行态字段混进工作流状态也没人发现）；
二是两个请求同时给同一条 pipeline 生成方案，第二个基于旧的检查点起步，产出一份谁都没看过的方案。

**逻辑怎么走的**

```python
# workflow/graph.py —— 出口守卫
202  allowed = frozenset(NODE_OUTPUTS[name]) | SHARED_OUTPUT_KEYS
203  undeclared = allowed - STATE_KEYS
204  if undeclared:                                # 装配期就报，不留到运行期
205      raise ValueError(f"NODE_OUTPUTS[{name}] 声明了 EtlWorkflowState 里没有的键…")

223  if unknown:
224      raise ValueError(f"节点 {name} 回写了未声明的 state 键 {unknown}…")
228  assert_json_serializable(out, where=f"节点 {name} 的输出")
```

```python

119  token = new_uuid()                             # 锁值必须唯一，否则下面的比较恒真
120  acquired = await redis.set(key, token, nx=True, ex=ttl)
123      raise GenerationInProgressError(details={"pipeline_id": int(pipeline_id)})
130      await redis.eval(RELEASE_LOCK_SCRIPT, 1, key, token)   # 只删自己那把锁
```

- **第 202-205 行**：装配图时就校验「`NODE_OUTPUTS[name]` 声明的键确实在
  `EtlWorkflowState` 里」。这类检查放装配期，成本是一次集合运算，收益是
  **配置错误变成启动失败而不是运行期的一个静默字段**。
- **第 222-227 行**：节点回写时再拦一次。两处都要，因为前者管「声明对不对」，
  后者管「这次真的写没写」。**出口守卫是三层状态隔离里唯一可自动验证的一环**。
- **第 228 行**：出口处过一遍 `assert_json_serializable`。放在**节点出口**而不是只在
  `snapshot()`——检查点是在节点返回时写的，等 `snapshot()` 才发现，**坏检查点已经落库了**。
- **第 119-120 行**：锁值是 `new_uuid()`。注释写得很硬：「改不了 token 必须唯一，否则比较恒真」。
- **第 130 行**：释放用 Lua **比较并删除**（脚本在 [:92-94](../backend/workflow/graph.py#L92)）。

  此时 A 收尾时一句裸 `DEL` 就把 B 的锁删了——B 的互斥保护凭空消失，
  而两个请求都返回成功，日志里什么都没有。**所以「比较」不是锦上添花，它和「加锁」同等重要。**
- **第 121-123 行**：取不到锁**立刻失败、不等待、不排队**（[graph.py:97-103](../backend/workflow/graph.py#L97)）。
  排队会让「用户连点两下」变成两条串行的生成，第二条基于第一条之前的旧 state 起步。
- **第 127-137 行**：释放失败**不能**盖住 body 里的异常——`finally` 里抛错会把

**最容易看漏的地方**

1. **`Optional[RunnableConfig]` 必须逐字这么写**（[graph.py:207-215](../backend/workflow/graph.py#L207)）。

   （因为本文件有 `from __future__ import annotations`），写成 `RunnableConfig | None`
   类型系统等价、**白名单却对不上**，于是每次 `add_node` 都打一条 UserWarning，
   而且 **config 根本不会被注入**。这不是风格问题，有用例守着
   （`tests/test_workflow_graph.py` 的 `test_graph_assembly_warns_nothing_about_the_config_annotation`）。
2. **锁必须包住 `ainvoke` 而不是 `astart` 那层**（[graph.py:402-403](../backend/workflow/graph.py#L402)）：
   `_run` 里 `async with generation_lock(...)` 包住 `graph.ainvoke`，节点里看不到锁。
   锁的粒度是「一整轮生成」，不是「一次 LLM 调用」。
3. **`build_graph` 不给 checkpointer 默认值**（[graph.py:264-271](../backend/workflow/graph.py#L264)）：
   默认 `None` 会让 `interrupt()` 在运行期报「没有 checkpointer」，而那时图已经跑了一半。
   装配期就要拿到它——「忘了配检查点」应当变成启动失败。

**如果让我重写**

我会把**生成锁的 TTL 与「一次生成最长可能耗时」绑起来**，而不是写死 600 秒。
现在（[graph.py:86-88](../backend/workflow/graph.py#L86)）TTL 是常量 600，
注释也承认是「暂定值」；但一次生成实际可能包含 3 轮自动修复 + 每轮一次 DeepSeek 调用，
慢的时候会逼近这个上限。锁提前过期 = 互斥保护消失（正好是上面那个 B 被 A 删锁的场景）。
稳妥的做法是**看门狗续期**：生成期间每隔 TTL/3 续一次（同样用「比较并续期」的 Lua），
代价是多一个后台任务；或者退一步，把 TTL 从 `settings` 读、与
`LLM_AUTOFIX_MAX_ROUNDS × 单次调用超时` 挂钩。**这是我知道但项目还没做的一处。**

## 精读 9：`commit` —— 把「审批通过」变成「一条排队中的运行」（[services/run.py:130](../backend/services/run.py#L130)）

> 这是 M3 的咽喉：**全项目只有两处签发执行权**——`commit`（签 `seatunnel.submit`）与 `request_cancel`（签 `seatunnel.stop`，[run.py:459](../backend/services/run.py#L459)），
> 两处是同一套写法。读懂其一，就懂了「为什么一张票只能用一次」不是靠自觉。
> 💡 `request_cancel` 值得多看一眼：**取消**也是外部副作用，所以它不直接调 SeaTunnel，而是**照样签一张绑定 `seatunnel.stop` 的票**、照样经 Outbox 交给 worker——
> 注释写明理由：「如果在这里直接调 SeaTunnel，就等于在服务层开了第二个副作用出口」。**「连停作业都不能绕过 ToolBroker」**是这条铁律最容易被破的地方。

**它要解决什么**

一张已经审批通过的准备单，要变成「一条正在排队的运行」。这件事有四个必须**同生共死**的产物：
运行记录（`execution_run`）、投递消息（`outbox_message`）、执行令牌（`capability`）、证据事件（账本）。
要么四者全在，要么全不在——**半成品是最坏的结果**：有运行没消息 = 一条永远不动的僵尸；有消息没运行 = worker 拿到一个不存在的 id。

**逻辑怎么走的**（八步，每一步的注释都写了「为什么是这个顺序」）

- 第 143 行：**`Idempotency-Key` 缺失直接拒**，不给默认值。因为 `execution_run.idempotency_key` 是唯一约束，用随机值兜底会把「重复点按钮」变成两条真实运行。
- 第 149 行（①）：**先查角色**——它只需要准备单的 `project_id`，比指纹校验便宜一个量级。**贵的检查放后面**不是微优化，它决定了「一个没权限的人狂点提交」会发生什么。
- 第 157 行（②）：`assert_committable` 做 be-13 的前置校验（指纹对得上 / 审批齐 / 未过期），并把**签发令牌需要的事实**一并返回（指纹、环境、租户、资源范围、影子表名）。这里定下了「批的到底是哪一份制品」。
- 第 162 行（③）：**并发闸门** `assert_no_active_run` —— 同一版本任一时刻只允许一条活跃运行。挡的是「两个请求同时提交，往同一张影子表写两遍」，而**全量覆盖写恰好不会报错**。
- 第 170 行（④）：**签发 Capability**，绑定 `preparation_id / env / artifact_sha256 / tenant_id / project_id / tool`。注意**绑的不是「谁点的按钮」**：按钮点两次不该产生两张票，而同一份制品在 dev 与 prod 执行**必须**是两张票——**环境在绑定里**。
- 第 180-195 行：落 `capability` 行，**只存 `token_sha256`**。这一行是「库被读走也没用」的全部依据。
- 第 197 行（⑤）：建 `ExecutionRun`，`status=queued`，把**影子表名 / 正式表名 / 错误表名**一起落库（它们来自冻结的资源范围，不是运行时现算）。
- 第 214 行（⑥）：Outbox 入队，**令牌原文随载荷走**。这是设计上唯一能把它交到 worker 手里的通道——因为库里只有哈希。注释还专门解释「它为什么不算凭据」：TTL 300 秒、单次消费、绑定制品。
- 第 223 行（⑦）：**两条证据分开记**——「一张令牌被签发」与「一次运行被创建」是审计上两个不同的问题（「谁批的」与「谁跑的」）。
- 第 264 行起（⑧）：推进流程状态，**刻意不用 `workflow.transitions` 的转移表**——那张表的出边只覆盖 M2 的生成/冻结段，审批之后的状态归 M3。用它会得到一个「看起来统一、实际漏掉一半状态」的转移检查。
- 函数返回前 `await session.commit()`：**事务边界在这一层**，四者同生共死。这里**不** `apply_async`——投递交给 beat 扫 Outbox（理由：进程崩了不能丢消息）。

**最容易看漏的地方**

1. 🔴 **`session.refresh(row)` 会吃掉尚未 flush 的改动**（同一文件 [:392](../backend/services/run.py#L392) 的注释就是这条的墓志铭）。
   `apply_transition` 一度在末尾 `refresh` 整行，于是 `tasks/execution._fail` 先写在实例上的 `error_message` / `failure_snapshot`
   **被冲回旧值**——运行**确实** failed，**失败现场却是空的**（详情页 `error_message` 为 null、`failure_snapshot` 是 `{}`），
   而账本里那条 `run.failed` 又写着失败了。**「有结论、没原因」的失败最难排查**。
   改法是**把刚写下去的那几个字段赋回内存实例**，而不是 `refresh`；抢锁失败那条只读状态列。
   ⚠️ 想改成「加一次 `flush()`」也行不通：项目守卫 `tests/test_service_commit_boundary.py` 规定 `services/` 里公开函数要自己 `commit()`，
   而 `apply_transition` 是**故意不提交**的（事务边界归调用方：worker 的 `session_scope`、API 侧 pause/cancel 各自提交）。
   **守卫逼出来的改法反而更对**：修掉的是「任何调用方暂存的改动都会被吃掉」这一类，而不是 `_fail` 这一处。
2. **`RunSummary` 与 `RunDetail` 的共有字段被 `model_dump()` 展开后再显式传一次 → `TypeError`**（`get_run`，本会话修掉的另一个缺陷）。
   后果不是某个边缘接口 500，而是**提交执行 / 运行详情 / 暂停 / 取消四条主路径全 500**，而**副作用已经落库**——
   用户看到「操作失败」、库里躺着一次真实运行。**报错的方向和事实相反**。
3. **停止失败时坚决不改状态**（[execution.py:284](../backend/tasks/execution.py#L284)）：控制面已标 `cancelled`，
   而这次调用没能让作业真停下——**库里的结论与事实不一致**，这个矛盾要留给人看，不是在这里悄悄改回 `running`。

**如果让我重写**

我会把「签发令牌」与「落运行 + 入队 + 记证据」**拆成两个函数**，用参数把「已签发的事实」传过去。
现在八步写在一个函数里是对的（事务要一致），但它已经长到 **150 行以上**，
而里面混着三种不同性质的判断：**权限**（①）、**业务前置条件**（②③）、**密码学操作**（④）。
三种判断的**失败语义不同**（403 / 409 / 500），挤在一个函数里时，后来者加一个新检查很容易放错位置——
比如把一次「指纹失效」写成 500。真拆的收益是：`facts` 变成显式入参，
「谁在什么条件下能签发」这一句话就有了**唯一一处**可读的地方。
另一个想改的是 **`idempotency_key` 现在只防「同一次点击」**：两个不同的 key 提交同一份准备单，
靠 ③ 的并发闸门挡（返回冲突而不是复用第一条运行）。更顺手的做法是让它的语义明确成
「同一准备单 + 同一制品指纹 → 同一运行」，把幂等键从 `run:{idempotency_key}` 换成
`run:{preparation_id}:{artifact_sha256}`——**但那样就把「重试」与「第二次提交」合并了**，
而这两件事在审计上该不该合并，我还没想透，所以现在没改。

## 精读 10：`publish_run` —— 为什么「换表」不能只判一次（[services/publish.py:315](../backend/services/publish.py#L315)）

**它要解决什么**

一次运行跑完、影子表写好之后，把影子表**原子地换到正式表的位置**（be-18）。
难点不在那句 DDL，而在：**这件事一旦被执行第二次，后果是把正式表换回旧数据——而且两次都「成功」**。
所以整个函数的结构不是「怎么换」，而是**「怎么保证它只发生一次、并且结论有据」**。
它**没有 HTTP 入口**（[publish.py:319](../backend/services/publish.py#L319) 的注释写着理由）：
把发布做成一个按钮，等于把一次 P0 动作的触发权交给任何能点按钮的人，而不是交给质量门禁。

**逻辑怎么走的**（九步，每一步都在堵一个具体的错法）

```python
328  # ① 幂等短路：本 run 已经有过一次 Swap 尝试，就**不再执行第二次**
331  prior = await _latest_event(..., event_types=(SWAP_SUCCEEDED, SWAP_FAILED))
337  if prior is not None: return _result_from_event(run=run, event=prior)
341  if await _consumed_publish_capability(...):   # 令牌消费过、但没有结论事件
350      await _fail_run(..., final_state="unknown", reason="prior_attempt_without_verdict")
369  await _claim_for_publish(session, run=run, now=now)     # ② 条件 UPDATE 抢状态
372  _assert_artifact_matches(facts)                          # ③ 准备单与冻结版本指向同一份制品
376  report = facts.quality_report                             # ④ 质量门禁（未过则抛，未通过即无令牌）
```

逐行说「在防什么」：

- **第 331-338 行 ①**：查的是**事件**不是状态——因为「换过表」这件事只有账本的事件能证明。
  短路返回的是**当时那条结论**，不是「成功」：上次失败也照样短路（失败也要留证，不能无限重试）。
- **第 341-365 行**：第三分支，也是最值得讲的一处——
  令牌**被消费过、却没有结论事件**，说明 DDL 很可能已经发出去了、结论没落账。
  这时唯一安全的动作是**什么都不做**：既不重试（可能换第二次）、也不当成功，
  而是标成 `unknown`（`final_state="unknown"`）并抛一条要求人工核对的错。
  **「不知道」在这里是一个合法的结论**，比猜一个强。
- **第 369 行 ②**：条件 UPDATE 抢状态，**未命中不许覆盖**——先看清是什么状态再决定。
- **第 372 行 ③**：制品一致性放在质量门禁**之前**。
  理由写在注释里：它发现的是**控制面自身的不一致**（准备单与冻结版本指向了不同的制品），
  这比「数据质量不合格」更根本——质量结论再对，制品不对也没意义。
- **第 376-395 行 ④**：质量未过 → **抛错之前先 `commit()`**（第 388 行），
  让「库里记着失败」与「用户看到失败」不脱节；而且此时**根本没签发令牌**，
  所以「未通过质量却执行 Swap」在令牌层面就不可达。
- **第 401 行 ⑤**：这才是**唯一真正的互斥**。注释把容易误解的地方说透了：
  ② 的条件 UPDATE 把 `status` 从 `running` 写成 `running`，**本身不是排他操作**，
  它只是「状态还算不算数」的检查。真正的互斥靠 Redis `SETNX`，且用 `finally` 释放
  （第 404-405 行）——临界区里的每条失败路径都不该靠「记得手动放锁」。
- **第 420-441 行 ⑥**：只读预检（影子表在不在、空不空、正式表在不在）。
  不过就**在签发令牌之前**失败，所以**正式表连一条写命令都没见过**。
  `allow_empty_shadow=target.read_rows == 0`：源端本来就零行时，空影子表是合法的。
- **第 443-452 行 ⑦**：令牌在门禁与预检**都过了之后**才签。
  「门禁失败时不签发」比「签了再拒绝」强一个数量级。
- **第 484-497 行 ⑨**：**服务端自己再观测一次**，与执行器报回的 `state` 互为交叉验证。
  两个独立观测不一致 → 判 `unknown`（用例里那个「撒谎的假发布器」就是守这一条的）。
- **第 499 行起**：结论落状态与账本，payload 里带**换表前后的表指纹**与 `fingerprint_scope`
  ——「换对了没有」这句话必须能对着证据复述，而不是只写一个 `succeeded`。

**最容易看漏的地方**

1. 🔴 **真正的互斥是 Redis 独占键（⑤），不是状态条件 UPDATE（②）**。
   两者都在这个函数里、相隔 30 行，**看起来是同一件事**。
   只留 ② 的话，Celery 双投（至少一次投递的常态）会双放行——
   而 Swap 是**对合变换**，执行两次的净效果是**把正式表换回旧数据**，且两次都返回成功。
   这是全项目「最贵的 30 行」。
2. **① 短路的是「事件」而不是「状态」**：把它写成查 `run.status == succeeded` 就错过了一半
   （上次失败、状态回到 failed 的情况会重新走一遍全流程）。
3. **`_publish_claimed` 单独拆出来不是分层洁癖**：拆开才能让「获取独占键 → 释放独占键」
   在**源码上**包住完整临界区（[publish.py:411-414](../backend/services/publish.py#L411) 的 docstring）。
   否则以后加一条失败路径，就要靠人逐条数「这条放了锁没有」。
4. **「令牌消费过但没有结论」必须与「换表失败」分开**：后者可以留下明确结论，
   前者连 DDL 有没有生效都不知道。**两种未知要分开记**，否则人工核对时拿不到正确的处置动作。
5. **发布没有人工重试入口**（[publish.py:329](../backend/services/publish.py#L329) 的注释）：
   不是偷懒，而是「重投只可能来自 Celery」这个前提下，重试入口只会给人一个
   把正式表换回去的机会。回滚是**另一条**受管路径（`target.rollback_cleanup` + 四连范围校验），
   不是「再点一次发布」。

**如果让我重写**

我会把 ③④⑥ 这三道前置条件抽成**一张数据驱动的检查表**（每项：名字 / 判定函数 / 不过时的
`reason` 与错误码 / 是否允许签发），循环执行。理由：现在这三道检查各自散在 100 行里，
**「哪些条件不过就不签发」这句话需要在脑子里重新拼一遍**；
抽成表之后它变成可数的一行行数据，还能顺手加一条元用例守「每个 reason 都有对应的错误码」。
代价是有些检查需要 `session` 与网络观测（不是纯函数），得把「观测」与「判定」再拆一层——
这也是我暂时没动它的原因：这三道检查的顺序本身有语义（③ 必须在 ④ 前），
表格化容易把顺序变成隐式的东西。
