## 1. 模块定位

### 1.1 做什么

1. **Prepare（`create_preparation`）**：把一个**已冻结** `pipeline_version` 的冻结事实固化成一条
   不可变 `preparation`（仅 `status` 可改），算出 `input_fingerprint`、组装 `resource_scope` /
   `budget` / `rollback_plan`，调 PDP 得出 `risk_level` 与 `required_slots`。**零外部副作用**。
2. **Approve（`decide`）**：按职责槽收集 `approval_decision`（一个槽只允许一条），
   强制四眼与职责分离，接受 `approve` / `reject` / `return` 三种决定，推导并推进 `preparation.status`。
3. **流程位置与过期**：维护 `preparation.status`；`expire_due_preparations` 把过期未批完的单置 `expired`。
4. **向 be-14 暴露 `assert_committable`**：Commit 前的最终一致性校验（状态 / 有效期 / 槽齐备 /
   制品指纹三方一致 / 输入指纹未变 / 档案就绪 / 回滚方案 / 预算与范围成形），返回 `CommittableFacts`。
5. **证据留痕**：每一次准备、每一次审批、每一次**协议类**拒绝都写 `evidence_event`。

### 1.2 明确不做

- **不签发 Capability、不创建 `execution_run`、不写 `outbox_message`**——那是 be-14 的 Commit。
  Prepare 阶段**零外部副作用**（`services/preparation.py` 模块 docstring：`1-7`）。
- **不调用任何 `ToolName`**（无 DDL、无 SeaTunnel、无目标库写入）。影子表名只**拼**不**建**
  （`shadow_table_name`，`:113`）。
- **不修改 `pipeline_version` 及其四件制品**（🔒 不可变）；改动只能冻结新版本 → 新 `preparation`。
- **不判定「谁能当审批人」**——角色授予属 be-02；本模块只**校验**已授予的角色（`active_roles`）。
- **不实现 Commit 路由**（`POST /api/v1/preparations/{id}/commit` 属 be-14，见 §7）。
- **不做门禁**（be-11）。本模块**复用** `build_gate_context` 拿判定结果，不自己跑门禁检查。
- **不自造错误码**（`00-模板与全局约定.md` §一.7）；全部取自 `core/errors.py`。

## 5. 核心逻辑

### 5.1 Prepare 时序（`create_preparation`，`services/preparation.py:520`）

1. 载入 `pipeline_version`（`repository.load_version`）与 `pipeline`；`payload.project_id` 若给**只做一致性校验**
   （项目的唯一事实来源是 `pipeline.project_id`，`:534`–`:537`）。
2. 角色校验：`_roles` 现查 `role_assignment`，须持 `maker`（`_CREATE_ROLES`，`:96`/`:541`），否则 `ROLE_REQUIRED`。
3. **冻结态校验**：`version.frozen_at is None` → `CONFLICT`（未冻结的版本是草案，锚不住，`:544`）。
4. **流程推进**：`_enter_preparing`（`:702`）用 `workflow.transitions.assert_transition(status, "prepare")`
   校验合法（只覆盖 `version_frozen → preparing`），再把 `pipeline.status` 落成 `PENDING_APPROVAL`。
5. 载入四份制品（`repository.artifact_rows`）+ `_require_fresh_profile`（`:261`）：版本钉住的源端档案
   必须**还在、还 READY、（若设了有效期）未过期**，否则 `METADATA_PROFILE_EXPIRED`。
6. `build_gate_context`（`:559`）：**与门禁共用同一份上下文构造**，产出 `env` / `level` /
   `source_metadata_sha256` / `policy_decision`——「门禁判过的」与「准备单上写的」不可能分叉。
7. `decision.blocked`（P0）为真 → 先写 `POLICY_BLOCKED` 事件再抛 `POLICY_BLOCKED`，**不落任何 `preparation`**（`:571`–`:595`）。
8. 算 `input_fingerprint`（`_fingerprint_payload`，`:435` + `core.ids.fingerprint`，`:602`）。
9. `INSERT preparation`（`:612`）：`status=pending`、`frozen_at=now`、
   `expires_at=now + settings.PREPARATION_TTL_HOURS`（默认 72 h，`core/config.py:147`）。
10. `supersede_previous`（`:639`）：同 pipeline 上仍活跃的旧单 → `superseded`（见 §5.6）。
11. 写两条账本事件（同事务）：`preparation.created` + `policy.evaluated`（`:657`/`:672`）。
12. `await session.commit()`（`:698`）后返回 `get_preparation(...)`。
13. **不产生任何 `outbox_message` / `capability` / `execution_run`**（`test_发起准备零副作用` 守住）。

### 5.2 Approve 时序（`decide`，`services/approval.py:108`）

1. 载入 preparation / version / pipeline（均带 `tenant_id`）。
2. **角色**：审这个槽的人须真持对应角色（`active_roles` 现查，不信 JWT），否则 `ROLE_REQUIRED`（`:139`–`:142`）。
3. **槽匹配**：`slot ∈ row.required_slots`，否则 `VALIDATION_ERROR`（`:147`–`:150`）。
4. **自批拦截**（协议类）：`is_self_approval(row.created_by, subject.user_id)` → 写 `approval.self_denied` 后抛
   `SELF_APPROVAL_FORBIDDEN`（`:156`–`:167`）。
5. **职责混用**（协议类）：`check_duty_separation` + `check_dual_checker_distinct`
   （另一槽取 `existing[other].approver_id`，未决定则跳过）→ 写 `approval.duty_denied` 后抛 `DUTY_CONFLICT`（`:170`–`:197`）。
6. **指纹一致性**（协议类）：`version.sha256 == row.artifact_sha256` **且** 重算 `current_input_fingerprint ==
   row.input_fingerprint`，否则写 `approval.stale_denied` 后抛 `FINGERPRINT_MISMATCH`（`:199`–`:224`）。
7. **状态合法性**（状态类）：`row.status ∈ {pending, partially_approved}`，否则 `CONFLICT`——**只写 structlog 不写账本**（`:228`–`:240`）。
8. **有效期**：`expires_at <= now`（经 `as_utc`）→ `PREPARATION_EXPIRED`（`:246`）。
9. **不覆盖既有决定**：该槽已有决定 → `CONFLICT`（状态类，不写账本）（`:250`–`:260`）。
10. `INSERT approval_decision`（冗余写 `preparation_created_by` / `artifact_sha256` / `fingerprint_at_decision`）（`:263`–`:278`）。
11. `derive_status()` 算新状态并 `UPDATE preparation.status`（走 ORM 白名单守卫）（`:280`–`:287`）。
12. **推进 `pipeline.status`**：`approved → APPROVED`、`rejected → REJECTED`；
    `superseded`（return 路径）**不改 pipeline**。此处**不走转移表**（见 §10 偏离 8）。
13. 写 `approval.granted|rejected|returned`（`comment` 正文入 payload）→ `commit()`。

### 5.3 状态机

| 当前 status | 事件 | 新 status | 触发者 |
|---|---|---|---|
| `pending` | 某必需槽 approve（未齐） | `partially_approved` | `derive_status` |
| `pending` / `partially_approved` | 全部必需槽 approve | `approved` | `derive_status` |
| `pending` / `partially_approved` | 任一槽 reject | `rejected` | `derive_status` |
| `pending` / `partially_approved` | 任一槽 return | `superseded` | `derive_status` |
| `pending` / `partially_approved` | 新准备单创建 | `superseded` | `supersede_previous` |
| `pending` / `partially_approved` / `approved` | `now() >= expires_at` | `expired` | `expire_due_preparations` |
| 任一终态 | 任意决定 | 不变（`ConflictError`） | — |

**非法转移处理**：`decide` 只接受 `{pending, partially_approved}`；终态一律 409 `CONFLICT`，
把 `(status, slot, decision)` 记入 structlog（`preparation_decide_rejected`，`:229`/`:251`），**不写账本**——
非法转移是客户端状态过期，不是协议拒绝（`services/approval.py` 模块 docstring 第 4–10 行）。
`approved` 是唯一允许 Commit 的状态，**且过期后不许执行**（`expires_at` 是硬边界）。

### 5.4 状态推导（纯函数，`services/approval.py:77`）

优先级 `reject` > `return` > 全部 approve > 部分 approve > `pending`。`required` 为空（P3 免审批）
直接返回 `approved`（否则免审批单永远卡在 pending）。「任一槽 reject 即 rejected」**排在全部 approve 之前**，
使结论与遍历顺序无关（`test_状态推导的优先级是拒绝大于退回大于通过`）。

### 5.5 四眼的四条判定（复用 be-02，本模块不重写）

`has_role` / `is_self_approval` / `check_duty_separation` / `check_dual_checker_distinct` 全在
`engines/policy/roles.py`；违规抛 `ValueError`，由 `services/approval.py` 翻译成
`ROLE_REQUIRED` / `SELF_APPROVAL_FORBIDDEN` / `DUTY_CONFLICT`。三层兜底：

| 层 | 机制 | 位置 |
|---|---|---|
| 服务端 | 四条纯函数 + 角色现查 | `services/approval.py:139`–`:197` |
| DB CHECK | `ck_approval_decision_no_self_approval` | `models/governance.py:130` |
| 授权源头 | 授予时 `check_duty_separation`（be-02）；审批时再复核 | be-02 |

### 5.6 一个槽只有一条决定 / 重复发起

`uq_approval_decision_preparation_id_slot` + `__immutable__`（无白名单）共同保证决定写即不可改、
一个槽永远只有一条。同一槽第二次提交 → 409。改主意的唯一合法路径：换 `pipeline_version` → 新 `preparation`
→ 重走双槽审批；旧单连同其 `approval_decision` 永久保留。
`supersede_previous`（`services/preparation.py:717`）对旧单**只改 `status` 列**、不物理删除、
不动其 `approval_decision`，并逐行赋值（不用批量 `update()`，否则绕过 ORM 守卫），每行写一条
`preparation.superseded` 事件（payload `{replaced_by, reason}`）。

### 5.7 `assert_committable`（Commit 前置，`services/preparation.py:817`）

十条检查**从便宜到昂贵**排序（先在内存判状态与槽位，再查库比指纹）：

| # | 校验 | 不满足 | 代码 |
|---|---|---|---|
| ① | `status == approved` | `PREPARATION_EXPIRED` / `APPROVAL_INCOMPLETE` | `:838`–`:843` |
| ② | `expires_at` 未过（硬边界，`as_utc`） | `PREPARATION_EXPIRED` | `:846` |
| ③ | 必需槽齐备且每条都是 approve | `APPROVAL_INCOMPLETE` | `:850`–`:861` |
| ④ | 版本仍冻结（`frozen_at` 非空） | `CONFLICT` | `:871` |
| ⑤ | 制品指纹三方一致：`version.sha256 == row.artifact_sha256`，且 `expected_artifact_sha256` 若给须相等 | `FINGERPRINT_MISMATCH` | `:875`–`:878` |
| ⑥ | 源端档案仍就绪未过期 | `METADATA_PROFILE_EXPIRED` | `:886` |
| ⑦ | 重算 `input_fingerprint` 与 `row.input_fingerprint` 一致 | `FINGERPRINT_MISMATCH` | `:889`–`:898` |
| ⑧ | 每条决定的 `fingerprint_at_decision == 当前指纹` | `FINGERPRINT_MISMATCH` | `:902`–`:906` |
| ⑨ | `rollback_plan.steps` 非空 | `CONFLICT` | `:909`–`:911` |
| ⑩ | `budget` 与 `resource_scope.writes` 成形 | `CONFLICT` | `:914`–`:915` |

全部通过 → 返回 `CommittableFacts`。**本函数只读，不写任何表**（写与事务属 be-14）。
与设计 §6.5 的差异（不重跑 PDP / 不逐条复查制品哈希 / 不复查自批）见 §10 偏离 2。

### 5.8 输入指纹（`_fingerprint_payload`，`services/preparation.py:435`）

形状 `{v:1, source_metadata_sha256, sources[], secrets[], quality{}, supervision{}}`，
经 `core.ids.fingerprint`（内部走 be-12 的 `canonical_bytes`）——**禁止在此手写 `json.dumps`**。
`secrets` 覆盖 `secret_reference.version`：Vault 轮转后即使表结构没变，旧审批也失效。
`create_preparation` 与 `current_input_fingerprint` **共用同一份 `_fingerprint_payload`**：两处各写一遍
的结果是「刚发起的单立刻报指纹不符」。比率的 `Decimal` 一律 `str()` 后进指纹（跨平台逐字节可复现）。

### 5.9 影子表命名（`shadow_table_name`，`services/preparation.py:113`）

`<表>__shadow_v<版本号>`；超 64 字符时截断表名并补 8 位哈希（尾部版本段保留）。
**全仓库唯一一份定义**：be-14/be-15/be-18 必须复用它——审批人看到的
`resource_scope.writes[*].shadow_table` 与执行期真正建的表一旦不是同一个名字，等于「批的和写的不是一张表」。

## 7. 异步任务与尚未实现的部分

- **本模块无写副作用**，因此不投 Outbox、不建 Celery 任务。`create_preparation` 是一次同步请求内完成的
  读 + 判定 + 写库。
- ❌ **`expire_due_preparations` 无生产方**：设计 §3.2 说由 `tasks/maintenance.py` 周期调用。实际
  `tasks/maintenance.py` 只有 `enforce_retention` / `checkpoint_ledger` 两个骨架任务，
  `celery_app.py` 的 `beat_schedule` 也没有过期扫描项；全仓库除用例与定义处外**无调用方**。
  后果：`preparation.status` **永不自动转 `expired`**，过期只能靠 `decide` / `assert_committable`
  的实时判定拦下（二者都判 `expires_at`）。见 §12。
- ❌ **前沿契约里有、后端没有的 3 条路由**（`frontend/src/api/preparation.ts`）：
  `GET /preparations/{id}/timeline`、`GET /preparations/{id}/risk-reasons`、`POST /preparations/{id}/commit`
  （末者归 be-14）。前两者的数据其实已经在 `PreparationDetail.timeline` / `.risk_reasons` 里。
- ❌ **`approval_state()`（`services/approval.py:401`）是死代码**：无任何调用方。
- ❌ **`platform` 级集成/E2E 未自动化**：幂等重放、跨租户、真 PG 并发、账本验链——本机无 Docker（CLAUDE.md §9），
  欠账与 M2 一致。

## 11. 实现期发现的问题

> 四条**真缺陷**都在实现期被用例当场抓获并修掉，此处登记「症状 → 根因 → 修法 → 守它的用例」。
> 末尾附一条 SQLite 时区坑（纪律项）。

### 缺陷 1 — `_build_resource_scope` 误用 `PlanOutput.schema_name`（发起准备 500）

- **根因**：目标端的库名列是 `PlanOutput.database`，源端才是 `PlanInput.schema_name`。写错属性名不是「取到空值」而是 `AttributeError`。
- **症状**：任何 `create_preparation` 直接 500，报错栈指向拼 `resource_scope` 那一行，读起来像「数据源字段缺失」，实际是属性名错。
- **修法**：`writes[*]` 取 `item.database`（`services/preparation.py:322`），并在注释里写明「源端才是 `schema_name`」（`:320`–`:323`）。
- **守它**：`test_发起准备落单并推进流程状态`（跑通 `_build_resource_scope`）、`test_提交前校验通过并给出事实`（断言 `resource_scope["writes"][0]["shadow_table"] == "orders_wide__shadow_v1"`）。

### 缺陷 2 — `supersede_previous` 对没有 `project_id` 列的 `PipelineVersion` 加连接条件（重发准备单 500）

- **根因**：`PipelineVersion` **没有** `project_id` 列（归属由 `pipeline` 表达，见 `models/pipeline.py`）。在 `supersede_previous` 的查询里追加 `PipelineVersion.project_id == ...` 会得到 `AttributeError`。
- **症状**：**第二次**发起准备（同 pipeline 已有活跃旧单）时 500，看起来像「重发这个功能坏了」，而首次发起一切正常。
- **修法**：范围靠 `join(PipelineVersion, ...).where(PipelineVersion.pipeline_id == pipeline_id)` 收窄，不碰 `project_id`（`services/preparation.py:739`–`:749`），注释写明「想在这里再补一条 project 相等，只会得到一个 `AttributeError`」。
- **守它**：`test_重新发起会取代旧单`（重发路径全绿，旧单置 `superseded`）。

### 缺陷 3 — 详情 / 状态 / 时间线读 `Preparation.decisions` 关系集合（会话身份映射快照）

- **根因**：`Preparation.decisions` 是 `lazy="selectin"` 关系集合，**在会话身份映射里是快照**——同一会话内刚 `INSERT + flush` 的那条决定不会进集合，除非显式 `populate_existing`。
- **症状**（三处，都指向同一根因、但表现各不相同）：
  1. 刚落决定后立刻读**详情** → `can_commit=false`（少算了刚批的那一槽）；
  2. **时间线**少一格——少的恰恰是「刚刚发生了什么」；
  3. **待办列表**把刚批过的单子又列一次（`mine_decided` 判断依赖决定集合）。
- **修法**：一律**查库**取决定——`decisions_for()`（批查，`:160`）/ `decisions_of()`（单查，`:183`），
  `get_preparation` / `get_status` / `_timeline` / `list_preparations` / `approval._decisions` 全部改走它们。
  注释写明「关系集合要么是会话快照、要么得靠 `populate_existing`，而那种『读的人得记得加一个选项』的正确性迟早会漏」（`:165`）。
- **守它**：`test_时间线按时间顺序拼出关键节点`、`test_状态轮询接口给出待决槽`、`test_待办列表只给该槽未决的人`、`test_两槽齐备后通过并推进流程状态`。

### 缺陷 4 — `_summary()` 与 `can_commit` 用了两份决定来源（同一响应自相矛盾）

- **根因**：`_summary()` 一度**自己**从 `row.decisions` 现取 `decided_slots`，而同一响应里的 `can_commit`
  用调用方**新查**的决定算——两者是同一份数据的两份来源。
- **症状**：`can_commit=true` 而 `decided_slots=[]`（前端拿到自相矛盾的响应：按钮可点，但显示「无人审批」）。
- **修法**：`_summary()` 收 `decided: Mapping` 参数（调用方传入），**不读** `row.decisions`（`services/preparation.py:1001`–`:1017`）。
- **守它**：`test_两槽齐备后通过并推进流程状态`（`can_commit=true` **且** `decided_slots` 两槽齐）、`test_列表的can_commit是廉价判据`。

### 纪律项 — 库读出的 datetime 在 SQLite 上是裸值，凡比较/排序都要过 `core.ids.as_utc`

生产（PG `timestamptz`）读回来**带时区**，`as_utc` 是空操作；SQLite **不保留时区**，读回来是**裸值**。
于是「拿库里的时间与 `utcnow()` 比」会 `TypeError`（dev 跑用例才暴露，生产看不出），
「拿两个都从库里读出的裸值再排序」却会**通过**——同一张单子一半时间戳带时区、一半不带，症状是排序偶发错乱。
本模块的出口统一走 `services/preparation.py::_at`（`:148`），并在所有比较/排序处显式 `as_utc`：
`_require_fresh_profile:292`、`_can_commit:986`、`approval.decide:246`、`_timeline` 的排序键 `:1360`、
详情决定的排序键 `:1129`。**别只修崩掉的那一处**。
