## 1. 模块定位

### 1.1 做什么

1. **确定性判定**：`evaluate(ctx, now=...) → GateResult`（`engines/gate/gate.py:56`）是「让不让上生产」的**唯一判定入口**，纯同步函数，可复现（同一份制品 + 同一份策略 + 同一份档案 → 同一份结论）。
2. **五类检查 + 固定执行序**：`policy → syntax → schema → mapping → resource`（`CHECK_ORDER`，`engines/gate/types.py:32`），任一类产生 `block` 即**短路**（`gate.py:75-77`）。
3. **三档结论合成**：`pass / warn / block`（`compose_conclusion`，`types.py:188`），`info` 不参与结论。
4. **可定位的 finding**：每条 finding 带 `id`（确定性）、`severity`、`category`、`code`、**已脱敏**的 `message`、判别式 `locator`（HOCON 行 / Plan 路径 / DAG 节点 / 源表）与可选 `suggestion`。
5. **有限自动修复回路**：`arun_autofix_loop`（`engines/autofix/loop.py:339`）——≤3 轮、去抖、策略阻塞即停手、补丁是唯一变更形态。
6. **Plan 补丁**：`PlanPatch` / `apply_plan_patch`（`engines/autofix/patch.py:56` / `:81`），JSON-Pointer 风格，`PatchError` 表达非法路径。
7. **门禁的 service 入口**：`build_gate_context`（`services/pipeline/gating.py:137`，读档案 + 读数据源 + **跑 PDP**）+ `run_gate`（`gating.py:216`）。
8. **两个图节点**：`gate_node`（`workflow/nodes/gate.py:60`，结论 → 状态转移）与 `autofix_node`（`workflow/nodes/autofix.py:59`，只改 `draft_plan`）。
9. **两个接口**：`GET /pipeline-versions/{version_id}/gate`（读**落库**结论，`api/pipeline_versions.py:109`）与 `POST .../autofix`（跑一轮修复，`:123`）。

### 1.2 明确不做

- **不做风险评级**（be-07）。门禁只把 `PolicyDecision` 翻译成 finding（`checks/policy.py`），判定本身在 `engines/policy`。
- **不做审批**（be-13）。`required_approval_slots` 只是一条 `info` 提示，槽位与人选归 be-13。
- **不做冻结**（be-12）。门禁只产出结论；「有阻塞就不许冻结」由 `freeze_version` 与 `freeze` 节点各自执行。
- **不做执行**（M3）。finding 里的 `locator` 只是给人看的落点，不驱动任何副作用。
- **不做 IO、不取时间、不联网**：`engines/gate/*` 与 `engines/autofix/*` 是纯函数层——档案、PDP 结论、解析结果一律由 service 装进 `GateContext`（`engines/gate/context.py:85`），`now` 由调用方注入。
- **不修 HOCON**：修复的产物只有 `draft_plan`（`workflow/nodes/autofix.py:31-35` 说明为什么），HOCON 由紧随其后的 `generate_hocon` 节点按新 Plan 重渲染。

## 5. 核心逻辑

### 5.1 检查清单：每类判什么、结论怎么合

| 执行序 | 检查 id | 类别（前端） | 判什么 | 产出的 finding `code` |
|---|---|---|---|---|
| 1 | `policy` | `policy` | PDP 的 `PolicyDecision`：缺结论默认拒绝、P0/P1 阻断、需要两个审批槽（info）、申报预算超过 PDP 上限 | `missing_policy_decision`、`policy_blocked`、`required_approval_slots`、`budget_exceeds_policy` |
| 2 | `syntax` | `syntax` | HOCON 能否解析；令牌字段是否在白名单；**是否出现明文口令** | `syntax`、`bad_placeholder`、`findings_truncated`（截断时追加） |
| 3 | `schema` | `schema` | 源列是否存在、类型是否兼容（`ok/cast/no` 三态）、目标列是否存在、可空性与长度、档案是否过期 | `source_field_absent`、`source_type_mismatch`、`target_field_absent`、`nullability_violation`、`length_truncation_risk`、`unknown_data_type`、`type_incompatible`、`type_needs_cast`、`profile_expired` |
| 4 | `mapping` | `field_mapping` | 映射自洽性：目标字段重复、同一源字段多次映射、派生列缺输入/类型不匹配、质量规则引用、**敏感字段没脱敏** | `duplicate_target_field`、`source_field_mapped_multiple_times`、`transform_missing_input`、`transform_kind_mismatch`、`quality_rule_field_missing`、`dangling_quality_rule_id`、`mask_missing_for_sensitive` |
| 5 | `resource` | `resource` | 数据源是否登记、资源范围是否越权/跨库、密钥引用是否登记、预算是否为正 | `data_source_not_registered`、`scope_unauthorized`、`cross_database`、`unregistered_secret`、`budget_nonpositive` |

具体判定行号：`checks/policy.py:55/122`、`checks/syntax.py:42`、`checks/schema.py:220/344/409`、`checks/mapping.py:50`（六个子函数）、`checks/resource.py:52`（五个子函数）。

**结论合成**（`types.py:188`）：`block > warn > pass`，写成 `max(severity_rank)` 而不是「有 block 就 block，否则有 warn 就 warn」——
后者在加第四档严重度时会静默错。`info` 的 rank 是 0，**不参与**结论（`types.py:42-44` 说明了为什么）。

### 5.2 短路：遇到第一个阻塞就停

`evaluate` 按 `CHECK_ORDER` 顺序跑，**任何一类产生 `block` 就 `break`**（`gate.py:75-77`）。理由是：

- 后一类检查的**前提**已被推翻。HOCON 解析失败时还去核对「列存不存在」，只会对着一个空配置报出几十条连带错误，把真正的原因埋在噪声里。
- 门禁的读者是人。一次报 3 条相关的、而不是 40 条连带的，才修得动。

代价是「一次只暴露一类问题」，多轮修复——这个代价是有意付的（`gate.py:21-27`）。
`info` 与 `warn` **不触发短路**。诊断用途走另一个函数 `evaluate_all`（`gate.py:88`）——**刻意不做成开关**：
把开关打开的生产路径会开始一次报 40 条。

单类检查内部还有一道上限：`MAX_FINDINGS_PER_CHECK = 50`，超出时截断并追加一条 `findings_truncated` 的 `warn`（`checks/base.py:34/40/81`）。

### 5.3 🔴 PDP 必须走 `services.policy.decide_for_project`

`build_gate_context` 里那行 `await decide_for_project(...)`（`gating.py:190`）不能换成直接调 `engines.policy.decide`：

- 直接调会漏掉三件只有 service 层知道的事：① 生效规则集（内置基线 ⊕ 租户覆盖，尤其是「谁关掉了哪条基线」）；② 预算默认值（来自 Settings）；③ 被忽略的越权覆盖要入账。
- 漏掉②的后果**不是判松，而是判死**：`engines/policy/pdp.py:57` 在 `defaults=None` 时落到 `_ZERO_DEFAULTS`（`pdp.py:115`，五项上限全为 **0**），
  于是五项预算条条超限、门禁**永远 block**，而报错文案是「超过 PDP 批复的上限 0」——
  看起来像策略表没配，实际是调用方少传了预算来源。`gating.py:184-189` 留了一段注释守这条。

### 5.4 finding 的三条纪律

1. **`locator` 是扁平的可辨识联合**（`types.py:101`，Pydantic `discriminator="kind"`），四种形状各自独立：`HoconLocator(line/column)` / `PlanLocator(path)` / `DagNodeLocator(node_id)` / `SourceTableLocator(data_source_id/schema/table)`。
   前端靠 `locator.kind` 决定跳去 HOCON 编辑器某一行还是 Plan 表单某个字段。
2. **`message` 必须已脱敏**：统一出口 `safe_message()`（`checks/base.py:66`），business 代码不得自行拼——
   finding 的来源里有列名、表达式等可能含样值的内容，而文案会被前端原样渲染。`scan_plaintext_secret_fields()`（`checks/base.py:131`）把疑似凭据的赋值行抹掉（用例 `test_gate_checks.py:240`）。
3. **`id` 必须确定性**：`"{check_id}.{code}.{locator_key}"`（`types.py:198`）。
   自动修复靠它去抖（`frozenset((check_id, code, locator_key))`），带随机数或时间戳会让「同一问题修不掉」被判成「新问题」，于是无限重试。
   用例：`test_gate_checks.py:650`（同输入两次运行 finding id 完全一致）。

`make_finding()`（`types.py:203`）是构造 finding 的**唯一出口**——`id` 与 `category` 由 `check_id` 派生，调用方不许自己拼（`check_id_to_category` 处理唯一的例外：检查 id 叫 `mapping` 而类别叫 `field_mapping`）。

### 5.5 自动修复回路的四条约束

`_drive()`（`engines/autofix/loop.py:109`）是一个**生成器**，被同步 / 异步两个驱动共用（`loop.py:116-127` 说明为什么）——
若为「修复要调 async 模型」而把本体改成 `async def`，Celery 里那些纯同步调用方就被迫套事件循环；若两处各写一遍控制流，四条约束就会出现两份实现。

| 约束 | 实现 | 用例 |
|---|---|---|
| 1. **轮次上限 ≤ 3** | `max_rounds` 由 `settings.LLM_AUTOFIX_MAX_ROUNDS` 注入（`workflow/nodes/autofix.py:53`、`artifacts.py:78`） | `test_autofix.py:212`（轮次用满标耗尽） |
| 2. **策略阻塞即停手** | 出现 `category == "policy" && severity == "block"` 的 finding，`repair` 一次都不调（`loop.py:147-160`）；`GateResult.has_policy_block` 是同一判据（`types.py:184`） | `test_autofix.py:114`、`:137`、`:515`（异步驱动下策略阻断依旧零调用） |
| 3. **补丁是唯一变更形态** | 修复只能通过 `PlanPatch`（JSON Pointer 的 add/remove/replace）；`apply_plan_patch` 抛 `PatchError` 时该轮**无效但轮次照常消耗**（`loop.py:172-176`） | `test_autofix.py:336`、`:392`–`:460` 八条 |
| 4. **去抖** | 下一轮要修的阻塞项签名（`frozenset((check_id, code, locator_key))`）此前出现过 → 立即停下（`loop.py:199-204`）；`seen` 初值就是**第一轮**的签名 | `test_autofix.py:156`、`:180` |

`AutofixOutcome`（`loop.py:73`）区分三种「没修好」：`exhausted`（轮次用尽）、`stopped_by_debounce`（打转）、`stopped_by_policy`（策略拒绝）；
前端只有 `autofix_exhausted` 一个布尔，所以 `AutofixOutcome.autofix_exhausted` 把前两者都算进去（`loop.py:100-106`）——**「还有救」与「没救了」必须能分辨**。

### 5.6 🔴 策略阻塞不进修复回路（图结构上可见）

`route_after_gate`（`workflow/graph.py:176`）对 `has_policy_block` 直接返回 `terminal`，**不进 `autofix`**：

> P0/P1 是治理判定，模型改不掉，让它改只是把「策略拒绝」伪装成「模型没修好」，还白烧三轮 LLM 的钱。（`graph.py:179-182`）

这一条与 §5.5 约束 2 是同一个约束的两处实现，**放在路由而不是节点里**，是为了让「它压根没进修复」这件事在图结构上可见。

### 5.7 复检用同一份 ctx，不重建

`RecheckFn` 的签名由 engines 定死为同步的 `(plan, hocon) -> GateResult`（engines 不许做 IO），
所以复检只能靠「拿**同一份** `GateContext` 换掉 `plan` / `hocon_content` / `parse_result` 三个字段再跑一次纯函数」：

- 图内：`workflow/nodes/autofix.py:17-23` 说明为什么在本节点 `await build_gate_context(...)` 建一次、**不能每轮重建**；
- 手动：`artifacts.py:252-269` 的 `recheck` 闭包用 `context.model_copy(update={...})`。

两处做法**逐字一致**，否则「手动修复」与「图内修复」会对同一份制品给出不同结论。
每轮重建还有第二个坏处：3 轮修复会读 3 次库、拿到 3 个可能不同的档案快照，让「为什么第 2 轮结论变了」无从解释。

### 5.8 🔴 `validation_result["gate"]` 直接是 `GateResult`，不是信封

门禁结论平铺进 HOCON 制品元信息：`{"parse": {...}, "gate": <GateResult>, ...}`（`gating.py:113-131`）。
`gate` 节点把它与渲染段合并后放回 `hocon_meta`（`workflow/nodes/gate.py:143`），`_persist_turn` **原样落库**（`generation.py:426-432` 留了一段注释说明早先这里又拼了一次）。

- **别再套一层**（写成 `{"gate": artifact_meta()}`）：那样 `validation_result["gate"]` 就成了信封，
  `get_gate` 拿它当 `GateResult` 解析会报「`evaluated_at`/`conclusion` 缺失」，**表面看像门禁没跑，实际是元信息套了两层**。
- 同理，`generation_context` 手拼 dict 时多一个 `plan_issue_count`，症状是「生成成功、答题 422：Extra inputs are not permitted」——**写的一侧多一个键，报在读的一侧**。
- 规矩：这类 JSON 列的形状**只有一份定义**（`gating.render_meta` / `GateOutcome.artifact_meta` / `clients.llm.base.GenerationContext`），消费方对未知键一律 `extra="ignore"`。
- 用例：`tests/test_artifact_meta_shape.py:83`（`gate` 键直接是 `GateResult` 不是信封）、`:94`（两条生产路径拼出同一组键）、`:118`（自动修复段的类型没变）。

### 5.9 手动修复的事务边界

`run_autofix`（`artifacts.py:220`）：

1. 只对**草案**开放（`frozen_at is not None` → 409）——冻结版本不可变，对它跑修复要么改历史、要么产出一份谁也审批不到的制品；
2. 建 ctx → 造 `repair` / `recheck` 两个回调 → 调 `arun_autofix_loop`；
3. `outcome.rounds_used` 非 0 时把修复后的制品落成**新的一组行**（`_persist_repaired`，`artifacts.py:662`），并让候选行指向它们；
4. 落库前用**新制品**重算一次门禁（`gating.run_gate`，`artifacts.py:687`）——`outcome.result` 是从内存 ctx 推出来的，落库的那份必须以新制品为输入；
5. 末尾 `await session.commit()`（`artifacts.py:301`）。

第 5 步不可省：不提交的后果比「多一次提交」重得多——门禁结论会显示成修好了，而用户一刷新，制品又变回修复前那份，他会以为修复是「只在这次响应里生效」的。

### 5.10 门禁结论 → `PipelineStatus`

`status_after_gate(verdict)`（`workflow/transitions.py:172`）：`pass` / `warn` → `GENERATED`，`block` → `GATE_FAILED`，
**未知 verdict 直接 `ValueError`**（回落意味着引擎哪天多出第四档结论时会被静默当成通过或阻断）。
`gate_node` 再走一次 `assert_transition`（`workflow/nodes/gate.py:112-117`）——两步走：前者验**取值**，后者验**转移合法性**，少任一个都会让「引擎多出第四档结论」或「从 `version_frozen` 重跑门禁」静默通过。

**门禁阻断不是 HTTP 错误**：`block` 只把状态推到 `gate_failed`，由自动修复接手；只有「阻断态下强行冻结」才是 `GATE_BLOCKED`（`workflow/nodes/gate.py:25`）。

### 5.11 无状态复用判据

`gate_node` 对**同一份草稿**复用已有结论，指纹覆盖 `plan + hocon + 档案 sha256`（`workflow/nodes/gate.py:75-91`）。
所以「修复后重新渲染的 HOCON」一定能重新跑门禁——**这正是自动修复回路的基础**。

| # | 触发条件 | 错误码 | HTTP | 依据 |
|---|---|---|---|---|
| 1 | 阻断态下请求冻结（图内路径） | `GATE_BLOCKED` | 409 | `workflow/nodes/freeze.py:74` |
| 2 | 有阻塞项时冻结（HTTP `/freeze` 路径） | `VALIDATION_ERROR`（**不是** `GATE_BLOCKED`，见 §10.21） | 422 | `artifacts.py:399` |
| 3 | 读一份没有落库门禁结论的制品 | `CONFLICT` | 409 | `artifacts.py:213`（提示「重新生成一次」） |
| 4 | 对已冻结版本跑修复 | `CONFLICT` | 409 | `artifacts.py:230` |
| 5 | 草稿制品不完整（缺 Plan 或缺非空 HOCON） | `PLAN_INVALID` | 422 | `workflow/nodes/gate.py:65`、`freeze.py:89` |
| 6 | 未建 Plan 就进修复节点 | `PLAN_INVALID` | 422 | `workflow/nodes/autofix.py:63` |

**门禁命中的问题一律不是 HTTP 错误**——它们变成 `GateResult.findings`，由前端渲染。
这是刻意的：把「方案有问题」回成 4xx 会让「重跑一次会不会好」变成用户唯一的动作。

## 7. 异步任务

**本模块无 Celery 任务。** 门禁与修复都在 LangGraph 图内同步执行（`gate_node` / `autofix_node` 是 `async def`，由图调度）。
理由是门禁必须是**可复现的纯判定**：`evaluate` 是同步纯函数（`gate.py:56`），
PDP 那一段 async 由 service 先算好放进 `ctx`（`gating.py:184-200`）——投 Celery 会把「用哪一份档案快照判的」变成不可复现。

唯一的异步边界是修复回路里的 `await provider.complete_json(...)`（`repair.py:89`），由 httpx 承担。
`arun_autofix_loop` 之所以存在异步驱动，是因为**手动修复接口**（`artifacts.py:271`）在请求内调模型；
Celery 场景下的同步驱动（`run_autofix_loop`，`loop.py:316`）留给了离线批处理与单测。
