## 1. 模块定位

### 1.1 做什么

1. 认证：用户名口令登录（argon2id）、access/refresh 签发、刷新轮转、登出撤销。
2. 登录防护：Redis 失败计数与锁定 + `login_attempt` 审计留痕（**审计不依赖易失存储**）。
3. 上下文解析：从 JWT 与路径参数构造 `SubjectContext`，校验租户一致。
4. 项目与成员：项目读取/改名、成员增删、职责槽授予与回收。
5. 职责分离：`require_role` 依赖 + 互斥/自批判定谓词（纯函数）。
6. 认证审计事件写入账本。

### 1.2 明确不做（防职责膨胀）

- **不签发 Capability**（Ed25519，be-05）。本模块只签发 HS256 用户令牌，两者算法与用途都不同。
- **不做业务资源授权**。数据源/Pipeline/审批单的可见性由各模块自查；本模块只提供判定谓词与依赖。
- **不实现审批流程**（be-13）。本模块只提供「谁不能审批谁」的规则。
- **不管理 Vault Secret**（be-03）。
- **不建用户**。M1 由种子脚本创建；在线建用户未定（§10）。

### 3.1 🔴 ID 类型：本仓库一律 `bigint`

**对账结论，勿改**：本字典 §1 的 FK 全是 `bigint`（`tenant_id` / `project_id` / `user_id` / `member_id` / `granted_by`），

**四方一致指向整数 ID**。凡看到 `user_id: number` 一律视为正确，不要「修正」成字符串。

（本仓库 `core/ids.py` 的 `new_uuid()` 只用于 `jti` 等不可枚举的令牌标识，不用于实体主键。
该文件 docstring 曾写「对外暴露的实体 ID 用 UUID4」，与模型/字典/前端矛盾，已修正。）

## 5. 核心逻辑

### 5.1 登录

1. 按 `tenant_code` 查 `tenant`；不存在或 `suspended` → `BAD_CREDENTIALS`（**不区分「租户不存在」**，避免枚举租户）。
2. 查锁定计数 ≥ 阈值 → `ACCOUNT_LOCKED`(423)，写 `login_attempt(success=false, reason="locked")`。
3. 按 `UK(tenant_id, username)` 查 `app_user`；不存在或校验失败 → 计数 +1（TTL=窗口）、写
   `login_attempt(reason="bad_credentials")`、抛 `BadCredentialsError`（文案统一）。
4. `status=locked` → `ACCOUNT_LOCKED`；`disabled` → `FORBIDDEN`。
5. `verify_and_update_password` 返回新哈希（argon2 参数升级）→ **同事务**更新 `password_hash`。
6. 删计数、更新 `last_login_at`、写 `login_attempt(success=true)`、提交。
7. 查 active 职责槽取 distinct `project_id`，签发令牌对。
8. 账本追加 `AUTH_LOGIN_SUCCEEDED` / `AUTH_LOGIN_FAILED`（独立事务，失败不回滚登录结果）。

### 5.2 🔴 登录锁定键必须带租户（本次修正）

**原设计的缺陷**：`auth:login_fail:{username}` 没有租户维度，而 `app_user` 的唯一性是
`UK(tenant_id, username)`。攻击者只需在自己租户内对 `admin` 连续失败，就能把**其它所有租户**的
`admin` 一起锁死——这是跨租户拒绝服务，且不需要任何越权就成立。

**修正**：键改为 `auth:login_fail:{tenant_code}:{username}`。
`tenant_code` 在步骤 1 之后必定可得（登录体携带），失败路径也拿得到。

`core/redis.py` 的 `KEY_LOGIN_FAIL` 模板同步修改；`login_attempt` 表**不加租户维度**——
它按 `username` 聚合才能看出「某个用户名正在被爆破」，而那是跨租户也想知道的事实。

### 5.3 刷新与登出

| 步骤 | 刷新 | 登出 |
|---|---|---|
| 1 | `decode_token(refresh_token, expected_type="refresh")` | 取 access payload |
| 2 | `KEY_TOKEN_DENY` 命中 → `UNAUTHENTICATED` | 写 `KEY_TOKEN_DENY:{access.jti}`，TTL=剩余有效期 |
| 3 | 查 `app_user`，停用即拒 | 若有 refresh，decode 后写其 `jti` |
| 4 | 重查 active 职责槽 → 新 `project_ids` | — |
| 5 | 签发新 access + 新 refresh，旧 refresh `jti` 写入 denylist（轮转） | — |

### 5.4 项目上下文解析（每个业务请求）

1. 从 `Authorization: Bearer` 取 access，`decode_token(expected_type="access")`。
2. 查 `KEY_TOKEN_DENY`（**登出后旧 access 仍有效期内也必须被拒**）。
3. 按 `sub` 载入 `app_user`，构造 `SubjectContext`；**`tenant_id` 取自 DB，不信任 JWT 里的值**。
4. `bind_contextvars(tenant_id, subject_id, request_id)`。
5. `require_project`：不存在 → `NOT_FOUND`；`project.tenant_id != subject.tenant_id` → `TENANT_MISMATCH`；非成员 → `FORBIDDEN`。
6. `require_role` 用 `active_roles()` **实时查库**，不足 → `ROLE_REQUIRED`。

### 5.5 职责槽授予

1. `require_role(CHECKER_SECURITY)` 通过。
2. 同事务查 `project_member`；不存在或 `removed` → `CONFLICT`。
3. 取该成员 `active_roles`，调 `check_duty_separation(held, granting=role)`；违规 → `DutyConflictError`。
4. `INSERT role_assignment`（`granted_by=subject.user_id`）；撞 UK → `CONFLICT`。
5. 写审计（§5.7），提交。

### 5.6 授权判定（唯一事实来源）

```
有效职责槽 = { ra.role | ra.project_id = :pid AND ra.user_id = :uid
                            AND (ra.valid_from IS NULL OR ra.valid_from <= :at)
                            AND (ra.valid_to   IS NULL OR ra.valid_to   >  :at)
                            AND pm.status = 'active' AND p.status = 'active' }
```

1. **不使用 JWT 里的角色声明**——角色以 `role_assignment` 实时查询为准（可能已被回收）。
2. 查询强制带 `tenant_id`；跨租户 → `TENANT_MISMATCH`。
3. `valid_to` 是**开区间上界**（`>` 而非 `>=`）。
4. `project.status=archived` 视为无有效槽位。

### 5.7 安全红线落地（本模块具体做法）

| 红线 | 本模块怎么做 |
|---|---|
| 无明文 Secret | 口令只在请求体内瞬时存在；`login_attempt` 只存粗粒度 `reason` 码，不存口令相关细节；证据 payload 只含 `username`/`ip`/`reason`/`user_id` |
| 租户隔离 | 所有查询经 `project.tenant_id` 或 `app_user.tenant_id` 过滤；跨租户抛 `TENANT_MISMATCH` 并写账本 |
| 四眼强制 | 服务端 `check_duty_separation` + DB 唯一约束；自批由 `approval_decision` 的 CHECK 兜底（be-13 触发） |
| 不可变制品 | 本模块不写任何 `__immutable__` 表；`password_hash` 在 `app_user`（可变表）上 |
| 证据账本单入口 | 只经 `harness.EvidenceLedger.append()`；与业务事务**解耦**，账本失败不回滚登录 |

## 8. 验收标准

1. 登录成功签发 access(30min)/refresh(7d)；`login_attempt` 落两行（失败 + 成功）。
2. 连续失败达阈值 → 第 N+1 次 `ACCOUNT_LOCKED`(423)，**正确口令亦然**。
3. **跨租户锁定隔离**：租户 A 的失败计数不影响租户 B 的同名用户（§5.2 的修正必须有对应用例）。
4. 登出后旧 access 访问 `/auth/me` → 401。
5. 刷新轮转：旧 refresh 再用 → 401。
6. `grant_role` maker→checker_data 被服务层拒绝。
7. `require_role` 对已回收角色：JWT 未过期但角色已删 → `ROLE_REQUIRED`。
8. **反例必须覆盖**：越权（非成员）、跨租户、自批、职责混用、锁定、refresh 重放、已撤销令牌复用。
9. 纯函数单测（内存 SQLite / 无 IO）：`is_assignment_valid` 的 `at == valid_to` 边界应为**无效**；
   `check_duty_separation` 的 maker×checker 拒绝、checker_data×checker_security **允许**、operator 不互斥。
