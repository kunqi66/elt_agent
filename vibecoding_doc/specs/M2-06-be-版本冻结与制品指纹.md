## 1. 模块定位

### 1.1 做什么

1. **制品指纹算法**（`engines/fingerprint/`，纯函数）：
   `sha256 = SHA256(canonical_json(artifact_envelope(parts)))`，五部分 = `etl_plan` + `hocon` +
   `quality_contract` + `supervision_contract` + `source_metadata_profile_sha256`。
   这是全系统唯一被「审批结论 / Capability / 执行」共同引用的制品标识（be-12 §8「指纹即信任根」）。
2. **规范化规则**：键排序、无空白、UTF-8 不转义、`Decimal`/`float` 定标成 4 位小数字符串、
   `null` 键不省略；**以及排除清单**——哪些字段进指纹、哪些必须剥掉（§5.4）。
3. **冻结 `freeze_version()`**：把一个**候选行**（草案，`frozen_at IS NULL`）冻结成不可变版本，
   六道闸逐道判定（§5.1），失败即拒；成功则落 `frozen_at/frozen_by/note`、把
   `pipeline.current_version_id` 指过去、状态转 `version_frozen`。
4. **版本间 Diff**（`engines/diff/`，纯函数）：两份 `ArtifactParts` 的结构化差异，逐条带 `path`。
5. **只读制品读取**：版本详情（含冻结清单 `FreezeArtifactManifest`）、Plan / HOCON / 门禁结论。
6. **候选行内容的重写**（`_persist_repaired`，自动修复路径）：每一轮修复产出一组**新的**制品行，
   让候选行重新指向它们——不改历史行（CLAUDE.md §5.4）。

### 1.2 明确不做

- **不做门禁判定**（be-11）。冻结只读落库的门禁结论并判「有没有 block」，不重跑。
  `get_gate` 刻意不重算：策略表改过之后「现在的结论」与「审批时看到的结论」会不一样，
  把后者当前者，等于让用户看到一份与他审批时不同的结论（`api/... artifacts.py:203`）。
- **不做 Prepare / 审批 / Capability**（be-05 / be-13）。本模块只保证 `pipeline_version.sha256`
  是那个被下游引用的值，不负责把它写进 `preparation` / `approval_decision` / `capability`。
- **不做执行期的工作流状态协调**（be-09）。冻结节点的编排逻辑在 `workflow/nodes/freeze.py`，
  它只调 service；本模块的 service 不 import `workflow`。
- **不做制品摘要复核接口**（be-12 §3.1 的 `/verify`）：仓库里没有这条路由，见 §7 与 §10.9。
- **不取当前时间、不读配置**：`now = datetime.now(UTC)` 在 service 内取，但指纹引擎
  （`engines/fingerprint/`、`engines/diff/`）**完全不碰时钟**，时间类字段全在排除清单里。

## 5. 核心逻辑

### 5.1 `freeze_version()` 的六道闸（顺序不能换）

实现在 `services/pipeline/artifacts.py:350` 起，逐道如下：

| # | 闸 | 判什么 | 失败 | 代码位置 |
|---|---|---|---|---|
| 1 | **必须在草案上冻结** | `version.frozen_at is None`。已冻结的再冻一次没有语义——冻结是不可逆的 | `ConflictError` 409 | `:379` |
| 2 | **指纹必须与落库制品一致** | 从**落库的四个制品行**重算 `ArtifactParts`（`parts.parts_from_rows`）与候选行上的 `sha256` 比对（`parts.fingerprint_matches`）。不一致说明「生成之后制品被动过」，此时冻结等于把「审批看到的 A」与「执行拿到的 B」绑在一起 | `ConflictError` 409 | `:382`–`:392` |
| 3 | **HOCON 密钥令牌必须都解得开** | `_assert_tokens_resolvable`（`:308`）：① 每个令牌字段名在 `SECRET_FIELDS` 白名单；② 令牌指向的数据源在本租户里**存在 + `status="active"` + 有 `secret_ref_id`** | `ConflictError` 409 | `:394` |
| 4 | **门禁不得有阻塞项** | 读**落库的**门禁结论（`get_gate`，不重跑），`any(f.severity == "block")` 即拒 | `ValidationError` 422 | `:398`–`:402` |
| 5 | **写入方必须是当前用户** | `version.frozen_by = ctx.user_id`（四眼的后置条件靠它判定）| — | `:405` |
| 6 | **冻结的收尾** | `version.frozen_at = now`、`note = note` → `flush()` → `repository.set_current_version(...)` 把 `pipeline.current_version_id` 指向它、`status` 转 `version_frozen` → `commit()` | — | `:404`–`:425` |

**顺序为什么不能换**：

- 闸 1 必须最先。它是一次「这行还是草案吗」的廉价判据；放在指纹重算之后就变成
  「先算了一遍哈希才被告知这行早就冻过了」——多做一次读且错误语义变模糊。
- 闸 2 必须在闸 3–6 之前。**指纹是信任根**：若指纹都对不上还在往下走，等于可能把一个
  被动过的制品冻进去，后面所有判定的对象都是错的。
- 闸 3 在闸 4 之前：令牌不可解析是「这份制品将来执行不了」，属制品本身的问题；
  门禁 block 是「这份制品不该上生产」，属治理判定。先制品后治理——先排除「根本跑不起来」，
  再谈「许不许跑」，报错才是用户能直接动手修的那一条。
- 闸 5 必须在闸 6 之前：`frozen_by` 与 `frozen_at` 是同一次写入的两列，先定写入方再落冻结时间，
  「谁冻的」不会有中间态。
- 闸 6 的 `flush()` 必须在 `set_current_version` 之前：`frozen_at` 落值 —— `__freeze_column__` ——
  之后整行连同 `__mutable_columns__` 白名单一起失效（§5.2），所以这一行必须先写干净再被标记冻结。

### 5.2 不可变性（两道，一在 ORM、一在 DB 语义）

- `models/base.py:84` 的 `before_flush` 守卫：凡 `__immutable__ = True` 的模型，UPDATE / DELETE 抛
  `ImmutableViolationError`。**逐列**判断，报错能直接指出是哪个字段。
- `PipelineVersion.__freeze_column__ = "frozen_at"`（`models/pipeline.py:199`）：`frozen_at` 为空时
  是候选行，`__mutable_columns__` 里的 10 列（`:185`）可改——重生成、自动修复改的正是这几列；
  `frozen_at` **一旦落值**，白名单失效，**整行连 `note` 都不可改**。
  `_is_frozen`（`base.py:118`）依据是**库里已存的值**，不是「本次改动里有没有 `frozen_at`」——
  否则同一事务里先写 `frozen_at` 再改别的列就能绕过守卫。
- **为什么修正只能产生新版本**：审批结论与 Capability 都绑 `sha256`；允许原地改，则「审批通过的那份」
  与「实际执行的那份」可能不同，四眼与 Capability 同时失效。
- **冻结不可逆**：重复冻结失败于闸 1（`ConflictError` 409）。本机端到端实测过：对同一行再冻一次被 409 拒。
- **候选身份列也不可改**：`pipeline_id` / `version_no` 不在白名单里——候选可以改内容，不能改归属。

### 5.3 事务边界与并发

- **事务边界归 service**：`core.db.get_session` 只借连接、不提交。`freeze_version` 末尾的
  `await session.commit()`（`:425`）是「冻结真的落库」的唯一保证——冻结是**不可逆事实**，
  不提交的话响应说「已冻结」而库里还是草案，下一次生成会心安理得地复用/覆盖这个候选。
  扫源码的守卫用例 `tests/test_service_commit_boundary.py` 强制每个写入口都有 `commit()`。
- **并发递增的实现与设计不同**（见 §10.13）：设计用 `SELECT ... FOR UPDATE` + `version_no + 1`；
  实现用「一个 pipeline 最多一行候选」的**部分唯一索引** `uq_pipeline_version_one_candidate`
  （`models/pipeline.py:172`，`WHERE frozen_at IS NULL`）+ `get_or_create_candidate`（`repository.py:362`）
  里的 `begin_nested()` savepoint 重试（`_VERSION_RETRY = 3`，`repository.py:58`）。
  `version_no = MAX(version_no) + 1` 在**候选创建**时算（`next_version_no`，`:283`），不在冻结时算。
  **禁止**对 `pipeline_version` 做 `SELECT ... FOR UPDATE`（锁不可变表会让「只增不改」的语义变味）。
- **制品落库不在 `freeze_version` 内**：四件制品由调用方先落（`workflow/nodes/freeze.py:103` 的
  `save_artifacts` + `get_or_create_candidate`、或 `generation._persist_turn`），`freeze_version`
  只对已存在的候选行做冻结状态翻转。这与 be-12 §5.1「同一事务内插 5 张表」不同，见 §10.14。

### 5.4 指纹：参与与排除（内容寻址）

**五部分**（`ArtifactParts`，`engines/fingerprint/parts.py:90`）：`etl_plan`（`dump_plan` 的产物）、
`hocon_content`（逐字节）、`quality_contract`、`supervision`、`source_metadata_sha256`。

**排除清单**（`EXCLUDED_KEYS`，`:48`，理由见 `:45`–`:83` 的注释，逐类）：

| 排除项 | 理由 |
|---|---|
| 数据库行 id：`id` / `pipeline_id` / `tenant_id` / `project_id` / `version_id` / `version_no` / `current_version_id` / `etl_plan_id` / `hocon_artifact_id` / `quality_contract_id` / `supervision_contract_id` / `source_metadata_profile_id` | 自增、可变的编排事实，与制品内容无关；纳入会让同一份制品在不同 Pipeline 下算出不同指纹 |
| 时间戳：`created_at` / `updated_at` / `frozen_at` / `generated_at` / `deleted_at` | 时间属审计事实；纳入会让「重算指纹」永远失败 |
| 操作者与备注：`frozen_by` / `note`，及**任意深度**的 `*_by` 后缀（`EXCLUDED_KEY_SUFFIXES`）| 同时间戳 |
| `generation_context` | 模型与提示词版本是**来源信息**而非制品；同一产物的复制应得同一指纹 |
| 派生校验结果：`valid` / `validation_errors` / `sha256` / `parser_version` / `validation_result` | 内容是判定输入，这些是判定结论与工具版本；校验器升级不应让历史指纹失效 |
| 可变编排状态：`status` | 可变编排状态 |

**关键的一条——排除的是「行 id」，不是「语义引用」**：`_is_excluded`（`:114`）只在**每部分顶层**
剥名为 `id` 的键；其下的 `inputs[0].data_source_id`、`id` 字符串节点（DAG 靠它互相引用）**必须进指纹**。
把「所有 id 排除」照字面实现，会放行一份「连的是 A 库」的方案带着旧指纹走完治理。
`tests/test_fingerprint.py` 用两条用例钉住这两个方向。

**内容寻址的结果**：正因为 `pipeline_id` / `version_no` / 时间戳 / 操作者 / `generation_context`
全在排除清单里，**两条不同生成会话跑同一需求会得到同一个 `sha256`**。这是**设计**，不是碰撞——
`pipeline_version.sha256` 因此**没有**全局唯一约束（`models/pipeline.py:161` 的注释：全局唯一会禁掉
「两条 pipeline 由同一方案派生」与「重新生成」两个合法场景）。本机端到端实测同一需求两次生成命中
同一值 `f3ea7843bbf37148…`（**手测观察，非用例金标准**，见 §10.19）。

| 项 | 规则 | 反例 |
|---|---|---|
| 键排序 | `core.ids.canonical_json`（`sort_keys=True`）递归排序 | 依赖 `dict` 插入顺序 |
| 分隔符 | `,` / `:`，无空白 | `indent=2` 的美化输出 |
| 编码 | UTF-8，非 ASCII 原样保留 | `ensure_ascii=True` |
| 整数 | 原样十进制 | `1` 与 `1.0` 混用 |
| 比率 / 小数 | 定标成 4 位小数字符串（`_QUANTUM = Decimal("0.0001")`），如 `"0.0500"` | 二进制浮点尾数 |
| `float` | 必须 `Decimal(str(value))` 中转（`:145`）| `Decimal(0.05)` 会带二进制尾数 |
| 布尔 | `True` / `False` 原样（**必须在 `int` 之前判**，`:140`）| `1` / `"true"` |
| 空值 | `null`，**键不省略** | 省略 `null` 键 |
| 数组 | 保持语义顺序**不排序** | 对 `field_mappings` 排序 |
| HOCON | 逐字节，**不 trim / 不归一**（`:104`）| 对 HOCON 做换行归一 |

`FINGERPRINT_FORMAT_VERSION = 1` 写进信封的 `"v"` 键；改规范化规则必须**递增**它。

### 5.6 指纹只能由**落库的制品**重算

`services/pipeline/parts.py`（模块 docstring）把这条写成一等公民：若指纹是从 Plan 现推质量契约、
现推督导契约，那么**落库的那两行就退出信任链了**——库里存什么就不重要了，只要 Plan 一样指纹就一样，
于是有人改了本该不可变的 `quality_contract.rules` 不会有任何东西报错。

所以两个方向共用同一对构造器：

```
quality_contract_body(plan, pipeline_id) ──┬─→ QualityContract(**body)   落库
                                           └─→ body                      进指纹
quality_body_from_row(row) ──────────────────→ body                      校验时重算
```

`save_artifacts` 用前者建行、`parts_from_rows` 用后者重算；两边的键名与值来自同一个 dict，
**在结构上就不可能漂移**。`freeze_version` 用的正是 `parts_from_rows`（闸 2）。

### 5.7 🔴 冻结一度用错令牌闸（已修，进 §5/§10）

`_assert_tokens_resolvable` 的 docstring 记着这次误用：一开始拿**执行前**的
`assert_no_unresolved_tokens` 去卡冻结，于是**每一份合法制品都冻不了**——制品本来就该带令牌
（令牌正是「口令不进制品」的手段），报错还写着「仍有未替换的密钥令牌」，读起来像渲染器漏了替换。

两道闸判两件不同的事，别混：

- `assert_no_unresolved_tokens`（`engines/hocon/types.py:92`）：**执行前**，令牌必须**一个不剩**；
- `secret_token_problems`（`engines/hocon/types.py:109`）：**冻结前**，令牌必须**解得开**
  （字段在白名单、指向的数据源 active 且有 `secret_ref_id`）。
  返回 `tuple[str, ...]`（空 = 全可解析），冻结侧在非空时拒绝。

守它的是 `tests/test_hocon_secret_gates.py`（含「执行前的闸会拦下这份制品、冻结前的闸必须放行它」）。

### 5.8 `validation_result` 的形状只有一份定义

`hocon_artifact.validation_result` 由两段拼成，**各只有一份实现**：

- 渲染段 `gating.render_meta(rendered)`（`gating.py:72`）：`sha256` / `parser_version` / `renderer_version` / `job_name` / `token_count`；
- 解析/门禁段 `GateOutcome.artifact_meta()`（`gating.py:113`）：`parse` / `gate` / `policy_decision_id` / `policy_version`。

**`gate` 这一键直接就是 `GateResult` 的转储，不是它的信封**。曾经渲染节点、门禁节点、落库路径各拼一份，
门禁节点多套一层信封（`{"gate": {...}}`），于是 `get_gate` 把信封当 `GateResult` 解析，报
「`evaluated_at`/`conclusion` 缺失」——**而门禁其实跑了**。生成路径与自动修复路径（`_persist_repaired`，`:712`）
必须拼出**同一组键**（9 个）。守它的是 `tests/test_artifact_meta_shape.py`。

### 5.9 版本间 Diff

`engines/diff/version_diff.py:103`。**只做展示**：不回写指纹、不判门禁、不碰数据库。
形状以 `frontend/src/api/pipeline.ts` 的 `fetchVersionDiff` 为准——一维 `entries` 平表
（`{path, kind, before, after}`），与 be-12 §6.4 的 `sections` / `locator` / `sha_changed` 不同
（差异逐条登记在 `version_diff.py` 的模块 docstring，此处转记 §10.18）。

`path` 约定：Plan 字段无前缀（`field_mappings[3].target_type`、`inputs[0].table`）；带 `id` 的数组按
`id` 匹配（`quality_contract.rules[E_NULL_PK].params`），否则按下标；其余段带段名前缀
（`quality_contract.*` / `supervision.*` / `source_metadata_profile_sha256`）；HOCON 用 `hocon:<旧行号>`。
Plan 段**跳过** `quality_rules` 与 `budget` 两个顶层键（由专门段表达，不跳会让同一处改动出现两次）。
`diff_versions`（`artifacts.py:432`）两侧各自重算 `ArtifactParts` 再比——**不**比数据库行
（行里的 `id` / `created_at` 每版都不同，比行会让每一版都显示「全变了」）。自己跟自己比返回空 diff，不报错。

## 7. 异步任务

- **本模块无 Celery 任务**。冻结是「读到当下事实（候选行 + 落库制品 + 门禁结论）后立刻翻转状态」的
  同步动作，全程在一次请求/一次图执行内完成；把它异步化只会引入「提交了但还没冻上」的中间态，
  而这正是 `frozen_at` 想排除的东西。
- **不需要 Outbox**：本模块不投递任何消息。be-12 §5.1 设想的「业务事务提交后追加证据、失败进 Outbox」
  因证据账本写入**根本未实现**（§10.10）而无从谈起。
- ❌ **`/verify` 制品摘要复核接口未实现**（be-12 §3.1 / §6.5）：仓库里只有引擎级 `matches()`
  与**账本**验链脚本 `backend/scripts/verify_ledger.py`（它验的是证据链，不是制品指纹）。
  PRD §10.5「所有不可变制品均可通过摘要复核」目前靠 `freeze_version` 内建的指纹比对（闸 2）
  与 `tests/test_fingerprint.py` 的引擎级往返，缺一个「按版本号读回并复核」的独立接口。见 §10.9。
