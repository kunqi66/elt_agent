## 1. 模块定位

### 1.1 做什么

1. 探查远端库的库表结构与列注释，落成**不可变档案**（`metadata_profile` 一行一版）。
2. 列级敏感判定：按列名/注释/人工标注推断 `SensitiveKind` + `SensitiveLevel`。
3. 抽样并**脱敏**：样本值一律走摘要，只有 `public` 级（且策略允许）才留明文。
4. 档案版本化：同一数据源每次探查 `version + 1`，历史版本可查（供 be-11 比对漂移）。
5. 档案读写接口：列表、单档案、结构快照、脱敏样本。

### 1.2 明确不做

- **不做「解密样本」**。服务层从来没有这个函数，**这是刻意的**：一旦存在，
  它迟早会被某个「导出调试」需求调用，而样本脱敏是红线 7 的唯一抓手。
- **不改远端库**。探查是纯读（`information_schema` / `SHOW` / `SELECT ... LIMIT`）。
- **不做质量契约**（be-16）。这里只判敏感级别，不管空值率/类型漂移。
- **不做跨数据源关联探查**。一个数据源一次探查。

## 3. 涉及的表

| 表 | 动作 | 关键约束（字典 §3） |
|---|---|---|
| `metadata_profile` | **INSERT + 状态字段 UPDATE** | `UK(data_source_id, version)`；`schema_snapshot` JSONB |

| `evidence_event` | 写 | `METADATA_PROBED` |

### 3.1 🔴 `metadata_profile` 是「不可变制品」的例外，但只是部分例外

CLAUDE.md §5.4 的不可变表清单里**没有** `metadata_profile`，这是有意的：
一次探查是「先占位（`probing`）→ 再填内容（`ready`/`failed`）」的两阶段写，
硬套 `__immutable__` 会让流程无法表达。

但**内容的不可变性由版本保证**：`schema_snapshot` / `masked_samples` 一旦写入
`ready` 就不再改；要更新只能升 `version`。`UPDATE` 只允许动
`status` / `error_message` / `completed_at` 三个字段，且只允许在 `probing` 行上
（`_mark_failed` 里有 `WHERE status='probing'` 兜底）。

|---|---|---|
| POST | `/datasources/{id}/probes` | **202** `{profile_id, version}`；body 见 §4.1 |
| GET | `/datasources/{id}/profiles` | 档案列表（倒序），含 `status` / `tables_count` / `sampling` |
| GET | `/datasources/{id}/profiles/{version}` | 单档案；`probing` 也返回（前端要显示进度），**不 404** |
| GET | `/datasources/{id}/profiles/{version}/schema` | `?table=` 可选；`failed` 档案 → 409 |
| GET | `/datasources/{id}/profiles/{version}/samples` | `?table=&limit=`；未抽样表 → 404 且 `details.sampled_tables` |

### 4.1 `ProbeRequest`

```jsonc
{
  "scope": "schema_only" | "selected_tables" | "full_tables",   // 默认 schema_only
  "tables": ["orders", "users"],        // 仅 selected_tables 必填
  "sampling": { "rows": 100 },          // schema_only 时 rows 必须为 0 或不给
  "masking_policy": {}                  // 只允许**更严**（见 §5.3）
}
```

`scope=schema_only` 与 `sampling.rows > 0` **同时出现即 422**：只探结构却要样本文本，
说明调用方对这两个字段的理解互斥，静默取其一等于替用户做了他没表达的决定。
`selected_tables` 不给 `tables` 同理。

### 4.2 与其他模块的契约


## 5. 核心逻辑

### 5.1 脱敏契约（`engines/masking/policy.py` 的三条不变量）

1. **不可逆**：`digest = sha256(f"{salt}\x1f{column}\x1f{value}").hexdigest()[:12]`。
   不是「加密后能解」，是单向摘要——**没有解密函数**（§1.2）。
2. **同值同显**：salt 固定为 `f"{tenant_id}:{data_source_id}:{profile.version}"`，
   同一档案内同一个值给出同一个摘要，用户才能看出「这两行是同一个客户」。
   跨档案 salt 不同（version 参与），所以拿两份导出做交叉比对得不出对应关系。
3. **不泄漏长度**：输出固定 `kind:12位十六进制`。原值长度不进摘要输出——
   否则「手机号摘要长 11 位」这种事会把长度本身变成可读信息。

`SensitiveLevel.PUBLIC` 且 `keep_public_plain=True` 时留明文。**默认级别是 `internal`
而非 `public`**：兜底成 public 等于默认不脱敏。

### 5.2 🔴 判定顺序敏感 + 取较高者

- 规则表**有序**，先命中先赢：`id_card` 必须排在宽泛的 `id`/`name` 规则之前，
  否则 `user_id_card` 会被判成 NAME，级别从 restricted 掉到 confidential。
- 人工标注（`declared`）与规则推断**取较高者**，不是让标注覆盖规则：
  覆盖意味着一次误标就能把手机号降级成 public；取较高者最坏是过于保守。

### 5.3 `merge_policy` 只允许更严

调用方传的 `masking_policy` 记在档案里（`requested` 字段供追溯），
但**实际生效的策略只会比默认更严**。放宽的请求被静默记录而不被执行——
写在这里是因为「用户以为他放宽了、实际没有」需要一个明确的行为定义，
而不是某天被人当成 bug「修」掉。

### 5.4 🔴 探查结果**不能**走 `ToolResult.detail`

`harness/broker.py::_safe_detail` 会丢掉所有非白名单键，且任何 Mapping/list/tuple/set
值一律丢。这是有意的（防止执行器顺手把远端数据塞进账本），但它意味着：

> **探查结果必须由执行器自己落库**，工具只返回扁平的摘要键
> （`{profile_id, version, tables_count, target}`）。

因此 `MetadataProbeArgs` 需要一个明确的 `profile_id`——「往哪个档案里写」。
早先的设计里 executor 自己新建一行，调用方再猜 id；现在的形态是 service 先建
`probing` 行拿到 id，再把它交给工具。**这条是 be-04 的架构地基**，
改 `_safe_detail` 的白名单去迁就探查结果会削弱所有工具的 payload 卫生。

### 5.5 执行流程

1. `start_probe`：`require_project_roles` → 数据源必须 `active` → 抽样参数校验 →
   `merge_policy()` 落库 → INSERT `probing` 行（version = MAX+1）→ 投 Celery → 返回 `(profile_id, version)`。
2. worker `run_metadata_probe`：读状态；非 `probing` 直接返回（重投安全）。
3. `metadata_probe_executor(args, ctx, session)`：
   - 载入 profile（**带 `tenant_id` 与 `data_source_id` 双重条件**，防跨租户写）；
   - 物化凭据 → 采集 schema → 按 `scope` 抽样（`full_tables` 只抽前 20 张表）；
   - 逐列 `infer_sensitivity`，写 `sensitive_level` 与 `masked`；
   - 逐值 `mask_value`，填 `masked_samples`；
   - `schema_snapshot` / `masking_policy` / `sampling` / `tables_count` / `model_hash(sha256)` 落库；
   - `status=ready`，commit；
   - 异常时（**含任何 `Exception`，不只 `ProbeFailure`**）按类型分类 → `status=failed` +
     `error_message = failure.message[:512]` → commit → 返回失败摘要（**不抛**）。
4. service 追加账本 `METADATA_PROBED`。

### 5.6 安全红线落地

| 红线 | 本模块怎么做 |
|---|---|
| 脱敏默认开启 | 判定与脱敏在**同一个纯函数模块**里，执行器没有「不脱敏」的分支；`masked` 标志如实反映存储内容 |
| 无明文 Secret | 凭据只在 executor 内物化（`_materialize_credentials`），用完即弃；档案与返回值里都没有 |
| 副作用唯一出口 | 探查经 `ToolBroker.execute(METADATA_PROBE)`；executor 由 `clients/` 注册，`services/` 不 import 驱动 |
| 证据账本单入口 | `METADATA_PROBED` 经 `append()`；payload 只有计数与目标，没有样本 |
| 租户隔离 | executor 载入 profile 时同时校验 `tenant_id`；service 侧所有查询带 `tenant_id` |
| 不可变制品 | 内容只 INSERT 一次，`UPDATE` 只限状态三字段（§3.1） |

## 6. 错误码

| 触发 | 码 | HTTP |
|---|---|---|
| 非项目成员 | `ROLE_REQUIRED` | 403 |
| 数据源不存在 / 跨租户 | `NOT_FOUND` | 404 |
| 数据源已停用 | `CONFLICT` | 409 |
| `schema_only` + `rows>0` / `selected_tables` 无 `tables` | `VALIDATION_ERROR` | 422 |
| 档案尚在 `probing` 时取 schema/samples | `CONFLICT` | 409 |
| 档案 `failed` 时取 schema/samples | `CONFLICT` | 409 |
| 该表未被抽样 | `NOT_FOUND` + `details.sampled_tables` | 404 |

`NOT_FOUND` 优先于 `TENANT_MISMATCH`：跨租户时不该告诉调用方「这个 id 存在」。

## 7. 异步任务

| 任务 | 队列 | 幂等 | 说明 |
|---|---|---|---|
| `tasks.metadata.run_metadata_probe` | `etl.default` | 是 | `load_profile_state` 非 `probing` 即返回；异常只记日志**不重抛**（重抛会让 Celery 反复重投一个必然失败的探查） |

结果**不放进 result backend**（`ignore_result=True`）：探查结果可能有几十 KB 的
结构快照，塞进 Redis result backend 是纯浪费，真值在 `metadata_profile` 里。

## 8. 验收标准

1. **明文样本从未离开执行器的那一个栈帧**：用一个「一眼能认出来」的口令与手机号做数据，
   断言它不出现在 `masked_samples` / `schema_snapshot` / 返回值 / 账本 payload / 响应体里。
2. 版本递增：连探三次得 version 1/2/3，老档案仍可读。
3. `sensitive_level` 按列名判定；人工标注只能**提高**。
4. 同一档案内同一原值 → 同一摘要；不同列同值 → 不同摘要。
5. `masked` 标志与存储内容一致（内部级别列标 `masked=True` 且值确为摘要）。
6. `full_tables` 只抽前 20 张表，但 `tables_count` 是 30。
7. 失败路径：驱动抛 `RuntimeError` 时 `error_message` **不含驱动原文**（可能带连接串）。
8. 反例：停用数据源、跨租户、`probing` 未完成取样本、未抽样表、`schema_only`+`rows>0`。
