## 1. 职责与边界

- **做什么**
  1. 提供**唯一写入入口** `EvidenceLedger.append(session, event)`：在串行化事务内锁链尾、算 `prev_hash` 与 `event_hash`、插入 `evidence_event`。
  2. 定义并固化 `event_hash` 的**规范化序列化规则**，使同一事件在任何语言、任何时间点重算都得到同一哈希（可复现性是验链的前提）。
  3. 每 `LEDGER_CHECKPOINT_INTERVAL`（默认 100）条事件落一个 `evidence_ledger_block`：对 `chain_head_hash|from_seq|to_seq` 做 Ed25519 签名，`key_id` 支持轮转。
  4. 在 append 入口**强制脱敏校验**：payload 命中键名黑名单或值形态敏感正则即 `raise`，不静默改写。
  5. 提供零依赖独立验链器 `scripts/verify_ledger.py`（只连 PG 读 + 读公钥文件）。
  6. 提供账本查询与导出（`/api/v1/governance` 下的只读子路由）：JSON / CSV、按时间区间、事件类型、主体过滤，权限为 auditor。
- **不做什么**
  - **不决定写什么事件**：事件类型与业务语义由各模块（be-02 be-03 be-05 be-13 be-14 be-16 be-18）决定，本模块只负责「怎么写才不可篡改」。
  - **不做脱敏的"修复"**：命中敏感内容直接拒绝写入，把问题暴露给调用方（静默替换会让「账本里看不到明文」变成假象，而真实泄露已经在别处发生过）。
  - **不存 Secret 与原始数据行**：payload 只允许引用（id、指纹、计数、枚举、掩码值）。
  - **不承担审计日志职责**：运行日志是 structlog 那条链路（be-21），本模块不写日志、不落 `evidence_event` 之外的表。
  - **不修改历史事件**：任何「补写/纠正」都必须新增事件；`evidence_event` 与 `evidence_ledger_block` 均置 `__immutable__ = True`。
- **所在分层**：`harness/`（写入侧）+ `models/`（表定义，已存在）+ `scripts/`（独立运维工具）+ `api/` + `services/`（查询与导出，薄编排）。依赖方向：`broker/services/tasks → harness/ledger → models/evidence`，**单向**，本模块不依赖 `services/`。

本模块的路由与 be-07 的策略路由同属 `/api/v1/governance` 前缀，按模块分文件挂载（`api/governance.py` 只聚合，不写逻辑）。

#### 与初稿的差异

| 项 | 初稿 | 采纳 | 理由 |
|---|---|---|---|
| 查询路径 | `GET /governance/ledger` | `GET /governance/evidence` | 前端已定型；账本对用户的名字就是「证据」 |
| **分页** | `page` / `page_size` | **`cursor` + `limit`** | **这条比路径重要**：账本在持续 append，offset 分页会漏读或重读——翻页时新事件插进来，第二页会重复第一页的尾巴。游标基于 `seq` 才稳定 |
| 验链 | `GET .../verify` | `POST /evidence/verify` | 验链要重算全链，是有代价的动作，不该能被 GET 缓存或预取 |
| 过滤参数名 | `occurred_from`/`occurred_to` | `from`/`to` | 前端 `EvidenceFilter.from/to` 已定型 |
| `event_type` | 数组 | 逗号分隔字符串 | 前端 `filter.event_type?.join(',')`；**未知取值 → 422**（静默丢掉一个筛选项会让用户看到一份「看起来完整」的结果） |
| `/blocks` 列表 | 独立路由 | **取消** | 检查点没有独立展示价值；`block_seq` 已挂在每条事件上，验链结果里有 `checked_blocks`/`started_from_block_seq` |
| 验链报告字段 | `first_broken_seq` / `broken_reason` | `broken_at_seq` / **`broken_kind`** + `broken_reason` + `broken_detail` | 三者都要：前端按 `kind` 选修复动作，运维要 `at_seq` 与 `detail` 定位字段 |
| 导出 `limit` | 未定义 | 映射为 `max_events` | 否则服务端的 `limit` 参数会变成一个静默无效的入参 |
| `actor_name` | 无 | 有 | 审计要给人看，「id=7 做了某事」谁也认不出是谁 |

**`broken_kind` 取值与前端 `LedgerBreakReason` 逐字一致**（`hash_mismatch` / `prev_hash_mismatch` / `signature_invalid` / `missing_event`）；
**加值必须同步前端**，否则前端走 default 分支显示「未知错误」。
未识别的取值后端映射为 `null` 而非原样下发。

### 3.2 Python（跨模块契约）

```python
# harness/ledger.py
@dataclass(frozen=True, slots=True)
class LedgerEvent:
    tenant_id: int
    event_type: EvidenceEventType
    subject_type: str          # 例 "capability" / "preparation" / "run" / "pipeline_version"
    subject_id: str            # 字符串化 id（evidence_event.subject_id 是 varchar）
    payload: Mapping[str, Any] # **必须已脱敏**；本类不做掩码，只做拒绝
    occurred_at: datetime      # 由调用方注入 UTC 时刻；账本内部禁止取当前时间
    project_id: int | None = None
    actor_id: int | None = None
    artifact_hash: str = ""

@dataclass(frozen=True, slots=True)
class CheckpointResult:
    block_seq: int
    from_event_seq: int
    to_event_seq: int
    chain_head_hash: str
    key_id: str
    signed_at: datetime

@dataclass(frozen=True, slots=True)
class VerifyReport:
    ok: bool
    checked_events: int
    checked_blocks: int
    first_broken_seq: int | None
    broken_reason: str | None
    checked_at: datetime

class EvidenceLedger:
    def __init__(self, *, signer: LedgerSigner, checkpoint_interval: int) -> None: ...
    async def append(self, session: AsyncSession, event: LedgerEvent) -> EvidenceEvent: ...
    async def append_many(self, session: AsyncSession, events: Sequence[LedgerEvent]) -> list[EvidenceEvent]: ...
    async def sign_checkpoint(self, session: AsyncSession, *, now: datetime) -> CheckpointResult | None: ...
    async def chain_head(self, session: AsyncSession, *, tenant_id: int | None = None) -> str: ...
    async def verify_chain(self, session: AsyncSession, *, from_seq: int = 1,
                           to_seq: int | None = None) -> VerifyReport: ...

def compute_event_hash(*, seq: int, actor_id: int | None, event_type: EvidenceEventType,
                       subject_type: str, subject_id: str, artifact_hash: str,
                       payload: Mapping[str, Any], prev_hash: str, occurred_at: datetime) -> str: ...

ZERO_HASH: str = "0" * 64   # 创世条目的 prev_hash

class LedgerSigner:
    def __init__(self, *, private_key_path: str, key_id: str) -> None: ...
    def sign(self, message: bytes) -> str: ...          # base64(Ed25519 签名)
    @staticmethod
    def verify(public_key_pem: bytes, message: bytes, signature_b64: str) -> bool: ...
```

**契约**：`append()` 成功返回已持久化（已 `flush`，未必 commit）的 `EvidenceEvent`。它**不** commit、**不** 开新事务——事务边界属于调用方，这样「业务事实 + 证据」才能原子提交。同一事务内重复 `append` 会依次拿到连续 `seq`。

## 4. 数据模型

| 表 | 列（本模块相关） | 约束 / 索引 |
|---|---|---|
| `evidence_event` | `seq` `tenant_id` `project_id` `actor_id` `event_type` `subject_type` `subject_id` `artifact_hash` `payload` `prev_hash` `event_hash` `occurred_at` | `uq_evidence_event_seq`、`uq_evidence_event_event_hash`、`ix_evidence_event_tenant_id_occurred_at`、`ix_evidence_event_event_type`、`ix_evidence_event_subject`；`__immutable__ = True`（禁止 UPDATE/DELETE），无 `updated_at` |
| `evidence_ledger_block` | `seq` `from_event_seq` `to_event_seq` `chain_head_hash` `signature` `key_id` `signed_at` | `uq_evidence_ledger_block_seq`；`__immutable__ = True` |
| `preparation` / `capability` / `execution_run` | 无 | 本模块不读业务表（`verify_chain` 只读 `evidence_event` 与 `evidence_ledger_block`） |

**链的全局性**：`seq` 与 `event_hash` 是**全局唯一**（不带 `tenant_id` 的复合唯一），因此 `evidence_event` 构成**单条全局链**；`tenant_id`/`project_id` 只用于查询过滤与租户隔离，**不参与分链**。这一点必须写进实现注释：如果误把 `tenant_id` 当作分链维度，验链就会漏检跨租户插入。表定义见 [核心数据字典 §7](../核心数据字典.md)。

**`seq` 的生成**：使用 `MAX(seq) + 1` 在链尾锁内计算，**不用 sequence/identity**——链要求 `seq` 无洞，而 sequence 在事务回滚后会留下空洞，验链器将无法用「连续性」做快速完整性判断。

## 5. 核心流程

### 5.1 `append` 主流程

```
1. 校验脱敏：_assert_payload_safe(event.payload)     → 命中即 raise（不写）
2. 事务与隔离级别：调用方必须已在 SERIALIZABLE 事务内；
   本方法用 session.connection().execution_options(isolation_level="SERIALIZABLE")
   时缺省补设（缺省情况见 §10）
3. 锁链尾：SELECT seq, event_hash FROM evidence_event ORDER BY seq DESC LIMIT 1 FOR UPDATE
   空表时改用 pg_advisory_xact_lock(<ledger 固定 key>) —— 没有行可锁时 FOR UPDATE 锁不住任何东西
4. seq = 上一行的 seq + 1（空表为 1）；prev_hash = 上一行 event_hash（空表为 ZERO_HASH）
5. event_hash = compute_event_hash(...)
6. INSERT evidence_event
7. 若 seq % checkpoint_interval == 0 → sign_checkpoint(session, now=event.occurred_at)
8. flush；返回 ORM 实例
```

第 3 步与第 7 步都必须与业务写入处在**同一个事务**：检查点覆盖的事件区间一旦提交就不能再变，若检查点在另一个事务里写，就会出现「签名覆盖了尚未提交的事件」或「事件提交了但没有检查点」两种不一致。

### 5.2 并发写入的串行化

| 场景 | 机制 | 结果 |
|---|---|---|
| 两个事务同时 append | 第 3 步 `FOR UPDATE` 使后者等待前者提交 | 串行化，`seq` 连续无洞 |
| 表为空时并发 append | `pg_advisory_xact_lock` 替代行锁 | 同上 |
| 锁等待超时（`lock_timeout`） | 事务失败，调用方按 §6.4 重试 | 不产生断链 |
| READ COMMITTED 下的幻读 | **必须 SERIALIZABLE**：即使 `FOR UPDATE` 锁到行尾，第二个事务在 READ COMMITTED 下也不会看到第一个事务**新插入**的行（无行可锁），于是算出同一个 `seq` → `uq_evidence_event_seq` 冲突 | 冲突即 `SerializeError`，重试 |
| 重试 | 捕获 SQLSTATE `40001`（serialization_failure）与 `40P01`（deadlock_detected），退避 `min(2^n * 10ms + jitter, 500ms)`，最多 5 次 | 超限 → `CONFLICT`（见 §7） |

### 5.3 检查点与密钥轮转

```
append（第 100 条）──┬── 同事务 sign_checkpoint()
                     └── 记录 LEDGER_CHECKPOINT_SIGNED 事件？（见下）
beat（兜底）────── 每 1 小时扫「已提交但未被任何 block 覆盖的最大区间」补齐签名
```

- 签名消息 = `f"{chain_head_hash}|{from_event_seq}|{to_event_seq}"`，沿用与 `event_hash` 相同的转义规则；`chain_head_hash` 是区间末端事件的 `event_hash`。
- `from_event_seq` = 上一个 block 的 `to_event_seq + 1`（无前块则为 1），保证**区间连续无缝**；有缝即视为实现缺陷，`verify_chain` 报 `broken_reason="checkpoint_gap"`。
- 密钥轮转：`key_id` 取自私钥文件的**文件名**（`ledger_signing_key_<key_id>.pem` → `<key_id>`），因此轮转只需换私钥文件与挂载路径 `LEDGER_SIGNING_KEY_PATH`，无需新增配置项（`Settings` 当前没有 `LEDGER_KEY_ID`，见 §10.3）。**旧公钥文件永久保留**在 `deploy/ledger/keys/<旧 key_id>.pub.pem`，验链器按每个 block 的 `key_id` 取对应公钥，因此轮转不影响历史验证。私钥轮转流程见 `core/keys.py`（生成 → 挂载 → 更新路径 → 重启 api/worker/beat）。
- `LEDGER_CHECKPOINT_SIGNED` 事件本身也写进账本（`subject_type="evidence_ledger_block"`，`subject_id=str(block_seq)`）。注意它由**下一个** append 写入：签名事件不可能包含自己的哈希。

### 5.4 验链（`verify_chain` / `verify_ledger.py`）

1. 从 `from_seq` 开始按 `seq` 升序流式读取事件（`server_side_cursor` 或 `fetchmany(1000)`，避免把全表读进内存）。
2. 断言 `seq` 连续（`seq[i+1] == seq[i] + 1`），断裂即报 `first_broken_seq` 与 `broken_reason="sequence_gap"`。
3. 逐条重算 `event_hash`，并与库中值比对；不符即报 `broken_reason="event_hash_mismatch"`。
4. 逐条断言 `prev_hash == 上一条的 event_hash`（首条为 `ZERO_HASH`）；不符即报 `broken_reason="prev_hash_mismatch"`。
5. 遍历 `evidence_ledger_block`（按 `seq` 升序）：用该块 `key_id` 对应的公钥验证签名；再断言 `chain_head_hash` 等于 `to_event_seq` 那一条的 `event_hash`；不符即报 `broken_reason="checkpoint_signature_invalid"` / `"checkpoint_head_mismatch"`。
6. 输出 `VerifyReport`；CLI 退出码：`0` 全部通过、`1` 发现断链、`2` 运行环境/参数错误（连不上库、公钥缺失、`key_id` 无对应公钥）。

## 6. 关键算法与规则

### 6.1 `event_hash` 的规范化序列化（可复现性规则）

```
event_hash = SHA256( join("|", [
    str(seq),                        # 十进制无前导零
    str(tenant_id),                  # 🔴 2026-10-16 补入，理由见下
    "0" if project_id is None else str(project_id),   # 🔴 同上
    "0" if actor_id is None else str(actor_id),
    event_type.value,                # 存 value 而非成员名，与库中 CHECK 口径一致
    subject_type,                    # NULL/未设 → 空串
    escape(subject_id),
    artifact_hash,
    escape(canonical_json(payload)), # 见下
    prev_hash,
    occurred_at_utc_iso(),
]) )

occurred_at_utc_iso() = occurred_at.astimezone(UTC).strftime("%Y-%m-%dT%H:%M:%S.%f+00:00")
escape(s) = s.replace("\\", "\\\\").replace("|", "\\|")   # 仅对 payload 与 subject_id 施加
```

🔴 **`tenant_id` / `project_id` 必须参与哈希**（2026-10-16 修正）。原式只列了
`seq/actor_id/event_type/subject_*/artifact_hash/payload/prev_hash/occurred_at`，
把这两个字段留在了哈希覆盖之外，后果是：**把一条事件改挂到别的租户名下，验链照样通过**。
多租户账本的核心价值恰恰是「谁在哪个租户做了什么」，而它的归属却不可验证。

原设计把它们排除的理由是「`tenant_id` 不参与**分链**」——但这是两件事：
「不做分链维度」（链仍是一条全局链，`seq`/`event_hash` 仍全局唯一）与
「不参与哈希覆盖」被混为一谈了。一条全局链完全可以、也应该在每条事件内覆盖自己的租户归属。

**这是唯一能改它的时机**：哈希格式一旦有真实数据落库就再也改不动（改了等于全链失效），
而此刻账本尚无数据，改动是免费的。`compute_event_hash` 的 golden test（§9.1）需按新输入重算。

| 规则 | 取值 | 理由 |
|---|---|---|
| payload 序列化 | `core.ids.canonical_json`：`sort_keys=True`、`ensure_ascii=False`、`separators=(",",":")`、`default=str` | 键序与空白差异会让同一语义算出不同哈希；`ensure_ascii=False` 保留中文原样 UTF-8，读账本时人可读 |
| payload 编码 | 显式 `encode("utf-8")` | 跨语言一致性前提；禁止依赖平台默认编码 |
| 时间 | UTC、带微秒、固定 6 位、后缀固定 `+00:00` | 禁止用 `isoformat()` 默认行为（微秒为 0 时会省略、时区可能输出 `Z` 或 `+00:00` 两种形态） |
| NULL | 一律在参与哈希前转成「空串」或 `"0"`（见上） | 明确区分「无值」与「值恰好是字符串 `null`」 |
| 分隔符转义 | payload 与 `subject_id` 内的 `\`、`|` 先转义 | JSON 允许出现 `|`，不转义会产生歧义拼接（两个不同事件可能算出同一串） |
| 浮点数 | payload 内**禁止**出现 float；比率一律用 `numeric(6,4)` 语义的字符串（如 `"0.0500"`） | `repr(0.1)` 跨语言/跨版本不保证一致 |
| datetime | payload 内**禁止**出现 datetime 对象 | `canonical_json` 的 `default=str` 会把它变成平台相关格式；调用方必须先转成 §6.1 的时间格式字符串 |

以上七条是**验链的前提**，任何一条放宽都会让 `scripts/verify_ledger.py` 在另一台机器上误报断链。实现上用一个 golden test 固定住（见 §9.1）。

### 6.2 脱敏前置校验（append 入口，命中即 `raise`）

1. **键名黑名单**：复用 `core/logging.py` 的 `_SENSITIVE_KEY_RE`（`pass*`/`secret`/`token`/`api_key`/`authorization`/`credential`/`private_key`/`signature`/`conn_str` …）递归检查 payload 的**所有**层级键名（深度上限 6，与日志处理器一致）。
2. **值形态检测**：复用 `core/logging.py` 的 `_VALUE_RULES`（`sk-*`、`Bearer *`、DSN URL、PEM 私钥、JWT 三段式、18 位身份证、11 位手机号、邮箱）。命中即拒绝。
3. **拒绝而非替换**：与日志处理器「`[REDACTED_*]` 替换」不同，账本**抛异常**。理由：账本永久保留且是审计事实来源，静默替换会产生「看起来很干净」的记录，而真正的泄露已经发生了（值到了不该到的地方）。让调用方在开发期就炸掉。
4. 例外白名单：`subject_id` 若为 `jti`（UUID 形态）不触发形态检测；`artifact_hash` 是 hex64，不参与检测（只检测 payload 与 `subject_type`/`subject_id`）。

### 6.3 单入口为什么不可绕过

`evidence_event` 的 `prev_hash` 必须等于当前链尾，`seq` 必须连续，二者只有在「锁链尾 + 算哈希 + 插入」这一处原子完成才能成立。任何模块自己 `INSERT` 会：① 拿不到一致的 `seq`（并发下必冲突或分叉）；② 极易忘记 `event_hash` 覆盖 `prev_hash`，导致断链在很久以后才被发现；③ 绕过 §6.2 的脱敏前置。因此 `models/evidence.py` 的 `__immutable__` 只保证「不改历史」，**「只能从一处写」靠 Code Review 与 §9.13 的检查保证**（ORM 层无法表达"这张表只有一个合法写入者"）。

### 6.4 事务隔离级别与重试

```python
RETRYABLE_SQLSTATES = {"40001", "40P01"}
MAX_APPEND_RETRIES = 5
# 退避：min(2**attempt * 10ms, 500ms) + random.uniform(0, 10ms)
```

退避里的随机抖动是**允许**的（写入路径的抖动不影响判定确定性），但**不得**让抖动进入任何参与哈希的值。

### 6.5 导出格式

- JSON：`{"events":[...],"report":{...},"exported_at":"...","filter":{...}}`；`events` 元素字段与 §3.1 查询一致。
- CSV：固定列序 `seq,occurred_at,event_type,tenant_id,project_id,actor_id,subject_type,subject_id,artifact_hash,prev_hash,event_hash,payload_json`；`payload_json` 是单行 JSON（引号转义），分隔符逗号、编码 UTF-8（带 BOM 以便 Excel 正确识别中文）。CSV 只用于人读与归档，**验链请用 JSON**（CSV 往返会破坏字段类型）。

### 6.6 性能

- `append` 在关键路径上（Commit、每次 ToolBroker 拒绝、每次状态流转）。开销构成：1 次 `SELECT ... ORDER BY seq DESC LIMIT 1 FOR UPDATE`（走 `uq_evidence_event_seq` 反向索引扫描，`O(log n)`）+ 1 次 INSERT + 每 100 次的 1 次 Ed25519 签名（Ed25519 签名为微秒级，不是瓶颈）+ 断链重试（正常情况下为 0）。
- **不再加索引**：每个额外索引都会线性放大 INSERT 成本，而账本写入频率高、查询频率低（auditor 偶发查询）。
- 序列化开销与 payload 体积线性相关；建议单个 payload ≤ 8 KiB（约定，非硬约束），超出的内容应落对象存储后只引用摘要。
- 长期体积：`EVIDENCE_RETENTION_DAYS=0`（永久），且每 100 条一个 block。**当前不做分区**（见 §10）。

## 7. 错误码与拒绝语义

| # | 触发条件 | 错误码 | HTTP | 写账本 |

## 8. 安全与合规约束

1. **单入口**：`evidence_event` 与 `evidence_ledger_block` 只经 `harness/ledger.py` 写入；`models/evidence.py` 的 `__immutable__` 挡住 UPDATE/DELETE。
2. **无明文**：§6.2 的前置校验是硬门；payload 只允许 id、哈希、枚举、计数、掩码值。账本导出接口返回的内容因此可以安全地交给审计人员（仍受 auditor 角色限制）。
3. **密钥分离**：账本签名用 `LEDGER_SIGNING_KEY_PATH`，与 Capability 的 `CAPABILITY_SIGNING_KEY_PATH` **必须不同**（`core/keys.py` 的 `--kind` 已强制区分）；私钥只挂载在 api/worker/beat 容器（`/run/secrets:ro`），不进仓库，不写日志。公钥是公开信息，**必须**进仓库归档。
4. **签名覆盖范围**：检查点签名覆盖 `chain_head_hash`（进而覆盖链上全部历史）+ 区间边界，因此「删掉中间某条 + 重算后续哈希」也会被检查点揭穿（重算后 `chain_head_hash` 与已签名值不符）。
5. **权限**：查询/导出仅 `auditor`（`role_assignment` 为唯一事实来源，不用 JWT 角色声明）；`verify` 同为只读。写账本没有 HTTP 入口——**外部永远不能直接写事件**，只能通过做业务动作间接产生。
6. **租户隔离**：查询强制 `tenant_id` 过滤（链是全局单链，但可见性按租户收紧）。
7. **不可抵赖**：`actor_id` 为 NULL 的事件只允许系统动作（beat/worker 自动流转）产生；凡是人触发的动作必须带 `actor_id`（Code Review 与 §9.12 断言）。

## 9. 测试要点

**单元测试（纯函数 + SQLite 内存库）**
1. **哈希 golden test**：固定一组输入（含中文 payload、NULL `actor_id`、微秒为 0 的时间）→ 断言 `compute_event_hash` 输出与硬编码的 64 位 hex 完全一致。这条测试是跨版本、跨语言的锚点，**任何改动都视为破坏兼容**。
2. **转义反例**：`subject_id="a|b"` 与两条 `subject_id="a"`、`subject_type="b"` 的事件必须算出不同哈希（防歧义拼接）。
3. **NULL 表示**：`actor_id=None` 与 `actor_id=0` 的哈希必须不同。
4. **时间格式**：同一时刻的 `datetime` 带不同 `tzinfo`（UTC / +08:00）必须算出同一哈希；微秒为 0 时也必须输出 6 位微秒。
5. **脱敏前置反例**：payload 含 `{"password": "..."}` / `{"note": "13800138000"}` / `{"s": "sk-abcdefgh"}` / 嵌套 3 层的敏感键 → 4 条用例都 `raise`。
6. **float / datetime 反例**：payload 含 `0.05` 或 `datetime.utcnow()` → `VALIDATION_ERROR`。
7. `escape` 与 `canonical_json` 不得改变 payload 语义（往返一致）。

**集成测试（真实 PG，标 `@pytest.mark.integration`）**
8. **并发写入**：`asyncio.gather` 50 个事务各 append 1 条 → 断言 `seq` = 1..50 连续无洞、`verify_chain().ok is True`、`prev_hash` 链完整。
9. **篡改检测**：直接 SQL 改一条 payload（绕过 ORM 钩子）→ 断言 `verify_chain` 报 `event_hash_mismatch` 且 `first_broken_seq` 等于被改条目的 `seq`。
10. **删除检测**：删中间一条 → 报 `sequence_gap`（配 `prev_hash_mismatch`）。
11. **检查点**：写 100 条 → 断言恰好 1 个 block；再写 1 条 → 仍 1 个（区间为 1..100）；写满 200 → 2 个 block 且区间无缝。
12. **密钥轮转**：用 key_A 签第 1 块、key_B 签第 2 块 → 断言两块都能验证通过（依赖公钥归档）。
13. **写入者检查**：全仓 AST 扫描，断言 `evidence_event` / `evidence_ledger_block` 的构造只出现在 `harness/ledger.py`（其余模块只允许 import `EvidenceLedger`）。
14. **`actor_id` 断言**：`event_type` 属于「人触发」集合（`approval.*`、`capability.issued`、`swap.*`、`rollback.*`）时 `actor_id` 不得为 NULL。
15. **独立验链**：`uv run python scripts/verify_ledger.py --dsn ... --pubkeys deploy/ledger/keys --expect-ok` 在同一容器外的纯 Python 环境跑通（断言脚本不 import `core.*` / `fastapi`）。
16. **权限**：非 auditor 查 `/api/v1/governance/ledger` → 403 `ROLE_REQUIRED`；断言账本新增一条由 be-02 写入的权限拒绝事件（subject 为该次请求的 actor，payload 只含 `required_role="auditor"`）。

## 10. 未决与风险

1. **`evidence_ledger_block.tenant_id` 语义待定**：链是全局单链，而 ORM 与数据字典给 block 加了非空 `tenant_id`（继承 `TenantMixin`）。多租户下「这个签名块属于哪个租户」没有自然答案。建议：block 的 `tenant_id` 一律填签名时执行方的租户，或改列可空。需 owner 拍板并同步 [核心数据字典 §7](../核心数据字典.md) 与 migration。
2. **缺少 `ledger.exported` / `ledger.verified` 事件类型**：批量导出审计数据与发起验链都是有审计价值的动作，但 `EvidenceEventType` 当前没有对应成员。当前实现：导出与验链只记 structlog 审计日志。建议在 `models/enums.py` 追加这两个成员（需 owner 拍板）。
3. **`Settings` 缺账本签名 `key_id` 配置**：`Capability` 有 `CAPABILITY_KEY_ID`，但账本侧只有 `LEDGER_SIGNING_KEY_PATH`。当前解法是**从私钥文件名推导 `key_id`**（见 §5.3），不改配置；若 owner 认为隐式推导不利于运维，应新增 `LEDGER_KEY_ID` 并同步 `.env.example`。
4. **缺少专用错误码**：payload 敏感命中目前映射 `INTERNAL_ERROR`（500）。建议新增 `LEDGER_PAYLOAD_UNSAFE`，使调用方能区分「我传了敏感值」与「服务内部故障」。
5. **`psycopg` 未显式声明依赖**：`scripts/verify_ledger.py` 与 `settings.postgres_dsn_sync` 需要 `psycopg`，而它当前只由 `langgraph-checkpoint-postgres` 间接引入。应 `uv add psycopg[binary]` 显式声明，否则上游包换实现时脚本会突然坏掉。
6. **beat 缺检查点兜底条目**：`tasks/maintenance.py` 已有 `tasks.maintenance.checkpoint_ledger` 骨架，但 `tasks/celery_app.py` 的 `beat_schedule` **没有**调度它（只有 retention-cleanup）。需补一条（建议 3600 s），否则低流量期检查点只能靠 append 的第 100 条触发，长期无检查点。
7. **append 的事务隔离级别由谁设**：当前设计是「调用方已在 SERIALIZABLE 事务内」，但 `core/db.py` 的 `session_scope()` 并未设定隔离级别。若调用方遗漏，就会出现 §5.2 表格里的幻读场景（表现为偶发 `uq_evidence_event_seq` 冲突并重试，掩盖了根因）。需在实现时由 `ledger` 主动检测并设置，或统一在 `session_scope` 里提供 `serializable=True` 参数。验证方式：M3 并发用例（§9.8）在未设隔离级别时**应该**先失败，用它证明必须设。
8. **账本无分区、永久保留**：`EVIDENCE_RETENTION_DAYS=0`，表会无限增长。当前不做分区（引入分区会改变验链 SQL 与 `MAX(seq)` 的索引行为，需一并改验链逻辑）。验证方式：M4 用 Benchmark L2 产生的真实事件量估算年增长，再决定按 `occurred_at` 月分区。
9. **跨语言验链**：`ensure_ascii=False` + UTF-8 是当前约定；若未来用 Go/Java 独立验链，需要一份可执行的规范（本文件 §6.1 是规范文本，golden test §9.1 是唯一可执行判据）。验证方式：M4 交付时提供一个非 Python 的最小验证片段。
10. **检查点写入对关键路径的耦合**：第 7 步在 append 事务内签名，签名失败会连带业务事务失败。备选是「异步补签」（append 只写事件，beat 补签），代价是短窗口内检查点缺失。当前选同步（更简单、更强），若 M3 实测 `p99` 抖动明显则改为异步。

### 10.2 M1 实现中新发现

11. **🔴 `event_hash` 的覆盖范围缺了 `tenant_id` / `project_id`**（已修正，记此以防回退）：原式把它们留在覆盖之外，
    后果是「把一条事件改挂到别的租户名下，验链照样通过」——多租户账本的核心价值
    恰恰是「谁在哪个租户做了什么」，而它的归属却不可验证。
    随之必须固化的还有两条序列化约定（`escape()` 转义分隔符、`occurred_at` 固定 6 位微秒）。
12. **`from_seq > 1` 的区间验链不能校验首条 `prev_hash`**：那一段本就缺了头，
    去对 `ZERO_HASH` 必然失败，于是「只想复核最近一千条」会变成一个永远返回断链的功能
    ——**一个总是报警的告警等于没有告警**。代价是报告的 `ok` 只代表**这一段**自洽，
    因此 `VerifyReport` 必须带 `started_from_block_seq`（非 null = 部分验证）。
13. **`checked_blocks` 只统计完全落在已验区间内的检查点**：只按 `from_event_seq` 判的话，
    一个覆盖 1..1000 的块在「只验了 3 条」时也会被算进来，报告会显示
    「验了 3 条事件、覆盖 1 个检查点」，而那个检查点里的 997 条谁都没看过。
14. **`broken_kind` 是新增字段而非替代 `broken_reason`**：前端需要机器可读的类型来选修复动作，
    运维需要 `broken_at_seq` + `broken_detail` 定位到具体字段。只有散文时前端无法分支。
15. **越权读账本的拒绝写账本是「尽力而为」**：写失败只记 structlog 并回滚，
    不能让一个失败的 append 把会话留在坏事务里，也不能把 403 变成 500。
16. **CSV 必须带 BOM**：否则 Windows Excel 按 GBK 读，中文列全乱码。
    列序**写死而非反射**——反射出来的列序会随模型改动而变，而拿旧文件对账时列序必须可预期。
