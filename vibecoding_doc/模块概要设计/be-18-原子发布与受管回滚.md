## 1. 职责与边界

- **做什么**
  - 定义 `TargetPublisher` Protocol，把「把影子表变成正式表」这一动作抽象为跨数据库可替换的实现（Doris / MySQL）。
  - 实现 Doris 的 `REPLACE WITH TABLE … swap=true` 与 MySQL 的 `RENAME TABLE` 三步交换，并各自给出**执行前后对账**（表存在性、列一致性、行数/主键指纹）。
  - 在发布前复核门禁：质量报告 `passed=True`、run 状态合法、制品与输入指纹一致、`target.publish_swap` 的 Capability 可签发与可消费。
  - 维护 `run.status` 的发布相关转移（`running → succeeded / failed`），并写 `swap.succeeded` / `swap.failed` 证据事件。
  - 实现受管回滚 `rollback_cleanup`：权限、状态、Preparation、范围四重校验后清理未发布影子数据，状态 `rolling_back → rolled_back`，写 `rollback.started` / `rollback.succeeded`。
- **不做什么**
  - 不做质量判定（`passed` 由 [be-17](be-17-质量契约与数据分流.md) 给出，本模块只消费）。
  - 不使用 LLM、不做根因解释（归 [be-19](be-19-根因诊断.md)）。
  - 不生成 SeaTunnel HOCON、不提交/停止作业（归 be-10 / be-15；本模块只发 `target.*` 工具）。
  - 不实现「已发布成功之后的回退」（需要再次 Swap 并重新审批）——见 §10。
  - 不直接连目标库执行 DDL：一切 DDL 经 `harness.ToolBroker.execute()`（副作用唯一出口），`clients/target/*` 只提供可被 Broker 调用的具名操作。
- **所在分层**：`clients/target/`（外部系统封装，持有目标端连接）← `services/publish.py`（编排、状态条件更新、证据事件）→ `api/runs.py`（路由归属 be-14，仅转发）。`clients/target/` **不得** import `services/` 或 `harness/`；`engines/` 不参与本模块（无纯算法可下沉）。

## 3. 对外接口

### 3.1 HTTP（前缀 `/api/v1/runs`，路由挂载归 be-14）

| 方法 | 路径 | 权限 | 幂等 | 要点 |
|---|---|---|---|---|
| POST | `/{run_id}/rollback` | 项目内 `operator`（查 `role_assignment`，不用 JWT 角色声明） | **必须带 `Idempotency-Key`** | 触发受管回滚；重复 key 返回首次响应快照（`idempotency_key.response_snapshot`） |
| GET | `/{run_id}/publish` | maker / operator / auditor | 天然幂等 | 返回发布状态与对账明细（`pre_fingerprint` / `post_fingerprint` / `final_state`）；无发布记录 → `publish_state="not_attempted"` |

发布动作本身**无 HTTP 触发入口**：`passed=True` 后由 worker 自动发布（PRD §14.1 第 10 步）。人工重试已发布失败的 run 不在本轮范围（§10）。

### 3.2 Python（跨模块接口）

```python
# clients/target/base.py —— 所有模型 extra="forbid"
class ColumnInfo(BaseModel):
    name: str; ordinal: int; type_text: str; nullable: bool

class TableInfo(BaseModel):
    name: str; exists: bool; columns: tuple[ColumnInfo, ...] = ()
    row_count: int | None = None
    table_fingerprint: str | None = None   # f"{row_count}:{sum_crc32_pk}"

class PublishResult(BaseModel):
    ok: bool
    final_state: Literal["published", "not_published", "unknown"]
    published_table: str | None; previous_data_table: str | None   # 后者 = Swap 后持有旧正式表数据的表名
    pre_fingerprint: str | None; post_fingerprint: str | None
    detail: dict[str, Any]                # 对账明细：列一致性、行数、耗时

class CleanupResult(BaseModel):
    ok: bool
    shadow_dropped: bool                  # 影子表原本不存在 → False 且 ok=True（幂等友好）
    formal_unchanged: bool; detail: dict[str, Any]

class TargetPublisher(Protocol):
    """一次发布/一次清理的全部目标端动作。实现必须满足：失败路径**不得**对正式表做任何写操作；
    所有判定以执行后对账为准，不以 DDL 返回值为准。"""
    async def describe(self, table: str) -> TableInfo: ...
    async def exists(self, table: str) -> bool: ...
    async def publish(self, run: RunRef, plan: PublishPlan) -> PublishResult: ...
    async def rollback_cleanup(self, run: RunRef, plan: RollbackPlan) -> CleanupResult: ...

# clients/target/registry.py —— DORIS → DorisTargetPublisher；MYSQL → MySQLTargetPublisher；其余抛 UnsupportedTargetError
def build_publisher(data_source: TargetEndpointRef) -> TargetPublisher: ...

# services/publish.py —— 编排入口
async def publish_run(session: AsyncSession, *, tenant_id: int, run_id: int) -> PublishResultDTO:
    """发布前置门禁 + 签发发布 Capability + ToolBroker.execute(TARGET_PUBLISH_SWAP) + 状态转移 + 证据。"""
async def request_rollback(session: AsyncSession, *, tenant_id: int, project_id: int,
                           run_id: int, actor_id: int,
                           idempotency_key: str) -> RollbackResultDTO:
    """受管回滚入口。非 operator 抛 ROLE_REQUIRED；状态/范围校验失败抛相应错误码。"""
async def get_publish_state(session: AsyncSession, *, tenant_id: int, run_id: int) -> PublishStateDTO: ...
```

`RunRef = (run_id, tenant_id, project_id, shadow_table, formal_table, error_table)`；`PublishPlan = (shadow_table, formal_table, expected_columns, primary_key_columns, run_id)`；`RollbackPlan = (shadow_table, formal_table, keep_error_rows=True)`。所有 *Plan 由 `services/publish.py` 从 `execution_run` 与冻结版本构造，**任何表名都不得来自请求体**。

## 5. 核心流程

### 5.1 原子发布

```
be-17 finalize_report → passed=True ──▶ services/publish.publish_run(run)
 1 幂等短路：查最近一条 swap.succeeded 事件（subject=run）→ 有则直接返回 already_published
 2 前置门禁（§6.1）：状态条件 UPDATE 抢占（WHERE status='running' 未命中则按下方语义处理）
 3 目标端只读预检：describe(shadow) / describe(formal) 结构一致 + 期望列 ⊆ 影子列
 4 记录 pre_fingerprint(shadow) 与 pre_fingerprint(formal)
 5 签发 Capability(tool=target.publish_swap, subject=run.triggered_by, TTL=300s) → 证据 capability.issued
 6 ToolBroker.execute(TARGET_PUBLISH_SWAP, token, {run_id})   ← jti 原子消费
 7 publisher.publish() 执行 DDL（Doris: REPLACE WITH TABLE swap=true / MySQL: RENAME 三步）
 8 执行后对账（§6.2）→ final_state ∈ {published, not_published, unknown}
 9 published → status=succeeded + 证据 swap.succeeded（payload 记表名与两个指纹）
   ≠published → status=failed + 证据 swap.failed + failure_snapshot.swap
```

非法转移的处理：第 2 步的条件 UPDATE 未命中时读当前状态决定语义——`succeeded` 走幂等短路；`failed/interrupted/rolling_back` 抛 `CONFLICT`（`detail.reason="run_not_publishable"`）；`queued` 抛 `CONFLICT`（作业未启动）。

### 5.2 受管回滚

```
operator ── POST /runs/{id}/rollback (Idempotency-Key) ──▶ services/publish.request_rollback
 1 幂等：idempotency_key 命中 → 返回 response_snapshot
 2 权限：role_assignment 含 operator（本租户本项目）
 3 Preparation 事实：run.preparation.artifact_sha256 == pipeline_version.sha256
 4 范围校验（§6.4）：shadow_table 后缀 / ≠ formal / database 与目标数据源一致
 5 残留作业检查：seatunnel_job_id 对应作业未终止 → 先经 seatunnel.stop（P2 工具），等终态
 6 抢占：条件 UPDATE status IN ('failed','interrupted') → 'rolling_back'（未命中则按 §6.5 判定）
 7 签发 Capability(tool=target.rollback_cleanup, subject=operator, TTL=300s)
 8 ToolBroker.execute(TARGET_ROLLBACK_CLEANUP, token, {run_id})
 9 publisher.rollback_cleanup()：DROP TABLE IF EXISTS <shadow> + 断言 formal 未被改动
10 成功 → status=rolled_back + finished_at + 证据 rollback.succeeded
   失败 → 保持 rolling_back + ROLLBACK_FAILED + 证据 run.failed(payload.kind="rollback")
```

### 5.3 状态机

| 当前状态 | 事件 | 新状态 | 非法转移处理 |
|---|---|---|---|
| `running` | 门禁通过 + Swap 成功（`final_state=published`） | `succeeded` | — |
| `running` | Swap 失败或 `final_state≠published` | `failed` | — |
| `running` | 质量报告 `passed=False` | `failed` | 由 be-17 触发；本模块不投递 Swap 命令 |
| `running` | 回滚请求 | 不变 | `CONFLICT`（必须先 stop/cancel 到终止态） |
| `failed` / `interrupted` | 回滚抢占成功 | `rolling_back` | 条件 UPDATE 未命中 → 读状态后按 §6.5 处理 |
| `rolling_back` | cleanup 成功 | `rolled_back` | — |
| `rolling_back` | cleanup 失败 | `rolling_back`（保持） | 抛 `ROLLBACK_FAILED`；不回退到 `failed`，避免「看似可重试但已被部分清理」的假象 |
| `rolling_back` | 重复回滚请求且未超 stale 窗口 | 不变 | `CONFLICT`（`detail.reason="rollback_in_progress"`） |
| `rolling_back` | 重复回滚请求且已超 stale 窗口 | `rolling_back`（重入） | 视为上次 worker 已死，允许重新执行（DH: 见 §6.5） |
| `rolled_back` | 重复回滚请求 | `rolled_back` | 幂等返回既有结果（`already_rolled_back=true`） |
| `succeeded` | 回滚请求 | 不变 | `CONFLICT`（已发布回退未实现，见 §10） |
| `queued` | 回滚请求 | 不变 | `CONFLICT`（先取消） |

## 6. 关键算法与规则

### 6.1 发布前置门禁（缺一不可，服务端与 Broker 双重校验）

| # | 条件 | 校验点 |
|---|---|---|
| 1 | run 存在且 `tenant_id / project_id` 匹配 | `services/publish.py`（repository 强制带租户） |
| 2 | `run.status == running` | 条件 UPDATE |
| 3 | `quality_report.passed is True` | `services`（快速失败、友好错误）+ `ToolBroker` 的 `RequireQualityPassed` precondition（兜底防绕过） |
| 4 | `preparation.artifact_sha256 == pipeline_version.sha256` | `services`；不等 → `FINGERPRINT_MISMATCH` |
| 5 | 目标端预检通过（影子/正式表结构一致、期望列齐全） | `TargetPublisher.describe()` |
| 6 | Capability 可签发并能通过 `ToolBroker` 校验（subject/tool/env/artifact_sha256/exp 全部匹配） | `harness.capability.issue/verify` |

**质量报告这个附加条件在 ToolBroker 里的表达方式**：`harness/broker.py` 为每个 `ToolName` 提供一个前置钩子：

```python
class Precondition(Protocol):
    async def check(self, ctx: ToolContext) -> None: ...   # 不满足则抛领域异常

TOOL_PRECONDITIONS: dict[ToolName, Precondition] = {
    ToolName.TARGET_PUBLISH_SWAP: RequireQualityPassed(),   # 读同租户 run.quality_report，断言 passed is True
    ToolName.TARGET_ROLLBACK_CLEANUP: RequireManagedRollbackContext(),
    # …
}
```

`RequireQualityPassed` 不满足时抛 `QualityRejectedError`（→ `QUALITY_REJECTED`），Broker 在抛出前写 `swap.failed`（payload `reason="quality_not_passed"`）。放在 Broker 而非调用方的理由：副作用唯一出口必须自带准入条件，否则任何新增调用路径都会绕过质量门禁；这与四眼审批「服务端 + DB 约束双保险」同构。该钩子是对 [be-05](be-05-Harness内核与工具代理.md) 的**接口要求**，需在 be-05 文档中同步体现。

补充：**发布 Capability 只在质量报告通过后才签发**，因此「未通过质量却执行 Swap」在令牌层面即不可达；门禁失败时不签发令牌，比事后拒绝更强。

### 6.2 执行后对账（`final_state` 的确定方式）

DDL 的返回值不可信（超时、连接中断、客户端杀进程都可能发生在「语句已生效」之后）。统一用**执行后对账**判定最终态：

```
pre_shadow = fingerprint(shadow)      # 发布前
pre_formal = fingerprint(formal)      # 发布前
（执行 DDL，忽略返回值，只记耗时与异常）
post_formal = fingerprint(formal)
post_shadow = fingerprint(shadow)
```

| 观测 | 判定 |
|---|---|
| `post_formal == pre_shadow` 且 `post_shadow == pre_formal` | `published`（正式表已是本次数据，原名未变） |
| `post_formal == pre_formal` | `not_published`（未生效，正式表原样） |
| 其他（无指纹可比、DDL 报错且表不存在、指纹读失败） | `unknown` → 归类为失败，`failure_snapshot.swap.status="unknown"`，需人工核对 |

`fingerprint(table) = f"{COUNT(*)}:{COALESCE(SUM(CRC32(CAST(<pk> AS VARCHAR))), 0)}"`（Doris 与 MySQL 均支持 `CRC32`）。**已知局限**：只覆盖行数与主键集合，不覆盖全部列内容，因此「行数相同且主键和相同但内容不同」检测不到——写入路径由「影子表只被本次 run 写入」这一前提保证，故可接受；需在 `PublishResult.detail` 中标注 `fingerprint_scope="rowcount+pk_crc32"`。

### 6.3 Doris 实现

- 语义：`ALTER TABLE <shadow> REPLACE WITH TABLE <formal> PROPERTIES("swap" = "true");`（冻结决策原文）。`swap=true` 表示**两表交换**而非替换：语句执行后，名为 `<formal>` 的表持有本次数据（表名不变，业务侧无感），名为 `<shadow>` 的表持有**原正式表数据**——这天然形成一份可回溯的备份，同时让「再交换一次」成为理论上的回退手段（本轮不实现，见 §10）。
- 硬性前提（预检逐条断言，任一不满足即在不触碰正式表的前提下失败）：
  1. 两张表在**同一个 database**，且都是 OLAP 表；
  2. 列名、列顺序、列类型、null 属性完全一致（`information_schema.columns` 逐列比对）；
  3. 分区/分桶/副本数等表属性一致；
  4. 影子表行数 > 0 或 `read_rows == 0`（空影子表发布会在 §10 的未决项里有结论前先拒绝）；
  5. `expected_columns ⊆ shadow.columns`。
- 原子性说明：该语句在 Doris FE 的元数据层一次提交，不存在「改了一半」的中间态；但**客户端超时不代表未生效**，必须走 §6.2 对账。
- 失败处理：DDL 报错 → 直接进入对账；对账结果 `not_published` → 正式表未被改动，run 置 `failed`；`unknown` → run 置 `failed` 并标记需人工核对（不自动重试，避免在未知态上叠加第二次 Swap）。

### 6.4 MySQL 实现

- 语义：`RENAME TABLE <formal> TO <tmp>, <shadow> TO <formal>, <tmp> TO <shadow>;`
  - 单条 `RENAME TABLE` 语句内的多个 rename 由 MySQL 8 **原子执行**（DDL 原子化），不存在中间态；
  - 交换后 `<formal>` 名持有本次数据，`<shadow>` 名持有原正式表数据 —— 与 Doris `swap=true` 的终态**一致**，因此 `services/publish.py` 的对账逻辑对两种实现共用。
  - 备份表命名：交换后影子表名下即为备份，其名字由影子表命名规范决定（`<formal>__run<run_id>_shadow`，由 be-14/be-16 生成），可追溯；不需要额外生成备份名。
- 差异与注意：
  - `RENAME TABLE` 只改元数据，但会短暂持有元数据锁；视图/存储过程/外键中对旧表名的引用**不会**随 rename 自动更新——`PublishPlan` 若涉及目标端下游视图，需在 `resource_scope` 中登记（预检时 `SHOW FULL TABLES WHERE Table_type='VIEW'` 检查一遍，命中则拒绝并提示）。
  - MySQL 8 的 `CAST` 失败会直接报错，因此质量谓词必须用 `REGEXP` 前置校验（见 be-17 §6.1），否则错误行会让整个 sink 失败。
- 失败处理：语句失败即整体回滚（原子），正式表原样；对账仍要跑一遍以覆盖「语句成功但客户端超时」的情形。

### 6.5 回滚的重复执行与状态保护

```sql
-- 抢占（唯一一次生效的成功路径）
UPDATE execution_run
   SET status = 'rolling_back', updated_at = now()
 WHERE id = :run_id AND tenant_id = :tenant_id AND project_id = :project_id
   AND status IN ('failed', 'interrupted')
RETURNING id;
```

- 影响 0 行时读当前状态：
  - `rolled_back` → 幂等返回既有结果，不重复执行；
  - `rolling_back` → 取该 run 最近一条 `rollback.started` 事件的 `occurred_at`；距今 ≤ `settings.CAPABILITY_TTL_SEC`（300s，复用既有配置，不新增项）→ `CONFLICT`（`detail.reason="rollback_in_progress"`）；超窗口 → 视为上次 worker 已死，允许重入（写入新的 `rollback.started`，`payload.attempt += 1`）；
  - `succeeded` → `CONFLICT`（`detail.reason="already_published"`）；
  - `running` / `queued` → `CONFLICT`（`detail.reason="run_not_terminal"`）。
- 幂等的第二层：`Idempotency-Key`（`idempotency_key` 表，`scope="run.rollback:{run_id}"`），同 key 同 `request_hash` 直接回放 `response_snapshot`；同 key 不同 `request_hash` → `IDEMPOTENCY_CONFLICT`。
- 第三层：`target.rollback_cleanup` 的 Capability 单次消费（Redis `SETNX` + PG 唯一约束），重复消费 → `CAPABILITY_REPLAYED`。
- 回滚**必须可重复执行**：`rollback_cleanup` 内所有动作幂等（`DROP TABLE IF EXISTS`、`formal_unchanged` 为断言而非变更），因此从 `failed` 重试是安全的。

### 6.6 发布与回滚的并发

| 场景 | 结果 |
|---|---|
| 同一 run 两个 Swap 请求并发 | 状态条件 UPDATE 互斥 + Capability 单次消费：一个成功，另一个 `CAPABILITY_REPLAYED`；若两个请求都被拒则读状态走幂等短路 |
| Swap 与 Rollback 竞争 | 状态集合不相交（Swap 要 `running`，Rollback 要 `failed/interrupted`）：谁先改状态谁赢；败者得到 `CONFLICT`，不会出现「回滚途中把影子发布了」或「发布成功后影子被清掉」 |
| Outbox 重投同一条 Swap 命令 | `outbox_message.idempotency_key` UK + 第 1 步的 `swap.succeeded` 幂等短路 |
| 回滚中收到第二个回滚 | §6.5 的 stale 窗口规则 |
| 两个不同 run 并发发布到同一正式表 | 由 be-14/be-16 的「同一 PipelineVersion 只允许一条活跃 run」与影子表按 run 命名约束；跨版本并发发布同一正式表不在本轮支持范围（§10） |

## 7. 错误码与拒绝语义

| 触发条件 | 错误码 | HTTP | 是否写证据账本 |
|---|---|---|---|
| 质量报告未通过（`passed != True`）仍请求发布 | `QUALITY_REJECTED` | 409 | 是（`swap.failed`，`reason="quality_not_passed"`） |
| Swap 执行失败或对账为 `not_published` / `unknown` | `SWAP_FAILED` | 500 | 是（`swap.failed`，payload 记表名与两个指纹） |
| `preparation.artifact_sha256 != pipeline_version.sha256` | `FINGERPRINT_MISMATCH` | 409 | 是（`swap.failed` / `run.failed`，`kind="rollback"`） |
| 非 operator 触发回滚 | `ROLE_REQUIRED` | 403 | 是（协议类拒绝） |
| 跨租户访问 run | `TENANT_MISMATCH` | 403 | 见 be-17 §10（缺合适事件类型） |
| run 状态不允许发布/回滚 | `CONFLICT`（`detail.reason`） | 409 | 是（`run.failed`，`kind="publish"` / `"rollback"`） |
| 回滚正在执行（stale 窗口内） | `CONFLICT`（`reason="rollback_in_progress"`） | 409 | 否（未改变任何事实） |
| 回滚执行失败 | `ROLLBACK_FAILED` | 500 | 是（`run.failed`，`payload.kind="rollback"`；见 §10 事件类型缺口） |
| 目标端不可达 / 超时 | `DATASOURCE_UNREACHABLE` / `DATASOURCE_TIMEOUT` | 502 / 504 | 是（同上） |
| Capability 已消费 | `CAPABILITY_REPLAYED` | 409 | 是（`capability.rejected`） |
| Capability 过期 | `CAPABILITY_EXPIRED` | 403 | 是（`capability.rejected`） |
| 同一 `Idempotency-Key` 不同请求体 | `IDEMPOTENCY_CONFLICT` | 409 | 否 |
| 目标端类型不支持（`registry` 无法构造 publisher） | `INTERNAL_ERROR` | 500 | 是（`swap.failed`）。生成期应由门禁提前以 `GATE_BLOCKED` 阻断 |

## 8. 安全与合规约束

- **副作用唯一出口**：所有目标端 DDL 经 `ToolBroker.execute(ToolName.TARGET_PUBLISH_SWAP | TARGET_ROLLBACK_CLEANUP, token, args)`；`services/publish.py` 不得自行 `await publisher.publish()` 绕过 Broker——`services` 只构造参数、判定状态、写证据，执行由工具承担。
- **表名来自服务端**：`shadow_table / formal_table` 只从 `execution_run` 读取；接口请求体不接受任何表名/库名。回滚范围校验四连：后缀命中影子表命名规范、`shadow != formal`、database 与目标数据源 `endpoint.database` 一致、数据源 `type ∈ {doris, mysql}`。目的是保证一次误操作最多删掉一个影子表，永远删不到正式表。
- **无明文 Secret**：目标端连接凭据由 be-15 在 worker 内存中物化后交给 `clients/target`；本模块不接触 `SecretReference` 的值，异常信息不得包含连接串（`core/errors.py` 已兜底：数据库异常不原样透出）。
- **审计**：`swap.succeeded` / `swap.failed` / `rollback.started` / `rollback.succeeded` 必写证据账本；payload 只含 `run_id / shadow_table / formal_table / final_state / pre_fingerprint / post_fingerprint / actor_id`，**不含任何业务数据行**。
- **权限**：回滚角色校验以 `role_assignment` 为唯一事实来源（不信任 JWT 角色声明，权限可能已被回收）；`artifact_sha256` 一致性校验保证「回滚的是被审批过的那一版」。
- **不可变**：发布/回滚只改 `execution_run`（可变表）状态，绝不 UPDATE `quality_report` / `preparation` / `capability`；审计事实靠新的事件行承载。
- **最小权限**：目标端账号只授予目标库的 `DROP TABLE` / `ALTER` / `RENAME` 与 `SELECT`，不授予跨库权限（部署期在 `deploy/doris/init` 与 MySQL 授权脚本中限制，见 be-22）。

## 9. 测试要点

- **单元测试（`FakePublisher`，无真实目标端）**
  - 门禁：`passed=False` → 抛 `QUALITY_REJECTED` 且**未调用** `publisher.publish`（断言调用次数为 0）；
  - `final_state` 三态分支：`published → succeeded`、`not_published → failed`、`unknown → failed` 且 `failure_snapshot.swap.status="unknown"`；
  - 状态机非法转移：`queued` / `succeeded` / `rolling_back` 下请求发布与回滚的返回码；
  - 回滚幂等：`rolled_back` 再请求 → `already_rolled_back=true` 且不重复调用 cleanup；同 `Idempotency-Key` 重放 → 返回 `response_snapshot`；同 key 不同 body → `IDEMPOTENCY_CONFLICT`；
  - 范围校验反例：构造 `shadow_table` 等于正式表名 / 后缀不符 / 跨库 → 拒绝且不调用 cleanup（**这是「回滚不会误删正式表」的核心证明**）。
- **集成测试（真实目标端，ECS 上跑）**
  - Doris：建 formal + shadow（含差异数据）→ `publish` → 断言正式表内容为影子数据、`<shadow>` 持有旧数据、`final_state=published`、`status=succeeded`；
  - MySQL：同上，断言三步交换的终态与 Doris 一致；
  - 结构不一致（列类型不同 / 少一列）→ 预检失败，正式表指纹不变；
  - 硬中断后的回滚：造 `interrupted` 的 run + 影子表 → `request_rollback` → 影子表被删除、正式表指纹不变、`status=rolled_back`、账本出现 `rollback.started` / `rollback.succeeded`。
- **故障注入**
  - DDL 失败注入（把 formal 改名制造冲突）→ `not_published` + `SWAP_FAILED` + 正式表原样；
  - 「DDL 超时但实际生效」注入（在 publisher 内注入超时异常但真的执行 DDL）→ 断言 `final_state=published` 且 run 最终 `succeeded`（证明判定不依赖返回值）；
  - cleanup 中途失败注入 → 状态保持 `rolling_back`、`ROLLBACK_FAILED`、可重试成功；
  - 协议反例：`passed=False` 的 run 不存在任何 `etl.target.publish_swap` 的 outbox 行；重复回滚不产生第二条 `rollback.succeeded`。

## 10. 未决与风险

| 事项 | 现状 | 验证方式 |
|---|---|---|
| 已发布成功后的回退（`succeeded → rolled_back`） | **本轮不实现**。需要「再次 Swap」+ 重新审批 + P1 级权限，语义上等价于一次新的发布 | M4 评估：Doris `swap=true` 已留下旧数据在影子表名下，技术上可行；需先定权限与审批要求 |
| 空影子表发布 | 会清空正式表，但当前语义下可能被判为 `passed=True`（空源场景，见 be-17 §10） | M3 演示前拍板；在此之前 `publish` 预检对 `shadow.row_count == 0 && read_rows > 0` 直接拒绝 |
| 跨 PipelineVersion 并发发布同一正式表 | 无锁保护（不同版本 = 不同 prepare，影子表名不同，但 formal 相同） | 需要「按 formal_table 加互斥」的方案（PG advisory lock 或 Redis 锁）；M3 先在文档记录，M4 实现 |
| Doris `REPLACE WITH TABLE` 的实机行为 | `swap=true` 的表名/数据归属、同库同结构要求、是否需要额外权限，均无实机确认 | M3 在 ECS Doris 2.1 上手跑一次并记录 `SHOW TABLES` / `COUNT(*)` 前后对照 |
| 备份表（Swap 后影子名下的旧数据）清理策略 | 未定义；`DROP` 走哪个工具、由谁触发（operator 手工 / maintenance）未定 | M4 随保留策略定；若需自动清理，应复用 `TARGET_ROLLBACK_CLEANUP` 并加 `mode` 参数（会改动工具契约，需同步 be-05） |
| 事件类型缺口 | 回滚失败没有 `rollback.failed` 事件类型 | 建议新增 `ROLLBACK_FAILED = "rollback.failed"`；在此之前用 `run.failed` + `payload.kind="rollback"` |
| `ToolBroker` precondition 钩子 | be-05 文档尚未编写，钩子形态是本文档提出的**要求** | 写 be-05 时必须同步；若 be-05 不提供钩子，则降级为「仅服务层校验」，并在交付自检中标注该绕过风险 |
| 发布失败的人工重试入口 | 无 HTTP 端点（重试需要新 Capability 与新的门禁评估） | M4 评估是否开放 `POST /runs/{id}/publish`（operator，需重新签发令牌） |
