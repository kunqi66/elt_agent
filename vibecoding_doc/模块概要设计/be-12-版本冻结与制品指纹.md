## 1. 职责与边界

- **做什么**：
  - 定义**制品指纹算法**：`sha256 = SHA256(canonical_json(etl_plan + hocon + quality_contract + supervision_contract + 源 Profile 指纹))`，并固化「哪些字段参与、哪些必须排除」与规范化规则（键排序、数值定标、空值表示、时间剔除、UTF-8 编码）。
  - `freeze()`：门禁 pass/warn 之后，在同一事务内写入 5 张不可变制品表 + `pipeline_version`，并更新 `pipeline.current_version_id`。
  - 处理版本号并发递增（`UK(pipeline_id, version_no)` + 行锁 + 重试）。
  - 版本间 **Diff**（纯函数）：Plan / HOCON / Schema / 质量规则 / 预算的结构化差异，带 `locator`。
  - 指纹复核：按已冻结版本重算 `sha256` 并比对，证明「所有不可变制品均可通过摘要复核」（PRD §10.5）。
- **不做什么**：
  - **不做**门禁判定（[be-11](be-11-确定性门禁与有限自动修复.md)）；冻结只是「门禁结论 + 制品」的一次原子落库。
  - **不做** Prepare / 审批（[be-13](be-13-准备单与四眼审批.md)）；本模块只保证 `preparation.artifact_sha256` 的**来源**是这里算出的 `sha256`。
  - **不做**草稿落库与运行时环境/连接器可用性判断：草稿在 Workflow State（be-09 §5.4），本模块是唯一的制品写入口。
- **所在分层**：`engines/fingerprint/`、`engines/diff/`（纯函数）+ `services/version.py`（事务编排）+ `api/pipelines/versions.py`（路由）。

## 3. 对外接口

### 3.1 HTTP

## 5. 核心流程

### 5.1 `freeze()` 时序

```
1. 前置校验（事务外，只读）
   1.1 tenant_id / project_id 过滤后取 pipeline；不存在 → NOT_FOUND
   1.2 校验角色（maker）与 Pipeline 归属 → ROLE_REQUIRED / TENANT_MISMATCH
   1.3 assert_transition(status, "freeze")  → 只允许 generated 出边，否则 CONFLICT
   1.4 gate.verdict == "block" → GATE_BLOCKED（details 带 findings 摘要）
   1.5 profile.status == "expired" 或 expires_at < now → METADATA_PROFILE_EXPIRED
   1.6 占位符完整性：RenderedHocon.placeholders 全部能对应到已登记的 secret_reference 键名
   1.7 计算 sha256 = artifact_sha256(parts)

2. 事务开始（REPEATABLE READ）
   2.1 SELECT ... FROM pipeline WHERE id=:id FOR UPDATE        ← 串行化同一 Pipeline 的并发冻结
   2.2 version_no = COALESCE(MAX(version_no), 0) + 1
   2.3 INSERT etl_plan / hocon_artifact / quality_contract / runtime_supervision_contract
   2.4 INSERT pipeline_version（含 sha256、generation_context、frozen_at）
   2.5 UPDATE pipeline SET current_version_id=:new, status='version_frozen'
   2.6 harness.EvidenceLedger.append(PIPELINE_VERSION_FROZEN)
   2.7 COMMIT

3. 提交后
   3.1 返回 VersionBrief；接口层把 Idempotency-Key 的响应快照写入 idempotency_key
```

**为什么证据事件在同一事务内**：`PIPELINE_VERSION_FROZEN` 是「版本存在」这一事实的证据；若分开提交，会出现「版本已存在但无证据」（审计缺口）或「有证据但版本被回滚」（假证据）。若 [be-06](be-06-证据账本与验链.md) 的 `append()` 必须使用独立串行化事务（链尾 `advisory lock`），则退化为「业务事务提交后立即追加，追加失败进 Outbox 重试」——具体形态以 be-06 契约为准，见 §10。

**为什么冻结前必须重跑前置校验**：门禁结论是在草稿上产生的，从门禁到用户点「冻结」之间存在时间窗（可能数分钟）。窗口内 Profile 可能过期、草稿可能被新一轮生成覆盖。故冻结以**服务端此刻的输入**为准，不信任前端提交的任何 fingerprint。

### 5.2 版本号并发递增

- 主机制：步骤 2.1 的 `SELECT ... FOR UPDATE` 锁住 `pipeline` 行，同一 Pipeline 的冻结被串行化，`version_no` 因此单调且不重号。
- 兜底机制与禁止项：唯一约束 `uq_pipeline_version_pipeline_id_version_no` 是第二道防线——若因跨进程/隔离级别差异仍命中唯一冲突，捕获 `IntegrityError` → 重算 `version_no` 重试，**最多 3 次**，仍失败则 `ConflictError`（`CONFLICT`，409）。**禁止**在 `pipeline_version` 上做 `SELECT ... FOR UPDATE`：锁不可变表会让「只增不改」的语义变味。

### 5.3 不可变性

- `PipelineVersion` 与其四件制品均置 `__immutable__ = True`，由 `models/base.py` 的 `before_flush` 守卫拦截 UPDATE/DELETE。
- **为什么修正只能产生新版本**：审批决定（[be-13](be-13-准备单与四眼审批.md)）与执行能力令牌（[be-05](be-05-Harness内核与工具代理.md)）都绑定 `sha256`。若允许原地修改，则「审批通过的那份制品」与「实际执行的制品」可能不同，四眼审批与 Capability 同时失效。故修正是 `freeze()` 的又一次调用，产生 `version_no + 1`。
- `__mutable_columns__` 在 `PipelineVersion` 上为空——**没有任何列可以在冻结后被修改**，包括 `note`。
- `VERSION_IMMUTABLE` 的触发场景：

| 场景 | 触发点 |
|---|---|
| 代码里对已冻结版本赋值任意列 | ORM `before_flush` → `ImmutableViolationError` → API 层映射 `VERSION_IMMUTABLE` |
| 试图删除版本或制品 | 同上（`session.deleted` 分支） |
| 对同一版本再次冻结 | `assert_transition`（`version_frozen` 无 `freeze` 入边）→ `CONFLICT` |
| 不同 Pipeline 产生完全相同的制品 | 命中 `uq_pipeline_version_sha256` → `CONFLICT`，详见 §10.2 |

### 5.4 无独立状态机

本模块驱动 `PipelineStatus` 的 `generated → version_frozen` 单条转移（转移表见 [be-09](be-09-LangGraph工作流与三层状态.md) §5.5）。非法转移抛 `CONFLICT` 且状态不变。

## 6. 关键算法与规则

### 6.1 规范化序列化（`canonical.py`）

**唯一入口**：`canonical_bytes(payload) = canonical_json(payload).encode("utf-8")`，其中 `canonical_json` 复用 `core/ids.py` 的实现（`sort_keys=True, ensure_ascii=False, separators=(",", ":")`）。第二处实现规范化 JSON 就是指纹系统的第一次分叉，因此**禁止**在别处手写 `json.dumps` 来算指纹。

规则清单：

| 项 | 规则 | 反例（会导致指纹漂移） |
|---|---|---|
| 键排序 | 按键的 Unicode 码点升序递归排序 | 依赖 `dict` 插入顺序 |
| 分隔符 | `,` 与 `:`，无任何空白 | 带 `indent=2` 的美化输出 |
| 编码 | UTF-8，非 ASCII 原样保留（不转 `\uXXXX`） | `ensure_ascii=True` |
| 数值（整数） | 原样十进制，无前导零、无 `.0` | `1` 与 `1.0` 混用 |
| 数值（比率 / 字节以外的小数） | 一律以**定标字符串**表示，4 位小数（`Decimal.quantize(0.0001)`），如 `"0.0500"` | 二进制浮点 `0.05000000000000001` |
| 布尔 | `true` / `false` | `True` / `"true"` |
| 空值 | 一律 `null`；**键不省略** | 省略 `null` 键（后续加字段会改变语义） |
| 数组 | 保持语义顺序，不排序 | 对 `field_mappings` 排序 |
| 时间 | **不参与**指纹（见 §6.2） | 把 `frozen_at` 纳入输入 |
| 自增 ID | **不参与** | 把 `etl_plan.id` 纳入输入 |

### 6.2 参与与排除

`ArtifactParts`（参与指纹的完整集合）：

```python
class ArtifactParts(BaseModel):
    plan: EtlPlanModel                    # schema_version + inputs/outputs/field_mappings/
                                          # transforms/filters/quality_rules/dag/budget
    hocon_content: str                    # HOCON 全文（逐字节）
    quality_rules: list[QualityRule]      # = quality_contract.rules
    error_table_target: dict[str, Any]    # = quality_contract.error_table_target
    reject_rate_budget: str               # 定标字符串
    supervision: PlanBudget               # = 五个预算列
    warn_threshold_pct: int
    source_metadata_profile_sha256: str   # 只取 Profile 指纹，不取 snapshot 全文
```

指纹输入信封：

```json
{
  "v": 1,
  "etl_plan": { "schema_version": "1.0", "inputs": [], "outputs": [], "...": "..." },
  "hocon": "env {\n  ...\n}\n",
  "quality_contract": { "rules": [], "error_table_target": {}, "reject_rate_budget": "0.0500" },
  "supervision_contract": { "max_read_rows": 100000000, "...": 0, "warn_threshold_pct": 80 },
  "source_metadata_profile_sha256": "3f2a..."
}
```

**必须排除的字段**（逐项给理由）：

| 排除项 | 理由 |
|---|---|
| `pipeline_id` / `version_no` / 所有 `id` | 自增、可变的编排事实，与制品内容无关；纳入会让同一份制品在不同 Pipeline 下算出不同指纹 |
| `created_at` / `updated_at` / `frozen_at` / `frozen_by` / `note` | 时间与操作者属审计事实，非制品内容；纳入会让「重算指纹」永远失败 |
| `generation_context` | 模型与提示词版本是**来源信息**而非制品；同一产物的复制应得到同一指纹（数据字典 §3 已明确指纹输入不含它） |
| 校验派生结果：`etl_plan.valid` / `validation_errors`、`hocon_artifact.sha256` / `parser_version` / `validation_result` | `content` 已在信封内，其余是派生结论与工具版本；校验器升级不应让历史指纹失效 |
| `pipeline.current_version_id` / `status` | 可变编排状态 |

**为什么把「排除规则」写成契约**：任何一次「顺手把某个字段加进指纹输入」都会让**全部历史版本的 `verify` 失败**，且已签发 Capability 的指纹校验会全线拒绝。这是本仓库最容易造成事故的一处改动，故单测必须逐项锁定（§9）。

### 6.3 `artifact_sha256`

```python
def artifact_sha256(parts: ArtifactParts) -> str:
    return sha256_hex(canonical_bytes(artifact_envelope(parts)))
```

`artifact_envelope` 负责：(a) 把 Pydantic 模型转成「键集合完整」的 dict（`model_dump(mode="json", exclude_none=False)`）；(b) 把 `Decimal` 转定标字符串；(c) 剥掉 §6.2 的排除项。`hocon_content` 已是字符串，直接进入，不做任何 trim/规范化——**HOCON 的字节就是它的身份**（be-10 §6.3 保证了渲染确定性）。

### 6.4 版本间 Diff（纯函数）

```python
class FieldDiff(BaseModel):
    locator: Locator                      # 复用 be-11 §3.2 的三种形态
    kind: Literal["added", "removed", "changed"]
    before: str | None
    after: str | None

class VersionDiffSection(BaseModel):
    section: Literal["etl_plan", "hocon", "schema", "quality_rules", "supervision", "generation_context"]
    changes: list[FieldDiff]

class VersionDiff(BaseModel):
    from_version_no: int
    to_version_no: int
    from_sha256: str
    to_sha256: str
    sha_changed: bool
    sections: list[VersionDiffSection]
```

| section | 算法 | locator |
|---|---|---|
| `etl_plan` | 按定义域遍历 Pydantic 字段，逐路径比较 | `{"kind":"field","path":"field_mappings[3].target_field"}` |
| `hocon` | `difflib.unified_diff`，按 hunk 归组；每条 hunk 用起始行号定位 | `{"kind":"hocon","line":42,"col":1,"hocon_path":null}` |
| `schema` | 源/目标 Profile 的字段集合差（新增/删除/类型变更的列） | `{"kind":"field","path":"schema.orders.user_id"}` |
| `quality_rules` | 以 `rule.id` 为键做集合差 | `{"kind":"field","path":"quality_rules[rule_id=E_NULL_PK].params"}` |
| `supervision` | 五个预算 + `warn_threshold_pct` 的逐项比较 | `{"kind":"field","path":"budget.max_read_rows"}` |
| `generation_context` | 逐项比较（模型、提示词版本、修复轮次） | `{"kind":"field","path":"generation_context.model_version"}` |

HOCON 全文 Diff 可能极大：`?section=hocon` 时按 hunk 分页（每页 200 hunk），默认 `section=all` 时 `hocon` 段只返回 `hocon_added / hocon_removed` 计数与**前 20 个 hunk**。

`generation_context` 独立成段是刻意的：它**不影响指纹**（§6.2），但「同一需求两次生成得到相同指纹、不同模型版本」是需要人能看出来的一件事。

### 6.5 指纹失效判定

| 变化 | 影响 | 处理 |
|---|---|---|
| 制品内容变化（Plan / HOCON / 质量规则 / 预算任一） | `sha256` 变化 | 必须产生新版本；原版本不变 |
| 源或目标 `metadata_profile` 重新探查（`sha256` 变化） | 新版本的指纹必然变化 | 生成期：`profile.status=expired` 或 `expires_at < now` → **阻止生成**（`METADATA_PROFILE_EXPIRED`，PRD §12）；已冻结版本：**不阻止**，但其 `source_metadata_profile_id` 指向的 Profile 已非最新，前端与 Prepare 页展示「依据 Profile vN 已过期（当前 vM）」提示 |
| `parser_version` / 校验器升级 | **不影响**任何指纹 | 无需重算；新版校验器对历史版本的重校验结果差异属预期 |
| 渲染器（be-10）行为变化 | HOCON 内容变化 → 新版本指纹变化；历史指纹**不再能由当前渲染器复现** | 用 `/verify` 校验历史版本时必须用「内容」而非「重新渲染」——`verify` 只重算信封哈希，不重渲染 |

**`/verify` 的语义**：读回已冻结的 `etl_plan.plan`、`hocon_artifact.content`、四件制品与 `source_metadata_profile.sha256`，重新计算指纹并与库中 `sha256` 比对。它验证的是「库内制品未被篡改」，**不是**「用当前代码能复现同样的制品」。两条命题独立，不要混。

### 6.6 与下游的关系

```
pipeline_version.sha256 ──┬──▶ preparation.artifact_sha256（冗余列，快查一致）
                          ├──▶ approval_decision.artifact_sha256（审批时看到的指纹）
                          └──▶ capability.artifact_sha256（令牌绑定的指纹）
```

三处冗余同一值，是为了让「指纹一致性校验」不必反复 JOIN 到 `pipeline_version`。一致性由 [be-13](be-13-准备单与四眼审批.md) 与 [be-05](be-05-Harness内核与工具代理.md) 在 Commit 时比对；不一致 → `FINGERPRINT_MISMATCH`（审批自动失效，需重新 Prepare）。

## 7. 错误码与拒绝语义

| 触发条件 | 错误码 | HTTP | 写证据账本 |
|---|---|---|---|
| 冻结时 `gate.verdict == "block"` | `GATE_BLOCKED` | 403 | 是（`PIPELINE_GATE_EVALUATED` 已在门禁阶段写过；此处追加一条拒绝记录，见 §10.4） |
| Pipeline 状态不是 `generated` | `CONFLICT` | 409 | 否 |
| `version_no` 并发冲突重试耗尽 | `CONFLICT` | 409 | 否 |
| `sha256` 命中 `uq_pipeline_version_sha256` | `CONFLICT` | 409 | 否（见 §10.2） |
| 试图 UPDATE / DELETE 已冻结制品 | `VERSION_IMMUTABLE` | 409 | **否**（ORM 守卫在失败事务中抛出，账本写入不可用；见 §10.4） |
| 绑定的 Profile 已过期 | `METADATA_PROFILE_EXPIRED` | 409 | 否 |
| 占位符对应的 Secret 引用未登记 | `GATE_BLOCKED` | 403 | 否 |
| 版本不存在 / 不属于本项目（含跨租户） | `NOT_FOUND` | 404 | 否 |
| 跨租户访问项目本身 | `TENANT_MISMATCH` | 403 | 否 |
| 同 `Idempotency-Key` 不同请求体 | `IDEMPOTENCY_CONFLICT` | 409 | 否 |
| 冻结成功 | — | 200 | **是**：`PIPELINE_VERSION_FROZEN`，payload `{version_no, sha256, gate_verdict, profile_id, autofix_rounds}` |

## 8. 安全与合规约束

- **不可变**：见 §5.3。ORM 守卫是第一道，数据库层面无更新路径（无 `updated_at` 列的 `CreatedAtMixin`）。
- **审计**：`PIPELINE_VERSION_FROZEN` 经 `harness.EvidenceLedger.append()` 写入（总纲 §4.6，账本单入口）；payload 只含指纹与引用，不含制品正文与样本。
- **租户过滤**：`freeze()` / `verify_version()` / Diff 路由的每次查询强制带 `tenant_id + project_id`；`version_no` 不是全局唯一，**只能**在 Pipeline 作用域内解析。
- **Secret**：冻结时校验「HOCON 中的每个占位符都有对应已登记的 `secret_reference` 键名」，但**不读取、不物化**值；`hocon_artifact.content` 里因此永远只有 `${...}`。
- **指纹即信任根**：`sha256` 是本系统唯一被「审批结论 / Capability / 执行」共同引用的制品标识。任何绕过 `artifact_sha256()` 手工拼指纹的代码都视为安全缺陷；`grep` 检查应只命中 `engines/fingerprint/` 一处（对应 README §5 的「全仓 grep 无绕过调用」）。
- **权限**：冻结要求 `maker`；读版本要求项目成员；一律查 `role_assignment`，不用 JWT 内的角色声明。

## 9. 测试要点

**单元测试（纯函数，无 IO）**
- `canonical_bytes`：键顺序打乱后结果相同；`Decimal("0.05")` → `"0.0500"`；`None` 不被省略；`ensure_ascii=False` 生效（中文原样）。
- **排除项逐项锁定**：对 `ArtifactParts` 的每个参与字段做一次「改一个字节 → 指纹必变」；对 §6.2 的每个排除项做一次「改它 → 指纹**不变**」（**反例测试**：把 `frozen_at` 塞进信封后指纹变化，即说明实现越界）。
- `artifact_sha256` 稳定性：固定样例的期望十六进制值写成常量断言（金标准），防止无意改动规范化规则。
- `diff_versions`：`section` 过滤；`added/removed/changed` 三分支；`generation_context` 段在模型版本变化时出现、在制品不变时 `sha_changed is False`；空 Plan（无 transforms / 无 quality_rules）与单元素数组的边界。

**集成测试（真 PG，标 `integration`）**
- 并发冻结：同一 Pipeline 两个并发请求 → 一个 `version_no=1`、另一个 `version_no=2`，无重号、无重复 `sha256`。
- 事务原子性：注入一个在 INSERT `pipeline_version` 之后、COMMIT 之前的异常，断言四件制品表与 `pipeline` 状态**全部回滚**（不留孤儿制品行）。
- 幂等：同 `Idempotency-Key` 重放 → 返回同一 `version_no`，且 `pipeline_version` 只多 1 行。
- `/verify`：正常版本 `match=true`；手工 UPDATE 一行 `hocon_artifact.content`（绕过 ORM，直接 SQL）后 `match=false`。

**必须覆盖的反例**
- **指纹失效**：改 `etl_plan.plan` 中一个字段值 → 新版本 `sha256` 必变；原版本 `sha256` 与 `/verify` 结果不变。
- **不可变**：`session` 上修改已冻结版本的 `note` → `ImmutableViolationError`，API 层返回 `VERSION_IMMUTABLE`。
- **越权**：用他项目的 `pipeline_id` 调 Diff → 404；`maker` 之外的成员调 `POST /versions` → `ROLE_REQUIRED`。
- **阻断与过期**：对 `gate_failed` 的 Pipeline 冻结 → `GATE_BLOCKED`；`expires_at` 设为过去 → `METADATA_PROFILE_EXPIRED`。两者都不得使 `pipeline_version` 新增行。

## 10. 未决与风险

1. **证据事件是否与业务事务同提交**：取决于 [be-06](be-06-证据账本与验链.md) 的 `append()` 签名（它需要 `advisory lock` 保护链尾，可能要求独立连接）。**这是本模块唯一的硬依赖缺口**。若必须独立事务，则采用「业务提交后追加 + 失败进 Outbox 重试」的补偿路径，并接受「极短时间内存在无证据的版本行」这一窗口。**验证方式**：M2 与 be-06 联调，用「提交后立即 kill 进程」的用例观察是否丢事件。
2. **`uq_pipeline_version_sha256` 是全局唯一**：现有 ORM 定义要求 `sha256` 在**全库**唯一。若两个不同 Pipeline 生成了完全相同的制品（演示环境用同一份种子数据时很可能发生），第二次冻结会命中该约束。三种处理各有代价：(a) 删除该约束（改表结构）；(b) 命中时**复用**既有版本行（跨 Pipeline 共享版本，语义混乱）；(c) 返回 `CONFLICT` 并要求用户调整需求（可用性差）。**建议 (a)**——`sha256` 的唯一性应由 `(pipeline_id, sha256)` 或干脆不约束来保证，制品内容相等本就允许存在于两个 Pipeline。**需拍板后调整 `models/pipeline.py`**。
3. **`frozen_at` 的时区与精度**：落 `timestamptz`，但 `generation_context` 内的 `generated_at` 是 ISO 字符串。两者语义不同（冻结时刻 vs 生成时刻），前端不要混用。**待确认**：`generation_context` 是否需要独立结构化列以支持查询。
4. **拒绝事件的账本类型缺失**：`GATE_BLOCKED` / `VERSION_IMMUTABLE` 属协议类拒绝，按总纲 §4.6「协议类拒绝一律写账本」应有对应事件类型，但 `EvidenceEventType` 中目前没有版本相关的拒绝类型（只有 `PIPELINE_VERSION_FROZEN`）。**建议新增 `PIPELINE_VERSION_DENIED`**；在新增前，`VERSION_IMMUTABLE` 只记 `structlog` 审计日志（原因：ORM 守卫抛出时事务即将回滚，同事务写账本不可行）。需拍板。
5. **Diff 的规模上限**：两个大版本之间 HOCON 可能完全不同（例如源表换了），unified diff 的 hunk 数会很大。当前用分页 + 默认截断缓解，但未定义「差异过大时退化为摘要」的阈值。**待观察**：fe-04 用真实演示用例评估。
6. **`parser_version` 未参与指纹的后果**：校验器升级后，历史版本的 `validation_result` 与当前校验器结论可能不一致，而指纹不变——这是**有意为之**（§6.2），但需在运维文档（be-22）中写明「历史版本的 validation_result 是历史事实，不可用当前校验器重新解释」。
7. **Profile 过期后的执行口径**：本模块只负责**生成期阻止**；已冻结版本在 Prepare / Commit 时是否因 Profile 过期而阻断，由 [be-13](be-13-准备单与四眼审批.md) 定义（基线见 §6.5「不阻止但提示」），本模块不越界决定。
