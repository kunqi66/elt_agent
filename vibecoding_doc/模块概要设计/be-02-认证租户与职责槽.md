## 1. 职责与边界

- **做什么**
  1. 认证：用户名口令登录（argon2id 校验）、access/refresh 令牌签发、刷新、登出撤销。
  2. 登录防护：Redis 失败计数与锁定（`KEY_LOGIN_FAIL`）、`login_attempt` 审计留痕。
  3. 租户与项目上下文解析：从 JWT 与路径参数得到 `SubjectContext`，校验租户一致。
  4. 项目与成员管理：项目 CRUD、成员增删、职责槽（`role_assignment`）授予与回收。
  5. 职责分离判定：提供 `require_role` 权限依赖、职责混用与自批的可复用判定谓词。
  6. 认证类审计事件写入（`AUTH_LOGIN_SUCCEEDED` / `AUTH_LOGIN_FAILED`）。
- **不做什么**
  - 不签发 Capability 执行令牌（Ed25519，be-05）；本模块只签发 HS256 用户令牌。
  - 不做业务资源授权（数据源、Pipeline、审批单的可见性由各模块按 `role_assignment` 自查），本模块只提供判定谓词与依赖。
  - 不实现审批流程本身（Prepare/Approve/Commit 在 be-13）；本模块只提供「谁不能审批谁的」规则。
  - 不管理 Vault Secret（be-03）。
- **所在分层**：`api/auth.py` / `api/projects.py` 只做校验、权限注入、调 service、组装响应；`services/auth.py` / `services/project.py` 编排；**纯判定函数**（职责互斥、自批判定）放 `engines/policy/roles.py`（纯函数层，禁 import fastapi / core.errors）；ORM 在 `models/tenant.py`。依赖方向：api → services → engines/models，且 services 可调 `harness.EvidenceLedger`。

## 5. 核心流程

### 5.1 登录

1. 按 `tenant_code` 查 `tenant`；不存在或 `status=suspended` → `BAD_CREDENTIALS`（不区分「租户不存在」，避免枚举租户）。
2. 查 `KEY_LOGIN_FAIL = auth:login_fail:{tenant_code}:{username}` 计数 ≥ 阈值 → `ACCOUNT_LOCKED`(423)，写 `login_attempt(success=false, reason="locked")`。（键含租户维度，理由见 §6.4）
3. 按 `UK(tenant_id, username)` 查 `app_user`；不存在或 `verify_and_update_password` 返回 false → 计数 +1（TTL = 窗口），写 `login_attempt(reason="bad_credentials")`，抛 `BadCredentialsError`（文案统一，不区分用户不存在/口令错）。
4. `status=locked` → `ACCOUNT_LOCKED`；`status=disabled` → `FORBIDDEN`。
5. 若 `verify_and_update_password` 返回新哈希（argon2 参数升级），同事务更新 `password_hash`。
6. 删除 `KEY_LOGIN_FAIL` 计数；更新 `last_login_at`；写 `login_attempt(success=true)`；提交。
7. 查主体 active 的 `role_assignment`，取 distinct `project_id`，`issue_token_pair(user, project_ids)`。
8. `harness.EvidenceLedger.append(AUTH_LOGIN_SUCCEEDED / AUTH_LOGIN_FAILED)`（独立事务，见 §8）。

### 5.2 刷新与登出

| 步骤 | 刷新 | 登出 |
|---|---|---|
| 1 | `decode_token(refresh_token, expected_type="refresh")` | 取 access payload（已认证） |
| 2 | 查 `KEY_TOKEN_DENY = auth:denied_jti:{jti}` 命中 → `UNAUTHENTICATED` | 写 `KEY_TOKEN_DENY:{access.jti}`，TTL=剩余有效期 |
| 3 | 查 `app_user` 与 `status`；停用即拒 | 若有 refresh，`decode` 后写 `KEY_TOKEN_DENY:{refresh.jti}` |
| 4 | 重查 active 角色槽 → 新 `project_ids` | — |
| 5 | 签发新 access + 新 refresh，并把**旧 refresh jti** 写入 `KEY_TOKEN_DENY`（轮转） | — |

### 5.3 项目上下文解析（每个业务请求）

1. `get_current_subject` 从 `Authorization: Bearer` 取 access，`decode_token(..., expected_type="access")`；失败 → `UNAUTHENTICATED` / `TOKEN_EXPIRED`。
2. 查 `KEY_TOKEN_DENY` 是否含其 `jti`（登出后仍持有旧 access 的请求被拒）。
3. 按 `sub` 载入 `app_user`，构造 `SubjectContext`（`tenant_id` 取自 DB，**不信任 JWT 里的 `tenant_id`**）。
4. `bind_contextvars(tenant_id, subject_id, request_id)`（be-01 的上下文贯穿点）。
5. 路径含 `project_id` 的接口经 `require_project` 调 `resolve_project`：项目不存在 → `NOT_FOUND`；`project.tenant_id != subject.tenant_id` → `TENANT_MISMATCH`；非成员 → `FORBIDDEN`。
6. `require_role(*roles)` 用 `active_roles()` 实时查库判定；不足 → `ROLE_REQUIRED`。

### 5.4 职责槽授予

1. `require_role(RoleName.CHECKER_SECURITY)` 通过（谁能授权由路径声明，见 §3.1）。
2. 同事务内查 `project_member`（不存在或 `status=removed` → 先 `add_member` 或 `CONFLICT`）。
3. 取该成员当前 `active_roles`，调 `check_duty_separation(held, granting=role)`；违规抛 `DutyConflictError`。
4. `INSERT role_assignment`（`granted_by=subject.user_id`）；撞 `UK` → `CONFLICT`。
5. 写审计（见 §8），提交。

### 5.5 状态与非法转移

| 实体 | 状态 → 事件 → 新状态 | 非法转移处理 |
|---|---|---|
| `app_user` | active → 连续失败达阈值 → locked；locked → 窗口过期/管理员解锁 → active | 对 `disabled` 用户登录 → `FORBIDDEN`，不改状态 |
| `project_member` | active → 移除 → removed；removed → 重新加入 → active（复用同一行） | `removed` 成员调用业务接口 → `FORBIDDEN` |
| `role_assignment` | 无 → 授予 → 存在（有效期内）→ 回收 → 物理删除 | 重复授予 → `CONFLICT`；授予导致职责混用 → `DUTY_CONFLICT` |

本模块不直接改 Pipeline/Preparation 状态（那在 be-13）。

## 6. 关键算法与规则

### 6.1 授权判定（唯一事实来源）

判定输入：主体 `user_id`、`project_id`、查询时刻 `at`（默认 `utcnow()`）。

```
有效职责槽 = { ra.role | ra.project_id = :pid AND ra.user_id = :uid
                            AND (ra.valid_from IS NULL OR ra.valid_from <= :at)
                            AND (ra.valid_to   IS NULL OR ra.valid_to   >  :at)
                            AND pm.status = 'active' AND p.status = 'active' }
```

规则：
1. **不使用 JWT 里的角色声明**。JWT 只承载身份与 `projects[]` 提示；角色以 `role_assignment` 实时查询为准（可能已被回收）。
2. 查询强制带 `tenant_id`（经 `project.tenant_id` 校验），跨租户 → `TENANT_MISMATCH`。
3. `valid_from` / `valid_to` 为空表示无界；`valid_to` 为**开区间上界**（`>` 而非 `>=`）。
4. `require_role(*roles)` 是「或」语义；需要「与」时串联多个依赖。
5. 项目 `status=archived` 视为无有效槽位（不参与判定）。

### 6.2 职责混用判定（`check_duty_separation`）

| 待授予 `granting` | 现有 `held` | 结果 |
|---|---|---|
| `maker` | 含 `checker_data` 或 `checker_security` | 拒绝 → `DUTY_CONFLICT` |
| `checker_data` / `checker_security` | 含 `maker` | 拒绝 → `DUTY_CONFLICT` |
| `checker_data` | 含 `checker_security` | **允许**（两槽可由不同人；由 §6.3 保证同单不同人） |
| `operator` / `auditor` | 任意 | 允许（不与 maker/checker 互斥） |

三层兜底：**① 应用层** `check_duty_separation` 于 `grant_role` 内先校验（给出可解释错误）；**② DB 触发器** `role_assignment` 上的 BEFORE INSERT/UPDATE 触发器重复同一规则（防绕过 service 的写入）；**③ 唯一约束** `UK(project_id, user_id, role)` 阻止重复授予。触发器的 DDL 见未决与风险。

### 6.3 四眼与自批判定

| 规则 | 判定 | 落点 |
|---|---|---|
| 申请人不得自批 | `is_self_approval(preparation.created_by, approver_id)` 为真即拒 | 应用层（be-13）+ DB CHECK `approver_id <> preparation_created_by`（已存在） |
| 两个审批槽必须不同人 | `check_dual_checker_distinct(decisions[checker_data].approver_id, decisions[checker_security].approver_id)` 违规即拒 | 应用层（be-13）；`UK(preparation_id, slot)` 保证每槽一条 |
| 审批人须持有对应槽 | `active_roles(project_id, approver_id)` 含 `slot.value` | 应用层（be-13），本模块提供 `active_roles` |
| 高风险禁止一人多槽 | 同 §6.2，且 P1/P2 强制双槽（`RiskLevel.min_approval_slots=2`） | 应用层 + 触发器 |

失败一律抛 `SelfApprovalForbiddenError` / `DutyConflictError`，并写 `APPROVAL_SELF_DENIED` 类证据事件（be-13 落）。

### 6.4 登录锁定算法

- 计数键 **`auth:login_fail:{tenant_code}:{username}`**，`INCR` 后 `EXPIRE` 窗口（默认 900s）；命中阈值即视为锁定，键未过期期间即使口令正确也拒绝（防止爆破成功）。
  - 🔴 **必须带 `tenant_code`**（2026-10-16 修正）。原设计为 `auth:login_fail:{username}`，而 `app_user` 的唯一性是 `UK(tenant_id, username)`——键少了租户维度，攻击者只需在**自己租户内**对 `admin` 连续失败，就能把其它所有租户的 `admin` 一起锁死。这是**跨租户拒绝服务**，且不需要任何越权即可成立。`tenant_code` 在登录第 1 步之后必定可得，失败路径也拿得到。
- 成功登录 `DEL` 该键。
- 阈值与窗口为配置项（见未决与风险）；`login_attempt` 表提供可追溯的失败历史（Redis 可能被清空，审计不依赖易失存储）。
- 计数维度是 `(租户, username)` 而非 `IP`：IP 维度由 Nginx `limit_req zone=login_zone rate=10r/m` 承担。
- `login_attempt` 表**不加租户维度**：它要能按 username 跨租户聚合，才看得出「某个用户名正在被爆破」。

## 7. 错误码与拒绝语义

| 触发条件 | 错误码 | HTTP | 写证据账本 |
|---|---|---|---|
| 用户名不存在 / 口令错 / 租户不存在或停用 | `BAD_CREDENTIALS` | 401 | 是（`AUTH_LOGIN_FAILED`） |
| 失败次数达阈值（窗口内） | `ACCOUNT_LOCKED` | 423 | 是（`AUTH_LOGIN_FAILED`，`reason=locked`） |
| `disabled` 用户登录 | `FORBIDDEN` | 403 | 是（`AUTH_LOGIN_FAILED`） |
| 缺/坏/类型不符令牌 | `UNAUTHENTICATED` | 401 | 否 |
| 令牌过期 | `TOKEN_EXPIRED` | 401 | 否 |
| 已撤销（`KEY_TOKEN_DENY` 命中）令牌 | `UNAUTHENTICATED` | 401 | 否 |
| 登录成功 | `OK` | 200 | 是（`AUTH_LOGIN_SUCCEEDED`） |
| 非项目成员访问项目资源 | `FORBIDDEN` | 403 | 否 |
| 跨租户访问 | `TENANT_MISMATCH` | 403 | 是（高风险，建议走 `policy.blocked` 语义，见未决） |
| 角色不足 | `ROLE_REQUIRED` | 403 | 否 |
| 授予导致职责混用 | `DUTY_CONFLICT` | 403 | 是（建议新增事件，见未决） |
| 审批人 = 申请人 | `SELF_APPROVAL_FORBIDDEN` | 403 | 是（`APPROVAL_SELF_DENIED`，be-13 落） |
| 项目/成员/角色不存在 | `NOT_FOUND` | 404 | 否 |
| 重复加入成员 / 重复授予角色 | `CONFLICT` | 409 | 否 |

## 8. 安全与合规约束

- **口令**：argon2id 哈希（`pwdlib[argon2]`），明文只在请求体内瞬时存在，永不落库、落日志（be-01 脱敏链兜底）。登录路径用 `verify_and_update_password` 以随库升级自动迁移哈希参数。
- **令牌**：HS256，含 `jti`；登出/刷新轮转把 `jti` 写入 `KEY_TOKEN_DENY`，TTL = 剩余有效期（不无限增长）。
- **授权不信任 JWT**：角色一律查 `role_assignment`（含 `valid_from`/`valid_to`）；`tenant_id` 以 DB 为准。
- **租户过滤**：所有查询强制带 `tenant_id`；跨租户 → `TENANT_MISMATCH` 并写账本。
- **四眼与自批**：服务端 + DB 三层兜底（§6.2、§6.3），不做前端置灰式「软拦截」。
- **审计**：`AUTH_LOGIN_SUCCEEDED` / `AUTH_LOGIN_FAILED` 经 `harness.EvidenceLedger.append()` 写入，payload 只含 `username`、`ip`、`reason`、`user_id`，**不含口令**。账本写入与业务事务解耦（be-06 的独立串行化事务）；写入失败记 `error` 但不回滚登录结果——账本断链由验链脚本暴露。
- **错误语义**：`BAD_CREDENTIALS` 文案不区分「用户不存在」与「口令错」，避免账号枚举；`login_attempt.reason` 只存粗粒度码，不存口令相关细节。

## 9. 测试要点

- **单元测试**（纯函数，内存 SQLite / 无 IO）
  - `is_assignment_valid`：`valid_to` 边界（`at == valid_to` 应为无效，开区间）。
  - `check_duty_separation`：maker×checker_data 拒绝、checker_data×checker_security 允许、operator 不与任何角色互斥。
  - `check_dual_checker_distinct`：同人两槽 → `ValueError`。
  - `is_self_approval`：相等为真、不同为假。
- **集成测试**（真实 PG/Redis）
  - 登录成功签发 access(30min)/refresh(7d)，`login_attempt` 落两行（失败 + 成功）。
  - 连续失败达阈值 → 第 N+1 次 `ACCOUNT_LOCKED`(423)，且**正确口令亦然**。
  - 登出后旧 access 访问 `/auth/me` → 401（`KEY_TOKEN_DENY` 生效）。
  - 刷新轮转：旧 refresh 再用 → 401。
  - `grant_role` maker→checker_data：行为与触发器两条路径都要被拒（模拟绕过 service 直接 INSERT 触发触发器）。
  - `require_role` 对已回收角色：JWT 未过期但角色已删 → `ROLE_REQUIRED`。
- **必须覆盖的反例**：越权（非成员访问项目）、跨租户、自批、职责混用、锁定、refresh 重放、已撤销令牌复用。
- **DB 层断言**：`role_assignment` 触发器存在且生效；`approval_decision` 自批 CHECK 在真实 PG 上生效（SQLite 不校验 CHECK 语义时标 `integration`）。

## 10. 未决与风险

| 事项 | 现状 | 建议 / 验证方式 |
|---|---|---|
| 首个租户/管理员的引导 | `RoleName` 无平台管理角色，无种子脚本 | 提供 `scripts/seed_admin.py` 建 tenant+user+首个 `checker_security`；M1 内确认 |
| 建项目 / 授权所需的角色 | `RoleName` 无 `admin`；本文件暂定「建项目需 maker、授权需 checker_security」 | 需拍板：是否新增 `admin` 角色或由 `checker_security` 兼任 |
| `role_assignment` 职责互斥触发器 DDL | 仅有模型注释与唯一约束，触发器未建 | 在 Alembic 迁移中用 `op.execute` 创建 `BEFORE INSERT OR UPDATE` 触发器；集成测试证明可拒绝直连 INSERT |
| 缺少成员/角色/项目类审计事件 | `EvidenceEventType` 无 `member.added` / `member.role_granted` / `member.role_revoked` / `project.created` | **建议新增**上述四个事件类型（`enums.py` 追加）；在此之前这些动作不写账本，只落 structlog |
| 登录锁定阈值未冻结 | Redis 键注释仅给 TTL 15min | 建议 `LOGIN_FAIL_MAX_ATTEMPTS=5`、`LOGIN_FAIL_WINDOW_SEC=900`，加进 `Settings` |
| `tenant_code` 传递方式 | 登录体携带；JWT 的 `tenant_id` 不作为授权依据 | 若改为子域名/请求头需同步 Nginx 与前端；M1 维持登录体携带 |
| 命名不一致 | `models/tenant.py` 注释指向 `services/member_service.py`，本设计定为 `services/project.py` | 实现时二选一并同步注释；建议 `services/project.py`（成员与职责槽同属项目域） |
| 用户创建入口 | 无注册接口；`AppUser` 无创建 API | M1 由种子脚本 + 管理员邀请创建；是否开放在线建用户待定 |
| 审计事件与登录事务的原子性 | 账本为独立事务，登录已提交后追加失败会留痕缺失 | M4 评估：失败登录的账本写入是否改走 Outbox 保证至少一次 |
