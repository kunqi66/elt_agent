## 1. 职责与边界

- **做什么**
  1. **项目列表与切换**：列出当前用户可见的项目；切换后写全局项目上下文供其他模块使用。
  2. **项目基本信息**：`code` / `name` / `env` / `status` 展示（有权限时可改名称与描述）。
  3. **环境标记的醒目提示**：`env` 是 PDP 判定的关键输入，`prod` 必须与 dev / staging 显著区分（§6.2）。
  4. **成员管理**：成员列表（用户 / 邮箱 / 状态）、添加成员、移除成员。
  5. **职责槽管理**：`role_assignment` 的授予与回收（`maker` / `checker_data` / `checker_security` / `operator` / `auditor`），含临时授权的有效起止时间、授予人与授予时间。
  6. **四眼规则可视化**：用角色矩阵表讲清「谁不能审什么」，并显式列出互斥规则。
  7. **租户信息**（只读）与**个人设置**（身份、修改密码、退出登录）。
  8. **安全交互**：敏感操作的二次确认 + 操作理由输入 + 审计留痕提示。
- **不做什么**
  - **不做授权判定**：谁能管理成员、谁能授予角色，一律由后端判定并以 `can_manage_members` / `can_manage_roles` 下发；前端只据此控制按钮可见性。`maker` 与 `checker_*` 互斥在前端只做**提示**，判定与拒绝由服务端 + DB 触发器完成。
  - **不展示凭据**：成员管理不涉及密码；修改密码表单不回显任何旧值，强度策略以后端为准，前端不自行实现复杂度规则。
  - **不做用户 CRUD**：本模块不创建 `app_user`，只把**已存在**的用户加进项目。
  - **不管理数据源 / Pipeline / 审批**：分别属 fe-03 / fe-04 / fe-05。
- **所在分层**：前端展示层。只经 `src/api/project.ts` 与 `src/api/auth.ts` 调 `/api/v1/projects/*` 与 `/api/v1/auth/*`。

## 3. 对外接口

### 3.1 API 调用清单

除标「已实现」者外全部标注「（待后端 be-02 落地）」。写接口的 `reason`（操作理由）是**必填**字段，随审计事件落账（§8）。

| 方法 | 路径 | 权限（服务端判定） | 幂等 | 说明 |
|---|---|---|---|---|
| GET | `/api/v1/auth/me` | 已登录 | 天然 | 当前用户画像（含 `projects[]` 与角色）。**已实现** |
| GET | `/api/v1/auth/tenant` | 已登录 | 天然 | 当前租户 `{id, code, name, status}` |
| POST | `/api/v1/auth/password` | 已登录 | 必带 | 修改密码，body `{old_password, new_password}` |
| POST | `/api/v1/auth/logout` | 已登录 | 天然 | 退出登录（吊销当前 refresh）。**已实现** |
| POST | `/api/v1/auth/logout-all` | 已登录 | 必带 | 吊销该用户全部 refresh（见 §10） |
| GET | `/api/v1/projects` ｜ `/{project_id}` | 项目成员 | 天然 | 可见项目列表；详情含 `can_manage_members` / `can_manage_roles` |
| PUT | `/api/v1/projects/{project_id}` | 待定（见 §10） | 必带 | 更新 `name` / `description`；**`env` 与 `code` 不可改** |
| GET / POST | `/api/v1/projects/{project_id}/members` | 读：项目成员；写：`can_manage_members` | 读天然 / 写必带 | 成员列表；添加成员 body `{user_id, reason}` |
| DELETE | `/api/v1/projects/{project_id}/members/{member_id}` | `can_manage_members` | 必带 | 移除成员（`status` 置 `removed`） |
| GET / POST | `/api/v1/projects/{project_id}/role-assignments` | 读：项目成员；写：`can_manage_roles` | 读天然 / 写必带 | 列表含 `granted_by` `valid_from` `valid_to`；授予 body `{user_id, role, valid_from?, valid_to?, reason}` |
| DELETE | `/api/v1/projects/{project_id}/role-assignments/{assignment_id}` | `can_manage_roles` | 必带 | 回收角色（body 带 `reason`） |

## 5. 核心流程

**项目上下文建立（应用启动）**：① `main.ts` → `useAuthStore.loadProfile()` → `GET /auth/me`（已实现）；② `profile.projects` 作为候选列表，`restoreCurrentProject()` 从 localStorage 取上次项目 id；③ 上次 id 不在候选列表（被移出项目）→ 回退到第一个项目，列表为空 → 显示引导页；④ 切换项目 → `setCurrentProject(id)` → 顶栏 `EnvBadge` 立即反映新项目 `env`；⑤ 其他模块的所有请求在切换后重新拉取（由 fe-01 的响应式上下文负责）。

**成员添加**：① 「添加成员」→ `InviteMemberDialog`，候选用户来自后端（本租户内、尚未加入本项目）；② 选用户 + 填操作理由（必填）→ 生成 `Idempotency-Key` → `POST members`；③ 成功 → 关闭弹窗，成员列表局部刷新（不整页重载）；④ 失败按 §7 错误码分支。

**职责槽授予（含互斥提示）**：① 成员行点「授予职责」→ `RoleGrantDialog`；② 选择 role —— 若该用户已持有 `maker` 且本次选 `checker_data` / `checker_security`，或反向，则显示红色互斥提示（文案见 §6.3）但**不阻断提交**；③ 可选填 `valid_from` / `valid_to`（临时授权），填理由（必填）；④ 敏感操作二次确认（`checker_security` 的授予额外要求手动输入角色名，见 §6.5）；⑤ 生成 `Idempotency-Key` → `POST role-assignments`；⑥ 后端拒绝（`DUTY_CONFLICT` / `CONFLICT`）→ 按 §7 提示，前端不假设自己已拦下。

**角色分配展示态**：`role_assignment` 无 `status` 列，只有 `valid_from` / `valid_to`，界面据此派生三个**展示态**（不落库）：

| 展示态 | 判定 | 界面表现 |
|---|---|---|
| 生效中 | `valid_from ≤ now` 且（`valid_to` 为空 或 `now < valid_to`） | 绿色「生效中」标签 |
| 未生效 | `valid_from > now` | 灰色「未生效（YYYY-MM-DD 起）」 |
| 已失效 | `valid_to ≤ now` | 灰色删除线 + 「已失效」；回收按钮禁用（历史记录保留） |

回收是**物理删除行**（数据字典除不可变表外无软删除约定），历史由证据账本承载；前端在二次确认中写明「回收后该记录仅存于证据账本」。

## 6. 关键算法与规则

**6.1 项目列表列**：项目名称（`name`，主标识）｜编码（`code`，等宽字体，跨系统对账用）｜环境（`env` → `EnvBadge`）｜状态（`status`：active 显示「活跃」，archived 灰显 + 「已归档」）｜成员数（`member_count`）｜我的角色（`profile.projects[].roles` 以标签并列，无角色时显示「无职责槽」）。

**6.2 环境标记（`EnvBadge`）——本模块最重要的视觉规则**

`env` 是 PDP 判定的关键输入：写 `prod` 的正式表是 **P0 直接阻断**的触发条件之一，且 `prod` 会强制走完整四眼审批。因此环境**不允许**以中性灰标签呈现。

| env | Element Plus tag type | 图标 | 文案 | 额外规则 |
|---|---|---|---|---|
| `dev` | `info` | `Tools` | 开发 | 顶栏小徽章 |
| `staging` | `warning` | `Warning` | 预发 | 顶栏小徽章 |
| `prod` | `danger`（实心 + 顶栏左侧 4 px 红色竖条） | `WarningFilled` | 生产 | 顶栏大徽章 + 全局顶部细红条（`position: sticky`，不可关闭） |

- `prod` 的红色顶条在**所有页面**可见，不限于本模块——只要当前项目 `env = prod` 就常驻，避免用户在 Studio 里误以为在预发环境操作。
- 项目详情页对 `env = prod` 追加说明：「生产环境下的执行需完整四眼审批；写正式表的动作触发 P0 判定。」
- **`env` 不可编辑**：`PUT /projects/{id}` 不接受 `env` 与 `code`。这是刻意的——把 dev 提升为 prod 必须新建项目，避免用「改一下环境标记」绕过审批要求。若后端允许编辑，前端也不提供入口，并在 §10 记为冲突项。

**6.3 四眼与互斥规则的可视化（`RoleMatrixTable`）**

| 角色 | 发起 Prepare | 审数据槽 | 审安全槽 | Commit | 管策略/评测 | 查看账本 |
|---|---|---|---|---|---|---|
| `maker` | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ |
| `checker_data` | ❌ | ✅ | ❌ | ❌ | ❌ | ❌ |
| `checker_security` | ❌ | ❌ | ✅ | ❌ | ✅ | ❌ |
| `operator` | ❌ | ❌ | ❌ | ✅ | ❌ | ❌ |
| `auditor` | ❌ | ❌ | ❌ | ❌ | ❌ | ✅（只读） |

**显式互斥说明文案**（`FourEyesExplainer.vue` 正文，逐条列出，不用图示代替文字）：① 同一项目内，`maker` 与 `checker_data`、`checker_security` **互斥**：一个人不能既提交又审批；② 申请人**不得**审批自己的 Preparation，即使他通过其他途径拿到了审批角色；③ `checker_data` 与 `checker_security` **可由同一人兼任**（两个槽位仍是独立的两次决定），但 P1 场景下建议由不同人担任；④ `operator` 只能对**审批已通过且指纹一致**的版本执行 Commit，不能修改准备单内容；⑤ `auditor` 全程只读，不能执行任何副作用操作。

**前端只做提示**：`RoleGrantDialog` 在出现互斥组合时显示红色提示并说明「服务端将拒绝该授予」，但不禁用提交按钮——禁用会掩盖后端的权威判定，也让用户在前后端规则不一致时无从判断。真正的拦截在 `services/member_service.py`（跨行约束，CHECK 表达不了）与 DB 触发器。

**6.4 临时授权的展示**：`valid_from` / `valid_to` 均可空（都空 = 永久授权；只填 `valid_to` = 限期授权）。时间选择器用 `ElDatePicker` 的 `datetimerange`；**时区统一按浏览器本地时区输入，提交前转 ISO 8601 带偏移量**，避免服务端按 UTC 解析导致偏移。`valid_to` 必须晚于 `valid_from`（前端校验）；两者都不得超过 `now + 365d`（避免「永久」被写成 2099 年）。列表中显示到期倒计时（剩余天数），到期前 7 天在项目设置入口挂角标提醒。

**6.5 敏感操作的二次确认（`SensitiveActionDialog`）**：以下操作走统一确认组件，且**要求输入操作理由**（必填，最少 10 个字符）：

| 操作 | 影响范围（弹窗逐条列出） | 额外确认 |
|---|---|---|
| 授予 `checker_security` | 该用户获得审批安全槽、管理 P0–P3 策略、触发 Benchmark 的能力 | 需手动输入 `checker_security` |
| 授予 `operator` | 该用户可对已审批版本执行 Commit 与回滚 | 需手动输入 `operator` |
| 移除成员 | 该成员的全部 `role_assignment` 一并失效；其历史审批记录保留在账本 | 需手动输入用户名 |
| 回收任一 `checker_*` | 该用户立即失去对应槽位审批能力；其在途待审批准备单需由他人接手 | 无需额外输入 |
| 修改项目名称 | 该名称出现在所有列表与账本载荷中 | 无需额外输入 |

**审计留痕提示**：确认弹窗与操作成功后的 toast 都必须写明「本次操作已写入证据账本（操作人 / 时间 / 影响对象 / 理由）」。这不是可选文案——它让操作者对留痕有明确预期。

**6.6 修改密码**：字段 `old_password` / `new_password` / `confirm_password`。三方一致性（`new === confirm`）与「新密码不得等于旧密码」在前端做；**强度策略以后端为准**，前端不实现长度/复杂度规则（避免前后端策略漂移），只在字段下方展示后端下发的策略说明文本。提交成功 → 服务端吊销全部 refresh token（是否含当前会话取决于后端实现，见 §10）→ 前端提示「密码已修改，请重新登录」并调用 `logout()`。表单**不回显**任何密码值；请求体不进日志（`client.ts` 不打印请求体）。

**6.7 租户信息（只读）**：展示 `tenant.name` / `tenant.code` / `tenant.status`。`status = suspended` 时页面顶部显示红色信息条「租户已暂停，部分功能不可用」，但**不隐藏数据**（只读可见更有助于排查）。

## 7. 错误码与拒绝语义

| 触发条件 | 错误码（`ErrorCode`） | HTTP | 前端表现 | 写证据账本 |
|---|---|---|---|---|
| 被授予人的角色组合触发互斥 | `DUTY_CONFLICT` | 403 | 弹窗内红色提示「同一项目内 maker 与 checker_* 互斥」，保留已填内容供调整；提示可去 `/settings/four-eyes` 查看规则 | 是 |
| 重复授予同角色 | `CONFLICT` | 409 | 提示「该用户已持有此职责」并刷新列表（幂等键相同则返回既有行） | 否 |
| 成员已存在 | `CONFLICT` | 409 | 提示「该用户已是项目成员」；候选列表刷新 | 否 |
| 权限不足（无权管理成员/角色） | `FORBIDDEN` / `ROLE_REQUIRED` | 403 | 按钮隐藏（`can_manage_*` 为 false 时本就不渲染）；若服务端拒绝则提示并刷新项目详情 | 是 |
| 跨租户访问项目 | `TENANT_MISMATCH` | 403 | 跳回项目列表并提示资源不存在 | 是 |
| 用户不存在 / 项目不存在 | `NOT_FOUND` | 404 | 空态 + 返回列表 | 否 |
| 移除自己 | `CONFLICT` 或 `FORBIDDEN` | 409 / 403 | 前端先提示「不能移除自己」；服务端再兜底 | 是 |
| 移除最后一个可管理角色的持有者 | `CONFLICT` | 409 | 提示「项目将失去全部管理者」，要求先指定继任者 | 是 |
| 旧密码错误 | `BAD_CREDENTIALS` | 401 | 定位到 `old_password` 字段并提示；**不触发全局 401 登出**（该请求在 `client.ts` 中需 `skipAuthRefresh: true` 且不进未授权回调，见 §10 风险） | 否 |
| 新密码不符合策略 | `VALIDATION_ERROR` | 422 | 展示后端 `details.fields[].reason`，不做本地复述 | 否 |
| 账号被锁定 | `ACCOUNT_LOCKED` | 423 | 提示联系管理员 | 否 |
| 同 `Idempotency-Key` 不同请求体 | `IDEMPOTENCY_CONFLICT` | 409 | 提示冲突并停止重试 | 否 |

前端按 `BizError.code` 分支，**不用 `message` 判断**。

## 8. 安全与合规约束

- **服务端是唯一判据**：按钮可见性取自后端下发的 `can_manage_members` / `can_manage_roles`；`myRoles()` 只用于展示。DB 层的 `UK(project_id, user_id, role)` 与职责互斥触发器是最后兜底，前端不得假设自己已拦下非法组合。
- **操作理由必填且入账**：授予、回收、移除、改项目名的请求体都带 `reason`，随证据事件落账。前端把 `reason` 作为必填项，不做「留空则自动填无」的兜底——自动填充会让审计失去意义。
- **环境标记不可编辑**：`env` 与 `code` 不在更新接口中出现，杜绝「改标记绕过生产审批」的路径（§6.2）。
- **无凭据**：本模块不接触数据源凭据；修改密码的请求体在 `client.ts` 不落日志、不进 Vue Devtools 的持久化状态（不写 store）。
- **不缓存成员与角色**：`members` / `assignments` 只存内存，路由离开时 `reset()`；项目上下文只持久化 `id` 与 `name`（不含角色）。
- **退出登录两条路径**：`logout()`（当前会话）与 `logout-all`（全部会话，用于怀疑凭据泄露时）。后者走二次确认并标明「将退出所有设备」。

## 9. 测试要点

- **单元测试（Vitest）**：`EnvBadge` 在 `prod` → danger 实心 + `WarningFilled` + 文案「生产」，`dev` / `staging` 分别为 info / warning，未知 env 值不崩溃；`ProjectRead.env === 'prod'` 时全局顶条渲染（staging / dev 不渲染）；`RoleGrantDialog` 互斥提示——已持有 `maker` 时选 `checker_security` 出现互斥提示且**提交按钮仍可用**，已持有 `checker_data` 时选 `checker_security` 不出现提示（两者不互斥）；`RoleGrantRequest` 的 `valid_to ≤ valid_from` 报错、超 365 天报错；`SensitiveActionDialog` 在 `confirm_text` 未准确输入或 `reason` 少于 10 字符时禁用确认；`ChangePasswordForm` 在 `new !== confirm` 或 `new === old` 时报错、成功后调用 `logout()`；`RoleMatrixTable` 的 5 行 × 6 列取值与 §6.3 表格逐格一致（防文案漂移）。
- **集成测试（真实 PG + 后端，ECS 上跑）**：**职责混用**（同一用户同一项目授予 `maker` + `checker_data` → `DUTY_CONFLICT`，DB 无该组合）；**跨项目不互斥**（A 在项目 1 是 `maker`、项目 2 是 `checker_data`，两次授予均成功）；**移除成员**（后 `project_member.status = removed`，其 `role_assignment` 全部失效，该用户请求项目资源 403）；**越权**（无 `can_manage_roles` 的成员 POST role-assignments → 403，界面无入口）；**幂等**（同 key 连点「授予」→ 只产生一条 `role_assignment`）；**改密**（旧密码错误 → 401 `BAD_CREDENTIALS` 且**不触发全局登出**，成功后旧 refresh 失效）；**移除自己**（返回 409/403 而非静默成功）；**租户隔离**（租户 A 用户请求租户 B 项目 id → `TENANT_MISMATCH`）。
- **必须覆盖的反例**：职责混用、越权授予、跨租户访问、移除自己、旧密码错误不得误登出。
- **测试基建**：改密用例需断言 `client.ts` 的 401 拦截器**没有**清除本地会话（该请求必须带 `skipAuthRefresh: true`），否则用户改错密码会被踢出登录。

## 10. 未决与风险

| 事项 | 现状 | 建议 / 验证方式 |
|---|---|---|
| **谁可以管理成员与角色** | `RoleName` 只有 maker / checker_data / checker_security / operator / auditor，**没有项目管理员角色**；PRD §2 也未定义 | 三选一：① 新增 tenant 级 `admin` 角色（需改 `RoleName` + migration）；② 仅 `maker` 可管理（但 maker 与 checker_* 互斥，会导致 checker 无法被授予）；③ 由 `checker_security` 管理安全角色、`maker` 管理 operator/auditor。**当前前端取服务端 `can_manage_*`，任一种都能落地**；需 be-02 拍板 |
| `POST /auth/password` 与 `logout-all` 路由 | 均未在 PRD/总纲出现，本文按最小必要提出 | 待 be-02 确认；若后端不提供 `logout-all`，前端只留「退出当前会话」 |
| 改密 401 被误判为「令牌过期」 | `client.ts` 的 401 拦截器会尝试静默刷新，失败则清会话并跳登录页 | 改密请求必须传 `skipAuthRefresh: true` 并旁路 `unauthorizedHandler`；当前 `skipAuthRefresh` 只跳过刷新、仍会走 `unauthorizedHandler`，需在 fe-01 的 `client.ts` 约定中**扩展**。这是已知风险点 |
| `env` 是否允许编辑 | 本文按「不可编辑」设计（安全考量） | 若后端 `PUT /projects/{id}` 接受 `env`，需明确是否要求额外审批；前端在未拍板前不提供入口 |
| 候选用户列表接口 | `InviteMemberDialog` 需要「本租户内未加入本项目的用户」 | 建议 `GET /api/v1/projects/{id}/member-candidates`；或复用租户用户列表 + 前端过滤（但会把全租户用户暴露给普通成员，不推荐） |
| 项目创建入口 | PRD §5 有「项目设置」但未明确是否支持自助建项目 | 本文未定义 `POST /projects`；若需要，建议限制为 tenant 管理员 |
| `role_assignment` 回收是否物理删除 | 数据字典未把该表标为软删除表 | 本文按物理删除 + 账本留痕设计；若改为 `status='revoked'` 需加列与 migration |
| 会话管理（登录设备列表） | 本文只做「退出 / 退出全部」 | 若需设备列表，需要后端提供 refresh token 正向台账（当前 refresh 只落 Redis 黑名单），成本较高，暂不做 |
| 项目切换后的全局刷新 | 切换项目需让 fe-02…fe-07 重新拉数据 | 属 fe-01 的横切职责（响应式项目上下文），需在 fe-01 中统一约定，避免各模块各自监听 |
| 角色矩阵表与后端规则的同步 | `RoleMatrixTable` 是**手写文案**，会随后端规则漂移 | 建议后端下发能力矩阵（`GET /auth/capabilities`）供前端渲染；在未实现前，§9 的矩阵一致性单测是唯一防线 |
| 临时授权到期后的自动失效 | 依赖后端鉴权时比对 `valid_from` / `valid_to` | 需确认 be-02 的 `require_role` 是否每次都校验时间窗；若不校验则临时授权形同虚设 |
