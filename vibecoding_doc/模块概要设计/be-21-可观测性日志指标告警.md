## 1. 职责与边界

- **做什么**
  1. 扩展 structlog 处理器链，把「日志→可查询的运行日志」打通，并保证**脱敏处理器是唯一出口**。
  2. 定义全套 Prometheus 指标（HTTP / Celery / Outbox / 运行执行 / SeaTunnel / 连接池 / 证据账本），并规定埋在**哪一层**。
  3. 在 api 暴露 `/metrics` 并保证它**不对公网开放**；为 worker / beat 各起一个只在内网可达的指标端口。
  4. 定义告警规则（指标 → 表达式 → `for` → 级别 → 渠道）与每条告警的**第一步处置动作**；实现钉钉机器人 webhook 发送器（加签、限流聚合、模板、失败重试与降级）。
  5. 提供 Grafana 看板清单与 `api/monitor` 的指标/日志/健康路由（2s 轮询的数据源，增量语义 `?since=`）。
- **不做什么**
  - **不定义业务状态**：`execution_metric` / `quality_report` 由 be-16、be-17 写入；本模块只把它们**读出来**喂给前端与 Prometheus，不二次加工口径。**不做根因诊断**（可解释根因是 be-19），`/logs` 只做检索与过滤。
  - **不做告警的业务决策**：预算判定由 `engines/supervision`（be-16）负责，超限时**引擎自己硬中断**；本模块的告警只是「让人知道」，不允许用告警替代引擎动作。
  - **不自行脱敏**：任何调用方不得因为「我要写日志」而自己拼掩码值——一律交给 `redact_processor`。
  - **不做 APM 追踪**：不引入 OpenTelemetry / 分布式追踪（单机 compose，收益不足以抵消复杂度）；跨进程串联靠 `request_id` 透传。
- **所在分层**：`core/metrics.py` 是横切基础设施（与 `core/logging.py` 同级），只依赖 `prometheus_client` 与标准库；`api/monitor.py` 只做校验/权限/转发；`clients/alerting/` 是外部系统（钉钉 API）封装；`deploy/*` 是配置，不含代码。依赖方向：`api → services → core/clients`，`core` 不被任何下层反向依赖。

## 3. 对外接口

### 3.1 HTTP

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/metrics` | 无（**仅内网**） | Prometheus 抓取端点；Nginx 不反代，且显式 `deny all`（§6.3） |
| GET | `/healthz` | 无 | 存活探针（已有），不查依赖 |
| GET | `/readyz` | 无 | 就绪探针（已有），查 PG + Redis；同时写 `elt_dependency_up` gauge |
| GET | `/api/v1/monitor/runs/{id}/metrics` | `operator` / `checker_*` / `auditor` | 运行指标序列，`?since=<iso8601\|epoch|last_ts>` 增量返回；2s 轮询数据源 |
| GET | `/api/v1/monitor/runs/{id}/logs` | 同上 | 运行日志，过滤 `?level=&since=&event_type=&limit=`，**脱敏后**返回 |
| GET | `/api/v1/monitor/health` | 同上 | 依赖健康汇总（PG / Redis / SeaTunnel / Outbox 积压 / 活跃 run 数） |

- `/metrics` 是**唯一不挂 `/api/v1` 前缀**的指标入口，与 `/healthz` 同级挂根路径（`main.create_app()` 里 `app.mount("/metrics", metrics_asgi_app())`）。
- `/api/v1/monitor/runs/{id}/metrics` 的增量语义：`since` 省略时返回最近 5 分钟或最近 300 点（取小）；返回体带 `next_since`，前端 2s 轮询时把它作为下次 `since`——**不引 WebSocket**（已冻结）。权限对齐 PRD §2.1：`maker` 只能看自己项目的运行（`role_assignment` + `project_member` 双重过滤）；`auditor` 全项目只读。
- 质量报告（`GET /runs/{id}/quality`）与根因诊断（`GET /runs/{id}/diagnosis`）归 be-17 / be-19，不在本模块；`monitor.py` 不代管，避免「监控模块变成什么都往里塞」。

## 4. 数据模型

本模块**只读**既有表，不新增业务表：

| 表 | 本模块动作 | 关键列（详见《核心数据字典》） |
|---|---|---|
| `execution_metric` | 只读（生产者 be-16） | `IDX(run_id, ts)`；`read_rows / written_rows / written_bytes / throughput / duration_sec / amplification_ratio / reject_rate` |
| `execution_run` | 只读 | `status`、`shadow_table / formal_table`、`failure_snapshot`、`project_id`（租户过滤依据） |
| `outbox_message` | 只读 + 运维重投 | `IDX(status, available_at)`；`status`、`attempts`、`available_at`、`last_error` |
| `evidence_event` / `evidence_ledger_block` | 只读 | `seq`、`event_hash`、`from_event_seq / to_event_seq`、`signed_at` |
| `quality_report` | 只读（供看板与 `/health` 摘要） | `run_id`、`reject_rate`、`error_code_dist` |

**需要新增的表（未决，必须先补《核心数据字典》§8 支撑表再实现）**：

- `run_log`：运行日志的**可查询副本**。字段建议 `{id, run_id (FK execution_run, IDX(run_id, ts)), ts, level, event_type, logger, message, fields (jsonb, 已脱敏), request_id}`；保留策略用 `settings.RUN_LOG_RETENTION_DAYS`（默认 90 天），由 `tasks.maintenance.enforce_retention` 清理。**没有这张表，`GET /runs/{id}/logs` 无法实现**——容器 stdout 的 `json-file` 日志（20m×5）不可按 run 检索。备选（不新增表）：直接查 `evidence_event`（按 `subject_type='execution_run'` + `subject_id` 过滤），`event_type` 当「事件类型」、按事件严重度映射 `level`，代价是丢掉非账本日志（如 SeaTunnel 客户端重试细节）。**建议新增 `run_log`**，`evidence_event` 保持审计口径（分工：`run_log` 排障，`evidence_event` 合规）。

## 5. 核心流程

### 5.1 日志：从进程 stdout 到「可查询 + 已脱敏」

```
业务代码 log.info("run_submitted", run_id=..., written_bytes=...)
  │
  ├─ structlog 处理器链（core/logging.py）
  │    merge_contextvars → add_logger_name → add_log_level → TimeStamper(iso,utc)
  │    → StackInfoRenderer → UnicodeDecoder
  │    → redact_processor            ← 唯一脱敏出口（键名 + 值形态两级命中）
  │    → run_log_processor           ← M4 新增：若绑定 execution_run_id 则落 run_log
  │    → renderer（prod=JSON / dev=Console）
  │
  ├─ StreamHandler(stdout) → docker json-file（max-size 20m, max-file 5）
  └─ run_log_processor → 进程内批量缓冲（每 100 条或 1s flush）→ PG run_log
```

- **顺序不可交换**：`run_log_processor` 必须在 `redact_processor` **之后**，保证落库的 `fields` 与打印的内容是同一次脱敏结果；两者分离会导致「日志干净但库里有明文」这种最难发现的泄漏。
- 批量写入：`run_log_processor` 只往内存队列 push，由后台任务/请求结束时 flush，避免每条日志一次 INSERT 把长事务拖慢。交叉引用：`run_log.request_id` 与 `evidence_event.payload.request_id` 共用同一个值，可从运行中心一键跳到审计证据。

### 5.2 指标：api 中间件 / service 关键点 / task 装饰器

| 埋点层 | 位置 | 方式 | 覆盖指标 |
|---|---|---|---|
| **HTTP** | `main.create_app()` 的 `ELTMetricsMiddleware`（在 `RequestContextMiddleware` 之后注册，保证能读到上下文） | 记录 `route`（取 `request.scope["route"].path`，**不用** URL 原值以免标签爆炸）、`method`、`status`、耗时 | HTTP 请求量/延迟/错误率 |
| **service 关键点** | `services/monitor` 只读；写侧在 be-14/be-16/be-17/be-06 的关键动作后调 `core/metrics` 的 `*_total.inc()` | 显式调用，**不用** AOP/MonkeyPatch | Outbox、运行执行、账本、Swap |
| **task 装饰器** | `tasks/celery_app.py` 订阅 `task_prerun` / `task_postrun` / `task_failure` / `task_retry` 信号 | 统一在信号里计数，任务函数零改动 | Celery 任务数/时长/重试/失败 |
| **beat 周期任务** | `tasks.outbox.scan_and_dispatch`（每 2s）与 `tasks.maintenance.*` | 扫描后直接把结果喂 `observe_outbox_scan()` / `set_ledger_gauges()` | Outbox 积压、账本检查点滞后 |
| **探针** | `api/health.readyz` | 每次探针执行时 `set_dependency_up()` | `elt_dependency_up` |

- worker / beat 进程通过 `celery.signals.worker_ready` / `beat_init` 调 `start_metrics_servers()`，在 `settings.WORKER_METRICS_PORT`(9101) / `BEAT_METRICS_PORT`(9102) 上各起一个 `prometheus_client.start_http_server`。**不引入 celery-exporter 容器**：单 worker 单 beat 拓扑下，进程内暴露比再加一个从 broker 读事件的组件更少故障点（`deploy/prometheus/prometheus.yml` 里那条注释掉的 `celery-exporter` 保持注释）。
- 端口只在 `elt_net` 内可达：compose 中**不写 `ports:`**，Prometheus 直接抓 `worker:9101` / `beat:9102`。

### 5.4 告警链路

`Prometheus`（`rules/elt.rules.yml`，每 30s 评估）→ 触发 → `Alertmanager`（分组/抑制/静默）→ webhook → `clients/alerting/bridge`（`POST /dingtalk`）→ `dingtalk.py`：加签 → 限流聚合 → 发送 → 失败重试 3 次 → 落盘 + 自告警。

## 6. 关键算法与规则

### 6.1 日志规范

**处理器链（固定顺序，见 §5.1）**：`merge_contextvars → add_logger_name → add_log_level → TimeStamper(iso, utc) → StackInfoRenderer → UnicodeDecoder → redact_processor → run_log_processor → renderer`。

**固定绑定字段**（全部由 `structlog.contextvars` 承载，业务代码不得把它们拼进 message 字符串）：

| 字段 | 绑定时机 | 备注 |
|---|---|---|
| `request_id` | `RequestContextMiddleware`（已有） | 优先沿用上游 `X-Request-ID`；Celery 从 outbox payload 取回后重新绑定，保证 api→worker 同一值 |
| `tenant_id` / `subject_id` | be-02 的 `get_current_subject` 解析后 | 授权判定不用 JWT 内角色声明，但 `subject_id` 可用于日志 |
| `project_id` | service 入口解析后 | `execution_run.project_id` 与它比对，不一致即 `TENANT_MISMATCH` |
| `pipeline_version_id` | M2 冻结版本后由 service 绑定 | — |
| `execution_run_id` | M3 Commit 后由 service/task 绑定 | **同时是 `run_log_processor` 的开关** |

**level 使用约定**

| level | 用于 | 例 |
|---|---|---|
| DEBUG | 诊断细节（仅非生产；生产被 `configure_logging` 抬到 INFO） | `llm_cache_lookup` 命中详情 |
| INFO | 状态迁移与关键动作的成功路径 | `pipeline.version_frozen`、`run.started`、`swap.succeeded` |
| WARNING | 可恢复异常、预算预警、**协议类拒绝**（401/403/409/423） | `readyz_postgres_failed`、`supervision_warning`、`app_error`(403) |
| ERROR | 需人工介入（依赖不可达、备份失败、账本签名失败、死信） | `outbox_message_dead`、`ledger_checkpoint_sign_failed` |
| CRITICAL | 数据完整性/合规风险（链断点、明文泄漏尝试） | `ledger_chain_broken`、`sensitive_value_detected_in_payload` |

**脱敏唯一出口**：`redact_processor` 是唯一掩码实现。业务代码不得自建 `_mask()`；异常处理器只回 `{code, message, request_id, details?}`，`details` 不含原始输入值（已有约定）。若某处确实需要检测「明文敏感值是否被误传入」，用 `logging._SENSITIVE_KEY_RE` / `_VALUE_RULES` 的同一份规则集做断言并记 CRITICAL，**不另写一套正则**。

**轮转与保留**

| 通道 | 载体 | 轮转 / 保留 |
|---|---|---|
| 进程 stdout | docker `json-file`，`max-size: 20m`、`max-file: 5`（已在 `docker-compose.yml` 的 `x-logging`） | 单服务约 100 MB 滚动；重启即丢历史，**不作为查询来源** |
| 运行日志（可查询） | PG `run_log`（§4） | `RUN_LOG_RETENTION_DAYS=90`，`tasks.maintenance.enforce_retention` 清理 |
| 审计证据 | PG `evidence_event` / `evidence_ledger_block` | `EVIDENCE_RETENTION_DAYS=0`（永久） |
| Prometheus TSDB | `prometheus_data` 卷 | 默认 15d；由 `--storage.tsdb.retention.time=90d` 与卷大小匹配（见 §10） |

### 6.2 `run_log_processor` 规则

1. 仅当 `event_dict` 含 `execution_run_id` 且 level ≥ INFO 时落库；否则原样返回（避免把启动期、健康检查等噪声灌进 90 天表）。
2. `message` 存 `event_dict["event"]`；`fields` 存**剩余键值**（已是脱敏后形态）；单条 `fields` 序列化后 > 8 KB 截断并记 `fields_truncated: true`（防一条日志把行写爆）。
3. 缓冲：进程内 `collections.deque` + 定时（1s）/定量（100 条）flush；flush 失败只记 WARNING（**日志写失败不得让业务失败**）。
4. 只写不更新：`run_log` 追加语义，不提供 UPDATE 接口。

### 6.3 `/metrics` 与 Nginx 的暴露策略

- `main.create_app()` 用 `app.mount("/metrics", metrics_asgi_app())` 挂载；Nginx 现有配置**没有** `/metrics` 的 `location`，请求会落到 `location /` 的静态回退（返回 `index.html`），公网拿不到指标——**但这是隐式行为，不可依赖**。
- 因此在 `deploy/nginx/nginx.conf` 显式加一条（与 `location ~ /\. { deny all; }` 并列）：`location = /metrics { deny all; return 403; }`——**指标端点绝不对外**，Prometheus 在内网直抓 `api:8000/metrics`。

- 部署自检（见 [be-22](be-22-部署备份与CICD.md) §9）：`curl -s -o /dev/null -w '%{http_code}' http://$SERVER_HOST/metrics` 必须是 `403`，**绝不允许** 200 且响应体含 `# HELP`。
- Prometheus 侧 `prometheus.yml` 的 `elt-api` job（已存在）保持 `targets: ["api:8000"]`、`metrics_path: /metrics`，走 compose 内网。`obs` profile 下 Prometheus 自身端口 `127.0.0.1:9090`、Grafana `127.0.0.1:3000`，均通过 SSH 隧道访问。

### 6.4 告警规则（`deploy/prometheus/rules/elt.rules.yml`）

级别：`critical`（立刻处理）/ `warning`（当日处理）。渠道：`dingtalk-security`（安全） / `dingtalk-ops`（运维） / `dingtalk-data`（数据）；由 Alertmanager 的 `route.routes` 按 `labels.channel` 分流。

| # | 指标 | 表达式 | `for` | 级别 | 渠道 | 收到后第一步 |
|---|---|---|---|---|---|---|
| 1 | 账本检查点签名失败 | `increase(elt_ledger_checkpoint_sign_failures_total[15m]) > 0` | `0m` | critical | security | 确认 `LEDGER_SIGNING_KEY_PATH` 是否挂载、权限是否 0600、`key_id` 是否与密钥匹配；立刻跑 `uv run python -m scripts.verify_ledger` 判断链是否已断 |
| 2 | Outbox 死信 | `increase(elt_outbox_dead_total[10m]) > 0` | `0m` | critical | ops | `SELECT topic, attempts, last_error FROM outbox_message WHERE status='dead' ORDER BY id DESC LIMIT 20`；先判 SeaTunnel 不可达还是 payload 非法，再用运维脚本重投（不手改库） |
| 3 | Outbox 积压 | `elt_outbox_oldest_pending_age_seconds > 120` | `5m` | warning | ops | `docker compose ps beat worker`；beat 挂了或 worker 队列堵了，查 `elt_celery_tasks_in_progress` |
| 4 | 硬中断发生 | `increase(elt_runs_interrupted_total[10m]) > 0` | `0m` | warning | data | 打开运行中心该 `execution_run_id` 的 `failure_snapshot`，看是预算还是脏数据触发；确认是否已进入 `interrupted` 并可回滚 |
| 5 | 拒绝率超预警 | `elt_run_budget_ratio{budget="reject_rate"} > 0.8 and elt_runs_active > 0` | `2m` | warning | data | 查 `quality_report.error_code_dist` 定位规则；硬阈值由引擎自行中断，此告警是提前量 |
| 6 | 写字节/行数预算 | `elt_run_budget_ratio{budget=~"write_bytes\|read_rows"} > 0.8` | `5m` | warning | data | 核对源表是否被误全量扫描；必要时下调契约或调大 `SUP_MAX_*`（改契约要重新冻结版本） |
| 7 | SeaTunnel 不可达 | `elt_seatunnel_probe_success == 0` | `2m` | critical | ops | `docker compose --profile demo ps seatunnel`；容器在但 REST 不通 → 看 `seatunnel_logs` 卷；若已切 CLI 退化路径，确认 `SEATUNNEL_CMD` |
| 8 | PostgreSQL 不可达 | `elt_dependency_up{dependency="postgres"} == 0` | `1m` | critical | ops | `docker compose ps postgres` + `pg_isready`；`/readyz` 已 503；先看磁盘是否写满（关联 #11） |
| 9 | Redis 不可达 | `elt_dependency_up{dependency="redis"} == 0` | `1m` | critical | ops | 查是否触发 `maxmemory 1gb` + `noeviction` 写入失败；同时注意 Capability 消费标记失效会让协议层拒绝（宁拒绝不放行） |
| 10 | worker 掉线 | `up{job="celery-worker"} == 0` | `2m` | critical | ops | `docker compose logs --tail=200 worker`；确认不是 1536m 内存 limit 触发的 OOMKill |
| 11 | 磁盘水位 | `(1 - node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}) > 0.85` | `10m` | warning | ops | `docker system df`；清理未上云的备份、`docker image prune`；PG WAL / Doris 数据卷是否异常增长 |
| 12 | 磁盘水位（严重） | 同 #11 且 `> 0.92` | `5m` | critical | ops | 立即停 `demo` profile（`docker compose --profile demo stop doris seatunnel`）腾出空间，再按 #11 处理 |
| 13 | 备份失败/过期 | `time() - elt_backup_last_success_timestamp_seconds > 93600`（26h） | `5m` | critical | ops | 看 `deploy/backup/backup.log` 与 OSS 上是否缺当日对象；手工 `deploy/backup/backup.sh` 复现错误 |
| 14 | 密钥即将到期 | `elt_secret_rotation_due_in_seconds < 604800`（7 天） | `1h` | warning | security | 按 90 天周期在 Vault 轮转该 KV 版本，更新 `secret_reference.version` 与 `last_rotated_at` |
| 15 | 账本检查点滞后 | `elt_ledger_checkpoint_lag_events > 200` | `10m` | warning | security | 确认 beat 的 `tasks.maintenance.checkpoint_ledger` 在跑；未签名区间过大 = 签名保护有缺口 |
| 16 | API 5xx 比例 | `sum(rate(elt_http_requests_total{status=~"5.."}[5m])) / sum(rate(elt_http_requests_total[5m])) > 0.02` | `5m` | warning | ops | 按 `route` 下钻，取响应体的 `request_id` 直接追日志 |
| 17 | 告警投递失败 | `increase(elt_alert_delivery_failures_total[15m]) > 0` | `0m` | critical | ops | 查 webhook 是否被钉钉限流/签名错误；检查 `deploy/alertmanager/failed-alerts.jsonl` 是否在堆积（这是「告警系统自己哑了」的信号） |

- 每条规则带 `labels.channel` 与 `annotations.summary`（一句话，含 `{{ $value }}`）与 `annotations.runbook`（本文 §6.4 的「第一步」）。`annotations` 里**禁止**出现连接串、IP + 密码、样本值。
- 抑制规则：`#11/#12` 触发时抑制 `#8/#9/#10`（磁盘满会连带一串依赖失败，避免告警风暴）；`#1` 抑制 `#15`。

### 6.6 钉钉发送器（`clients/alerting/dingtalk.py`）

| 关注点 | 规则 |
|---|---|
| 加签 | 若配置 `ALERT_DINGTALK_SECRET`：`sign = base64(HMAC-SHA256(secret, f"{timestamp}\n{secret}"))`，URL 追加 `&timestamp={ms}&sign={quote(sign)}`（钉钉加签规则）。未配 secret 时仅用 webhook（仅限内网可信场景） |
| 限流 | 进程内令牌桶：默认 20 条/分钟（钉钉机器人约 20 条/分钟）；超出不丢弃——合并为一条「N 条告警被聚合」摘要，附最早/最晚告警名与最高级别 |
| 聚合（上游） | Alertmanager：`group_by: [alertname, project_id, channel]`、`group_wait: 30s`、`group_interval: 5m`、`repeat_interval: 4h`（critical 可设 2h） |
| 去重 | Redis `SETNX alert:sent:{fingerprint}:{startsAt}`，TTL = `repeat_interval`；重复投递直接 ACK 不重发 |
| 模板 | markdown：`### [{level}] {alertname}` / 项目 / `request_id` / `execution_run_id` / 当前值 vs 阈值 / 触发时间 / 「去运行中心」链接 `{PUBLIC_BASE_URL}/runs/{execution_run_id}`（`PUBLIC_BASE_URL` 未配域名时用 `http://60.205.138.167`）。**模板里不得放连接串或样本值** |
| 重试 | 指数退避 3 次（1s / 4s / 16s）；仅对 5xx 与网络错误重试，4xx（签名/格式错误）不重试并记 ERROR |
| 降级 | 3 次仍失败 → `elt_alert_delivery_failures_total{channel="dingtalk"}.inc()` + 追加 `deploy/alertmanager/failed-alerts.jsonl`（含完整 payload 供事后补发）+ 记 structlog ERROR（脱敏）。规则 #17 会把「告警发不出去」这件事本身告出来（但此时也只能落到日志/磁盘——这是可接受的最后降级） |
| 静默 | 支持 Alertmanager `silences`；运维执行 `docker compose restart postgres` 前先建 10 分钟静默 |
| 关闭开关 | `ALERT_ENABLED=false`（已有配置，默认 false）时 bridge 只记日志不发送，便于本地与首次部署时验证配置 |

`clients/alerting/bridge.py` 是一个极小的 FastAPI 服务（复用后端镜像，`command: uvicorn clients.alerting.bridge:app --port ${ALERT_BRIDGE_PORT:-8060}`），在 compose `obs` profile 下常驻，只监听 `elt_net` 内部。

## 7. 错误码与拒绝语义

本模块对外只有 `api/monitor` 三个只读路由，因此错误码极少：

| 触发条件 | 错误码（`ErrorCode`） | HTTP | 写证据账本 |
|---|---|---|---|
| 查询参数非法（`since` 不是合法时间、`limit` 越界、`level` 非法） | `VALIDATION_ERROR` | 422 | 否 |
| `run_id` 不存在 | `NOT_FOUND` | 404 | 否 |
| 跨租户/跨项目访问运行 | `TENANT_MISMATCH` | 403 | 是（由 be-02 判定并写） |
| 角色不足（`maker` 访问他人项目运行） | `FORBIDDEN` / `ROLE_REQUIRED` | 403 | 是（由 be-02 判定并写） |
| `run_log` 未落库时的日志查询 | 返回空列表（200，`items: []`），**不报 500** | 200 | 否 |
| 健康汇总里某依赖不可用 | 200，`data.checks.<dep>="fail"`；仅整体不可用时 503（与 `/readyz` 一致） | 200/503 | 否 |

- `/metrics` **不做权限校验**（Prometheus 不带凭据）；防护在网络层（内网 + Nginx `deny all`），必须在安全组与部署自检里体现，而不是靠应用层。告警发送失败不产生 API 错误码（内部通道故障，以 `elt_alert_delivery_failures_total` + 落盘体现）。本模块**不新增 `ErrorCode`**。

## 8. 安全与合规约束

- **脱敏**：`redact_processor` 是唯一出口（§6.1）；`run_log.fields` 落库前已过脱敏；`/logs` 返回前**再校验一次**不含命中敏感规则的键（双保险，避免有人绕过 processor 直接 INSERT `run_log`）。`failure_snapshot`（be-16 写入）也要求已脱敏。
- **Secret**：`ALERT_DINGTALK_WEBHOOK` / `ALERT_DINGTALK_SECRET` 用 `SecretStr` 承载，只从环境注入；`failed-alerts.jsonl` 落盘前确认 payload 无凭据（Alertmanager 的 `labels`/`annotations` 本就禁止放连接串）。
- **租户过滤与权限**：`/monitor/*` 每次查询先解析 `tenant_id` + `project_id`，`execution_run` 查询强制带 `project_id`，角色用 `role_assignment` 判定（不用 JWT 声明）。`/metrics` 无鉴权但网络隔离；写类动作（Outbox 重投、静默）走运维脚本 + 账本事件，不在 HTTP 接口里暴露。Grafana 是**运维视角**（聚合指标，标签只到 `project_id`），不对租户用户开放，仅 SSH 隧道可达。
- **不可变与审计**：本模块不写任何不可变表（`run_log` 只追加）；跨租户/越权访问写 `evidence_event`（由 be-02 完成）；告警触发与静默操作记录在 Alertmanager 与 bridge 日志中。
- **数据最小化**：指标标签禁止出现 `run_id`、URL、错误消息原文（§5.3 命名约定），既是性能要求也是隐私要求（错误消息可能含表名/字段名）。

## 9. 测试要点

- **单元测试**
  - **脱敏处理器样本断言**（最关键）：构造 `log.info("x", password="p@ssw0rd123", phone="13800000001", id_card="110101199001011234", email="a@b.com", dsn="postgresql://u:p@h/db", token="sk-abcdefgh", jwt="eyJx.y.z")` → 断言渲染出的 JSON 中：`password` 为 `***`、无 `13800000001` / 无 18 位身份证 / 无 `a@b.com` / 无 `p@h` / 无 `sk-` 原文。用 `capsys` 抓 stdout 实现端到端断言，而不是直接调 processor（否则测不到渲染器）。
  - 深层嵌套（深度 >6）→ `[TRUNCATED]`；`bytes` → `<bytes:N>`。
  - `run_log_processor`：无 `execution_run_id` → 不落库；有且 level=DEBUG → 不落库；有且 INFO → 落库且 `fields` 已脱敏；`fields` > 8 KB → 截断并标记。
  - 指标助手：`observe_http` 对同 route 同 status 计数累加；`_rate` 类函数对标签值的**有界性**（route 用模板路径而非真实 URL）。
  - `dingtalk.build_markdown`：含 `execution_run_id` 与跳转链接；不含任何 `***` 之外的敏感键；超长字段被截断。
- **集成测试**（真实 PG / Redis）
  - `ELTMetricsMiddleware` 打一次 `GET /healthz` → `elt_http_requests_total{route="/healthz",status="200"}` 增加 1；`/readyz` 在 PG 挂掉时使 `elt_dependency_up{dependency="postgres"}` 归 0 且响应 503。
  - `/api/v1/monitor/runs/{id}/metrics?since=<t>` 只返回 `ts > t` 的点并给出 `next_since`；连续两次轮询无重复点（增量语义）。
  - `/api/v1/monitor/runs/{id}/logs?level=WARNING` 只返回 WARNING 及以上；跨项目访问 → 403 `TENANT_MISMATCH`；一次完整运行后 `/metrics` 文本中含 `elt_runs_started_total` / `elt_outbox_pending` / `elt_ledger_last_seq`。
- **必须覆盖的反例**：日志中不得出现明文（用真实样本值做断言）；跨租户读运行 → 403 且账本留痕；`/metrics` 经 Nginx 不可达（部署自检，见 be-22）。
- **验收判据（M4）**：`obs` profile 起后 Prometheus `targets` 全为 `UP`（api / worker / beat / node-exporter / prometheus 自身），Grafana 六个看板有数据，手工触发一次告警（临时把 `ALERT_DINGTALK_WEBHOOK` 指向测试群）能收到含 `request_id` 的钉钉消息。

| 新配置项未在 `Settings` / `.env.example` | 仅 `ALERT_DINGTALK_WEBHOOK` / `ALERT_ENABLED` 存在 | 需新增 `ALERT_DINGTALK_SECRET`、`ALERT_MIN_INTERVAL_SEC`、`METRICS_ENABLED`、`WORKER_METRICS_PORT(9101)`、`BEAT_METRICS_PORT(9102)`、`ALERT_BRIDGE_PORT(8060)`、`PUBLIC_BASE_URL`，同步 `core/config.py` + `.env.example` |
| Prometheus TSDB 保留期 | compose 未设保留参数 | 加 `command: --storage.tsdb.retention.time=90d --config.file=/etc/prometheus/prometheus.yml`；按磁盘余量调整（90d 与 15s 抓取在单机约数 GB） |
| SeaTunnel 指标口径 | 总纲 §8 已标「待 M3 实机验证」 | 优先用 be-16 的自采集（查目标表 + 自计时）驱动 `elt_run_*`；是否启用 Zeta 原生 telemetry 待实测，不可用则不引入 |
