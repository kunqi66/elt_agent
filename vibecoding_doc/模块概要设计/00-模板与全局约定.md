## 一、文档模板

每个模块文档**必须**包含下列 10 节（顺序固定，无内容的节保留标题写「无」并说明原因，不要删节——读者依赖固定的位置找信息）。

````markdown
# be-XX 模块名

> 上游：[概要设计总纲.md](../概要设计总纲.md) §X ｜ [PRD.md](../PRD.md) §6.X
> 数据：[核心数据字典.md](../核心数据字典.md) §X
> 代码位置：`backend/xxx/` ｜ 里程碑：M2 ｜ 依赖：be-01 be-07

## 1. 职责与边界
- **做什么**：3–6 条，动词开头。
- **不做什么**：显式排除相邻模块的职责（防止实现时越界，这一节比上一节更重要）。
- **所在分层**：api / services / engines / clients / harness / workflow / tasks / core，以及依赖方向。

## 2. 模块结构
目录树 + 每个文件一句话职责。文件尚未创建时标注「（待建）」。

## 3. 对外接口
- **HTTP**：方法 / 路径 / 权限（角色） / 幂等 / 请求与响应要点。表格形式。
- **Python**：被其他模块调用的函数/类签名（带类型注解），一句话说明契约与异常。
- 只列**跨模块**接口；模块内部私有函数不列。

## 4. 数据模型
只列本模块**读/写**的表与关键列、涉及的约束（唯一索引、CHECK、部分索引）。
表结构不在本文重复定义，指向《核心数据字典》。

## 5. 核心流程
主流程的步骤化描述（编号步骤，可含 mermaid 或 ASCII 时序）。
状态机用「状态 → 事件 → 新状态」表格表达，并写明**非法转移如何处理**。

## 6. 关键算法与规则
纯逻辑（校验、匹配、计算、判定）的输入/输出/边界条件。engines 层模块这一节是主体。

## 7. 错误码与拒绝语义
引用 `core/errors.ErrorCode` 的既有取值，列出「触发条件 → 错误码 → HTTP 状态 → 是否写证据账本」。
**不得自造错误码**；确实缺失的，写进「未决与风险」并说明建议新增的码。

## 8. 安全与合规约束
租户过滤、脱敏、Secret、审计事件、不可变、权限校验在本模块的具体落点。

## 9. 测试要点
- 单元测试（纯函数、边界、反例）
- 集成测试（真实 PG/Redis，协议类用例）
- 必须覆盖的**反例**：越权、重放、自批、指纹失效、超预算等（按模块相关性取）

## 10. 未决与风险
待实机验证、待拍板、已知不确定性。**不要用「可能/大概」把不确定写成结论。**
````

## 三、分层与依赖（复述铁律，写文档时必须自查）

1. `api/` **禁止**业务逻辑：只做参数校验、依赖注入、权限检查、调 service、组装响应。
2. `services/` 可调 `engines/` `clients/` `models/` `harness/`，**禁止** `import fastapi`。
3. `engines/` 是**纯函数层**：只依赖 Pydantic + 标准库；**禁止** fastapi、DB、Redis、网络、**LLM**。数据由 service 传入、结果返回 service。
4. `harness/` **禁止**依赖 `services/` 与 `api/`；它是所有副作用的唯一出口。
5. `tasks/` 只做编排，业务逻辑下沉 `services/`。
6. 跨层只传 **Pydantic 模型**，不传 ORM 实例。
7. 所有 SQL 查询强制带 `tenant_id` 过滤。

写「模块结构」时若某个文件不知道该放哪层，先回答：**它有 IO 吗？它有副作用吗？它是纯计算吗？**——纯计算进 `engines/`，外部系统进 `clients/`，副作用进 `harness/`，编排进 `services/`。

## 四、横切契约（所有模块共用，不要各写各的）

### 4.1 响应信封
统一由 `core/response.py` 组装：`{code, message, data, request_id}`；错误由 `core/errors.py` 的异常处理器统一产出 `{code, message, request_id, details?}`。模块只 `raise` 领域异常，**不自己拼响应体**。

### 4.2 幂等
所有**可能重放**的写接口必须支持 `Idempotency-Key` 请求头，落 `idempotency_key` 表（key UK + scope + request_hash + response_snapshot）；同 key 不同 request_hash → `IDEMPOTENCY_CONFLICT`。

### 4.3 日志与脱敏
一律 `structlog`，绑定 `request_id / tenant_id / project_id / subject_id / pipeline_version_id / execution_run_id`。
**业务代码不得自行拼接敏感值**——脱敏由 logging 处理器统一完成。文档里凡「记录日志」都要写清记录的是**引用/掩码**而非值。

### 4.4 时间与数值
时间 `timestamptz`；字节/行数 `bigint`；比率 `numeric(6,4)`；JSON 一律 `jsonb` + `schemas/` 层 Pydantic 强校验。

### 4.5 租户与权限
每个 service 入口先解析 `tenant_id / project_id` 上下文，repository 查询强制带上；跨租户访问 → `TENANT_MISMATCH`。角色校验用 `role_assignment`（职责槽的唯一事实来源），**不用 JWT 里的角色声明做授权判定**（JWT 只承载身份，角色可能已被回收）。

### 4.6 证据事件
关键动作经 `harness.EvidenceLedger.append()` 写入，事件类型取自 `EvidenceEventType`。文档的「错误码与拒绝语义」一节必须标注**哪些拒绝要写账本**（协议类拒绝一律要写）。

### 4.7 副作用
任何写外部系统 / 执行作业 / 改数据的动作，必须注册为一个 `ToolName` 并经 `ToolBroker.execute(tool, token, args)`。模块文档里出现「调用 SeaTunnel / 执行 DDL / 写目标表」时，必须写明走哪个工具名。

## 七、写作风格

- **中文正文，英文标识符**。注释写「为什么」，不写「是什么」。
- 用**表格**承载枚举型信息（路由、错误码、状态转移、阈值），用**编号步骤**承载流程，用**函数签名**承载接口。
- 不写营销词、不写「本模块非常重要」这类评价句。
- 不确定的地方写进「未决与风险」，标注**验证方式**（如「M3 实机验证 SeaTunnel REST 指标可用性」）。
- 引用其他文档用相对链接：`[be-05](be-05-Harness内核与工具代理.md)`、`[概要设计总纲 §5](../概要设计总纲.md)`。
