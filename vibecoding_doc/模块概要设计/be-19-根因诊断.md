## 1. 职责与边界

- **做什么**
  - 从失败现场抽取**结构化信号**：`execution_run.failure_snapshot`、`execution_metric` 序列、`quality_report`（含 be-17 的 `diagnostics`）、错误码/规则/字段分布，输出 `DiagnosisSignals`（只有计数、比率、时间、标识符）。
  - 用**确定性故障分类表**（纯规则，`taxonomy.py`）给出故障类别、可能原因与建议动作，并保证每条结论都带可追溯的信号引用（`evidence`）。
  - 用 `deepseek-reasoner` 把确定性结论补写成自然语言解释与排障顺序（**只增文本，不改结论、不驱动动作**），并在模型不可用时降级为纯确定性结论。
  - 诊断结果落 `execution_run.failure_snapshot[diagnosis]`，通过只读接口供给前端「根因诊断」面板与导出。
- **不做什么**
  - 不重新做质量判定、不改 `quality_report`（不可变制品；报告内的 `diagnostics` 归 [be-17](be-17-质量契约与数据分流.md)）。
  - 不触发硬中断、不停止作业、不发布、不回滚（归 be-16 / [be-18](be-18-原子发布与受管回滚.md)）；诊断输出**不得**成为任何自动决策的输入。
  - 不做故障自愈（不自动改预算、不自动重跑、不自动改质量契约）。
  - 不让 LLM 参与分类：类别、置信度、原因、动作一律由规则表给出（PRD §10.1 的确定性要求）。
  - 不投喂任何数据值：信号类型本身不含值，digest 也不投喂（见 §8）。
- **所在分层**：`engines/diagnosis/`（纯函数：信号提取、分类匹配、提示词渲染）← `services/diagnosis.py`（查库、调 LLM、落库、写证据）← `api/monitor.py`（只读转发）。LLM 调用在 `clients/llm/`（be-08），`engines/` **禁止** import 任何 LLM 客户端。

## 2. 模块结构

```
backend/
├── engines/diagnosis/               # 纯函数层：给定输入字符串恒定输出，可用于单测与回放
│   ├── __init__.py                  #（待建）导出 extract_signals / classify / flatten_signals / validate_findings
│   ├── signals.py                   #（待建）信号提取 + 信号扁平化 + 误差消息归类（关键词表）
│   ├── taxonomy.py                  #（待建）FaultCategory / Confidence / FaultRule 表（声明式条件）
│   ├── render.py                    #（待建）确定性结论 → Markdown 报告；以及 LLM 提示词渲染（无 IO）
│   └── keywords.py                  #（待建）error_message 归类的关键词表（唯一一处，集中审阅）
├── schemas/
│   └── diagnosis.py                 #（待建）RunSignalView / MetricPointView / QualityReportView / ErrorDigestView /
│                                    #        DiagnosisSignals / Finding / DiagnosisDTO（一律 extra="forbid"）
├── services/
│   └── diagnosis.py                 #（待建）diagnose_run / get_diagnosis / regenerate / export_report
└── clients/llm/                     #（be-08）Provider 抽象；本模块只使用 complete() 一种能力
```

`signals.py` 与 `taxonomy.py` 分离的理由：信号提取是「把事实翻译成数字」，分类表是「把数字翻译成结论」。两者都会变，但变更原因不同（新增指标 vs 新增故障模式），分开可以让分类表以数据形式被审阅与回归测试。

## 3. 对外接口

### 3.1 HTTP（前缀 `/api/v1/monitor`）

| 方法 | 路径 | 权限 | 幂等 | 要点 |
|---|---|---|---|---|
| GET | `/runs/{run_id}/diagnosis` | maker / operator / auditor（同项目） | 天然幂等 | 返回最近一次诊断；未生成过则**按需生成一次**（`regenerate=false` 语义），除非 run 未处于终止态 |
| POST | `/runs/{run_id}/diagnosis/regenerate` | operator | 必须带 `Idempotency-Key` | 强制重新提取信号并重新分类（用于指标补齐后复查）；历史保留最多 5 条 |
| GET | `/runs/{run_id}/diagnosis/export?format=json\|markdown` | 同上（只读） | 天然幂等 | 附件下载（`Content-Disposition`），内容仅供人工留档与审计 |

LLM 调用契约（对齐 be-08 的 Provider 抽象，签名以 be-08 定稿为准）：

```python
result: LLMResult = await provider.complete(
    model=settings.LLM_MODEL_DIAGNOSE,          # deepseek-reasoner
```

## 4. 数据模型

本模块**不新增表**，只读以下表 + 写 `execution_run.failure_snapshot`（既有 jsonb 列）：

| 表 | 读/写 | 关键列 | 用途 |
|---|---|---|---|
| `execution_run` | 读 + 写 `failure_snapshot` | `status` `read_rows` `written_rows` `written_bytes` `reject_rows` `duration` `error_message` `seatunnel_job_id` | 终止状态、汇总数、失败现场；**诊断结果回写 `failure_snapshot["diagnosis"]`** |
| `execution_metric` | 只读 | `ts` `throughput` `read_rows` `written_rows` `written_bytes` `duration_sec` `amplification_ratio` `reject_rate` | 吞吐形状、预算压力、断崖检测；按 `ix_execution_metric_run_id_ts` 取全序列（活跃 run 上限可控） |
| `quality_report` 🔒 | 只读 | `valid_rows` `rejected_rows` `reject_rate` `error_code_dist` `rule_hits` `passed` `diagnostics` | 错误码/规则分布与 be-17 的规则级诊断 |
| `error_record` 🔒 | 只读（聚合 + 抽样） | `error_code` `field_name` `rule_id` | 违规字段 Top-N 与每规则最多 3 条 digest 样本（**无原文**） |
| `runtime_supervision_contract` 🔒 | 只读 | 五个预算维度 + `warn_threshold_pct` | 计算 `budget_pressure` 的 used/limit/ratio |
| `pipeline_version` 🔒 | 只读 | `sha256` | 证据事件与导出的制品锚点 |

**落库位置的选择**：不写 `quality_report.diagnostics`（🔒 不可变，且「作业提交失败」「SeaTunnel 被杀」这类故障可能根本没有质量报告），而写 `execution_run.failure_snapshot`（本就是失败现场，jsonb 可更新）。写入形态：

```json
{
  "diagnosis": { "version": "diag-v1", "generated_at": "…", "category": "field_type_parse",
                 "confidence": "high", "rule_code": "D-002", "also_matched": ["D-006"],
                 "signals": { "…扁平化信号…" }, "findings": [ "…" ],
                 "llm": {"status": "ok", "model": "deepseek-reasoner",
                         "prompt_version": "diag-v1", "text": "…"} },
  "diagnosis_history": [ "…最多 5 条历史，仅保留 category/rule_code/generated_at/llm.status…" ],
  "swap": { "…be-18 写入的发布现场…" },
  "quality": { "…be-17 写入的分布摘要…" }
}
```

各写入方只改自己的子键（`swap` / `quality` / `diagnosis`），互不覆盖；写入用「读-改-写」在同一事务内完成，避免并发覆盖。

## 5. 核心流程

```
be-16 硬中断 / be-14 作业失败 / be-18 Swap 失败
        │  run.status ∈ {failed, interrupted, cancelled}
        ▼
(GET /diagnosis 按需) 或 (POST /diagnosis/regenerate)
 1 校验：run 存在、同租户、status 允许；preparation/pipeline_version 读出制品指纹
 2 读事实：run + execution_metric 全序列 + quality_report（可空）+ error_record（聚合 3 条查询）+ 监督契约
 3 服务层先归类 error_message → error_message_kind（原文不出服务层）
 4 engines: extract_signals → flatten_signals → classify → validate_findings
 5 LLM 增强解释（可失败）：render_llm_messages → provider.complete → 文本；异常 → status="unavailable"
 6 组装 DiagnosisDTO → 读-改-写 failure_snapshot.diagnosis（历史前移，最多 5 条）
 7 返回 200（LLM 不可用不影响可用性）
```

编号步骤的边界：

- 第 1 步只允许 `status ∈ {failed, interrupted, cancelled}` 的 run；`running/queued` → `CONFLICT`（`detail.reason="run_not_terminal"`），因为信号未收敛、结论会误导。
- 第 2 步的 `error_record` 查询必须是**聚合查询 + 每规则 ≤3 条 LIMIT 抽样**，禁止全表拉取（错误行可能上百万）。
- 第 4 步是纯函数段，可离线回放：给定同一 `(run, metrics, report, errors)` 必得同一结论（确定性验收点）。
- 第 6 步不写证据账本事件类型中不存在的值（见 §10）：信息落 `failure_snapshot`，不落账本。

### 状态机

本模块**不转移 `run.status`**（诊断是只读分析 + 写现场字段）。非法输入的处理用下表：

| run 当前状态 | 诊断请求 | 处理 |
|---|---|---|
| `failed` / `interrupted` / `cancelled` | 生成 / 重新生成 | 正常执行 |
| `running` / `queued` / `paused` | 任意 | `CONFLICT`（`reason="run_not_terminal"`） |
| `rolling_back` | 任意 | `CONFLICT`（`reason="rollback_in_progress"`，诊断与回滚都会读同一份现场，避免口径漂移） |
| `succeeded` | 生成 | `CONFLICT`（成功运行没有失败现场；若需成功运行的质量视图，读 be-17 报告） |
| `rolled_back` | 生成 | 允许（回滚后仍需解释当初为何失败） |

## 6. 关键算法与规则

### 6.1 信号提取（`signals.py`）

信号分七族，全部是「计数 / 比率 / 时间 / 标识符」，**不含任何字段值**：

| 族 | 代表键 | 来源与算法 |
|---|---|---|
| `error_mix` | `error_mix.<CODE>.count` / `.share` | `quality_report.error_code_dist`（缺失时退回 `error_record` 的 `GROUP BY error_code`）；`share = count / error_total` |
| `rule_mix` | `rule_mix.<rule_id>.count` | `quality_report.rule_hits` + 每规则 ≤3 条 digest 样本（样本本身不进 signals，只进 `diagnostics` 展示） |
| `violating_fields` | `violating_fields.<field>.share` | `error_record GROUP BY field_name`，取 Top-10，其余合并为 `__other__` |
| `throughput` | `throughput_peak` / `throughput_last` / `throughput_drop_at_sec` / `throughput_volatility` | 从 `execution_metric` 序列（按 `ts` 升序）求：`drop_at_sec` = 首个「相对前一点跌幅 ≥ 50% 且其后所有点均未回到峰值 50%」的点；`volatility` = 序列变异系数（std/mean），单点或 mean=0 → `None` |
| `budget_pressure` | `budget_pressure.<dim>.used_ratio` / `.exceeded` / `.warning` | 五个维度（read_rows / write_bytes / duration / amplification / reject_rate）分别用 `execution_run` 汇总值或序列末值与 `runtime_supervision_contract` 比较；`warning = ratio ≥ warn_threshold_pct/100` |
| `terminal` | `terminal_status` / `interrupted_by_supervision` / `job_stop_called` / `error_message_kind` | `run.status`；`job_stop_called` 取自 `failure_snapshot.reason ∈ {supervision, manual_stop, cancel}`；`error_message_kind` 由 `classify_error_message` 得到 |
| `metrics_shape` | `metrics_points` / `metrics_monotonic` | 点数；累计值序列出现下降 → `monotonic=false`（SeaTunnel 重启或计数回绕，会让放大比/吞吐解读失真，需在结论中标注） |

边界：`execution_metric` 为空 → 各吞吐键为 `None`/0，分类表不得因缺信号而误判（条件求值时缺失键视为「不满足」）；`error_total = 0` 时所有 `share` 定义为 0（不做除零）。

### 6.2 确定性故障分类表（`taxonomy.py`）

条件为声明式（对 §6.1 扁平化后的信号键求值），**按 `priority` 升序取首条命中为主结论**；`confidence` 由规则自带，不由 LLM 覆盖；`evidence_keys` 必填且非空（保证可解释）。

| code | priority | category | 条件（示意） | 结论要点 |
|---|---|---|---|---|
| `D-001` | 10 | `source_schema_drift` | `error_mix.E_SCHEMA_DRIFT.count > 0` 或 `source_schema_drift_hint = true` | 源端表结构变更（列改名/类型变化/新增列/表重建）；冻结版本依据的 Profile 已失效 |
| `D-002` | 20 | `field_type_parse` | `error_mix.E_TYPE_CAST.share ≥ 0.5` 且 `error_mix.E_SCHEMA_DRIFT.share < 0.05` | 源端出现无法按契约类型解析的值（脏值 / 格式混杂 / 自由文本化） |
| `D-003` | 21 | `field_type_parse` | `error_mix.E_NULL_PK.share ≥ 0.5` | 主键/增量字段大面积空值；可能是源端事务未提交或字段改空 |
| `D-007` | 35 | `target_write_rejected` | `error_message_kind ∈ {target_permission_denied, partition_missing, table_not_found, schema_mismatch_target}` | 目标端拒绝写入（权限/分区/表缺失或结构不匹配）；影子表或错误表本身没准备好 |
| `D-004` | 30 | `connection_interrupted` | `error_total == 0` 且 `metrics_points ≥ 2` 且 `throughput_last == 0` 且 `error_message_kind ∈ {connection_refused, connection_reset, auth_failed, timeout}` | 数据源/目标端连接中断或认证失效；数据面直接断流而非写错误表 |
| `D-005` | 40 | `resource_exhausted` | `error_message_kind ∈ {oom, memory}` 或（`budget_pressure.amplification.used_ratio > 0.8` 且 `throughput_volatility > 0.5`） | 内存/并发资源不足，吞吐剧烈抖动或 OOM |
| `D-006` | 50 | `budget_exceeded` | 任一 `budget_pressure.<dim>.exceeded = true` | 超预算硬中断；`reject_rate` 维度指向质量分流（配合 be-17 报告的规则命中） |
| `D-008` | 15 | `job_killed` | `job_stop_called = false` 且 `error_message_kind ∈ {killed, canceled, sigterm}` | 作业被外部终止（非我方 stop）：集群重调度、K8s/容器驱逐或人工 kill |
| `D-999` | 999 | `unknown` | 无条件（兜底） | 无确定性结论；返回完整信号清单供人工判断，`confidence="low"` |

设计要点：

- `D-008` 的 `job_stop_called = false` 约束避免了「我方硬中断被误判为作业被杀」；我方 stop 触发的中断应落到 `D-006`（超预算）。
- `D-001` / `D-007` 优先级高于 `D-006`：**先报最具体的因**（结构漂移、目标端拒绝），预算超限往往是结果而非原因。
- 新增故障模式的成本 = 表里加一行 + 一个 L1 夹具；不改 `signals.py` 也不改服务层。

`FaultCategory` 取值（本模块引入，需落 `models/enums.py`，见 §10）：`source_schema_drift` / `field_type_parse` / `connection_interrupted` / `resource_exhausted` / `budget_exceeded` / `target_write_rejected` / `job_killed` / `unknown`。
`Confidence` 取值：`high` / `medium` / `low`。
`SuggestedAction.code` 取值（前端按钮契约）：`INSPECT_ERROR_SAMPLES` / `RELAX_OR_CLEAN_RULE` / `REPROBE_METADATA` / `DIFF_VERSION` / `REVIEW_BUDGET` / `ADJUST_BUDGET_AND_REPREPARE` / `CHECK_DATASOURCE_CONNECTIVITY` / `CONTACT_DBA` / `MANUAL_INSPECT`。

### 6.3 可解释性校验

`validate_findings` 对每条 `Finding` 断言：`evidence` 非空，且每个 `evidence.key` 都能在 `flatten_signals` 的结果里查到。不满足的结论被剔除；若主结论被剔除且无其他命中，则整体降级为 `D-999 unknown`。这样「每条结论必须能追溯到具体信号」不是文案约定，而是**代码里的硬校验**——自由文本（LLM 输出）永远不进入 `possible_causes` / `suggested_actions`。

### 6.4 LLM 增强解释与投喂边界

- 调用：`settings.LLM_MODEL_DIAGNOSE`（`deepseek-reasoner`），`timeout = LLM_TIMEOUT_SEC`（90s），`max_tokens = 2048`。提示词由 `render_llm_messages` 生成，模板版本 `diag-v1` 记入 `llm.prompt_version`。
- 投喂内容（唯一来源）：`flatten_signals` 的键值表 + 确定性结论（`category` / `possible_causes` / `suggested_actions`）。**不投喂**：任何字段值、`error_record.reason` 的原始上下文、`payload_digest`（低熵值可被字典攻击）、连接串、`SecretReference`、`error_message` 原文、SeaTunnel 日志原文。
- 技术保障（而非仅约定）：投喂参数的类型是 `dict[str, float|int|str|bool]`，由 `DiagnosisSignals`（`extra="forbid"`）唯一产出；`services/diagnosis.py` 在调用前对 payload 做一次「键前缀白名单」断言（只允许 §6.1 列出的族前缀 + `error_message_kind` 这类标签键），任何非白名单键 → 拒绝调用并记 warning。
- 分工理由：分类必须可复现、可测试、可被 Benchmark 逐条断言（PRD §1.4 的拦截率/恢复率口径）；LLM 只做「把结构化结论写成通顺解释」这一不受保证影响的工作。若让模型参与判定，同一输入两次运行可能给出不同类别，L1 回归测试就无法成立。
- 降级路径：`LLMUnavailableError`（超时、限流、密钥缺失）→ `llm.status="unavailable"`、`llm.text=null`、写 structlog warning；接口照常返回 200 与确定性结论。`?require_llm=true` 时改为返回 `LLM_UNAVAILABLE`（503），供需要模型解释的自动化场景使用。
- 输出处理：模型文本原样展示（前端标注「模型生成，仅供参考」），**不解析为结构化字段**、不进入 `possible_causes`、不触发任何动作。

### 6.5 前端展示与导出

| 面板区 | 数据来源 |
|---|---|
| 结论卡 | `category`（中文标签映射）、`confidence` 徽标、`rule_code`、`possible_causes` |
| 建议动作 | `suggested_actions`（按钮按 `code` 路由到对应页面，`target` 给出跳转目标） |
| 证据表 | `evidence`（信号键 / 值），可展开 `signals` 全量 |
| 模型解释 | `llm.text`，`status != ok` 时显示「模型解释不可用，以下为确定性结论」 |
| 分流对照 | 复用 be-17 的 `error_code_dist` / `rule_hits` 图（同一 run 的数据，不在本模块重算） |
| 导出 | `export` 端点：`markdown` 用于人工留档，`json` 用于审计归档 |

## 7. 错误码与拒绝语义

| 触发条件 | 错误码 | HTTP | 是否写证据账本 |
|---|---|---|---|
| run 不是终止态（`running/queued/paused/rolling_back`） | `CONFLICT`（`detail.reason`） | 409 | 否（未改变事实） |
| run 为 `succeeded` 时请求诊断 | `CONFLICT`（`reason="no_failure_context"`） | 409 | 否 |
| run 不存在 | `NOT_FOUND` | 404 | 否 |
| 跨租户访问 run | `TENANT_MISMATCH` | 403 | 见 be-17 §10（缺事件类型） |
| 非 operator 调 `regenerate` | `ROLE_REQUIRED` | 403 | 是（协议类拒绝） |
| `regenerate` 缺 `Idempotency-Key` | `VALIDATION_ERROR` | 422 | 否 |
| 同 `Idempotency-Key` 不同请求体 | `IDEMPOTENCY_CONFLICT` | 409 | 否 |
| 读事实源失败（PG 查询失败） | `INTERNAL_ERROR` | 500 | 否（明细只在服务端日志） |
| LLM 不可用且 `require_llm=true` | `LLM_UNAVAILABLE` | 503 | 否 |
| LLM 不可用且未要求 | **不报错**，`llm.status="unavailable"` | 200 | 否 |
| `signals` 全空（无指标、无报告、无错误行） | 正常返回 `D-999 unknown` | 200 | 否 |

## 8. 安全与合规约束

- **脱敏默认开启**：`DiagnosisSignals` 的类型定义就是脱敏边界——字段里没有任何 `str` 类型承载业务值的槽位；`error_record` 只读 `payload_digest` / `field_name` / `error_code` / `rule_id`，**不存也不读原文**（错误表本身就没有）。
- **`error_message` 处理**：`services/diagnosis.py` 读 `execution_run.error_message` 后**只保留 `classify_error_message` 的类别标签**，原文不进入 signals、不进入 `failure_snapshot.diagnosis`、不进提示词、不写日志（日志只记 `error_message_kind` 与长度）。同时要求 be-14 / be-15 写入 `error_message` 时已完成脱敏（连接串与口令一律不写）。
- **LLM 上下文边界**：白名单键断言（§6.4）+ 类型层面无值；单测用哨兵验证接口层请求体不含哨兵字符串。
- **租户过滤**：所有查询带 `tenant_id`；`get_diagnosis` / `export` 也不例外。
- **不可变制品**：只读 `quality_report` / `error_record` / `preparation` / `pipeline_version`；唯一写入点是 `execution_run.failure_snapshot`（可变表），且只改 `diagnosis` / `diagnosis_history` 两个子键。
- **权限**：生成与重新生成需要 operator（写操作）；读取对项目内 maker / operator / auditor 开放（审计需要看得到结论与证据）。角色判定查 `role_assignment`，不信任 JWT 声明。
- **诊断不参与决策**：`DiagnosisDTO` 不被 be-16 / be-18 读取；代码层面 `engines/diagnosis` 不被 `services/publish.py` 或 `engines/supervision` import（可用 import-lint 单测断言）。
- **模型输出**：`llm.text` 作为不可信文本展示，前端必须转义渲染（禁 `v-html`），导出 Markdown 时对代码块内容做转义。

## 9. 测试要点

- **单元测试（纯函数，无 DB / 无 LLM）**
  - `extract_signals`：空 metrics、单点 metrics、累计值回绕（`monotonic=false`）、`error_total=0` 的除零防护、`throughput_drop_at_sec` 的四种边界（无跌落 / 跌落后恢复 / 末点跌落 / 全零）；
  - `classify_error_message`：关键词表每一类的正例 + 一段含连接串与口令的文本 → 只返回标签且不含原文片段；
  - `classify`：对七类故障各造一组扁平信号，断言 `category` / `rule_code` / `confidence`；断言确定性（同输入两次调用结果完全相等）；断言 `D-001`/`D-007` 优先于 `D-006`；断言我方 stop 的中断不会命中 `D-008`；
  - `validate_findings`：伪造 `evidence.key` → 结论被剔除；全部剔除 → 降级 `unknown`；
  - `flatten_signals` 的键集合快照测试（键集合是对外契约，改动必须同步本文与前端）。
- **集成测试（真实 PG）**
  - 用 be-20 的 **L1 假执行器**构造七类故障场景（源端 schema 漂移、类型解析异常、连接中断、OOM/资源不足、超预算硬中断、目标端写入拒绝、作业被杀），逐类断言分类结果与 `evidence` 非空；
  - 端到端串一次演示场景二：脏数据超限 → 硬中断 → `GET /diagnosis` 返回 `field_type_parse` 且第一条 evidence 指向错误码占比；
  - `regenerate` 保留历史（≤5 条）且 `failure_snapshot` 的其他子键（`swap` / `quality`）不被覆盖；
  - 反例：`running` 的 run 请求诊断 → `CONFLICT`；跨租户 → `TENANT_MISMATCH`；非 operator 调 `regenerate` → `ROLE_REQUIRED`。
- **降级与安全测试**
  - 假 LLM Provider 抛 `LLMUnavailableError` → 接口 200、`llm.status="unavailable"`、确定性结论完整；`require_llm=true` → 503 `LLM_UNAVAILABLE`；
  - 哨兵测试：让 run / metrics / report / error_record 中含唯一哨兵字符串，捕获假 Provider 收到的 messages，断言不含哨兵，也不出现在 `failure_snapshot` 与日志中；
  - import 边界断言：`engines/diagnosis/*` 不 import `clients/`、`core/errors.py`、`fastapi`；`services/publish.py` 不 import `services/diagnosis`。

## 10. 未决与风险

| 事项 | 现状 | 验证方式 |
|---|---|---|
| `FaultCategory` / `Confidence` 尚未进 `models/enums.py` | 取值定义在 `engines/diagnosis/taxonomy.py`，但会落 JSONB 并被前端消费，属于对外契约 | 建议上移到 `models/enums.py`（与 `EvidenceEventType` 同级）；上移前以本文表格为准 |
| 诊断生成无证据事件类型 | `EvidenceEventType` 中没有 `diagnosis.generated` / `diagnosis.feedback` | 建议新增两个类型；在此之前诊断只落 `failure_snapshot`，不写账本（账本缺失不影响可解释性，但审计链路不一致） |
| 人工反馈闭环 | **本轮不实现持久化**：不建表、不给前端按钮 | 规则表调优改走 be-20 的 L1 用例回归（可复现、可版本化）；M4 若需要线上反馈，再用 `diagnosis.feedback` 事件承载标注 |
| `sea_tunnel` 日志摘要 | 本模块**不读** SeaTunnel 日志文件（跨进程、可能含敏感参数），只用 `error_message_kind` 与指标推断 | M3 实机确认 SeaTunnel Zeta 是否提供结构化作业状态/退出码接口；若有，可新增一族信号 `job_exit`（不改分类表结构） |
| `deepseek-reasoner` 的稳定性与成本 | 90s 超时、2048 输出的取值未实测；reasoner 会产生 reasoning token 计入费用 | M4 用 20 个真实失败场景统计一次成功率与耗时分布，必要时把 `max_tokens` 落成 Settings |
| 相同 `generated_at` 的并发 regenerate | 「读-改-写」`failure_snapshot` 在同一事务内，但两个并发事务仍可能后写覆盖先写 | 用 `SELECT … FOR UPDATE` 锁 `execution_run` 行（M4 实现）；当前 M3 由 `Idempotency-Key` 兜底 |
| 成功运行的「运行诊断」 | 当前不支持（读 be-17 报告即可） | M4 评估是否需要「成功但接近预算」的提示（属于告警，不是根因诊断） |
