## 1. 职责与边界

- **做什么**
  - 定义并实现监督判定：五维度（读行数 / 写字节 / 时长 / 放大比 / 拒绝率）对 `runtime_supervision_contract` 的越界判定，纯函数，输出 `ok | warn | interrupt`。
  - 周期采集活跃 run 的指标，**增量**追加 `execution_metric` 并更新 `execution_run` 的汇总值。
  - 预警时发告警指标与 `supervision.warning` 证据事件（带降频规则）。
  - 硬中断：经 `ToolBroker` 调 `seatunnel.stop`，保存**脱敏**失败快照，写 `run.interrupted`，把 run 置 `interrupted`。
  - 采集降级：SeaTunnel 指标不可用时退化为「只查目标端错误表 + 时长自计时」。
- **不做什么**
  - 不做质量契约判定与数据分流（be-17）、不做 Swap 与回滚（be-18）、不做 LLM 根因诊断（be-19，本模块只暴露 `diagnose_run` 的**入口**，其实现属 be-19）。
  - **不让 LLM 参与监督判定**——判定是纯函数，与 PDP 同理：超预算必须确定性地中断（PRD §6.5.2）。
  - 不直接调用 SeaTunnel（必须经 `ToolBroker.execute(ToolName.SEATUNNEL_STOP, token, args)`）。
  - 不实现 Capability 签发（be-05）：硬中断所需的 Capability 由 be-14 在必要时机签发并提供给本模块。
  - 不搬业务数据：只读指标与错误表**计数**，不读错误行原文（`error_record` 只有 `payload_digest`）。
- **所在分层**：`engines/supervision/` 是**纯函数层**（无 IO / 无 DB / 无 Redis / 无网络 / 无 LLM，`mypy --strict` 覆盖）→ `services/supervision.py`（编排、事务、采集）→ `tasks/supervision.py`（Celery 编排）。

```python
# engines/supervision/models.py
class Dimension(StrEnum):
    REJECT_RATE = "reject_rate"
    WRITE_BYTES = "write_bytes"
    AMPLIFICATION = "amplification_ratio"
    READ_ROWS = "read_rows"
    DURATION = "duration"

class Severity(StrEnum):
    OK = "ok"
    UNKNOWN = "unknown"     # 指标不可用
    WARN = "warn"
    INTERRUPT = "interrupt"
class MetricSample(BaseModel):
    read_rows: int | None = None
    written_rows: int | None = None
    written_bytes: int | None = None
    read_bytes: int | None = None
    reject_rows: int | None = None
    valid_rows: int | None = None
    reject_rate: float | None = None
    duration_sec: int = 0          # 自计时，永远可用
class SupervisionContractDTO(BaseModel):     # 镜像 runtime_supervision_contract，不含 ORM
    max_read_rows: int
    max_write_bytes: int
    max_duration_sec: int
    max_amplification_ratio: float
    max_reject_rate: float
    warn_threshold_pct: int = 80

class DimensionVerdict(BaseModel):
    dimension: Dimension
    severity: Severity
    observed: float | None
    limit: float | None
    ratio_pct: float | None      # observed / limit * 100，用于前端进度条

class SupervisionVerdict(BaseModel):
    severity: Severity
    reason: DimensionVerdict | None            # 决定性维度（interrupt 时用于写失败快照）
    warnings: tuple[DimensionVerdict, ...]     # 所有达到 warn 的维度
```

## 5. 核心流程

### 5.1 采集循环（beat 每 30 s）

```
① tasks.supervision.collect_active_runs()
② 取活跃 run：SELECT id FROM execution_run WHERE status='running'
     ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 20        -- 只监督 running（paused 语义见 §10 第 7 条）
③ 逐条 services.supervision.collect_run(run_id)：
   a. 载入 contract（经 pipeline_version）+ 上一次 metric 点（用于算增量与瞬时吞吐）
   b. 采集：SeaTunnel client.metrics(job_id) → 行数/字节/状态；目标端错误表
      SELECT count(*), error_code FROM error_record WHERE run_id=:id GROUP BY error_code → 拒绝率/错误码分布；
      时长 = now - run.started_at（自计时，不依赖 SeaTunnel）
   c. 组装 MetricSample（缺失项 None）→ INSERT execution_metric → UPDATE execution_run 汇总列
   d. engines.supervision.evaluate(sample, contract, elapsed_sec) → verdict
   e. interrupt → interrupt_run()；warn → should_emit_warning() 通过则写 supervision.warning；ok → 无动作
   f. 作业状态 FAILED/FINISHED → 交给 be-17/be-18 推进后续阶段，本模块不再采集
④ 返回 {"collected": n, "warned": w, "interrupted": i}
```

采集频率固定 30 s（beat 的 `collect-run-metrics`，`expires=25` 防重入）。**采集本身不写状态**——除 interrupt 路径外，`execution_run.status` 只能由 be-14 的状态机写。

### 5.2 指标来源分工

| 指标 | 来源 | 可信度与理由 |
|---|---|---|
| `read_rows` / `written_rows` / `written_bytes` | SeaTunnel `metrics(job_id)` | 控制面只能从数据面拿到，属唯一来源；口径待实测（见 §10 第 4 条） |
| `read_bytes` | SeaTunnel `metrics(job_id)` | 用于算放大比；不可用则放大比维度判 `unknown` |
| `duration_sec` | **控制面自计时**（`now - started_at`） | 不依赖任何外部系统，永远可用 |
| `reject_rows` / `valid_rows` / `reject_rate` / `error_code_dist` | **目标端错误表 `error_record`**，经 be-17 的 `clients/target/errors_table.py: count_by_code(run_id)` 聚合 | 最可信：不受 SeaTunnel 指标口径影响，反映的是**最终落库结果**（概要设计总纲 §8 明确此分工）；分布同时用于失败快照与 be-19 根因诊断 |

拒绝率口径：`reject_rate = reject_rows / (reject_rows + written_rows)`；当 `reject_rows + written_rows == 0` 时为 `None`（判 `unknown`，避免除零与「刚起步就报拒绝率 100%」的误报）。

### 5.3 增量上报（避免高频全量刷新）

- `execution_metric` **只追加**，每采集点一行；`execution_run` 上是**汇总值覆盖**（不是累加），因为 SeaTunnel 指标本身是累计值——覆盖比 `+=` 更安全（`+=` 在重投时会重复累加）。采集只读**上一次** `execution_metric` 点（`ORDER BY ts DESC LIMIT 1`）算瞬时吞吐与增量；错误表查询走 `ix_error_record_run_id_error_code` 的索引聚合，不 `SELECT *`（错误表可能有百万行）。
- 前端 2 s 轮询读 `execution_run` 的汇总列 + 最近 N 个 metric 点，因此**写放大只发生在采集侧（30 s 一次）**。

### 5.4 硬中断路径（逐步）

```
1. evaluate() 返回 severity = interrupt，reason = 决定性维度
2. services.supervision.interrupt_run(run_id, reason_dimension)
   2.1 幂等闸门：UPDATE execution_run SET status='interrupted' WHERE id=:run_id AND status='running'
       （rowcount=0 → 已中断/已终态，直接返回）
   2.2 签发 stop 的 Capability：CapabilityIssuer.issue(preparation_id=..., subject_id=run.triggered_by,
       tool=ToolName.SEATUNNEL_STOP, env=..., artifact_sha256=preparation.artifact_sha256, ..., now=now)
       → 证据 capability.issued（与 be-14 的 Commit 用同一条签发路径）
   2.3 **停止命令随 Outbox 投给 Worker**（实现偏差，见 §11）：写一条
       `outbox_message(topic=Topic.RUN_STOP, payload={run_id, capability, reason,
       subject_id}, idempotency_key=f"supervision-stop:run:{run_id}")`，
       由 `tasks/execution.stop_run` 在 Worker 里执行
       `ToolBroker.execute(ToolName.SEATUNNEL_STOP, token, SeatunnelStopArgs(
       run_id=run_id, job_id=row.seatunnel_job_id, reason=...), ctx=ExecutionContext(
       caller="worker", ..., actor_id=subject_id, run_id=run_id))`
       （`job_id` **不进载荷**：它是 Worker 侧从 `execution_run.seatunnel_job_id` 现读的，
       载荷里带一份就有两个真相；载荷只带令牌与主体）
       ├─ stop 为 P2：注册表标 consumes_capability=True，验签 + jti 原子消费 → clients/seatunnel/client.stop(job_id)
       └─ 失败：重试 3 次（1/2/4 s）；仍失败 → snapshot.needs_manual_stop=true + 告警，
          run 仍置 interrupted（作业可能还在跑，不能因为 stop 失败就放弃中断流程）
       ⚠️ 本模块运行在 Worker 里，而 Worker 的 broker **刻意不带签发器**（`tasks/execution._broker`），
       所以这里不能就地执行再补一条消息——那等于给「被攻陷的 Worker」发签名能力。
       代价：库里的 `interrupted` 先于作业真的停下，中间态靠 `needs_manual_stop` 显式暴露。
       ⚠️ payload 必须带 `subject_id`：broker 在 BINDING 阶段拒 `actor_id=None`
       （`harness/broker.py::_expected_binding`），缺了它这条停止命令**永远执行不了**，
       而假 broker 的单测看不出来（只表现为「命令投出去了、作业没停」）。
   2.4 save_failure_snapshot()：最后 20 个 metric 点 + error_code_dist + 各维度实测/限额
       + 决定性维度 + 中断时刻；**全部脱敏**（无行级数据、无配置、无连接信息）
   2.5 写证据事件 run.interrupted（payload 闭集合：run_id / reason / dimension / observed /
       limit / job_id / needs_manual_stop。**observed 与 limit 写成字符串**——
       `harness/ledger.py` 拒 float：平台相关的 repr 会让同一语义在两台机器上算出不同哈希，
       而账本是靠哈希链自证的）
       → UPDATE execution_run SET finished_at=now(), error_message='SUPERVISION_INTERRUPTED'
       → 告警（Prometheus 计数器 + 钉钉 webhook，受 ALERT_ENABLED 控制）
3. run.status = interrupted → 允许受管回滚（be-18 的 target.rollback_cleanup）
```

语义与 `ErrorCode.SUPERVISION_INTERRUPTED` 一致：该错误码用于**面向用户解释**已发生的硬中断（be-14 在 `GET /runs/{id}` 的 `failure_snapshot` 中回填），本模块不直接抛给 HTTP 层。

### 5.5 人工动作与监督中断的区别

| 动作 | 写入者 | 是否调 SeaTunnel | 目标状态 | 可否恢复 | 证据事件 |
|---|---|---|---|---|---|
| 监督硬中断（含质量拒绝率超限，二者同一条路径） | `services/supervision.interrupt_run` | `seatunnel.stop` | `interrupted` | 不可恢复为 running；可进入受管回滚 | `run.interrupted` |
| 人工暂停 | `services/run.request_pause`（be-14） | 否（暂停后续阶段推进） | `paused` | 语义上可恢复（本文无 resume 接口，见 be-14 §10.3） | 记 `run` 相关的 structlog，无专用事件 |
| 人工取消 | `services/run.request_cancel`（be-14） | `seatunnel.stop` | `cancelled` | 不可恢复 | 由 be-14 记 `run.failed`（无专用 `run.cancelled` 事件，见 §10 第 5 条） |

三者的共同点：真正的停止动作都必须经 `ToolBroker` 调 `seatunnel.stop`；区别在**谁写状态**（监督写 `interrupted`，操作员写 `paused`/`cancelled`）与**是否允许回滚**。另需区分易混的一条：**作业结束后**质量报告 `passed=False` 由 be-17 置 `failed` 并写 `failure_snapshot.quality`，与运行中的拒绝率硬中断（本模块，置 `interrupted`）不是同一条路径；同一 run 两者只有一条会命中（中断后不再产出报告）。

## 6. 关键算法与规则

### 6.1 判定表达式与边界

设 `L` 为限额、`w = warn_threshold_pct`（默认 80）：

| 维度 | observed | limit | interrupt 条件 | warn 条件 |
|---|---|---|---|---|
| `reject_rate` | 目标端算出的比率 | `contract.max_reject_rate` | `observed >= limit` | `observed >= limit * w / 100` |
| `write_bytes` | `written_bytes` | `contract.max_write_bytes` | `observed >= limit` | 同上 |
| `amplification_ratio` | `written_bytes / read_bytes` | `contract.max_amplification_ratio` | `observed >= limit` | 同上 |
| `read_rows` | `read_rows` | `contract.max_read_rows` | `observed >= limit` | 同上 |
| `duration` | `elapsed_sec`（自计时） | `contract.max_duration_sec` | `observed >= limit` | 同上 |

**边界约定**：一律 `>=`（等于限额即越界），warn 与 interrupt 都用 `>=`。理由是限额是「不得超过」的语义——`>=` 让 `max_reject_rate = 0.05` 与「拒绝率恰好 5%」一致，且避免 `>` 在浮点比较下的静默放行。`warn` 与 `interrupt` 同时满足时取 `interrupt`。

**`amplification_ratio` 的特殊处理**：`read_bytes` 为 `None` 或 `0` 时，维度判 `unknown`（不算 `0` 或 `inf`）——`read_bytes = 0` 说明指标尚未上报，此时把比率当成极大值会产生误中断。

  ⚠️ 这一维的**来源**要盯住：`clients/seatunnel/models.py::JobMetricsDTO.read_bytes` 起初不存在，
  于是本维度恒判 `unknown`——阈值配着、用例绿着、**永远不会开火**（见 §11 2026-10-16 第二条）。
  `read_bytes = 0` 因此有两种含义：引擎没报这个计数器（占绝大多数），或真的读到 0 字节。

### 6.2 多维度越界时的优先级

```python
# ① 拒绝率：数据质量失守，继续跑只会把脏数据写满目标端
# ② 写字节：目标端存储是硬约束 ③ 放大比：异常通常是逻辑错误（如笛卡尔积）
# ④ 读行数：源端压力 ⑤ 时长：最不具体，放最后
DIMENSION_PRIORITY: tuple[Dimension, ...] = (
    Dimension.REJECT_RATE, Dimension.WRITE_BYTES, Dimension.AMPLIFICATION,
    Dimension.READ_ROWS, Dimension.DURATION,
)
```

`worst()` 先比 `severity`（`interrupt > warn > unknown > ok`），同级再按 `DIMENSION_PRIORITY` 取靠前的作为 `reason`。这个顺序决定**失败快照里记哪个原因**；所有达到 warn 的维度仍然全部进 `warnings`，前端不会丢信息。顺序固定为常量，任何调整都改 `thresholds.py` 一处并补单测。

### 6.3 指标不可用时的退化路径

| 缺失项 | 退化策略 | 影响 |
|---|---|---|
| `metrics()` 返回 `None`（SeaTunnel 指标接口不可用） | 只采 `duration`（自计时）+ `reject_rate`（查错误表）；`read_rows` / `write_bytes` / `amplification` 判 `unknown` | 读行数、写字节、放大比**不参与判定**；拒绝率与超时仍能硬中断（覆盖演示场景二的「脏数据超限」用例） |
| `error_record` 查询失败 | `reject_rate` 判 `unknown` | 只剩时长可判定 |
| 两者都不可用 | 全部 `unknown` | 只得靠时长；写 warning 提示「监督降级运行」并告警（本模块必须让降级**可见**，不能静默退化为无监督） |
| run 处于 `queued` | 不采集 | 尚未提交作业，无指标可言 |

退化路径**不改变判定语义**：`unknown` 维度既不触发 warn 也不触发 interrupt，绝不用 0 代替缺失值（用 0 会让所有维度看起来正常，是更危险的错误）。

### 6.4 预警降频规则

`supervision.warning` 每 30 s 一条会刷爆账本（一天 ≈ 2880 条/run），因此设三道闸门，`should_emit_warning()` 逐条判定：

| # | 规则 | 判据 |
|---|---|---|
| 1 | **首次越线必写** | 该 run 尚无 `supervision.warning` 事件 → 写 |
| 2 | **维度变化或升级必写** | 最近一条 warning 的 `payload.dimension` 与本次不同（换维度说明问题性质变了），或维度相同但本次已从 warn 升到 interrupt（随后立刻走中断路径）→ 写 |
| 3 | **同类降频** | 否则：同一维度且距上一条 warning `< 300 s` → 不写；`>= 300 s` → 写 |

实现：查 `evidence_event` 中 `event_type='supervision.warning'`、`subject_type='run'`、`subject_id=str(run_id)` 的**最近一条**（`ORDER BY seq DESC LIMIT 1`，走 `ix_evidence_event_subject`）。（`subject_type` 写作 `'run'` 而不是 `'execution_run'` 是实现偏差，见 §11：`services/governance.py` 把 `execution_run_id` 过滤映射成 `subject_type="run"`，写成 `execution_run` 的话这些事件在运行时间线里**一条都看不到**。）**不引入新的 Redis 键**：`core/redis.py` 的键空间是封闭清单（`KEY_LOGIN_FAIL` / `KEY_TOKEN_DENY` / `KEY_CAP_CONSUMED` / `KEY_META_CACHE` / `KEY_GEN_LOCK`），需要新键时应先加进 `core/redis.py` 再引用（见 §10 第 6 条）。用 DB 查询换取的代价是每次预警多一次索引查询，30 s 一次可接受。

### 6.5 幂等与并发

| 场景 | 处理 |
|---|---|
| 两个采集任务并发处理同一 run | `collect_active_runs` 用 `FOR UPDATE SKIP LOCKED` 选 run；`supervise_run`（Outbox 触发）可能与 beat 轮询撞车 → 允许，但 `execution_metric` 的 `ts` 用「取整到采集周期」的值（`ts = floor(now / 30s) * 30s`），使同一周期的重复采集**写入同一时刻的点**，前端与判定看到的序列不出现重复点。若仍需严格唯一，则加 `uuk_execution_metric_run_id_ts`（见 §10 第 2 条） |
| 重复中断请求（含 `interrupt_run` 被 Outbox 重投） | `2.1` 的条件 UPDATE（`WHERE status='running'`）保证只有一个赢家；输家 `rowcount=0` 直接返回，不重复调 `seatunnel.stop`、不重复写快照与事件 |
| run 在采集中被人工 cancel | 条件 UPDATE 输给 be-14 的 `cancelled`；监督侧不覆盖（采集只更新指标汇总列，不无条件写状态） |
| 采集写入与 be-14 的 `apply_transition` 并发 | 采集只写指标列 + `finished_at`（在 interrupt 分支内），状态转移走条件 UPDATE，互不覆盖 |

## 7. 错误码与拒绝语义

本模块是**内部监督链路**，无对外 HTTP 拒绝；`engines/` 抛 Python 异常，`services/` 映射为状态与事件。

| 触发条件 | 表现形式 | 写证据账本 |
|---|---|---|
| 预算维度达到 warn | 告警指标 + `supervision.warning`（受 §6.4 降频约束） | **是** |
| 预算维度达到 interrupt | `seatunnel.stop` + 失败快照 + `run.interrupted` + `status=interrupted` | **是** |
| `seatunnel.stop` 失败（重试后仍失败） | `failure_snapshot.needs_manual_stop = true` + 钉钉告警；run 仍 `interrupted` | 是（`run.interrupted` payload 记 `stop_ok: false`） |
| 全部维度 `unknown`（监督降级） | 告警（Prometheus `supervision_degraded_total`）+ 一条 `supervision.warning`（`dimension='degraded'`） | 是（同一条事件） |
| run 状态已不是 `running`（中断竞态输家） | 静默返回，记 structlog `supervision_interrupt_noop` | 否 |
| 契约缺失（`pipeline_version.supervision_contract_id` 指向的行不存在） | `INTERNAL_ERROR`（数据完整性错误，不是业务拒绝）+ 告警 | 否 |

面向用户解释的中断原因通过 `ErrorCode.SUPERVISION_INTERRUPTED`（既有）与 `failure_snapshot.reason_dimension` 呈现；本模块**不自造错误码**。

## 8. 安全与合规约束

- **PDP 与监督都不用 LLM**：`engines/supervision/` 只依赖 Pydantic + 标准库；`mypy --strict` 覆盖，且 import 图检查可证明无 LLM / 无 DB。
- **副作用唯一出口**：本模块唯一的外部写动作是停止作业，必须 `ToolBroker.execute(ToolName.SEATUNNEL_STOP, token, args)`；停止需要 Capability（工具注册表：P2，必需）。**不得**直接 `import clients.seatunnel` 调 `stop`。
- **失败快照脱敏**：`failure_snapshot` 只允许包含
  ```
  {reason: "supervision", reason_dimension, observed, limit, ratio_pct, interrupted_at, job_id,
   metric_points: [{ts, read_rows, written_rows, written_bytes, duration_sec, reject_rate}],
   error_code_dist: {"E_TYPE_CAST": 1203, ...}, needs_manual_stop: bool, stop_ok: bool}
  ```
  `reason` 取值与 be-19 的约定一致（`supervision` / `manual_stop` / `cancel`）；同列的 `quality` / `swap` / `diagnosis` 子键分别归 be-17 / be-18 / be-19，本模块写快照时**只更新上述键、不得整体覆盖该列**。**禁止**出现：错误行原文（`error_record` 本来也只有 `payload_digest`）、HOCON 内容、连接串、表数据样本、凭据信息。写入前由 `services/supervision.save_failure_snapshot` 用白名单构造 dict（不是"过滤掉危险键"，而是"只放白名单键"）。
- **租户过滤**：采集与中断的每一步查询带 `tenant_id`；`collect_active_runs` 是跨租户的 beat 任务，因此必须显式带 `tenant_id` 到各 service 调用（be-02 的 `system_actor` 或按 run 取出的 `project_id`/`tenant_id`），**不得**出现不带租户条件的全表更新。
- **证据账本与可观测**：`supervision.warning` / `run.interrupted` 均经 `harness.EvidenceLedger.append()`（payload 已脱敏）；Prometheus 指标（be-21 接入）`supervision_evaluate_total{severity}` / `supervision_warning_total{dimension}` / `supervision_interrupt_total{dimension}` / `supervision_degraded_total` / `supervision_collect_duration_seconds`。
- **性能**（PRD §10.4）：单次采集的 DB 写入 = 1 INSERT + 1 UPDATE + ≤2 聚合查询；30 s 周期下即使 100 条并发 run 也只是 100 次轻量事务。

## 9. 测试要点

**单元测试（纯函数，本机，`tests/`）**

- `dimension_verdict` 边界矩阵：`observed = 0.79L / 0.8L / 0.99L / 1.0L / 1.01L` 五档 × 五维度；断言 `0.8L → warn`、`1.0L → interrupt`（`>=` 语义）、`0.79L → ok`。
- `unknown` 传播：`observed is None` 或 `limit is None` → `unknown`；`read_bytes = 0` 时放大比判 `unknown`（不是 interrupt）。
- `worst` 优先级：构造 `{read_rows: interrupt, reject_rate: interrupt}` → `reason.dimension == reject_rate`；`{duration: interrupt, write_bytes: warn}` → 断言取 `duration`（interrupt 优先），而 `warnings` 里**恰好包含** `write_bytes`。
- `DIMENSION_PRIORITY` 覆盖全部 `Dimension` 成员（防止新增维度后忘加优先级——断言集合相等）；`budget_from_settings` 的默认值与《需求对齐记录》§四 一致（`1e8` / `50 GiB` / `7200` / `1.5` / `0.05` / `80`）。
- `should_emit_warning` 的三条规则各一个用例（用假的"最近一条事件"数据；若判定部分无法脱离 DB，则至少覆盖三条规则的分支）。

**集成测试（真实 PG，标 `integration`）**

- `collect_run`：造一条 `running` run + 可控的假指标源，跑两次采集，断言 `execution_metric` 两行、`execution_run` 汇总列被覆盖（不是累加）。
- **硬中断端到端 + 中断幂等**：注入超预算指标 → 断言 ① `seatunnel.stop` 只被调用一次（用假 broker 计数）② `failure_snapshot` 已写且不含任何禁用键（白名单断言）③ `evidence_event` 新增 `run.interrupted` ④ `status == interrupted`；并发两次 `interrupt_run`（或同一消息重投两次）断言 `stop` 调用次数 = 1、`failure_snapshot` 只写一次。
- **预警降频**：连续 10 个采集点全部超 warn，断言 `supervision.warning` 事件数远小于 10（按 §6.4 规则计算期望值），且**首次**必然写了。
- **L1 假执行器注入（对应《需求对齐记录》§二.6 的 Benchmark L1）**：`FakeSeatunnelExecutor` 可编程返回三种故障——① 超预算（`written_bytes` 直接给 2× 限额）② 超时（`duration_sec` 给 `max_duration_sec + 1`）③ 格式错乱（指标字段缺失/为 `None`，验证退化路径不中断且不误报）。三种场景各断言最终 `status` 与 `failure_snapshot` 内容。
- **降级路径与并发**：`metrics()` 返回 `None` 时靠错误表拒绝率仍能中断（演示场景二主路径），两者都不可用时只靠时长中断并断言有 `degraded` 预警；两个采集任务同周期并发时，断言 `execution_metric` 不出现同一 `ts` 的重复语义点（或按 §10 第 2 条加唯一约束后断言约束生效）。

## 10. 未决与风险

1. **SeaTunnel 指标接口可用性未验证**（与 be-15 §10 第 1 条同一件事）：若 Zeta 不提供 `job-metrics`，则本文 §6.3 的第二行成为**常态**而非降级——读行数/写字节/放大比三个维度将长期 `unknown`，只有拒绝率与时长真正生效。验证方式：M3 实机 `curl` 确认；若不可用，需重新评估「靠什么把 `max_read_rows` 落地」，可能改为「查源端表的 `count(*)`（对源库有压力，需评估）」或「接受该维度在 M3 不可用并在文档与前端明示」。
2. **`execution_metric` 缺少 `(run_id, ts)` 唯一约束**：并发采集可能写入语义重复的点（`ts` 取整到 30 s 周期可缓解但非强保证）。建议加 `UniqueConstraint("run_id", "ts")`（`uv run alembic revision`）。验证方式：加约束后重跑并发用例；若采集抖动导致 `ts` 抖动，则改为「先按周期取整再写入」并在 service 层补一条 upsert。
3. **warning 的去重依据是账本查询**：在极高并发（数百 run 同时预警）时会给账本表带来额外的读压力。验证方式：M3 用 100 run 压测 `collect_active_runs` 的单轮耗时；若超过采集周期的一半，再考虑引入 Redis 键（**届时必须先按 §8 的规范把键模板加进 `core/redis.py`**，不得在业务代码里裸写键名）。
4. **`written_bytes` / `read_bytes` 的口径未确认**：Zeta 上报的是逻辑数据字节还是压缩后字节、是否含 header，直接影响 `max_amplification_ratio = 1.5` 的命中率。验证方式：演示场景一实跑一次，把 Zeta 指标与 Doris 侧实际存储增量对比后，在 `thresholds.py` 注释记录结论并可微调默认值（默认值的最终裁定权在《需求对齐记录》，变更需追加一条）。
   **2026-10-16 进展**：`read_bytes` 已进 `JobMetricsDTO` 并被 `services/supervision._sample` 采用（此前硬写 `None`，见 §11），但**键名未经真机核对**——本地没有 SeaTunnel。解析处接受 `readBytes` / `readBytesTotal` / `sourceReceivedBytes` 及键名含 `receivedbytes`、`readbytes` 的前缀式计数器；认不出时把**未识别的数字计数器键名**记一条 debug（只记键名不记值），即校准线索。真机第一件事：跑一次演示场景一，看这行 debug 是否出现、`extra` 里有哪些计数器，据此定死键名。
5. **`run.interrupted` 与人工取消共用事件类型**：`EvidenceEventType` 没有 `run.cancelled` / `run.paused`，因此人工取消目前只能记 `run.failed`（由 be-14 决定），人工暂停无专属事件。建议追加 `run.cancelled` / `run.paused` 两个取值（本轮不自造）。验证方式：fe-06 的事件时间线需要区分时提出，追加取值只需改 `models/enums.py` + 一条 migration。
6. **`supervise_run` 与 `collect_active_runs` 的职责边界**：本文让两者并存（前者消除首采窗口，后者兜底续采）；若 be-14 最终改为纯轮询，则 `etl.run.supervise` topic 应删除（本文与 be-14 §10 第 2 条必须同时改）；若保留，需确认 `execution_metric` 的唯一约束（第 2 条）已落地，否则并存会放大重复点概率。
7. **`paused` run 不采集**：本文的采集条件是 `status='running'`。若 be-14 §10.3 把 `paused` 改为「真正停在 SeaTunnel 侧」，则 `paused` 也无需采集；若 `paused` 期间作业仍在跑（本文默认语义），则**必须把 `paused` 纳入采集范围**，否则暂停期间失去监督。验证方式：be-14 定稿 `paused` 语义后同步本节与 §5.1 第 ② 步。
