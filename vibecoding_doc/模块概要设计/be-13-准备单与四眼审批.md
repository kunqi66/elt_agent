## 1. 职责与边界

- **做什么**
  - 实现 Prepare：把 `pipeline_version` 的冻结事实固化为一条 `preparation`（不可变，仅 `status` 可改）。
  - 调 be-07 的 `engines/policy` 得出 `risk_level` 与 `required_slots`（纯规则，无 LLM）。
  - 实现 Approve：按职责槽收集 `approval_decision`，强制四眼与职责分离，接受 approve / reject / return 三种决定。
  - 维护 `preparation.status` 的流程位置与过期判定（`expires_at` → `PREPARATION_EXPIRED`）。
  - 向 be-14 暴露 `assert_committable()`：Commit 前的最终一致性校验（指纹 / 审批齐备 / 未过期 / 策略未阻断）。
  - 把每一次准备、每一次审批、每一次自批尝试写入证据账本。
- **不做什么**
  - **不签发 Capability、不创建 `execution_run`、不写 `outbox_message`**——那是 be-14 的 Commit。Prepare 阶段零外部副作用。
  - **不调用任何 `ToolName`**（无 DDL、无 SeaTunnel、无目标库写入、无元数据探查）。
  - 不修改 `pipeline_version` 及其四件制品（🔒 不可变，改动只能冻结新版本 → 产生新 preparation）。
  - 不判定「谁能当审批人」——角色授予属 be-02；本模块只**校验**已授予的角色。
  - 不实现 Commit 路由（`POST /api/v1/runs` 属 be-14）。
- **所在分层**：`api/preparations.py`（校验 / 权限 / 调 service / 组装响应）→ `services/preparation.py`、`services/approval.py`（编排 + 事务边界）→ `models/`（ORM）、`harness/ledger.py`（证据）、`engines/policy`（PDP）。依赖方向单向向下，不 import fastapi 到 services 及以下。

## 5. 核心流程

### 5.1 Prepare 时序（`create_preparation`）

```text
Maker → api/preparations → services/preparation
  ├─ 校验角色=maker / 项目成员 / tenant_id 一致
  ├─ 载入 pipeline_version + 四件制品 + metadata_profile；Profile 过期 → METADATA_PROFILE_EXPIRED
  ├─ 算 input_fingerprint（profile.sha256 + 参数摘要，含 secret_reference.version）
  ├─ PDP decide(intent, resource_scope, project.env, sensitive_level) → risk_level + required_slots
  ├─ P0 → POLICY_BLOCKED，不写 preparation（记 policy.blocked）
  └─ P1/P2 → INSERT preparation(pending, expires_at) → supersede 旧单 → 两条账本事件（同事务）→ PreparationDetail
```

编号步骤：

1. 解析 `SubjectContext`，用 `has_role(await active_roles(session, project_id=..., user_id=subject.user_id, at=now), RoleName.MAKER)` 判定，否则 `ROLE_REQUIRED`。
2. 载入 `pipeline_version` 与 `pipeline`，校验 `tenant_id` / `project_id` 与 `subject` 一致，否则 `TENANT_MISMATCH` / `FORBIDDEN`。
3. 校验源 Profile `status = ready` 且 `expires_at > now()`，否则 `METADATA_PROFILE_EXPIRED`。
4. 计算 `input_fingerprint`：`sha256_hex(canonical_bytes({profile_sha256, source_endpoint_digest, target_endpoint_digest, secret_ref: [path, version], quality_rules_sha256, supervision_contract_digest}))`。规范化只走 be-12 的 `engines/fingerprint/canonical.canonical_bytes`（be-12 §6.1 的「唯一规范化入口」，**禁止**在此手写 `json.dumps`）。**`input_fingerprint` 覆盖 Secret 引用的 `version`**：轮转后值变、指纹变，旧审批自然失效。
5. 组装 `resource_scope`：`{reads: [{data_source_id, database, tables[]}], writes: [{data_source_id, database, table, shadow_table}], secrets: [{secret_reference_id, path, version, key_names}]}`。只写**引用与定位**，不写值。
6. 调 `engines/policy/pdp.decide(intent=ToolIntent(...), scope=ResourceScope(...), env=project.env, level=源/目标最高 SensitiveLevel, now=now, project_overrides=...)` → `PolicyDecision`，取 `decision.level → preparation.risk_level`、`decision.required_slots`、`decision.reasons → preparation.risk_reasons`、`decision.budget`。**PDP 是纯函数，不查库、不调 LLM**（CLAUDE.md §5.3）。
7. `decision.blocked` 为真（P0）→ `PolicyBlockedError`（`POLICY_BLOCKED`），写 `policy.blocked`，**不落任何 preparation**。
8. `budget` = `pipeline_version.supervision_contract` 快照（六个 `SUP_*` 对应列）。
9. `rollback_plan` = `{shadow_table, formal_table, cleanup: ["drop_shadow_on_failure"], restore: ["rename_swap_back" | "doris_replace_with_swap_true"]}`；无回滚方案时 PDP 判 P1（见 §四 风险矩阵）。
10. `INSERT preparation`：`status=pending`、`frozen_at=now()`、`expires_at=now() + APPROVAL_TTL`（默认 72 h，见 §10）。
11. `supersede_previous(session, pipeline_id=..., keep_preparation_id=<新单>)`：旧单 `status → superseded`（仅 status 列，符合白名单）。
12. `EvidenceLedger.append(preparation.created)` 与 `policy.evaluated`（同事务）后提交。
13. **不产生任何 `outbox_message`、不调用任何 ToolName**，事务提交后返回 `PreparationDetail`。

### 5.2 Approve 时序（`decide`）

1. 幂等键登记（`idempotency_key` 表，`scope="preparation.decide"`）。
2. 载入 preparation；校验租户/项目一致。
3. **角色校验**：`held = await active_roles(session, project_id=..., user_id=subject.user_id, at=now)`；`has_role(held, slot 对应角色)` 为假 → `ROLE_REQUIRED`。
4. **槽匹配**：`slot ∈ preparation.required_slots`，否则 `ValidationError`（该单不需要这个槽）。
5. **自批拦截**：`is_self_approval(preparation.created_by, approver_id=subject.user_id)` 为真 → `SELF_APPROVAL_FORBIDDEN` **并写 `approval.self_denied`**（被拒也要留痕，PRD §12 明列）。
6. **职责冲突**：`check_duty_separation(held, granting=...)` 检出同一项目 maker 与 checker_* 混用，或 `check_dual_checker_distinct(data_checker, security_checker)` 检出两个 checker 槽同人 → `DUTY_CONFLICT`（写账本）。
7. **指纹一致性**：重算 `input_fingerprint` 并与 preparation 比对，同时比对 `pipeline_version.sha256 == preparation.artifact_sha256`，不一致 → `FINGERPRINT_MISMATCH`（写账本）。
8. **状态合法性**：`preparation.status ∈ {pending, partially_approved}` 且未过期，否则 `PREPARATION_EXPIRED` / `ConflictError`。
9. **不覆盖既有决定**：该槽已有 `approval_decision` → `ConflictError`（`approval_decision` 不可变，见 §6.3）。
10. `INSERT approval_decision`（`comment` 非空；冗余写 `preparation_created_by`、`artifact_sha256`、`fingerprint_at_decision`）。
11. `derive_status()` 计算新状态并 `UPDATE preparation.status`。
12. 写证据事件 `approval.granted|rejected|returned`；`approved`/`rejected` 时同步 `pipeline.status`（be-09 提供推进函数），随后提交事务。

### 5.3 状态机

| 当前 status | 事件 | 新 status | 触发者 |
|---|---|---|---|
| `pending` | 非全部必需槽中某槽 approve | `partially_approved` | `services/approval.decide` |
| `pending` / `partially_approved` | 全部必需槽 approve | `approved` | `derive_status` |
| `pending` / `partially_approved` | 任一槽 reject | `rejected` | `derive_status` |
| `pending` / `partially_approved` | 任一槽 return | `superseded` | `derive_status` |
| `pending` / `partially_approved` | 新准备单创建 | `superseded` | `supersede_previous` |
| `pending` / `partially_approved` / `approved` | `now() >= expires_at` | `expired` | `expire_due_preparations` |
| 任一终态（`approved`/`rejected`/`expired`/`superseded`） | 任意决定 | 不变 | — |

**非法转移处理**：`decide` 只接受 `{pending, partially_approved}`；其余状态一律 `ConflictError`（409，`ErrorCode.CONFLICT`），并把 `(status, slot, decision)` 记入 structlog（`preparation_decide_rejected`），**不写证据账本**——非法转移是客户端状态过期，不是协议拒绝；真正的协议类拒绝（自批、职责冲突、指纹失效）才写账本。

`approved` 是唯一允许 Commit 的状态；`approved` 之后过期仍需 `expired`（在过期前已通过审批的也不许过期后执行，`expires_at` 是硬边界）。

## 6. 关键算法与规则

### 6.1 状态推导（纯函数）

```python
def derive_status(
    required: Sequence[ApprovalSlot],
    decisions: Mapping[ApprovalSlot, ApprovalDecisionType],
) -> PreparationStatus:
    """优先级：reject > return > (全部 approve) > (部分 approve) > pending。"""
```

优先级固定为 `reject` → `return` → `approved` → `partially_approved` → `pending`：任一槽拒绝就是拒绝，不会被另一槽的通过掩盖；`return` 次之（本单作废但未定性为拒绝）。

### 6.2 四眼的四条判定（复用 be-02 的纯函数，本模块不重写）

```python
def has_role(roles: AbstractSet[RoleName], role: RoleName) -> bool                       # 判定①：审批人是否真持有该槽
def is_self_approval(preparation_created_by: int, approver_id: int) -> bool              # 判定②：自批
def check_duty_separation(held: AbstractSet[RoleName], *, granting: RoleName) -> None    # 判定③a：maker 与 checker_* 互斥
def check_dual_checker_distinct(data_checker: int, security_checker: int) -> None        # 判定③b：两槽不得同人
```

四条都在 `engines/policy/roles.py`（be-02），**本模块只调用、不复制**；违规抛 `ValueError`（纯函数层不 import `core.errors`），由 `services/approval.py` 翻译成 `ROLE_REQUIRED` / `SELF_APPROVAL_FORBIDDEN` / `DUTY_CONFLICT`。判定③b 的两个入参来源：本槽取 `subject.user_id`，另一槽取 `approval_decision.approver_id`；另一槽尚未决定时跳过，待其决定时再与前一条决定比对。

三层兜底的分工（README §5 的「四眼 + 自批拦截」行）：

| 层 | 机制 | 实现位置 | 能否被绕过 |
|---|---|---|---|
| 服务端 | `has_role` / `is_self_approval` / `check_duty_separation` / `check_dual_checker_distinct`（be-02 的纯函数，本模块在 `services/approval.py` 调用） | `engines/policy/roles.py` + `services/approval.py` | 不能（唯一写入路径） |
| DB CHECK | `ck_approval_decision_no_self_approval`（`approver_id <> preparation_created_by`） | `models/governance.py` | 不能（任何 INSERT 都过 CHECK，含将来新增的脚本） |
| 授权源头 | `role_assignment` 授予时经 `check_duty_separation` 校验 maker 与 checker_* 互斥 | be-02 `services/project.grant_role` | 不能（本模块审批时再复核一次） |

### 6.3 「一个槽只有一条决定」与重复审批

`uq_approval_decision_preparation_id_slot` + `__immutable__ = True`（无 `__mutable_columns__`）共同决定：**决定写了就不可改、不可删，一个槽永远只有一条**。因此：

- 同一槽第二次提交决定 → `ConflictError`（409）。**不做「新决定覆盖旧决定」**——覆盖会破坏「审批事实 = 当时看到什么就批了什么」的证据链。
- 需要改主意（如把 reject 改为 approve）的唯一合法路径：**更换 pipeline_version → 新 preparation → 重新走双槽审批**；旧单连同其 `approval_decision` 永久保留。
- `return` 同理：槽位被 `return` 占用后本单不可再审，maker 依 `comment` 修改需求 → 冻结新版本 → 新 preparation 创建时 `supersede_previous` 把旧单置 `superseded`。

### 6.4 指纹失效语义

| 变化 | 检测点 | 处理 |
|---|---|---|
| 源端 Profile 重新探查（`sha256` 变）或 `expires_at` 过期 | `assert_committable` 重算 `input_fingerprint` | `FINGERPRINT_MISMATCH`（Profile 过期另判 `METADATA_PROFILE_EXPIRED`） |
| `secret_reference.version` 轮转 | 同上（指纹覆盖 `version`） | `FINGERPRINT_MISMATCH` |
| 冻结了新版本 | 新 preparation 的 `artifact_sha256` 不同 | 旧单 `superseded`，旧 `approval_decision` **不物理删除**，Commit 时按指纹比对自动失效 |
| 客户端传了 `expected_artifact_sha256`（前端 Diff 页面上的那个） | `assert_committable` 入参 | 与 `pipeline_version.sha256` 不等 → `FINGERPRINT_MISMATCH` |

`approval_decision.artifact_sha256` / `fingerprint_at_decision` 两列的存在意义就是**事后可证「当时批的是哪一版」**；Commit 时逐个槽比对，只要有一个不等，该槽视为未通过。

### 6.5 `assert_committable` 校验清单（Commit 前置，be-14 调用）

| # | 校验 | 不满足时 |
|---|---|---|
| 1 | preparation 存在且租户/项目一致 | `NOT_FOUND` / `TENANT_MISMATCH` |
| 2 | `status == approved` | `APPROVAL_INCOMPLETE` |
| 3 | `expires_at is None or expires_at > now()` | `PREPARATION_EXPIRED` |
| 4 | `required_slots ⊆ {decision == approve 的槽}` | `APPROVAL_INCOMPLETE` |
| 5 | 每个 approve 决定的 `artifact_sha256 == pipeline_version.sha256` 且 `fingerprint_at_decision == 当前 input_fingerprint` | `FINGERPRINT_MISMATCH` |
| 6 | 重算 `input_fingerprint` 与 `preparation.input_fingerprint` 一致 | `FINGERPRINT_MISMATCH` |
| 7 | 源 Profile 未过期 | `METADATA_PROFILE_EXPIRED` |
| 8 | 重跑 PDP，`risk_level` 与 preparation 记录一致且不阻断 | `POLICY_BLOCKED` / `FINGERPRINT_MISMATCH`（策略变动使风险升级即视为事实已变） |
| 9 | `rollback_plan` 非空 | `POLICY_BLOCKED`（无回滚方案属 P1，P1 未加固不得提交） |
| 10 | 审批人 ≠ `created_by`（逐条复查，防历史数据绕过） | `SELF_APPROVAL_FORBIDDEN` |

全部通过后返回 `CommittableFacts`；be-14 用其中的 `artifact_sha256` / `environment` / `preparation_id` 签发 Capability。**本函数只读，不写任何表**——Commit 的写入与事务边界属 be-14。

## 7. 错误码与拒绝语义

| 触发条件 | 错误码 | HTTP | 写证据账本 |
|---|---|---|---|
| 非 maker 调 Prepare | `ROLE_REQUIRED` | 403 | 否 |
| 非该槽持有者调决定 | `ROLE_REQUIRED` | 403 | 否 |
| 项目/租户不匹配 | `TENANT_MISMATCH` / `FORBIDDEN` | 403 | 否 |
| 申请人尝试自批 | `SELF_APPROVAL_FORBIDDEN` | 403 | **是**（`approval.self_denied`） |
| maker 兼任 checker、两个 checker 同人 | `DUTY_CONFLICT` | 403 | **是** |
| 指纹变化 / 策略升级 | `FINGERPRINT_MISMATCH` | 409 | **是** |
| `expires_at` 已过 | `PREPARATION_EXPIRED` | 409 | 是（`expire_due_preparations` 时写一次，不在每次请求重复写） |
| 必需槽未齐 / 状态非 approved | `APPROVAL_INCOMPLETE` | 409 | **是**（Commit 前置拒绝属协议类） |
| P0 命中 | `POLICY_BLOCKED` | 403 | **是**（`policy.blocked`） |
| 源 Profile 过期 | `METADATA_PROFILE_EXPIRED` | 409 | 否 |
| 同槽重复决定 / 状态非法转移 | `CONFLICT` | 409 | 否 |
| 同 `Idempotency-Key` 不同请求体 | `IDEMPOTENCY_CONFLICT` | 409 | 否 |
| 无回滚方案 / P1 未加固 | `POLICY_BLOCKED` | 403 | 是 |

`APPROVAL_INCOMPLETE` 在错误码枚举中已存在（`core/errors.py`），本模块只引用不自造。缺失的码集中在 §10 第 1 条。

## 8. 安全与合规约束

- **不可变制品**：`preparation` 仅 `status` 可改（`__mutable_columns__`），`approval_decision` 完全不可改。任何试图 UPDATE 其他列（例如篡改 `risk_level` 降级）都会在 flush 前抛 `ImmutableViolationError`（`models/base.py:_guard_immutable`）。这使「审批一句话绑定一版制品」不可被事后修改。
- **无明文 Secret**：`resource_scope` 与 `budget` 只写 `secret_reference` 的 `path` / `version` / `key_names`，写入前由 `schemas/preparation.py` 校验拒绝任何含 `password` / `token` / `secret` 值的键（与 `data_source.endpoint` 同一套校验器）。
- **租户过滤**：所有查询带 `tenant_id`（`ProjectScopedMixin` 的列），service 入口先解析上下文；跨租户 → `TENANT_MISMATCH`。
- **授权依据**：角色一律查 `role_assignment`（含 `valid_from` / `valid_to`），**不读 JWT 的 roles 声明**（角色可能已被回收）。
- **审计事件**（一律经 `harness.EvidenceLedger.append(session, LedgerEvent(...))`，写入前强制脱敏；`LedgerEvent` 的 `tenant_id` / `subject_type`（`"preparation"`）/ `subject_id`（字符串化 id）/ `occurred_at`（**由调用方注入 UTC，账本内不取当前时间**）/ `project_id` / `actor_id`(= `subject.user_id`) / `artifact_hash` 均按 be-06 §3.2 填）：
  | 动作 | event_type |
  |---|---|
  | Prepare 成功 | `preparation.created` |
  | PDP 判定完成 | `policy.evaluated` |
  | P0 阻断 | `policy.blocked` |
  | 审批通过 / 拒绝 / 退回 | `approval.granted` / `approval.rejected` / `approval.returned` |
  | 自批尝试被拒 | `approval.self_denied` |
  payload 只放 `preparation_id` / `slot` / `risk_level` / `artifact_sha256` / `comment_digest`（意见做 sha256，避免把可能含敏感描述的长文本整段入账本），不放 `resource_scope` 明细中的表字段名之外的任何值。
- **日志**：`structlog` 绑定 `request_id / tenant_id / project_id / preparation_id / pipeline_version_id`；日志只记引用与掩码，业务代码不拼敏感值（脱敏由 logging 处理器统一完成）。
- **幂等**：两个写接口都要求 `Idempotency-Key`，落 `idempotency_key` 表（`scope` 分别为 `preparation.create` / `preparation.decide`）。

## 9. 测试要点

**单元测试（内存 SQLite，`tests/`）**

- `derive_status` 全组合：`{reject}`、`{return, approve}`、`{approve, approve}`、`{approve}`、`{}` 五类输入的返回值；边界：`required_slots` 为空时的行为（P3 免审批单，应返回 `approved` 并由 PDP 层保证不会走到这里）。
- 复用 be-02 的四条判定（`has_role` / `is_self_approval` / `check_duty_separation` / `check_dual_checker_distinct`）正例与反例（反例断言抛 `ValueError` 后由 service 翻译出具体 `code`）。
- ORM 守卫与 DB CHECK：对 `preparation` 改 `risk_level` 抛 `ImmutableViolationError`、只改 `status` 放行；对 `approval_decision` 改 `comment` 抛错；`approver_id == preparation_created_by` 的 INSERT 被 `ck_approval_decision_no_self_approval` 拒（SQLite 同样生效）。

**集成测试（真实 PG，标 `integration`）**

- **协议类必测反例**
  1. **自批拦截**：maker 直接调 `/decisions` → 403 `SELF_APPROVAL_FORBIDDEN`，且 `evidence_event` 新增一条 `approval.self_denied`。
  2. **职责冲突**：同项目内同时持有 `maker` 与 `checker_data` 的用户审批 → 403 `DUTY_CONFLICT`。
  3. **指纹失效**：审批通过后把源 `metadata_profile` 换成新版本（或把 `secret_reference.version` +1）→ Commit 前置校验（`assert_committable`）→ 409 `FINGERPRINT_MISMATCH`。
  4. **过期**：`expires_at` 置为过去 → `PREPARATION_EXPIRED`，且 `expire_due_preparations` 把 status 改为 `expired`。
  5. **同槽重复决定**：第二次 POST 同 `slot` → 409 `CONFLICT`，`approval_decision` 行数仍为 1。
  6. **幂等**：同 `Idempotency-Key` 重复 POST `/preparations` → 返回同一 `preparation_id`；同 key 改 body → `IDEMPOTENCY_CONFLICT`。
- **Prepare 零副作用（本条是本模块的硬性验收）**：调用 `create_preparation` 前后对 `outbox_message` 计数，断言增量 = 0；同时对 `execution_run`、`capability` 计数断言增量 = 0；用一个 monkeypatch 过的 `ToolBroker`（任何 `execute` 即失败）运行全流程，断言从未被调用。
- **四眼齐备与待办过滤**：单槽 approve 后 status = `partially_approved`、`committable == false`，双槽 approve 后 `committable == true`；`GET /preparations?slot=checker_data` 只返回该槽未决且状态为 `pending|partially_approved` 的单。

## 10. 未决与风险

1. **`PreparationStatus` 缺少 `returned`**：`return` 目前借用 `superseded` 终态，前端无法区分「被新单取代」与「被退回补充」，只能结合 `approval_decision.decision` 判断。验证/决策方式：M3 联调 fe-05 时若需要区分，向枚举追加 `returned` 取值（varchar + CHECK，加值不改类型，代价极低），并在 `derive_status` 加一条分支。
2. **审批有效期 `APPROVAL_TTL`（建议 72 h）尚未拍板**：本文按 72 h 写，`preparation.expires_at` 落库。验证方式：与项目负责人确认后写入 `Settings`（如 `PREPARATION_TTL_HOURS`），不要在 service 里硬编码。
3. **`input_fingerprint` 的字段集与 `pipeline.status` 推进函数均由 be-12 / be-09 提供**：本文写出的字段名（`profile_sha256` / `secret_ref.version` / `quality_rules_sha256` / `supervision_contract_digest`）与「`version_frozen → preparing → pending_approval → approved|rejected`」是 be-13 对二者的**接口要求**，需在其文档定稿后对齐；命名不一致时只改 `services/preparation.py` 与 `services/approval.py` 的调用点。
4. **PDP 重跑的一致性**：`assert_committable` 第 8 条会重跑 PDP。若策略表（`policy_rule` / `risk_policy_version`）在此期间被修改使风险升级，Commit 会被拒。这是有意的（审批必须绑定当时生效的策略），但需要 M3 确认「策略变更是否要求重走审批」已由《需求对齐记录》覆盖——当前记录未明确。验证方式：加一条集成用例，改 `policy_rule` 后断言 Commit 被 `POLICY_BLOCKED` 拒。
5. **`derive_status` 暂置于 `services/approval.py`**：它无 IO，理论可上移到 `engines/`，但 README 未给 be-13 分配 engines 目录（`mypy --strict` 只覆盖 `engines`/`harness`）。四眼判定已确认复用 be-02 的 `engines/policy/roles.py`，不再另立一份。
