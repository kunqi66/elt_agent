## 1. 职责与边界

- **做什么**
  1. 按当前用户在 `role_assignment` 中的职责槽过滤出**待办列表**，只呈现「我该审的」与「审过的」。
  2. 把 Prepare 冻结的全部事实（输入指纹、制品指纹、资源范围、敏感分级、预算、回滚方案、环境、职责槽、风险等级）完整、**只读**地呈现。
  3. 承载**审批操作**：通过 / 拒绝 / 退回三态 + 意见必填 + 二次确认，并处理 `SELF_APPROVAL_FORBIDDEN` 与 `DUTY_CONFLICT`。
  4. 可视化**双槽状态**（数据槽 / 安全槽各自的待办、决定、决定人、时间、意见），双槽齐备后才亮出 Commit 入口。
  5. 承载 **Commit 入口**（仅 operator）：确认弹窗 + 前端生成并复用 `Idempotency-Key`；表现**指纹失效**与**过期**。
- **不做什么**
  - **不做权限判定**：谁能审哪个槽、谁能 Commit 一律由后端查 `role_assignment` 判定；前端按钮禁用只是**展示层可见性**，不是安全边界。
  - **不编辑冻结事实**：对 `preparation` / `approval_decision` 只有读与新增；后端 `Preparation.__mutable_columns__ = {"status"}` 之外列一律拒绝，前端不得提供绕过入口。
  - **不签发 Capability、不创建 ExecutionRun**：Commit 只调后端接口；令牌内容与 Outbox 入队均在前端视野之外。
  - **不触碰 Secret**：`resource_scope` / `rollback_plan` 只含库表定位与步骤，页面不请求、不缓存、不回显任何连接串。
- **所在分层**：前端展示层。只经 `src/api/preparation.ts` 调 `/api/v1/preparations`，不直连数据面。

## 5. 核心流程

```
1. maker 在 Studio 冻结版本 → POST /preparations
2. 跳 /approval 并轮询；后端按 role_assignment 折算 my_slot
3. checker 打开详情 → GET /preparations/{id}（冻结事实只读渲染）
4. 点「通过/拒绝/退回」→ ApprovalDialog：意见必填校验 → 二次确认 → POST .../approvals
5. 双槽 approve 且指纹一致 → status=approved，出现 Commit 入口（仅 operator）
6. operator 点 Commit → 确认弹窗（再展示指纹/预算/回滚方案）
   → 生成 uuid v4 作 Idempotency-Key → POST .../commit
7. 成功 → 跳 /runs/{run_id}（fe-06）
```

**Preparation 状态机**（前端只读呈现，转移由后端执行）

| 状态 → 事件 → 新状态 | 前端表现 |
|---|---|
| `pending` → 一槽 approve → `partially_approved` | 已决定槽显示决定人/时间/意见；另一槽保持「待审批」 |
| `partially_approved` → 末槽 approve → `approved` | 徽章转 success；Commit 入口出现（`can_commit=true`） |
| 未终态 → 任一槽 reject → `rejected` | 全局红色告警条；审批与 Commit 按钮全禁用；引导 maker 回 Studio 重新冻结 |
| 未终态 → 任一槽 return → `pending`（该槽释放） | 该槽回到「待审批」并展示退回意见；不影响其他槽 |
| 未终态 → 超 `expires_at` → `expired` | 倒计时归零转红；提交动作返回 `PREPARATION_EXPIRED` |
| 未终态 → 同版本新建准备单 → `superseded` | 顶部提示「已被新准备单取代」+ 跳转链接 |
| `approved` → Commit 成功 → 不变（产生 run） | 跳转运行详情 |

**非法转移处理**：前端不做状态拦截，把后端 `CONFLICT` / `FINGERPRINT_MISMATCH` / `PREPARATION_EXPIRED` 映射为整页提示并强制刷新；提交中按钮一律 `disabled` 防连点，服务端仍是唯一判据。

**指纹失效表现**（`FINGERPRINT_MISMATCH`，409）

1. 页面进入失效态：`decisions[].stale = true` 的卡片加灰蒙层 + 「原审批已失效（指纹变化）」标签。
2. 顶部并列展示当前 `artifact_sha256` 与审批时值（各前 8 位，完整值可复制）。
3. 全部审批与 Commit 按钮禁用；主行动按钮改为「返回 Pipeline Studio 重新冻结」。
4. **不提供「忽略并继续」**，也不提供「重试 Commit」——重试必然再次 409。

**二次确认文案**（防止在相似准备单间误操作，必须回显不可变事实）：
`我将以 checker_data 身份审批：准备单 #1042 ｜ Pipeline 订单宽表同步 ｜ v7 ｜ 制品指纹 abc12345…（可展开完整 64 位） ｜ 输入指纹 def67890… ｜ 风险等级 P1 ｜ 环境 prod ｜ 敏感级别 confidential ｜ 本次决定：通过/拒绝/退回`。

## 6. 关键算法与规则

**待办过滤**（规则在后端，前端只透传 `scope`）：`scope='todo'` → `status ∈ {pending, partially_approved}` 且 `now < expires_at` 且当前用户在 `required_slots` 中至少占一个未决定槽。前端不本地重算该集合。

**列表列与格式化**

| 列 | 字段 | 格式化 |
|---|---|---|
| Pipeline | `pipeline_name` | 超长省略 + tooltip |
| 版本号 | `version_no` | 前缀 `v` |
| 制品指纹 | `artifact_sha256` | 前 8 位 + 等宽字体；悬停显示完整值 |
| 风险等级 | `risk_level` | `RiskLevelTag` 徽章 |
| 敏感级别 | `sensitive_level` | 公开 / 内部 / 机密 / 受限 |
| 环境 | `environment` | prod 用醒目样式（红色左边框 + 粗体） |
| 提交人 | `creator_name` | — |
| 冻结时间 | `frozen_at` | `YYYY-MM-DD HH:mm:ss`（本地时区） |
| 剩余有效期 | `expires_at` | 剩余时长；< 1 h 转 warning，已过期转 danger 显示「已过期」 |

筛选：`scope` / `status` / `risk_level` / `environment` / `slot` / 关键字（Pipeline 名或指纹前缀）。

**`RiskLevelTag` 徽章规范**（色值集中在此组件，其他组件不得自行写色）

| 等级 | tag type | 语义文案 |
|---|---|---|
| P0 | danger（实心） | 已阻断 / 禁止执行 |
| P1 | danger（浅色描边） | 高风险，强制双职责审批 |
| P2 | warning | 常规双职责审批 |
| P3 | info | 只读，免审批 |

**按钮可见性**（仅展示层，全部取后端字段）

| 按钮 | 可见条件 |
|---|---|
| 通过 / 拒绝 / 退回 | `my_slot !== null` 且 `status ∈ {pending, partially_approved}` 且 `now < expires_at` 且 `created_by !== current_user_id` |
| Commit | `can_commit === true` |
| 返回重新冻结 | `status ∈ {rejected, expired, superseded}` 或存在 `stale` 决定 |

**Commit 幂等键生成规则**

```ts
let commitKey: string | null = null
function ensureKey(): string { return (commitKey ??= crypto.randomUUID()) }
// 弹窗打开时首次生成；同一弹窗内的重复点击、网络失败后的「重试」复用同一 key；
// 弹窗关闭（成功或取消）后置 null，下次打开生成新 key —— 那是新的业务意图。
```

- 复用同一 key → 服务端经 `idempotency_key` 表返回 `response_snapshot`，不创建第二条 `execution_run`。
- 收到 `IDEMPOTENCY_CONFLICT`（同 key 不同请求体，不应出现）→ 提示「请求冲突，请刷新后重试」并停止重试。
- 非安全上下文（纯 HTTP + 非 localhost）下 `crypto.randomUUID()` 不可用，需 fallback 实现（见 §10）。

**过期倒计时**：`PreparationTimeline` 本地每秒刷新展示差值，不因此发请求；真实过期以服务端 `PREPARATION_EXPIRED` 为准（本地时钟不可信）。

## 7. 错误码与拒绝语义

| 触发条件 | 错误码（`ErrorCode`） | HTTP | 前端表现 | 写账本 |
|---|---|---|---|---|
| 当前用户是准备单发起人 | `SELF_APPROVAL_FORBIDDEN` | 403 | 按钮置灰 + tooltip「申请人不得审批自己提交的准备单」；若服务端仍拒绝则弹窗关闭并提示 | 是（`approval.self_denied`） |
| 同一人兼任 maker 与 checker_* | `DUTY_CONFLICT` | 403 | 提示「高风险操作禁止同一人兼任多个审批职责」；引导去 `/settings/roles` 解除 | 是 |
| 审批后制品/输入指纹变化 | `FINGERPRINT_MISMATCH` | 409 | 整页失效态，决定标 `stale`，禁止重试 | 是 |
| 双槽未集齐 / 槽位已决定 | `APPROVAL_INCOMPLETE` | 409 | 提示缺失槽位名（数据槽 / 安全槽） | 是 |
| 准备单已过期 | `PREPARATION_EXPIRED` | 409 | 倒计时归零转红；引导重新 Prepare | 是 |
| 同 `Idempotency-Key` 不同请求体 | `IDEMPOTENCY_CONFLICT` | 409 | 提示冲突并停止重试 | 否 |
| 角色不足（非该槽审批人 / 非 operator） | `FORBIDDEN` / `ROLE_REQUIRED` | 403 | 隐藏按钮 + 提示无权限；不暴露其他槽规则 | 是 |
| 非本租户/项目资源 | `TENANT_MISMATCH` | 403 | 跳回列表并提示资源不存在 | 是 |
| 资源不存在 | `NOT_FOUND` | 404 | 详情空态 + 返回列表 | 否 |
| 并发状态冲突（他人先决定） | `CONFLICT` | 409 | 提示状态已变更并强制刷新详情 | 是 |

所有分支基于 `BizError.code`（`client.ts` 已剥信封并抛 `BizError`），**不用 `message` 判断**；前端不自造错误码。

## 8. 安全与合规约束

- **前端置灰不是安全边界**：按钮禁用、状态遮罩、字段置灰都只是体验优化。服务端必须在每次写请求上重新校验「角色 + 槽位 + 自批 + 指纹 + 有效期 + 幂等」，DB 层 `CHECK (approver_id <> preparation_created_by)` 与 `UK(preparation_id, slot)` 是最后兜底。本模块代码不得出现「前端已拦截、服务端可省」的假设。
- **只读冻结事实**：`FrozenFactsPanel` 的 `readonly` 在类型上恒为 `true`，不实现任何可编辑分支。
- **无 Secret**：`ResourceScope` / `RollbackPlan` 只渲染库表定位、工具名与步骤描述；不渲染连接串，即使后端误下发也不渲染（fe-01 的响应字段白名单兜底）。
- **不做乐观更新**：审批与 Commit 结果一律以服务端响应替换本地状态；禁止本地先置「已通过」再回滚——网络失败会让审批人误以为决定已生效。
- **审计可见**：每次决定后回显 `decided_at` / `approver_name` / `artifact_sha256` / `fingerprint_at_decision`，与账本 `approval.granted` / `approval.rejected` / `approval.returned` 事件口径一致，便于审计员对账。
- **不缓存详情**：详情含资源范围与敏感分级，路由离开时 `reset()`，不写 `localStorage` / `sessionStorage`。

## 9. 测试要点

- **单元测试（Vitest + @vue/test-utils）**：`RiskLevelTag` 的四档映射与缺失取值容错；`ApprovalDialog` 的 `comment` 空/全空白禁用提交与三态确认文案；`CommitConfirmDialog` 同弹窗内 key 相同、关闭再开 key 不同；`PreparationTable` 过去时间渲染「已过期」而非负数、指纹截断 8 位且悬停完整；`isReviewable` 在 `my_slot === null` / `created_by === current_user_id` / `status === 'rejected'` 三个反例下返回 `false`。
- **集成测试（真实 PG + 后端，ECS 上跑）**：**自批拦截**（maker 自批 → 403 且 `approval_decision` 无新行）；**职责混用**（maker + checker_data → `DUTY_CONFLICT`）；**指纹失效**（版本指纹变化 → Commit 409 且 `stale` 生效）；**幂等**（同 key 两次 Commit → 一条 `execution_run`）；**并发审批**（两浏览器同槽 → 一成功一 `CONFLICT`）；**越权**（非 operator commit → 403 且无入口）。
- **必须覆盖的反例**：自批、职责混用、指纹失效、过期提交、越权 Commit、幂等重放。
- **测试基建**：本机无 Docker，集成用例标 `@pytest.mark.integration` 在 ECS 跑；前端交互用 Playwright 手工清单在 ECS 执行。

## 10. 未决与风险

| 事项 | 现状 | 建议 / 验证方式 |
|---|---|---|
| 审批列表轮询间隔 | 冻结决策只覆盖「运行指标 2 s」 | 本模块取 5 s，常量集中在 `stores/preparation.ts`；如需与运行中心统一，一处改 |
| `expires_at` 的 TTL | 字段存在，默认时长未冻结 | 建议 `PREPARATION_TTL_HOURS=24`，写入 be-13 与 Settings；前端只展示不计算 |
| `return` 后的目标状态 | 枚举有 `return`，但「清空该槽回 `pending`」还是「整单回 `pending`」未定 | 待 be-13 明确；两种前端都能渲染，只改文案 |
| maker 主动撤回准备单 | 未在 PRD 出现，故本文不定义路由 | 若需要，建议 `POST /preparations/{id}/withdraw`（仅 `created_by` 且未终态），需后端先落 |
| Commit 是否下发 `capability_jti` | 本文按最小暴露只回 `run_id` | 若审计需在运行详情展示 jti，由 fe-06 从 `/runs/{id}` 读取，不在 Commit 响应回 |
| `crypto.randomUUID()` 在非安全上下文不可用 | ECS 可能以 `http://IP` 提供前端 | M3 实机验证；需 fallback 到 `uuid v4` 库或 `crypto.getRandomValues` |
| `scope='done'` 的口径与 `risk_reasons` 展示深度 | 前者「我做过决定的 vs 该单已终态」未定；后者现为逐条 `code/title/detail` | 待 be-13 定义 `scope`；`risk_reasons` 若 PDP（be-07）输出更细，可加「查看命中规则原文」抽屉，但需先确认是否向非安全角色泄露策略细节 |
